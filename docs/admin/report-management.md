# 관리자 신고 관리 계획

관련 이슈: [#92](https://github.com/likelion-backendschool-9th/pawmento/issues/92). 담당 기준은 [관리자](README.md), [회의의 담당 분배](../meetings/2026-11-16.md#참석-및-담당)를 따른다. community의 기존 글 계약은 [post.md](../community/post.md), #21·#84다.

## 한눈에

- 끝나면: 합의된 관리자만 신고 목록·상세를 보고 처리하거나 기각하며, 중복 처리와 다른 도메인 조치 실패에서 원본이 보존된다.
- 이번 PR은 목록 기반 이후 상세·처리의 데이터, 응답, 담당별 제공 순서를 기록한다.
- 목록·상세의 만료 응답과 처리·숨김 계약을 정했다. 작업별 구현은 실제 제공 포트와 보호된 관리자 경로를 확인한 뒤 연결한다.
- 규모: 계약 확정 후 백엔드 목록 → 상세 → 처리 순서의 작은 작업·커밋·PR로 분리한다. 프론트는 백엔드 계약 확정 후 별도 계획 검토·구현으로 진행한다.
- 착수 조건: 해당 단위에 영향을 주는 질문의 답변과 담당 합의가 기록되고 계획이 승인돼야 한다. 문서 머지만으로 미답 질문이나 다른 담당 코드 수정이 승인됐다고 간주하지 않는다.

## 현재 작업 단위 — 신고 목록 계약 반영 (#92-R1)

[community의 목록 제안](https://github.com/likelion-backendschool-9th/pawmento/issues/92#issuecomment-7000963694)에 관리자 담당이 동의하는 범위다. 상세·처리·숨김은 목록 연결과 별도 작업으로 진행한다.

### 목록에서 채택하는 계약

- 경로: `GET /api/v1/admin/reports`. `status` 생략 시 PENDING, reportId 내림차순, `size` 생략 시20·허용 범위1~50이다. `status`는 PENDING/RESOLVED/DISMISSED만 허용한다.
- 커서는 마지막으로 반환한 `reportId`의 양의 10진수 Long 문자열이다. 첫 요청은 `cursor`를 생략하며, 다음 조회는 같은 상태 필터에서 `reportId < cursor`를 적용한다. 응답은 `items`와 `nextCursor`를 제공한다. 더 조회할 항목이 있을 때만 마지막 반환 항목의 ID를 `nextCursor`로 쓰며, 마지막 페이지·빈 목록은 `nextCursor: null`이다. 커서 ID의 실제 존재는 요구하지 않는다. (고침 #92: PR #152 리뷰에 따라 admin이 커서·종료 표현 결정)
- `status`·`size`·`cursor`는 admin 웹 어댑터가 검증한다. 명시한 빈 값, 허용되지 않은 상태(소문자 포함), 정수가 아닌 size/cursor, 범위 밖 size, 0 이하·Long 범위 초과 cursor는 거절한다. 웹 전용 `InvalidReportListRequestException`을 `RuleViolationException` 하위로 두어 공통 응답400 `VALIDATION`으로 변환한다. 안내 문구는 각각 `status는 PENDING, RESOLVED, DISMISSED 중 하나여야 해요.`, `size는 1 이상 50 이하의 정수여야 해요.`, `cursor는 양의 정수 신고 ID여야 해요.`로 정한다. MVC 기본 타입 변환 오류로 빠져 공통 응답을 우회하지 않도록 문자열 입력부터 검증한다. (고침 #92: 입력 오류는 admin 책임으로 결정)
- 항목은 `reportId`, `postId`, `status`, `reasonType`, `createdAt`, `snapshotTitle`, `snapshotExpired`, `postState`다. 사유 요약은 `reasonType`으로 대신하며 `postState`는 VISIBLE/HIDDEN/DELETED다.
- 목록 연결 시 admin application에 신고 상태(PENDING/RESOLVED/DISMISSED), 사유(SPAM/ABUSE/HARMFUL/MISINFO/PRIVACY/OTHER), 게시글 상태(VISIBLE/HIDDEN/DELETED)의 enum을 두고, admin outbound 어댑터가 #112 결과를 명시적으로 변환한다. community 도메인 enum을 admin 입력 포트나 웹 응답에 직접 노출하지 않는다. 알 수 없는 제공 값은 기본값이나 사용자 입력400으로 바꾸지 않고 내부 계약 오류로 실패시킨다. 현재 항목 모델의 String 교체와 변환 검사는 실제 포트 연결 작업에 포함한다.
- 만료 전에는 `snapshotExpired: false`와 신고 당시 제목을 반환한다. 만료 후에도 신고 행을 목록에 유지하며 `snapshotExpired: true`와 `snapshotTitle: null`을 반환한다. `snapshotExpired`는 JSON boolean이며 제목의 null 여부로 추론하지 않는다. #112가 `FindReportPagePort.Item`에 제공하는 값을 관리자 목록 응답으로 전달한다. ([담당자 답변](https://github.com/likelion-backendschool-9th/pawmento/pull/173#issuecomment-7120572008))
- `createdAt`의 HTTP 표현은 UTC ISO-8601 문자열(예: `2026-11-21T00:00:00Z`)이다. 목록 연결 시 `@WebMvcTest`에서 Spring 응답 설정으로 8개 필드와 날짜의 고정 기대값을 검사한다. 현재 기본 `JsonMapper` 단위 검사는 항목 매핑만 확인하며 HTTP 형식 검증을 대신하지 않는다.
- 사유 상세 전문·신고자/작성자 ID·현재 본문·회원 개인정보를 목록에 추가하지 않는다. 상세 계약에서 따로 다룬다.
- community가 #112에서 신고 저장과 운영 목록의 실제 조회 구현을 제공한다. 관리자 쪽에서는 #152의 목록 입력 포트·서비스·웹 기반에 제공된 조회 구현을 연결한다.
- 접수 규칙 초안에 관리자 측 이견은 없다. 스냅샷 저장과 보존은 아래 Q4 계약을 따르며 접수 구현은 community #112에서 진행한다.

### 작은 작업과 실제 착수 조건

1. **목록 계약 문서 반영:** 이 문서 한 파일과 #92 답변에 채택한 필드·조회 조건·담당 경계를 기록한다. 구현 완료로 표시하지 않는다.
2. **목록 연결 준비:** #112가 제공할 실제 입력 포트·query/result 타입을 확인한다. admin이 결정한 위 커서·종료 표현·입력 오류 계약에 필요한 상태 필터·배타적 ID 경계·추가 항목 존재 여부를 제공하는지 확인하고, 필요한 포트 조건은 #112 구현 PR 리뷰에서 제안한다.
3. **admin 목록 연결만 구현:** #112의 실제 저장/목록 포트 제공과 관리자 경로 보안 반영을 확인한 뒤 admin 소유 서비스·outbound 연결 어댑터·web DTO/컨트롤러·검사로 범위를 제한한다. 정확한 파일 목록은 기존 구조와 제공된 포트를 확인해 정한다. community/member/global 및 타 담당 테스트 변경은 소유자 합의 없이 하지 않는다.
4. **목록 검사만 검증:** #92-S1의 페이지·빈 결과·필드 매핑과 목록에 한정한 S4 권한/S5 잘못된 조회 입력/S9 의존 경계를 확인한다. 부분 검사만으로 S4/S5/S9 전체나 S2~S8 전체 완료로 표시하지 않는다.

제공 순서는 **계약 동의 → #112 신고 저장·운영 목록 포트 → #92 관리자 목록 연결**이다. 포트 제공 전 내부 구현 병행은 아직 별도 승인되지 않았으므로 타입/가짜 포트를 먼저 만들어 공유 계약을 선점하지 않는다. 보안 PR·실제 포트가 없으면 외부 HTTP 경로나 항상 빈 결과로 우회하지 않는다.

## 상세·처리 계약 (#92-R2·R3)

[community 담당 답변](https://github.com/likelion-backendschool-9th/pawmento/pull/173#issuecomment-7120151197)을 반영한다. 리스트의 필터·정렬·커서·8개 필드는 위 계약을 기준으로 한다.

### Q4 — 접수 스냅샷과 운영 상세

- #112의 접수 트랜잭션에서 글 한 행을 읽어 `snapshot_title`, `snapshot_body`, `snapshot_category_code`, `snapshot_post_version`을 함께 저장한다. 캡처 시각은 `created_at`과 같다. 작성자 ID는 `posts.author_id`를 사용한다. 신고 전용 데이터에 닉네임·이메일·연락처·IP·요청 헤더를 복제하지 않는다.
- 상세는 `reportId`, `postId`, `reporterId`, `authorId`, `status`, `reasonType`, `reasonDetail`, `createdAt`, 신고 `version`, `snapshot`(당시 `title`, `body`, `categoryCode`, `postVersion`), 현재 `postState`와 `postVersion`을 반환한다. 처리 뒤에는 `processedBy`, `processedAt`, `resolutionNote`를 반환한다. 신고자·작성자 정보는 내부 ID까지만 제공하고, 판단 자료는 신고 당시 내용으로 한정한다.
- 작성자가 삭제한 글의 만료 전 스냅샷은 유지하고 현재 상태를 DELETED로 표시한다. 공개 상세는 404다. 회원 탈퇴 이후에도 신고와 스냅샷, 내부 작성자 ID는 기존 보존 정책에 따라 유지한다.
- RESOLVED 또는 DISMISSED 처리 시점부터 1년이 지나면 `snapshot_title`, `snapshot_body`, `reason_detail`을 지운다. 신고 행과 재신고 판정에 쓰는 `snapshot_post_version`은 유지한다. PENDING은 처리 전에 정리하지 않는다. 만료 상세는 `snapshot: null`, `snapshotExpired: true`로 반환한다. 정리 작업은 첫 만료 전에 별도 PR로 진행한다.
- 만료된 신고는 목록에도 남고, 위 목록 계약에 따라 `snapshotTitle: null`과 `snapshotExpired: true`를 반환한다.

### Q3·Q5 — 처리·기각과 게시글 숨김

- PENDING 신고 한 건을 RESOLVED 또는 DISMISSED로 바꾼다. 글 작성자나 신고자 본인이 처리하면 403이다. 같은 글의 다른 PENDING 신고는 유지한다. 처리자 ID는 인증된 회원으로, 시각은 서버에서 정한다.
- 처리·기각 메모는 Post와 같은 JavaScript `trim()` 기준으로 앞뒤 공백을 제거한 뒤 1~500자다. 웹과 신고 도메인에서 같은 규칙과 문구를 적용한다. 메모는 신고 행에 저장하고 관리자 상세에서만 반환한다.
- RESOLVED는 공개 글 숨김과 한 트랜잭션에서 저장한다. 이미 숨기거나 삭제한 글은 신고만 처리하며, DISMISSED도 글을 변경하지 않는다. 상태는 삭제 시각이 있으면 DELETED, 다음으로 숨김 시각이 있으면 HIDDEN, 나머지는 VISIBLE이다.
- 신고의 기대 버전 조건부 갱신과 게시글의 버전 증가를 적용하고 저장을 flush한다. 어느 쪽이든 버전 충돌로 실패하면 전체를 롤백한다. 기대 버전 불일치, 처리 완료 후 재요청, 숨김 중 글 버전 충돌은 409로 응답하며 관리자는 최신 상세를 다시 조회한다.
- 숨긴 글은 공개 목록에서 제외하고, 상세는 비로그인·비작성자에게 404를 반환한다. 로그인한 작성자에게는 200과 `hidden: true`, 제목, “운영 정책에 따라 숨겨진 글이에요.”만 반환한다. 작성자 수정은 409, 소프트 삭제는 허용, 신고 접수는 404다. 숨김 해제·이의 제기·내 글 목록은 첫 버전 범위 밖이다.

### Q1·Q6 — 제공과 연결 범위

- 목록은 #112의 실제 조회 구현을 먼저 확인하고, 관리자 쪽에서 목록 웹 경계와 통합 검사를 연결한다.
- 상세는 community가 출력 포트 `FindReportDetailPort.find(reportId) → Optional<Detail>`와 조회 어댑터를 제공한다. 관리자 쪽에서는 입력 포트·서비스·웹 응답을 연결한다.
- 처리는 community가 `DecideReportUseCase.decide(DecideReportCommand)`와 저장·숨김을 함께 제공한다. 명령은 신고 ID, 기대 버전, 인증된 처리자 ID, 결정, 메모를 받는다. 관리자 쪽에서는 웹 요청·응답·입력 검증을 연결한다. community가 게시글 조회·숨김·수정·삭제 회귀와 DB 원자성을 검증하고, 관리자 쪽은 실제 HTTP 권한과 응답 매핑을 검증한다.
- 연결 전에는 제공될 실제 타입·파일을 대조한다. 공용 검사나 다른 담당 파일은 변경 범위를 해당 소유자와 맞춘다.

### Q2 — member 담당이 결정한 권한 계약

[member 담당자의 Q2 답변](https://github.com/likelion-backendschool-9th/pawmento/pull/93#issuecomment-6974395331)을 따른다. **아래는 관리자 담당이 새로 정한 계정 정책이 아니다.**

- 역할은 DB `member.role`의 USER/ADMIN이고, 로그인 시 JWT `role` 클레임을 `ROLE_ADMIN`으로 변환한다. 관리자는 `hasRole("ADMIN")`으로 판정하고 처리자 ID는 기존 `@LoginMember Long memberId`로 받는다.
- 로컬·소셜 가입은 USER만 허용하며 역할 변경 API는 만들지 않는다. DB 접근 권한이 있는 운영자가 가입된 대상 계정의 역할을 쿼리로 부여·회수한다. 이메일은 소문자로 조회하고 변경자·시각·대상을 팀 채널에 남긴다. 계정 생성/역할 부여 작업은 member 담당 책임으로 두며 이번 계획에서는 쿼리를 실행하지 않는다.
- 권한 부여 후 로그아웃/재로그인으로 새 토큰에 반영한다. 토큰 수명은 1시간, 리프레시 토큰은 없으며 **회수 전 발급된 ADMIN 토큰은 만료까지 최대 1시간 유효할 수 있다는 MVP 지연 정책**을 따른다. 즉시 회수 기능을 admin에서 임의 추가하지 않는다.
- 관리자 경로는 `/api/v1/admin/**`, 신고 컨트롤러는 `@RequestMapping("/admin/reports")`다. `/api/v1`은 WebConfig가 붙인다. 메서드·요청/응답 필드는 Q5에서 별도 확인한다.
- member 담당이 먼저 `global/security/SecurityConfig.java`의 `anyRequest()` 앞에 관리자 matcher 한 줄을 추가하고, 비로그인401·USER403·ADMIN 필터 통과 및 #14-S8 요청 검사를 작은 선행 PR로 제공한다. `docs/member/auth-base.md`의 판정·부여/회수·갱신 정책도 member 담당이 작성한다. 컨트롤러별 `@PreAuthorize` 방식으로 변경하지 않는다.
- admin은 **선행 보안 PR 번호·머지와 검사 통과를 확인한 뒤** 위 경로에서 기능을 제공하며, 자체 SecurityConfig/계정·역할 코드를 수정하지 않는다. 선행 보안 검사의 ADMIN 통과는 관리자 업무 컨트롤러의 성공 응답 검증과 구분하고, 새 API의 실제 요청 검사는 S4에서 확인한다.

## 운영 응답과 대상 데이터의 경계

- 목록과 상세는 같은 신고를 조회하더라도 응답의 허용 필드를 각각 지킨다. 목록에는 신고 사유 상세, 본문, 내부 회원 ID를 추가하지 않는다.
- 일반 공개 게시글 조회의 삭제·숨김 정책과 관리자 신고 조회의 스냅샷 열람은 각각의 경로에서 검사한다. 신고 상세용으로 일반 공개 조회 필터를 완화하지 않는다.
- 제공 순서는 #112 접수·목록 조회 → 관리자 목록 연결 → community 상세 조회 포트 → 관리자 상세 연결 → community 처리·숨김 → 관리자 처리 연결이다.

## 기존 백엔드 연동에서 적용할 기준

[다이어리 텍스트 CRUD 계획](../diary/basic-crud.md)과 #89의 책임 분리를 참고한다. 이는 신고 데이터 소유권·ADMIN 권한·API가 합의됐다는 뜻이 아니다.

- **업무 정책과 웹 형식을 구분한다.** 신고 상태 전이·처리 가능 여부는 합의된 도메인/애플리케이션에서 판단하고, JSON 타입·쿼리 형식은 웹 경계에서 검사한다. 웹에서만 막는 업무 정책은 입력 포트 직접 호출로 우회될 수 있으므로 서비스/도메인 검사와 직접 호출 회귀를 함께 둔다. 웹 DTO·JSON·HTTP 상태를 핵심 계층에 넘기지 않는다.
- **기술 예외를 좁게 변환하고 원인을 보존한다.** 같은 입력/충돌 응답을 유지하더라도 기존 throwable을 cause로 연결한다. Q1·Q5에서 정한 실제 DB 제약·조건부 쓰기의 실패만 합의된 애플리케이션 예외로 변환하며 모든 `DataIntegrityViolationException`을 신고 미존재/충돌로 포장하지 않는다. 다른 FK·CHECK 오류까지 정상 업무 거절로 오인하지 않는 검사도 둔다. #89의 diary FK 이름·pet 삭제 예외는 신고 기능에 복사하지 않는다.
- **경합과 원자성은 커밋 뒤 결과로 확인한다.** S6·S8에서 실제 PostgreSQL의 별도 연결/트랜잭션, latch/barrier로 경합 순서를 제어하고, 성공 응답·실패 응답과 새 트랜잭션에서 조회한 최종 상태를 함께 확인한다. 단순 순차 호출·mock 예외 발생만으로 실제 DB 경합/전체 롤백이 검증됐다고 표시하지 않는다. Q6에서 합의한 테스트만 보완한다.
- **기존 연동의 범위를 넘지 않는다.** #89는 diary와 pet의 기록 존재/삭제 제한을 연결했다. 신고 저장소·글 숨김·삭제 원문 조회·관리자 보안을 제공하는 계약이 아니므로 관리자 기능의 선행 조건을 완료 처리하지 않는다. Q1~Q6과 범위 밖 항목을 그대로 유지한다.

## API 계약

기존 WebConfig의 `/api/v1` 접두어와 관리자 경로 보호를 사용한다.

- `GET /api/v1/admin/reports`는 200과 기존 목록 계약의 페이지를 반환한다.
- `GET /api/v1/admin/reports/{reportId}`는 200과 Q4의 상세를 반환한다. 없는 신고는 404다.
- `PATCH /api/v1/admin/reports/{reportId}`의 웹 요청은 `resolution`, `version`, 처리 메모를 받아 처리 명령에 매핑한다. 처리자는 인증에서 얻는다. 성공하면 변경 뒤 상세를 200으로 반환한다. 미존재는 404, 인증·권한 위반은 401·403, 입력 오류는 400, 처리 충돌은 409다. 웹 요청 필드의 최종 이름은 처리 연결에서 제공 계약과 대조한다.

## 1. 권한 있는 운영자의 신고 목록 (#92-R1)

합의된 관리자만 상태별 신고 목록과 페이지 경계를 확인한다. 목록 필드·기본 상태·정렬·크기는 현재 작업 단위의 채택한 계약을 따른다. 커서·종료 표현·입력 오류는 위 admin 목록 계약을 따른다.

#92-S1 정상·경계: 목록 [테스트]
- Given ADMIN 운영자 A와 PENDING 신고21건(reportId 1~21), 더 큰 reportId의 RESOLVED 신고22와 DISMISSED 신고23이 함께 있다
- When A가 **status와 size를 생략**해 첫 목록을 조회하고, 응답의 다음 커서를 사용해 **status와 size를 계속 생략**한 다음 목록을 조회한다
- Then 첫 페이지는 PENDING ID21~2의20건, 다음 페이지는 PENDING ID1의1건으로 중복 없이 내림차순으로 보인다. ID22·23은 두 페이지 모두 제외돼야 하며 다른 상태의 신고가 페이지 크기를 차지하지 않는다 (고침 #92: 기본 PENDING 필터 누락을 검출하는 다른 상태·상위 ID 데이터 추가)
- Then 조건에 맞는 신고가 없으면 200·빈 목록이며 Q4에서 허용하지 않은 개인정보는 포함되지 않는다
- 첫 페이지의 nextCursor는 "2", 마지막 페이지와 빈 목록은 null이다. size=1/50과 cursor ID가 존재하지 않아도 배타적 ID 경계로 조회되는 경우를 확인한다. 잘못된 status/size/cursor는 위 admin 계약의400 VALIDATION·안내 문구로 확인한다 (고침 #92: 커서 경계·종료·오류 기대값 구체화)
- 목록 연결 시 enum 변환과 허용되지 않은 제공 값의 실패를 검사하고, `@WebMvcTest`에서 실제 HTTP 항목의 8개 필드와 createdAt의 UTC ISO-8601 고정 기대값을 확인한다. 기본 JsonMapper 단위 검사만으로 HTTP 검사를 완료 처리하지 않는다
- 목록 항목은 reportId/postId/status/reasonType/createdAt/snapshotTitle/snapshotExpired/postState만 매핑하며 사유 상세·신고자/작성자 ID·본문·회원 개인정보를 반환하지 않는다 (고침 #92: 만료 표시 필드 채택)
- 처리된 신고를 조회할 때 만료 전에는 `snapshotExpired: false`와 제목을, 만료 후에는 같은 신고 행에서 `snapshotExpired: true`와 명시적인 `snapshotTitle: null`을 반환한다. 필드 타입은 JSON boolean이고 상태 필터·정렬·커서 계약은 유지한다. (고침 #92: 스냅샷 만료 경계 반영)

## 2. 신고와 대상 내용의 운영 조회 (#92-R2)

관리자는 허용된 신고 상세와 Q4가 정한 시점·범위의 대상 내용을 확인한다.

#92-S2 정상: 상세와 삭제된 대상 [테스트]
- 접수 뒤 수정되거나 삭제된 글의 신고를 관리자가 조회하면 접수 스냅샷과 현재 상태·버전을 구분해 반환한다. 작성자 탈퇴 뒤에도 보존 기간 내 내부 ID와 스냅샷을 유지한다. 대상 글이 삭제됐으면 현재 상태는 DELETED이고 공개 상세는 404다. (고침 #92: 담당자 답변으로 상세 반환 범위 확정)
- 처리한 지 1년이 지난 신고의 정리 작업은 제목·본문·사유 상세를 지우고 재신고에 필요한 스냅샷 게시글 버전을 보존한다. 만료 상세는 `snapshot: null`, `snapshotExpired: true`이며 PENDING은 정리되지 않는다. 실제 정리 작업은 별도 PR에서 검증한다.

## 3. 처리·기각과 원본 보호 (#92-R3)

운영자는 허용된 상태 전이만 수행하고, 서버가 처리자·시각·버전을 기록한다. 게시글 조치는 Q3가 허용한 경우에만 포함한다.

#92-S3 정상: 처리·기각 [테스트]
- Given 승인된 상태 모델에서 신고 101은 PENDING·version0이고 A는 ADMIN이다
- When A가 RESOLVED 또는 DISMISSED와 기대 버전0을 보낸다
- Then 합의된 최종 상태와 새 버전을 반환하고 서버의 처리자 A·시각을 기록한다
- Then 클라이언트가 보낸 다른 처리자·임의 시각은 권한/감사 근거로 사용하지 않는다
- RESOLVED는 공개 상태의 글을 숨기고, 이미 숨기거나 삭제한 글은 신고만 처리한다. DISMISSED는 글 상태를 유지한다. 처리 메모는 필수이며 같은 글의 다른 신고는 PENDING으로 남는다. (고침 #92: 한 건씩 처리하는 담당 계약 반영)

#92-S4 실패: 관리자 권한 [테스트]
- Given 비로그인 요청과 USER 회원 B의 요청이 있다
- When 각각 목록·상세·처리를 요청한다
- Then 비로그인은 401, 일반 회원은 403이며 신고/원문·처리 정보는 노출되지 않는다
- Then 저장 상태·이력·대상 글은 바뀌지 않는다. 신고자 또는 글 작성자인 ADMIN도 본인 처리 요청은 403이며, 관계없는 ADMIN의 요청은 정상 시나리오에서 확인한다. (고침 #92: 본인 처리 금지 반영)
- 역할 부여 후 재로그인으로 새 ADMIN 토큰이 적용되고, 회수 전 기존 토큰은 최대1시간 유지될 수 있는 Q2 정책을 따른다. 보안 선행 검증은 member가 담당하고 새 관리자 API의 비로그인/USER/ADMIN 실제 요청은 이 시나리오에서 확인한다 (고침 #92: member 담당 Q2 답변 반영)

#92-S5 실패: 미존재와 잘못된 입력 [테스트]
- Given 관리자 A가 없는 신고999 또는 필터·페이지·처리 결정·기대 버전·메모 규칙에 어긋나는 입력을 보낸다
- Then 없는 신고는 404·NOT_FOUND, 잘못된 입력은 400·VALIDATION과 확정된 안내 문구를 받는다. 처리·기각 모두 공백만 있는 메모와 정리 뒤 501자 메모를 거절하고, 1자와 500자는 허용하는지 검사한다. (고침 #92: 처리 메모 계약 반영)
- Then 신고·대상 글·이력은 원본을 유지한다
- 삭제된 글의 존재와 신고 미존재를 혼동하지 않는다. Q4에서 허용한 상세 조회를 원본 삭제만으로 잘못 차단하지 않는다

#92-S6 실패: 충돌 [테스트]
- Given A와 C가 신고101의 version0을 읽고 서로 다른 최종 결정을 보낸다
- When A의 결정이 먼저 커밋되고 C가 version0으로 처리한다
- Then C는 409·CONFLICT이며 A의 결정·처리자·시각과 대상 조치가 유지된다
- 별도 PostgreSQL 연결/트랜잭션과 latch/barrier로 같은 버전을 읽은 실제 경합을 확인하고, 커밋 종료 후 새 트랜잭션에서 결정·이력·대상 상태를 확인한다. 기대 버전 사전 비교만으로 완료 처리하지 않는다 (고침 #92: #89의 실제 경합·최종 DB 상태 검증 기준 반영)

#92-S7 경계: 처리 완료 신고의 재요청 [테스트]
- Given A가 신고101의 version0을 RESOLVED·메모 `확인 완료`로 처리해 커밋했으나 응답을 받지 못했다
- When A가 같은 신고·결정·기대버전·메모로 재전송한다
- Then 409 CONFLICT를 받고, 최신 상세에서 실제 최종 상태·처리자를 확인한다.
- When C가 같은 결정을 보내거나 A가 다른 메모/반대 결정으로 처리 완료 신고를 요청한다
- Then 같은 409가 반환되며 원래 처리자·시각·메모·버전·글 상태·이력은 유지된다.
- 재요청의 동일성을 구분하지 않고 모두 409를 반환한다. (고침 #92: 처리 완료 건 재조회 계약 확정)

#92-S8 실패: 게시글 조치와 처리 상태의 원자성 [테스트]
- Given 신고101은 미처리이고 대상 글은 공개 상태다.
- When 신고 처리와 대상 글 조치 사이에 DB 실패 또는 경쟁 상태 변경이 발생한다
- Then 합의된 트랜잭션/조건부 쓰기 계약에 따라 전체가 롤백되고 부분 처리·조용한 원문 삭제가 남지 않는다
- 신고 처리와 필요한 숨김은 하나의 원자적 작업이다. 신고 상태만 바꾸는 중간 단계는 따로 배포하지 않는다. (고침 #92: 담당자 답변으로 원자성 확정)
- 신고 누적만으로 글이 숨겨지지 않고, 관리자가 RESOLVED로 처리할 때만 적용되는지 확인한다.
- [리뷰 요청](https://github.com/likelion-backendschool-9th/pawmento/pull/106#issuecomment-6998962206)을 반영해 **관리자 숨김과 작성자 수정이 같은 게시글 버전 검사에 참여**하도록 Q3·Q5·Q6의 포트/저장/검사 계약에 명시한다. 신고 version 검사만으로 게시글 경합을 보호했다고 간주하지 않는다. 실제 community 저장 구현과 변경 파일은 담당자와 합의한다
- 경합 사례: 작성자 수정 트랜잭션이 VISIBLE 게시글의 본문·버전을 읽은 상태에서 대기한다. 별도 관리자 트랜잭션이 숨김과 신고 처리를 먼저 커밋한 뒤, 대기 중이던 작성자가 이전 버전으로 수정을 저장한다. 실제 PostgreSQL의 별도 연결/트랜잭션과 latch/barrier로 이 순서를 제어한다
- 기대 결과: 늦은 작성자 수정 요청은409로 거절된다. 두 트랜잭션 종료 뒤 새 트랜잭션에서 관리자 숨김 상태와 숨김 커밋 시점의 기존 본문, 성공한 신고 처리 결과가 보존되고 작성자의 오래된 본문이 저장되지 않았음을 확인한다. 작성자 수정 실패로 이미 커밋된 관리자 처리를 롤백하거나 되돌리지 않는다 (고침 #92: 관리자 숨김 선커밋 뒤 오래된 작성자 수정의409·최종 상태 보존 검증 추가)
- admin에서 community의 작성자 삭제 유스케이스를 관리자 권한 우회용으로 호출하거나 다른 도메인 JPA를 직접 수정하지 않는다

#92-S9 경계: 기존 글 동작과 구조 [테스트]
- Given 관리자 운영 경로가 추가됐다
- When 기존 작성자 글 수정·삭제, 일반 공개 조회, 권한 거절과 새 운영 요청을 실행한다
- Then 기존 community 200/204·403·404·409 및 soft delete 계약을 유지하고 새로운 운영 권한이 일반 경로로 확장되지 않는다
- 숨긴 글은 공개 목록에서 제외한다. 작성자 상세만 200과 제목·숨김 안내를 반환하고 비작성자·비로그인은 404를 받는다. 작성자 수정은 409, 소프트 삭제는 허용한다. 삭제 뒤에는 작성자 상세도 404이며 신고 기록은 유지된다. (고침 #92: 작성자 전용 숨김 안내 반영)
- Then domain은 순수 자바 객체/`domain/exception`이며 JPA 엔티티는 `adapter/out/persistence`에 둔다
- Then 다른 도메인 연결은 합의된 입력 포트를 사용하고 domain에 Spring·JPA·application·adapter 의존을 추가하지 않는다
- 공용 아키텍처 검사와 기존 community/member 테스트 수정은 Q6에서 합의한 파일에 한정한다

## 범위 밖

- 신고 접수 구현은 Q1에서 담당·이슈를 따로 정한다. 사용자 접수 API를 관리자 계획에서 임의 구현하지 않는다
- member의 관리자 계정·역할 부여/회수 구현, 마이페이지, 질문 풀 관리, 공지·회원 제재·카테고리 운영
- 엽서 판매 운영은 우체통/판매 계약을 별도 확인한 다음 계획으로 분리한다. 이번 신고 기능에 함께 넣지 않는다
- 프론트 구현·HTTP 연결·화면 변경·공통 디자인 토큰 수정. 후속 프론트 작업은 기존 토큰을 그대로 사용하며 변경이 필요하면 사용자에게 먼저 알린다
- 삭제 원문 무기한 보관·전체 개인정보 열람·공통 감사 시스템·신규 전역 예외/핸들러를 합의 없이 도입하는 작업
- 이번 문서 PR을 구현 완료로 표시하거나 기능 이슈를 닫는 작업

## 작업 순서 — 작게 나누는 백엔드 구현

1. 문서에 담당자 답변과 만료 목록의 남은 확인을 기록한다.
2. #112의 실제 조회 구현 제공 후, #152의 관리자 목록 기반에 연결한다. 상태 필터·정렬·커서·빈 목록과 관리자 권한을 확인한다(S1·S4·S5·S9의 목록 범위).
3. community 상세 조회 포트 제공 후, 관리자 입력 포트·서비스·웹을 연결한다. 접수 당시 내용과 현재 상태, 삭제·만료·미존재와 권한을 확인한다(S2·S4·S5·S9의 상세 범위).
4. community 처리·숨김 PR 제공 후, 관리자 처리 웹·DTO·검증을 연결한다. 신고·글 상태의 원자성 및 실제 DB 경합은 community 저장 검사로 확인하고, 관리자 HTTP에서 200·400·401·403·404·409와 응답을 검증한다(S3~S9).
5. 첫 만료가 오기 전에 별도 정리 작업을 제공하고, 정리된 목록·상세 응답과 재신고 판정을 검증한다.

## 정한 것

- 이번 요청은 문서와 PR을 통한 팀 합의이며 코드 구현 허가가 아니다
- 백엔드부터 작은 작업 단위로 진행하고 프론트는 별도 작업·PR로 분리한다
- 타 담당 영역은 테스트·설정·리팩터링까지 사전 합의 없이 변경하지 않는다
- 예외는 기존 공통 기본 예외를 사용한다. 도메인 예외 재포장·도메인별 Advice·전역 핸들러에 개별 도메인 등록을 추가하지 않는다
