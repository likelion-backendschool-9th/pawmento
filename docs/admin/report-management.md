# 관리자 신고 관리 계획

관련 이슈: [#92](https://github.com/likelion-backendschool-9th/pawmento/issues/92). 담당 기준은 [관리자](README.md), [회의의 담당 분배](../meetings/2026-11-16.md#참석-및-담당)를 따른다. community의 기존 글 계약은 [post.md](../community/post.md), #21·#84다.

## 한눈에

- 끝나면: 합의된 관리자만 신고 목록·상세를 보고 처리하거나 기각하며, 중복 처리와 다른 도메인 조치 실패에서 원본이 보존된다.
- 이번 PR: **계획과 합의 질문만 작성한다. 기능 구현·공유 설정 변경·프론트 작업은 하지 않는다.** 아래 API·데이터·시나리오는 Q1~Q6의 검토안이며 답변 전 확정 계약이 아니다.
- 결정 필요: 신고 저장·접수·처리의 담당, ADMIN 권한과 API, 상태 전이·숨김, 삭제 원문·개인정보, 동시성, 테스트·공유 파일 범위.
- 규모: 계약 확정 후 백엔드 목록 → 상세 → 처리 순서의 작은 작업·커밋·PR로 분리한다. 프론트는 백엔드 계약 확정 후 별도 계획 검토·구현으로 진행한다.
- 착수 조건: 해당 단위에 영향을 주는 질문의 답변과 담당 합의가 기록되고 계획이 승인돼야 한다. 문서 머지만으로 미답 질문이나 다른 담당 코드 수정이 승인됐다고 간주하지 않는다.

## 기존 사실과 제안의 구분

- 담당 분배에는 도균의 관리자 신고 관리·엽서 판매 관리가 있으며, 관리자 계정·역할은 다윗 담당이다. 마이페이지는 사용자의 최신 담당 변경에 따라 당분간 다윗 담당이며 이 계획의 수정 범위가 아니다.
- [기존 프론트 데모](../../frontend/src/life/application/useCases.ts)는 신고 상태 `PENDING / RESOLVED / DISMISSED`를 쓰며 RESOLVED에서 글을 숨긴다. 이는 브라우저 데모 동작이지 서버 상태·권한·데이터 책임의 확정 근거가 아니다. 서버 계약은 Q1·Q3에서 확인한다.
- community의 작성자 삭제 계약은 soft delete이고 일반 조회는 삭제된 글을 제외한다. 작성자 수정·삭제 API는 #84의 계약과 실제 통합 상태를 확인한다. 신고 운영 조회를 위해 이 공개 조회의 필터를 풀지 않는다. #84 리뷰의 삭제 원문 조회 질문과 Q4를 연결한다.
- 운영 경로와 보안 체인에 코드가 보인다는 이유로 ADMIN 전용 접근이 보장됐다고 판단하지 않는다. Q2 합의 후 실제 요청으로 401·403·허용 경계를 확인한다.

## 기존 백엔드 연동에서 적용할 기준

[다이어리 텍스트 CRUD 계획](../diary/basic-crud.md)과 #89의 책임 분리를 참고한다. 이는 신고 데이터 소유권·ADMIN 권한·API가 합의됐다는 뜻이 아니다.

- **업무 정책과 웹 형식을 구분한다.** 신고 상태 전이·처리 가능 여부는 합의된 도메인/애플리케이션에서 판단하고, JSON 타입·쿼리 형식은 웹 경계에서 검사한다. 웹에서만 막는 업무 정책은 입력 포트 직접 호출로 우회될 수 있으므로 서비스/도메인 검사와 직접 호출 회귀를 함께 둔다. 웹 DTO·JSON·HTTP 상태를 핵심 계층에 넘기지 않는다.
- **기술 예외를 좁게 변환하고 원인을 보존한다.** 같은 입력/충돌 응답을 유지하더라도 기존 throwable을 cause로 연결한다. Q1·Q5에서 정한 실제 DB 제약·조건부 쓰기의 실패만 합의된 애플리케이션 예외로 변환하며 모든 `DataIntegrityViolationException`을 신고 미존재/충돌로 포장하지 않는다. 다른 FK·CHECK 오류까지 정상 업무 거절로 오인하지 않는 검사도 둔다. #89의 diary FK 이름·pet 삭제 예외는 신고 기능에 복사하지 않는다.
- **경합과 원자성은 커밋 뒤 결과로 확인한다.** S6·S8에서 실제 PostgreSQL의 별도 연결/트랜잭션, latch/barrier로 경합 순서를 제어하고, 성공 응답·실패 응답과 새 트랜잭션에서 조회한 최종 상태를 함께 확인한다. 단순 순차 호출·mock 예외 발생만으로 실제 DB 경합/전체 롤백이 검증됐다고 표시하지 않는다. Q6에서 합의한 테스트만 보완한다.
- **기존 연동의 범위를 넘지 않는다.** #89는 diary와 pet의 기록 존재/삭제 제한을 연결했다. 신고 저장소·글 숨김·삭제 원문 조회·관리자 보안을 제공하는 계약이 아니므로 관리자 기능의 선행 조건을 완료 처리하지 않는다. Q1~Q6과 범위 밖 항목을 그대로 유지한다.

## API 검토안 — 확정 전 구현 금지

경로의 `/api/v1`은 기존 WebConfig를 재사용한다. 최종 prefix·메서드·DTO·필드·이름은 Q1·Q2·Q5 답변으로 확정한다. 지금 새 컨트롤러·포트·테이블을 만드는 뜻이 아니다.

| 동작 | 검토용 요청 | 검토용 성공/입력 | 선행 답변 |
| --- | --- | --- | --- |
| 신고 목록 | `GET /api/v1/admin/reports?status=PENDING&size=20&cursor=...` | 200, 신고 요약·다음 커서. 신고 ID 내림차순, 기본20·최대50을 검토한다. 전체 상태 조회 여부와 필터의 필수 여부는 미정 | Q1·Q2·Q4·Q5·Q6 |
| 신고 상세 | `GET /api/v1/admin/reports/{reportId}` | 200, 허용된 신고·대상·처리 정보. 삭제 원문/수정 전 내용은 Q4가 허용한 범위에서만 반환 | Q1·Q2·Q4·Q5·Q6 |
| 처리/기각 | `PATCH /api/v1/admin/reports/{reportId}` | `resolution`, `version`, 선택/필수 여부를 합의할 처리 사유. 성공은 200 상세를 검토. 서버가 처리자·처리 시각을 정함 | Q1~Q6 |

검토용 데이터는 `reportId`, `postId`, `status`, `reason`, `createdAt`, `version`, `processedBy`, `processedAt`이다. 신고자·작성자 정보와 처리 메모는 Q4에서 공개 범위를 정한 뒤 추가한다. DB 테이블/컬럼·유니크 조건·연관 관계·DDL 적용 주체는 Q1·Q5 합의 전 확정하지 않는다. 신고 원문·현재 글·soft delete/숨김 상태를 혼동하지 않는다.

## 1. 권한 있는 운영자의 신고 목록 (#92-R1)

합의된 관리자만 상태별 신고 목록과 페이지 경계를 확인한다. 아래 수치·경로는 API 검토안이 채택된 경우의 제안이다.

#92-S1 정상·경계: 목록 [테스트]
- Given ADMIN 운영자 A와 PENDING 신고 21건이 있고 목록 계약이 승인됐다
- When A가 첫 목록과 다음 커서 목록을 조회한다
- Then 기본20건과 나머지1건이 중복 없이 안정된 순서로 보인다
- Then 조건에 맞는 신고가 없으면 200·빈 목록이며 Q4에서 허용하지 않은 개인정보는 포함되지 않는다
- 상태 필터·정렬·커서/페이지 방식이 달라지면 Q5 답변에 맞춰 구체 예시와 기대값을 먼저 고친다

## 2. 신고와 대상 내용의 운영 조회 (#92-R2)

관리자는 허용된 신고 상세와 Q4가 정한 시점·범위의 대상 내용을 확인한다.

#92-S2 정상: 상세와 삭제된 대상 [테스트]
- Given 신고 101은 글 201을 대상으로 하고 글 201은 접수 뒤 수정되거나 작성자가 삭제했다
- When 운영자 A가 신고 101의 상세를 조회한다
- Then 신고와 대상의 관계·현재 상태를 구분하고 Q4에서 선택한 원문/현재 내용만 반환한다
- Then 일반 공개 글 조회는 계속 삭제된 글을 404로 처리한다
- 원문 열람이 허용되지 않는 경우 내용은 반환하지 않고, 합의된 대상 상태만 표시한다. 실제 반환 필드·문구는 Q4 답변으로 구체화한다

## 3. 처리·기각과 원본 보호 (#92-R3)

운영자는 허용된 상태 전이만 수행하고, 서버가 처리자·시각·버전을 기록한다. 게시글 조치는 Q3가 허용한 경우에만 포함한다.

#92-S3 정상: 처리·기각 [테스트]
- Given 승인된 상태 모델에서 신고 101은 PENDING·version0이고 A는 ADMIN이다
- When A가 RESOLVED 또는 DISMISSED와 기대 버전0을 보낸다
- Then 합의된 최종 상태와 새 버전을 반환하고 서버의 처리자 A·시각을 기록한다
- Then 클라이언트가 보낸 다른 처리자·임의 시각은 권한/감사 근거로 사용하지 않는다
- 글 숨김 여부·필수 사유·여러 신고 동시 처리는 Q3의 답변대로 검사하며 미합의를 자동 적용으로 취급하지 않는다

#92-S4 실패: 관리자 권한 [테스트]
- Given 비로그인 요청과 USER 회원 B의 요청이 있다
- When 각각 목록·상세·처리를 요청한다
- Then 비로그인은 401, 일반 회원은 403이며 신고/원문·처리 정보는 노출되지 않는다
- Then 저장 상태·이력·대상 글은 바뀌지 않는다. ADMIN A의 같은 경로는 정상 시나리오로 확인한다
- 역할 부여/회수 뒤 적용 시점과 토큰 검증 방식은 Q2 답변에 따라 별도로 구체화한다

#92-S5 실패: 미존재와 잘못된 입력 [테스트]
- Given 관리자 A가 없는 신고999 또는 합의된 필터·페이지·resolution·version·사유 규칙에 어긋나는 입력을 보낸다
- Then 없는 신고는 404·NOT_FOUND, 잘못된 입력은 400·VALIDATION과 확정된 안내 문구를 받는다
- Then 신고·대상 글·이력은 원본을 유지한다
- 삭제된 글의 존재와 신고 미존재를 혼동하지 않는다. Q4에서 허용한 상세 조회를 원본 삭제만으로 잘못 차단하지 않는다

#92-S6 실패: 충돌 [테스트]
- Given A와 C가 신고101의 version0을 읽고 서로 다른 최종 결정을 보낸다
- When A의 결정이 먼저 커밋되고 C가 version0으로 처리한다
- Then C는 409·CONFLICT이며 A의 결정·처리자·시각과 대상 조치가 유지된다
- 별도 PostgreSQL 연결/트랜잭션과 latch/barrier로 같은 버전을 읽은 실제 경합을 확인하고, 커밋 종료 후 새 트랜잭션에서 결정·이력·대상 상태를 확인한다. 기대 버전 사전 비교만으로 완료 처리하지 않는다 (고침 #92: #89의 실제 경합·최종 DB 상태 검증 기준 반영)

#92-S7 경계: 같은 처리의 재전송 [테스트]
- Given 신고101의 처리가 커밋됐지만 클라이언트는 응답을 받지 못했다
- When 같은 결정/기대 버전으로 재전송한다
- Then Q5의 검토안이 채택되면 기존 결과를 반환하고 버전·이력·게시글 조치를 중복 반영하지 않는다
- 반대 결정/재개방의 허용·거부는 Q3·Q5에서 정한다. 모두 성공하거나 모두 충돌한다고 임의 결정하지 않는다

#92-S8 실패: 게시글 조치와 처리 상태의 원자성 [테스트]
- Given Q3에서 처리와 게시글 숨김을 같은 작업으로 묶기로 합의했고 신고101은 미처리다
- When 신고 처리와 대상 글 조치 사이에 DB 실패 또는 경쟁 상태 변경이 발생한다
- Then 합의된 트랜잭션/조건부 쓰기 계약에 따라 전체가 롤백되고 부분 처리·조용한 원문 삭제가 남지 않는다
- 상태 변경만 하는 첫 단위를 선택하면 이 시나리오는 **후속 게시글 조치 단위의 착수 조건**으로 남긴다. 적용하지 않은 검증을 통과했다고 표시하지 않는다
- admin에서 community의 작성자 삭제 유스케이스를 관리자 권한 우회용으로 호출하거나 다른 도메인 JPA를 직접 수정하지 않는다

#92-S9 경계: 기존 글 동작과 구조 [테스트]
- Given 관리자 운영 경로가 추가됐다
- When 기존 작성자 글 수정·삭제, 일반 공개 조회, 권한 거절과 새 운영 요청을 실행한다
- Then 기존 community 200/204·403·404·409 및 soft delete 계약을 유지하고 새로운 운영 권한이 일반 경로로 확장되지 않는다
- Then domain은 순수 자바 객체/`domain/exception`이며 JPA 엔티티는 `adapter/out/persistence`에 둔다
- Then 다른 도메인 연결은 합의된 입력 포트를 사용하고 domain에 Spring·JPA·application·adapter 의존을 추가하지 않는다
- 공용 아키텍처 검사와 기존 community/member 테스트 수정은 Q6에서 합의한 파일에 한정한다

## 범위 밖

- 신고 접수 구현은 Q1에서 담당·이슈를 따로 정한다. 사용자 접수 API를 관리자 계획에서 임의 구현하지 않는다
- member의 관리자 계정·역할 부여/회수 구현, 마이페이지, 질문 풀 관리, 공지·회원 제재·카테고리 운영
- 엽서 판매 운영은 우체통/판매 계약을 별도 확인한 다음 계획으로 분리한다. 이번 신고 기능에 함께 넣지 않는다
- 프론트 구현·HTTP 연결·화면 변경·공통 디자인 토큰 수정. 후속 프론트 작업은 기존 토큰을 그대로 사용하며 변경이 필요하면 사용자에게 먼저 알린다
- 삭제 원문 무기한 보관·전체 개인정보 열람·공통 감사 시스템·신규 전역 예외/핸들러를 합의 없이 도입하는 작업
- 이번 문서 PR을 구현 완료로 표시하거나 기능 이슈를 닫는 작업

## 작업 순서 — 작게 나누는 백엔드 구현

1. **문서·계약 검토** — Q1~Q6의 답변, 코드 소유자·포트·테스트 범위·선행 PR 기록. 답에 따라 API·데이터·S1~S9를 확정한다. 관리자 구현 승인과 타 담당 파일 수정 합의를 구분한다
   - 파일: 본인 계획문서 `docs/admin/report-management.md` 한 파일만. 공통 README·규칙 문서와 community/member/global/프론트 코드는 수정하지 않는다
   - 확인: 문서 링크·번호·공백 검사. 기능 테스트는 실행하지 않는다
2. **목록 조회만 구현** — R1, S1·S4·S5의 목록 부분·S9. 신고 원본 저장과 ADMIN 접근 계약이 준비된 뒤 하나의 작은 PR로 진행
   - 파일 후보: Q1에서 정한 소유 도메인의 조회 입력/출력 포트·서비스·읽기 어댑터·관리자 목록 웹 경계와 관련 테스트. 확정 전 admin/community 패키지 위치를 만들지 않는다
   - 확인: 새 목록 시나리오·권한 요청 검사, 수정된 범위의 구조 검사. 필터·페이지 경계와 빈 목록 확인
3. **상세 조회만 구현** — R2, S2·S4·S5의 상세 부분·S9. Q4가 정한 삭제 원문/개인정보 정책과 관리자 조회 포트가 선행
   - 파일 후보: 승인된 상세 포트·서비스·읽기 어댑터·응답/웹 경계·관련 테스트. 일반 조회 필터는 완화하지 않는다
   - 확인: 정상/미존재/삭제 대상/비관리자 요청과 반환 필드, 기존 공개 조회 회귀 검사
4. **처리·기각만 구현** — R3, S3~S7·S9. Q3·Q5의 전이·재시도·기대 버전·이력 계약 확정 후 별도 PR
   - 파일 후보: 승인된 도메인 정책·기본 예외 하위 타입·변경 포트·서비스·조건부 쓰기 어댑터·웹 경계·단위/DB/요청 테스트
   - 확인: 성공·권한·입력 실패·실제 동시 충돌·재전송과 원본 보존
5. **게시글 조치 연결(합의한 경우만)** — S8·S9. 상태 변경과 분리할 수 있는지 먼저 Q3에서 결정한다. 같은 원자적 작업이어야 하면 필요한 최소 포트·트랜잭션 연결을 4단계와 함께 검토하고 불완전한 중간 기능을 완료로 내지 않는다
   - 파일 후보: community 담당이 승인한 운영 입력 포트/어댑터와 최소 연동 코드·통합 테스트
   - 확인: 실제 DB 실패/경합의 전체 롤백, 기존 작성자 삭제·공개 조회 회귀. 공유 테스트 변경 범위를 별도 확인

각 구현 단위는 테스트까지 함께 통과한 뒤 해당 파일만 커밋·PR로 만든다. 목록·상세·처리를 하나의 큰 프론트/백엔드 PR로 합치지 않는다. 정확한 `./gradlew test --tests '<클래스>'` 선택 명령은 소유 패키지·테스트 이름 합의 후 단위별로 확정한다. 테스트 위치를 옮기거나 줄이면 검증 범위 대응표를 함께 갱신한다. 실제 PostgreSQL/Testcontainers·Linux 환경이 필요한 요청 검사는 [검사 기준](../testing.md)과 기존 실행 환경을 따른다.

## 정한 것

- 이번 요청은 문서와 PR을 통한 팀 합의이며 코드 구현 허가가 아니다
- 백엔드부터 작은 작업 단위로 진행하고 프론트는 별도 작업·PR로 분리한다
- 타 담당 영역은 테스트·설정·리팩터링까지 사전 합의 없이 변경하지 않는다
- 예외는 기존 공통 기본 예외를 사용한다. 도메인 예외 재포장·도메인별 Advice·전역 핸들러에 개별 도메인 등록을 추가하지 않는다
