## 현재 작업 단위 — 신고 목록 계약 반영 (#92-R1)

[community의 목록 제안](https://github.com/likelion-backendschool-9th/pawmento/issues/92#issuecomment-7000963694)에 관리자 담당이 동의하는 범위다. 기존 미합의 표는 아래 목록 결정과 모순되는 부분을 다시 질문하는 근거로 사용하지 않는다. 상세·처리·숨김은 이번 목록 작업과 분리한다.

### 목록에서 채택하는 계약

- 경로: `GET /api/v1/admin/reports`. `status` 생략 시 PENDING, reportId 내림차순, `size` 생략 시20·허용 범위1~50이다. `status`는 PENDING/RESOLVED/DISMISSED만 허용한다.
- 커서는 마지막으로 반환한 `reportId`의 양의 10진수 Long 문자열이다. 첫 요청은 `cursor`를 생략하며, 다음 조회는 같은 상태 필터에서 `reportId < cursor`를 적용한다. 응답은 `items`와 `nextCursor`를 제공한다. 더 조회할 항목이 있을 때만 마지막 반환 항목의 ID를 `nextCursor`로 쓰며, 마지막 페이지·빈 목록은 `nextCursor: null`이다. 커서 ID의 실제 존재는 요구하지 않는다. (고침 #92: PR #152 리뷰에 따라 admin이 커서·종료 표현 결정)
- `status`·`size`·`cursor`는 admin 웹 어댑터가 검증한다. 명시한 빈 값, 허용되지 않은 상태(소문자 포함), 정수가 아닌 size/cursor, 범위 밖 size, 0 이하·Long 범위 초과 cursor는 거절한다. 웹 전용 `InvalidReportListRequestException`을 `RuleViolationException` 하위로 두어 공통 응답400 `VALIDATION`으로 변환한다. 안내 문구는 각각 `status는 PENDING, RESOLVED, DISMISSED 중 하나여야 해요.`, `size는 1 이상 50 이하의 정수여야 해요.`, `cursor는 양의 정수 신고 ID여야 해요.`로 정한다. MVC 기본 타입 변환 오류로 빠져 공통 응답을 우회하지 않도록 문자열 입력부터 검증한다. (고침 #92: 입력 오류는 admin 책임으로 결정)
- 항목은 `reportId`, `postId`, `status`, `reasonType`, `createdAt`, `snapshotTitle`, `postState`다. 사유 요약은 `reasonType`으로 대신하며 `postState`는 VISIBLE/HIDDEN/DELETED다.
- 목록 연결 시 admin application에 신고 상태(PENDING/RESOLVED/DISMISSED), 사유(SPAM/ABUSE/HARMFUL/MISINFO/PRIVACY/OTHER), 게시글 상태(VISIBLE/HIDDEN/DELETED)의 enum을 두고, admin outbound 어댑터가 #112 결과를 명시적으로 변환한다. community 도메인 enum을 admin 입력 포트나 웹 응답에 직접 노출하지 않는다. 알 수 없는 제공 값은 기본값이나 사용자 입력400으로 바꾸지 않고 내부 계약 오류로 실패시킨다. 현재 항목 모델의 String 교체와 변환 검사는 실제 포트 연결 작업에 포함한다.
- `createdAt`의 HTTP 표현은 UTC ISO-8601 문자열(예: `2026-11-21T00:00:00Z`)이다. 목록 연결 시 `@WebMvcTest`에서 Spring 응답 설정으로 7개 필드와 날짜의 고정 기대값을 검사한다. 현재 기본 `JsonMapper` 단위 검사는 항목 매핑만 확인하며 HTTP 형식 검증을 대신하지 않는다.
- 사유 상세 전문·신고자/작성자 ID·현재 본문·회원 개인정보를 목록에 추가하지 않는다. 상세 계약에서 따로 다룬다.
- community가 신고 저장과 운영 목록 입력 포트를 제공하고 admin은 입력 포트를 소비한다. JPA 엔티티/저장소 직접 의존이나 admin의 신고 원본 복제는 하지 않는다.
- 접수 규칙 초안(중복/본인 신고·대상 상태·사유 유형/상세 제한)에 관리자 측 이견은 없으며 실제 접수 구현은 community의 #112에서 진행한다. 접수 스냅샷 필드/캡처 시점과 보존 정책은 이번 동의로 확정하지 않는다.

### 작은 작업과 실제 착수 조건

1. **목록 계약 문서 반영:** 이 문서 한 파일과 #92 답변에 채택한 필드·조회 조건·담당 경계를 기록한다. 구현 완료로 표시하지 않는다.
2. **목록 연결 준비:** #112가 제공할 실제 입력 포트·query/result 타입을 확인한다. admin이 결정한 위 커서·종료 표현·입력 오류 계약에 필요한 상태 필터·배타적 ID 경계·추가 항목 존재 여부를 제공하는지 확인하고, 필요한 포트 조건은 #112 구현 PR 리뷰에서 제안한다.
3. **admin 목록 연결만 구현:** #112의 실제 저장/목록 포트 제공과 관리자 경로 보안 반영을 확인한 뒤 admin 소유 서비스·outbound 연결 어댑터·web DTO/컨트롤러·검사로 범위를 제한한다. 정확한 파일 목록은 기존 구조와 제공된 포트를 확인해 정한다. community/member/global 및 타 담당 테스트 변경은 소유자 합의 없이 하지 않는다.
4. **목록 검사만 검증:** #92-S1의 페이지·빈 결과·필드 매핑과 목록에 한정한 S4 권한/S5 잘못된 조회 입력/S9 의존 경계를 확인한다. 부분 검사만으로 S4/S5/S9 전체나 S2~S8 전체 완료로 표시하지 않는다.

제공 순서는 **계약 동의 → #112 신고 저장·운영 목록 포트 → #92 관리자 목록 연결**이다. 포트 제공 전 내부 구현 병행은 아직 별도 승인되지 않았으므로 타입/가짜 포트를 먼저 만들어 공유 계약을 선점하지 않는다. 보안 PR·실제 포트가 없으면 외부 HTTP 경로나 항상 빈 결과로 우회하지 않는다.

목록 구현과 별개로 #112의 스냅샷 필드·캡처 시점 결정은 접수 담당과 먼저 맞춘다. 상세 원문 열람·보존/탈퇴·처리/숨김 정책 미답은 그 기능의 조건으로 남기며, 목록에 영향을 주는 부분만 구분해 확인한다.

## 담당 리뷰에서 확인된 결정과 남은 합의

### Q2 — member 담당이 결정한 권한 계약

[member 담당자의 Q2 답변](https://github.com/likelion-backendschool-9th/pawmento/pull/93#issuecomment-6974395331)을 따른다. **아래는 관리자 담당이 새로 정한 계정 정책이 아니다.**

- 역할은 DB `member.role`의 USER/ADMIN이고, 로그인 시 JWT `role` 클레임을 `ROLE_ADMIN`으로 변환한다. 관리자는 `hasRole("ADMIN")`으로 판정하고 처리자 ID는 기존 `@LoginMember Long memberId`로 받는다.
- 로컬·소셜 가입은 USER만 허용하며 역할 변경 API는 만들지 않는다. DB 접근 권한이 있는 운영자가 가입된 대상 계정의 역할을 쿼리로 부여·회수한다. 이메일은 소문자로 조회하고 변경자·시각·대상을 팀 채널에 남긴다. 계정 생성/역할 부여 작업은 member 담당 책임으로 두며 이번 계획에서는 쿼리를 실행하지 않는다.
- 권한 부여 후 로그아웃/재로그인으로 새 토큰에 반영한다. 토큰 수명은 1시간, 리프레시 토큰은 없으며 **회수 전 발급된 ADMIN 토큰은 만료까지 최대 1시간 유효할 수 있다는 MVP 지연 정책**을 따른다. 즉시 회수 기능을 admin에서 임의 추가하지 않는다.
- 관리자 경로는 `/api/v1/admin/**`, 신고 컨트롤러는 `@RequestMapping("/admin/reports")`다. `/api/v1`은 WebConfig가 붙인다. 메서드·요청/응답 필드는 Q5에서 별도 확인한다.
- member 담당이 먼저 `global/security/SecurityConfig.java`의 `anyRequest()` 앞에 관리자 matcher 한 줄을 추가하고, 비로그인401·USER403·ADMIN 필터 통과 및 #14-S8 요청 검사를 작은 선행 PR로 제공한다. `docs/member/auth-base.md`의 판정·부여/회수·갱신 정책도 member 담당이 작성한다. 컨트롤러별 `@PreAuthorize` 방식으로 변경하지 않는다.
- admin은 **선행 보안 PR 번호·머지와 검사 통과를 확인한 뒤** 위 경로에서 기능을 제공하며, 자체 SecurityConfig/계정·역할 코드를 수정하지 않는다. 선행 보안 검사의 ADMIN 통과는 관리자 업무 컨트롤러의 성공 응답 검증과 구분하고, 새 API의 실제 요청 검사는 S4에서 확인한다.

API는 권한 있는 운영자에게만 제공하고, 목록·상세 응답에서 허용한 필드만 반환한다. DB/파일 경로·토큰·인증 정보는 제공하지 않는다. 원문은 일반 공개 API의 삭제/숨김 필터를 풀어서 가져오지 않고 community의 운영 전용 입력 포트로 제공받는다.

### 신고 접수 시점 스냅샷·보존 초안 (Q1·Q4)

- **community 소유 제안:** 신고 접수 트랜잭션에서 reportId/postId와 제목·본문·categoryCode·postVersion·capturedAt을 일관된 한 시점의 값으로 저장한다. 작성자 ID의 저장 필요성·스냅샷별 중복 저장/공유 방식은 접수 설계에서 공동 확인하며 admin에 별도 원문 복제본을 만들지 않는다.
- **접수 전에 필드 합의:** 위 항목은 후보 필드다. 제목/본문은 기존 community 길이 제한을 따르며, 회원 이메일·연락처·닉네임·전체 프로필·요청 헤더·IP는 판단 자료에 필요하다고 확인되지 않아 새로 저장하지 않는 안을 제안한다. 신고 사유는 신고 레코드의 사용자 입력으로 관리하고 본문 스냅샷과 구분한다.
- **수정·삭제:** 신고 뒤 글을 수정해도 기존 스냅샷을 현재 원문으로 덮지 않는다. 작성자 soft delete 뒤에도 신고 처리에 필요한 허용 범위만 운영 경계에서 열람하고 공개 API는 계속404다. 글 수정/삭제와 접수의 경합 시 캡처·접수 허용 시점을 community가 정의하며, 제목·본문·버전이 서로 다른 시점으로 저장되지 않는 검증을 접수 담당과 합의한다.
- **탈퇴:** 회원 탈퇴가 신고 레코드/스냅샷을 자동 삭제하거나 개인정보를 계속 노출하는 정책을 admin에서 정하지 않는다. 내부 ID의 유지·익명화, 원문 내 개인정보 처리, 진행 중 신고의 판단 가능 범위를 member/community와 확인한다.
- **보존 기간:** 미처리/처리 완료 신고 및 처리 이력의 보존 기간·기간 기산점·자동 삭제/익명화 주체는 **미정**이다. 임의로 무기한·특정 일수를 정하지 않는다. 운영용 원문 저장을 제공하기 전에 기간과 기간 만료 시 상세 응답/처리 가능 여부를 명시하고 승인받는다. 결정되지 않은 보존 정책을 기본값으로 몰래 구현하지 않는다.
- **역할 분리:** community가 접수 저장과 보존 정책의 실제 적용을, admin은 합의된 내용의 조회·판단 요청을 담당하는 안이다. 보고서 다운로드·외부 내보내기·운영자 별도 복사 저장은 이번 범위에 넣지 않는다.

### 첫 버전 숨김·처리 동작 초안 (Q3)

**관리자 결정으로만 숨김, 신고 누적에 의한 자동 숨김 없음**을 제안한다. 숨김은 작성자 soft delete와 별개 개념이며 실제 상태/포트는 community 소유다.

| 관찰 경로·동작 | VISIBLE | HIDDEN 검토안 | 작성자 soft delete 이후 |
| --- | --- | --- | --- |
| 공개 목록·일반 목록 | 기존 계약대로 노출 | 목록 제외 | 기존처럼 제외 |
| 공개 상세(작성자가 같은 경로를 이용하는 경우 포함) | 기존 계약대로 조회 | 404. 작성자라는 이유로 공개 조회를 우회하지 않음 | 기존처럼404 |
| 작성자 전용 숨김 원문 열람 | 추가 기능 없음 | 첫 버전은 별도 전용 열람을 만들지 않는 안. 필요하면 계약·포트를 별도 합의 | 별도 복구/원문 열람 기능 없음 |
| 작성자 수정 | 기존 작성자 권한/검증 | 409 CONFLICT로 거부하는 안. 단순 수정으로 숨김을 해제하지 않음 | 기존처럼404 |
| 작성자 삭제 | 기존 작성자 soft delete | 작성자의 soft delete 허용안. 숨김 처리/신고 스냅샷을 복원·제거하지 않음 | 기존 중복 삭제404 유지 |
| 관리자 신고 상세 | 권한 범위 내 신고/스냅샷 | 권한 범위 내 신고/스냅샷 | 승인된 기간·범위 내 신고/스냅샷만 |

- PENDING → **RESOLVED**는 글 숨김과 신고 처리·처리자/시각·version 갱신을 같은 DB 트랜잭션으로 완료하는 안을 제안한다. 둘 중 하나만 반영되는 상태를 만들지 않는다. 이미 삭제된 글은 복구하거나 다시 공개하지 않고 현재 삭제 상태를 유지한 채 신고를 판단하는 동작을 community와 합의한다.
- PENDING → **DISMISSED**는 신고를 기각하고 글의 기존 노출 상태를 바꾸지 않는 안을 제안한다. 다른 신고에서 이미 숨긴 글을 기각 한 건으로 되살리지 않는다.
- 한 번에 **신고 한 건만 처리**, 같은 글의 다른 PENDING 신고는 자동 일괄 처리하지 않는 안을 제안한다. 각 상세에는 현재 글 상태를 표시해 이미 숨김/삭제된 경우를 구분한다.
- 기각/처리 메모는 판단 근거 기록을 위해 필수로 두는 안이다. 정확한 길이·정규화·원문 내 개인정보 취급을 합의한다. 본인이 접수했거나 작성한 글의 신고를 직접 처리할 수 있는지 정책은 공동 확인하며 임의 허용/거절하지 않는다.
- 재개방·숨김 해제·자동 제재는 첫 버전 범위 밖으로 두는 안이다. 작성자 수정/삭제·공개 목록/상세의 변경은 community 담당이 승인한 포트·파일만 수정한다. 이 표가 타 담당 구현 권한이나 실제 프론트 작업 승인은 아니다.

### 재요청·충돌 초안 — 첫 버전은 처리 완료409 (Q5)

community의 단순화 제안에 맞춰 **처리 완료 신고에 대한 모든 재처리 요청은409 CONFLICT 후 최신 상세 재조회**를 우선 검토한다. 동일 관리자·결정·기대버전·메모인지와 관계없이 적용하는 안이며 아직 공동 확정 전이다.

- 성공 응답 유실 뒤 같은 요청을 보내도200을 재사용하지 않고409로 현재 상태 확인을 유도한다. 원래 처리자·시각·메모·version과 글 상태/처리 이력을 바꾸지 않는다.
- 최신 상세에서 RESOLVED/DISMISSED와 실제 처리자를 확인하고 이미 수행된 조치를 중복 전송하지 않는다. 관리자 프론트는 이번 범위 밖이지만 후속 화면 계약은 이 결과를 따른다.
- 미처리 신고라도 기대 버전이 다르면409다. 처음 요청의 성공은200 상세를 유지하는 검토안이며, 미존재404·형식400·권한401/403과 구분한다.
- 동일 요청200 재사용, 멱등 키·처리 메모 기반 요청 식별은 첫 버전에 넣지 않는 안이다. 이후 성공 결과 재사용 요구가 생기면 별도 계획에서 다시 정한다. 검토안 교체는 [추가 댓글](https://github.com/likelion-backendschool-9th/pawmento/issues/92#issuecomment-6997802551)을 반영한 제안이지 담당 합의 완료 표시가 아니다.

### 보안·실제 신고 포트와 병행 가능한 작업의 합의 요청 (Q1·Q6)

현 계획의 보안·실제 원본/포트 선행 조건은 유지한다. 다음은 **작업 순서를 조정할 수 있는지 묻는 안**이며 즉시 코딩 허가가 아니다.

| 작은 작업 | 먼저 필요한 계약 | 실제 선행 코드와 병행 가능 여부·범위 |
| --- | --- | --- |
| 목록 입력/출력 계약과 내부 결과 매핑 | community 운영 목록 포트가 위 admin 계약의 필드·필터·커서/정렬을 지원하는지 확인, admin의 정확한 변경 파일과 검사 담당 합의 | 합의 후 admin 소유 입력 포트·결과 모델·서비스/가짜 출력 포트 검사만 별도 PR로 만들 수 있는지 확인. 실제 저장소/보안이 없는 중간 결과를 서비스 완료·S1/S4 통과라고 하지 않으며 외부 경로를 제공하지 않음 |
| 목록 HTTP·실제 조회 연결 | 위 계약 + member 보안 PR 머지/검사 + community 실제 신고 원본·목록 입력 포트 | 기존 계획대로 선행 코드 반영 후 작은 통합 PR. 보안 없는 컨트롤러나 항상 빈 목록/가짜 데이터로 우회하지 않음 |
| 상세 | 스냅샷 필드·보존/열람 범위·community 상세 포트 | 목록 작업과 분리. 계약 검토는 먼저 가능하지만 원문 저장/조회·보존 정책을 임의 구현하지 않음 |
| 처리·숨김 | 전이·재처리409·글 노출 표·원자성·community 처리/숨김 포트 | RESOLVED의 원자적 묶음을 합의하면 신고 상태만 먼저 성공시키는 단계를 배포하지 않음. 기능·검사 범위를 공동 확정한 다음 진행 |

현재 계약이 미정인 상태에서 의미 있는 admin 내부 동작을 확정해 구현할 수 있다고 보장하지 않는다. 병행을 선택하려면 해당 단위의 필드·포트·파일·구현 책임과 검증 범위가 먼저 승인돼야 한다. member 보안 설정·신고 저장소·타 도메인 테스트를 admin이 대신 만드는 방향은 제안하지 않는다.

## 기존 사실과 제안의 구분

- 담당 분배에는 관리자 담당자의 신고 관리·엽서 판매 관리가 있으며, 관리자 계정·역할은 member 담당자 담당이다. 마이페이지는 사용자의 최신 담당 변경에 따라 당분간 member 담당자 담당이며 이 계획의 수정 범위가 아니다.
- [기존 프론트 데모](../../frontend/src/life/application/useCases.ts)는 신고 상태 `PENDING / RESOLVED / DISMISSED`를 쓰며 RESOLVED에서 글을 숨긴다. 이는 브라우저 데모 동작이지 서버 상태·권한·데이터 책임의 확정 근거가 아니다. 서버 계약은 Q1·Q3에서 확인한다.
- community의 작성자 삭제 계약은 soft delete이고 일반 조회는 삭제된 글을 제외한다. 작성자 수정·삭제 API는 #84의 계약과 실제 통합 상태를 확인한다. 신고 운영 조회를 위해 이 공개 조회의 필터를 풀지 않는다. #84 리뷰의 삭제 원문 조회 질문과 Q4를 연결한다.
- 운영 경로와 보안 체인에 코드가 보인다는 이유로 ADMIN 전용 접근이 보장됐다고 판단하지 않는다. Q2 합의 후 실제 요청으로 401·403·허용 경계를 확인한다.

## 기존 백엔드 연동에서 적용할 기준

[다이어리 텍스트 CRUD 계획](../diary/basic-crud.md)과 #89의 책임 분리를 참고한다. 이는 신고 데이터 소유권·ADMIN 권한·API가 합의됐다는 뜻이 아니다.

- **업무 정책과 웹 형식을 구분한다.** 신고 상태 전이·처리 가능 여부는 합의된 도메인/애플리케이션에서 판단하고, JSON 타입·쿼리 형식은 웹 경계에서 검사한다. 웹에서만 막는 업무 정책은 입력 포트 직접 호출로 우회될 수 있으므로 서비스/도메인 검사와 직접 호출 회귀를 함께 둔다. 웹 DTO·JSON·HTTP 상태를 핵심 계층에 넘기지 않는다.
- **기술 예외를 좁게 변환하고 원인을 보존한다.** 같은 입력/충돌 응답을 유지하더라도 기존 throwable을 cause로 연결한다. Q1·Q5에서 정한 실제 DB 제약·조건부 쓰기의 실패만 합의된 애플리케이션 예외로 변환하며 모든 `DataIntegrityViolationException`을 신고 미존재/충돌로 포장하지 않는다. 다른 FK·CHECK 오류까지 정상 업무 거절로 오인하지 않는 검사도 둔다. #89의 diary FK 이름·pet 삭제 예외는 신고 기능에 복사하지 않는다.
- **경합과 원자성은 커밋 뒤 결과로 확인한다.** S6·S8에서 실제 PostgreSQL의 별도 연결/트랜잭션, latch/barrier로 경합 순서를 제어하고, 성공 응답·실패 응답과 새 트랜잭션에서 조회한 최종 상태를 함께 확인한다. 단순 순차 호출·mock 예외 발생만으로 실제 DB 경합/전체 롤백이 검증됐다고 표시하지 않는다. Q6에서 합의한 테스트만 보완한다.
- **기존 연동의 범위를 넘지 않는다.** #89는 diary와 pet의 기록 존재/삭제 제한을 연결했다. 신고 저장소·글 숨김·삭제 원문 조회·관리자 보안을 제공하는 계약이 아니므로 관리자 기능의 선행 조건을 완료 처리하지 않는다. Q1~Q6과 범위 밖 항목을 그대로 유지한다.

## API 검토안 — 확정 전 구현 금지

경로의 `/api/v1`은 기존 WebConfig를 재사용한다. prefix `/admin/reports`와 `/api/v1` 적용 방식은 Q2 답변을 따른다. 메서드·DTO·필드·이름·페이지 계약은 Q1·Q5에서 확정한다. 지금 새 컨트롤러·포트·테이블을 만드는 뜻이 아니다.

| 동작 | 검토용 요청 | 검토용 성공/입력 | 선행 답변 |
| --- | --- | --- | --- |
| 신고 목록 | `GET /api/v1/admin/reports?status=PENDING&size=20&cursor=...` | 200, 위 목록 계약의7개 필드. status 기본 PENDING, 신고 ID 내림차순, 기본20·최대50. 커서·입력 오류·페이지 응답은 위 admin 목록 계약을 따르며 #112의 실제 포트 타입과 연결 | #112 실제 목록 포트·보안 반영·목록에 필요한 잔여 타입/검사 범위 |
| 신고 상세 | `GET /api/v1/admin/reports/{reportId}` | 200, 허용된 신고·대상·처리 정보. 삭제 원문/수정 전 내용은 Q4가 허용한 범위에서만 반환 | Q1·Q2·Q4·Q5·Q6 |
| 처리/기각 | `PATCH /api/v1/admin/reports/{reportId}` | `resolution`, `version`, 선택/필수 여부를 합의할 처리 사유. 성공은 200 상세를 검토. 서버가 처리자·처리 시각을 정함 | Q1~Q6 |

검토용 데이터는 `reportId`, `postId`, `status`, `reason`, `createdAt`, `version`, `processedBy`, `processedAt`이다. 신고자·작성자 정보와 처리 메모는 Q4에서 공개 범위를 정한 뒤 추가한다. DB 테이블/컬럼·유니크 조건·연관 관계·DDL 적용 주체는 Q1·Q5 합의 전 확정하지 않는다. 신고 원문·현재 글·soft delete/숨김 상태를 혼동하지 않는다.

## 1. 권한 있는 운영자의 신고 목록 (#92-R1)

합의된 관리자만 상태별 신고 목록과 페이지 경계를 확인한다. 목록 필드·기본 상태·정렬·크기는 현재 작업 단위의 채택한 계약을 따른다. 커서·종료 표현·입력 오류는 위 admin 목록 계약을 따른다.

#92-S1 정상·경계: 목록 [테스트]
- Given ADMIN 운영자 A와 PENDING 신고21건(reportId 1~21), 더 큰 reportId의 RESOLVED 신고22와 DISMISSED 신고23이 함께 있다
- When A가 **status와 size를 생략**해 첫 목록을 조회하고, 응답의 다음 커서를 사용해 **status와 size를 계속 생략**한 다음 목록을 조회한다
- Then 첫 페이지는 PENDING ID21~2의20건, 다음 페이지는 PENDING ID1의1건으로 중복 없이 내림차순으로 보인다. ID22·23은 두 페이지 모두 제외돼야 하며 다른 상태의 신고가 페이지 크기를 차지하지 않는다 (고침 #92: 기본 PENDING 필터 누락을 검출하는 다른 상태·상위 ID 데이터 추가)
- Then 조건에 맞는 신고가 없으면 200·빈 목록이며 Q4에서 허용하지 않은 개인정보는 포함되지 않는다
- 첫 페이지의 nextCursor는 "2", 마지막 페이지와 빈 목록은 null이다. size=1/50과 cursor ID가 존재하지 않아도 배타적 ID 경계로 조회되는 경우를 확인한다. 잘못된 status/size/cursor는 위 admin 계약의400 VALIDATION·안내 문구로 확인한다 (고침 #92: 커서 경계·종료·오류 기대값 구체화)
- 목록 연결 시 enum 변환과 허용되지 않은 제공 값의 실패를 검사하고, `@WebMvcTest`에서 실제 HTTP 항목의7개 필드와 createdAt의 UTC ISO-8601 고정 기대값을 확인한다. 기본 JsonMapper 단위 검사만으로 HTTP 검사를 완료 처리하지 않는다
- 목록 항목은 reportId/postId/status/reasonType/createdAt/snapshotTitle/postState만 매핑하며 사유 상세·신고자/작성자 ID·본문·회원 개인정보를 반환하지 않는다 (고침 #92: community 목록 제안의 조회 조건·필드 채택)

## 2. 신고와 대상 내용의 운영 조회 (#92-R2)

관리자는 허용된 신고 상세와 Q4가 정한 시점·범위의 대상 내용을 확인한다.

#92-S2 정상: 상세와 삭제된 대상 [테스트]
- Given 신고 101은 글 201을 대상으로 하고 글 201은 접수 뒤 수정되거나 작성자가 삭제했다
- When 운영자 A가 신고 101의 상세를 조회한다
- Then 신고와 대상의 관계·현재 상태를 구분하고 Q4에서 선택한 원문/현재 내용만 반환한다
- Then 일반 공개 글 조회는 계속 삭제된 글을 404로 처리한다
- 신고 접수 시점 스냅샷을 채택하면 글201을 접수 후 수정/삭제해도 허용된 신고 당시 내용과 현재 글 상태를 구분하는 검사를 둔다. 탈퇴/보존 기간 경계와 노출 필드는 접수 설계의 Q4 답변으로 확정한다
- 위 관리자 초안을 채택하면 목록에는 요약만, 상세에는 접수 당시 자료와 현재 글 상태를 구분한다. 신고 뒤 수정/삭제해도 스냅샷을 덮지 않고, 보존 기간/탈퇴 경계는 합의한 정책으로 검사한다
- 원문 열람이 허용되지 않는 경우 내용은 반환하지 않고, 합의된 대상 상태만 표시한다. 실제 반환 필드·문구는 Q4 답변으로 구체화한다

## 3. 처리·기각과 원본 보호 (#92-R3)

운영자는 허용된 상태 전이만 수행하고, 서버가 처리자·시각·버전을 기록한다. 게시글 조치는 Q3가 허용한 경우에만 포함한다.

#92-S3 정상: 처리·기각 [테스트]
- Given 승인된 상태 모델에서 신고 101은 PENDING·version0이고 A는 ADMIN이다
- When A가 RESOLVED 또는 DISMISSED와 기대 버전0을 보낸다
- Then 합의된 최종 상태와 새 버전을 반환하고 서버의 처리자 A·시각을 기록한다
- Then 클라이언트가 보낸 다른 처리자·임의 시각은 권한/감사 근거로 사용하지 않는다
- 관리자 초안을 채택하면 RESOLVED는 숨김과 원자적으로 반영, DISMISSED는 현재 글 상태 유지, 신고 한 건만 처리·다른 신고 자동 처리 없음·처리 메모 필수다. 이 기대값은 Q3 합의 후 확정하며 미합의를 자동 적용으로 취급하지 않는다

#92-S4 실패: 관리자 권한 [테스트]
- Given 비로그인 요청과 USER 회원 B의 요청이 있다
- When 각각 목록·상세·처리를 요청한다
- Then 비로그인은 401, 일반 회원은 403이며 신고/원문·처리 정보는 노출되지 않는다
- Then 저장 상태·이력·대상 글은 바뀌지 않는다. ADMIN A의 같은 경로는 정상 시나리오로 확인한다
- 역할 부여 후 재로그인으로 새 ADMIN 토큰이 적용되고, 회수 전 기존 토큰은 최대1시간 유지될 수 있는 Q2 정책을 따른다. 보안 선행 검증은 member가 담당하고 새 관리자 API의 비로그인/USER/ADMIN 실제 요청은 이 시나리오에서 확인한다 (고침 #92: member 담당 Q2 답변 반영)

#92-S5 실패: 미존재와 잘못된 입력 [테스트]
- Given 관리자 A가 없는 신고999 또는 합의된 필터·페이지·resolution·version·사유 규칙에 어긋나는 입력을 보낸다
- Then 없는 신고는 404·NOT_FOUND, 잘못된 입력은 400·VALIDATION과 확정된 안내 문구를 받는다
- Then 신고·대상 글·이력은 원본을 유지한다
- 삭제된 글의 존재와 신고 미존재를 혼동하지 않는다. Q4에서 허용한 상세 조회를 원본 삭제만으로 잘못 차단하지 않는다

#92-S6 실패: 충돌 [테스트]
- Given A와 C가 신고101의 version0을 읽고 서로 다른 최종 결정을 보낸다
- When A의 결정이 먼저 커밋되고 C가 version0으로 처리한다
- Then C는 409·CONFLICT이며 A의 결정·처리자·시각과 대상 조치가 유지된다
- 별도 PostgreSQL 연결/트랜잭션과 latch/barrier로 같은 버전을 읽은 실제 경합을 확인하고, 커밋 종료 후 새 트랜잭션에서 결정·이력·대상 상태를 확인한다. 기대 버전 사전 비교만으로 완료 처리하지 않는다 (고침 #92: #89의 실제 경합·최종 DB 상태 검증 기준 반영)

#92-S7 경계: 처리 완료 신고의 재요청 [테스트]
- Given A가 신고101의 version0을 RESOLVED·메모 `확인 완료`로 처리해 커밋했으나 응답을 받지 못했다
- When A가 같은 신고·결정·기대버전·메모로 재전송한다
- Then **첫 버전 검토안은409 CONFLICT**이며 최신 상세를 조회해 실제 최종 상태·처리자를 확인한다. 기존 성공 결과200을 재사용하지 않는다
- When C가 같은 결정을 보내거나 A가 다른 메모/반대 결정으로 처리 완료 신고를 요청한다
- Then 같은409 검토안을 적용하고 원래 처리자·시각·메모·version·글 상태·이력은 유지된다
- 같은 요청/다른 요청 구분·멱등 키·정규화로200 재사용을 구현하지 않는다. 그 요구가 생길 때 후속 계획으로 다룬다. 공동 답변 후 정확한 응답/안내 문구를 확정한다 (고침 #92: community 추가 제안에 따라 첫 버전 재처리409·상세 재조회안으로 단순화)

#92-S8 실패: 게시글 조치와 처리 상태의 원자성 [테스트]
- Given Q3에서 처리와 게시글 숨김을 같은 작업으로 묶기로 합의했고 신고101은 미처리다
- When 신고 처리와 대상 글 조치 사이에 DB 실패 또는 경쟁 상태 변경이 발생한다
- Then 합의된 트랜잭션/조건부 쓰기 계약에 따라 전체가 롤백되고 부분 처리·조용한 원문 삭제가 남지 않는다
- 새 관리자 초안은 RESOLVED와 숨김을 같은 원자적 단위로 제안한다. 이를 채택하면 처리 상태만 먼저 성공시키는 기능을 완료로 내지 않는다. 다른 분리안을 합의하면 이 시나리오의 적용 범위를 먼저 수정하며, 미구현 검증을 통과했다고 표시하지 않는다
- Q3에서 **관리자 결정으로만 숨김**을 채택하면 신고 누적만으로 자동 숨김/공개 노출 변경이 발생하지 않는 경우도 확인한다. 공개 목록·상세의 숨김 처리와 작성자 화면의 열람/수정/삭제 기대값은 community와 합의한 뒤 명시하며, 미합의 상태로 완료 처리하지 않는다
- [리뷰 요청](https://github.com/likelion-backendschool-9th/pawmento/pull/106#issuecomment-6998962206)을 반영해 **관리자 숨김과 작성자 수정이 같은 게시글 버전 검사에 참여**하도록 Q3·Q5·Q6의 포트/저장/검사 계약에 명시한다. 신고 version 검사만으로 게시글 경합을 보호했다고 간주하지 않는다. 실제 community 저장 구현과 변경 파일은 담당자와 합의한다
- 경합 사례: 작성자 수정 트랜잭션이 VISIBLE 게시글의 본문·버전을 읽은 상태에서 대기한다. 별도 관리자 트랜잭션이 숨김과 신고 처리를 먼저 커밋한 뒤, 대기 중이던 작성자가 이전 버전으로 수정을 저장한다. 실제 PostgreSQL의 별도 연결/트랜잭션과 latch/barrier로 이 순서를 제어한다
- 기대 결과: 늦은 작성자 수정 요청은409로 거절된다. 두 트랜잭션 종료 뒤 새 트랜잭션에서 관리자 숨김 상태와 숨김 커밋 시점의 기존 본문, 성공한 신고 처리 결과가 보존되고 작성자의 오래된 본문이 저장되지 않았음을 확인한다. 작성자 수정 실패로 이미 커밋된 관리자 처리를 롤백하거나 되돌리지 않는다 (고침 #92: 관리자 숨김 선커밋 뒤 오래된 작성자 수정의409·최종 상태 보존 검증 추가)
- admin에서 community의 작성자 삭제 유스케이스를 관리자 권한 우회용으로 호출하거나 다른 도메인 JPA를 직접 수정하지 않는다

#92-S9 경계: 기존 글 동작과 구조 [테스트]
- Given 관리자 운영 경로가 추가됐다
- When 기존 작성자 글 수정·삭제, 일반 공개 조회, 권한 거절과 새 운영 요청을 실행한다
- Then 기존 community 200/204·403·404·409 및 soft delete 계약을 유지하고 새로운 운영 권한이 일반 경로로 확장되지 않는다
- 관리자 숨김 초안을 채택하면 공개/일반 목록 제외·일반 상세404(작성자 포함)·숨긴 글 수정409·작성자 soft delete 허용·삭제 뒤404 유지·스냅샷 보존을 각각 회귀 검사한다. 이 기대값은 Q3 답변 후 확정한다. 신고 누적 자동 숨김 여부도 함께 검증하며 데모 동작으로 확정하지 않는다 (고침 #92: community 숨김·작성자 열람 합의 항목 반영)
- Then domain은 순수 자바 객체/`domain/exception`이며 JPA 엔티티는 `adapter/out/persistence`에 둔다
- Then 다른 도메인 연결은 합의된 입력 포트를 사용하고 domain에 Spring·JPA·application·adapter 의존을 추가하지 않는다
- 공용 아키텍처 검사와 기존 community/member 테스트 수정은 Q6에서 합의한 파일에 한정한다

## 범위 밖

- 신고 접수 구현은 Q1에서 담당·이슈를 따로 정한다. 사용자 접수 API를 관리자 계획에서 임의 구현하지 않는다
- member의 관리자 계정·역할 부여/회수 구현, 마이페이지, 질문 풀 관리, 공지·회원 제재·카테고리 운영
- 엽서 판매 운영은 우체통/판매 계약을 별도 확인한 다음 계획으로 분리한다. 이번 신고 기능에 함께 넣지 않는다
- 프론트 구현·HTTP 연결·화면 변경·공통 디자인 토큰 수정. 후속 프론트 작업은 기존 토큰을 그대로 사용하며 변경이 필요하면 사용자에게 먼저 알린다
- 삭제 원문 무기한 보관·전체 개인정보 열람·공통 감사 시스템·신규 전역 예외/핸들러를 합의 없이 도입하는 작업
- 이번 문서 PR을 구현 완료로 표시하거나 기능 이슈를 닫는 작업

## 작업 순서 — 작게 나누는 백엔드 구현

아래는 기존 선행 코드 완료 후의 통합 구현 순서다. 위 병행 작업안이 공동 승인되면 목록 내부 계약/매핑 작업과 실제 HTTP·조회 연결을 별도 단위로 나누도록 이 순서와 검사 범위를 먼저 갱신한다. 이번 초안만으로 기존 착수 조건을 변경하지 않는다.

1. **문서·계약 검토** — Q1~Q6의 답변, 코드 소유자·포트·테스트 범위·선행 PR 기록. 답에 따라 API·데이터·S1~S9를 확정한다. 관리자 구현 승인과 타 담당 파일 수정 합의를 구분한다
   - 파일: 본인 계획문서 `docs/admin/report-management.md` 한 파일만. 공통 README·규칙 문서와 community/member/global/프론트 코드는 수정하지 않는다
   - 확인: 문서 링크·번호·공백 검사. 기능 테스트는 실행하지 않는다
2. **목록 조회만 구현** — R1, S1·S4·S5의 목록 부분·S9. member 보안 선행 PR의 관리자 경로 보호와 community 접수 후속 이슈/PR의 실제 신고 원본·운영 목록 포트가 준비된 뒤 하나의 작은 PR로 진행
   - 파일 후보: Q1에서 정한 소유 도메인의 조회 입력/출력 포트·서비스·읽기 어댑터·관리자 목록 웹 경계와 관련 테스트. 확정 전 admin/community 패키지 위치를 만들지 않는다
   - 확인: 새 목록 시나리오·권한 요청 검사, 수정된 범위의 구조 검사. 필터·페이지 경계와 빈 목록 확인
3. **상세 조회만 구현** — R2, S2·S4·S5의 상세 부분·S9. Q4가 정한 삭제 원문/개인정보 정책과 관리자 조회 포트가 선행
   - 파일 후보: 승인된 상세 포트·서비스·읽기 어댑터·응답/웹 경계·관련 테스트. 일반 조회 필터는 완화하지 않는다
   - 확인: 정상/미존재/삭제 대상/비관리자 요청과 반환 필드, 기존 공개 조회 회귀 검사
4. **처리·기각만 구현** — R3, S3~S7·S9. Q3·Q5의 전이·재시도·기대 버전·이력 계약 확정 후 별도 PR
   - 파일 후보: 승인된 도메인 정책·기본 예외 하위 타입·변경 포트·서비스·조건부 쓰기 어댑터·웹 경계·단위/DB/요청 테스트
   - 확인: 성공·권한·입력 실패·실제 동시 충돌·재전송과 원본 보존
5. **게시글 조치 연결(합의한 경우만)** — S8·S9. 상태 변경과 분리할 수 있는지 먼저 Q3에서 결정한다. 같은 원자적 작업이어야 하면 필요한 최소 포트·트랜잭션 연결을 4단계와 함께 검토하고 불완전한 중간 기능을 완료로 내지 않는다
   - 파일 후보: community 담당이 승인한 운영 입력 포트/어댑터와 최소 연동 코드·통합 테스트
   - 확인: 실제 DB 실패/경합의 전체 롤백, 기존 작성자 삭제·공개 조회 회귀. 공유 테스트 변경 범위를 별도 확인

각 구현 단위는 테스트까지 함께 통과한 뒤 해당 파일만 커밋·PR로 만든다. 목록·상세·처리를 하나의 큰 프론트/백엔드 PR로 합치지 않는다. 정확한 `./gradlew test --tests '<클래스>'` 선택 명령은 소유 패키지·테스트 이름 합의 후 단위별로 확정한다. 테스트 위치를 옮기거나 줄이면 검증 범위 대응표를 함께 갱신한다. 실제 PostgreSQL/Testcontainers·Linux 환경이 필요한 요청 검사는 [검사 기준](../testing.md)과 기존 실행 환경을 따른다.

## 정한 것

- 이번 요청은 문서와 PR을 통한 팀 합의이며 코드 구현 허가가 아니다
- 백엔드부터 작은 작업 단위로 진행하고 프론트는 별도 작업·PR로 분리한다
- 타 담당 영역은 테스트·설정·리팩터링까지 사전 합의 없이 변경하지 않는다
- 예외는 기존 공통 기본 예외를 사용한다. 도메인 예외 재포장·도메인별 Advice·전역 핸들러에 개별 도메인 등록을 추가하지 않는다
