# 다이어리·질문 가족 연동 계획

관련 이슈: [#32](https://github.com/likelion-backendschool-9th/pawmento/issues/32), [#31](https://github.com/likelion-backendschool-9th/pawmento/issues/31), 첨부는 [#33](https://github.com/likelion-backendschool-9th/pawmento/issues/33). 가족 API는 [#133](https://github.com/likelion-backendschool-9th/pawmento/issues/133) 담당이 구현한다.

## 목표와 선행 조건

가족 구성원이 같은 반려동물의 일기·질문 답변을 함께 조회하고 각자의 계정으로 작성한다. 다이어리와 질문의 저장소·날짜·진행은 계속 분리한다. 이 문서는 #32-R3, #31의 가족 공동 진행·접근 요구사항, #33의 부모 권한 기반 첨부 열람을 구체화한다.

선행 계약은 [가족 계획](../family/membership.md)의 `CheckPetAccessUseCase`와 `CheckPetAccessQuery(petId, memberId)`, `CheckPetAccessResult`다. #196은 접근 포트의 선행 PR이며 초대·탈퇴·이전 전체 구현을 뜻하지 않는다. 포트가 develop에 반영된 후 도메인별로 연결하고, 실제 가입·회수 종단 검증은 해당 가족 API까지 준비된 후 수행한다. 테스트 fixture만으로 가족 전체 완료를 표시하지 않는다.

## 권한 계약

역할은 `OWNER / FAMILY / NONE`이다. `EDITOR / VIEWER`를 새로 만들지 않는다. 인증 회원은 서버에서 결정하며 클라이언트의 작성자·역할을 신뢰하지 않는다.

| 동작 | OWNER | FAMILY | NONE |
| --- | --- | --- | --- |
| 일기·답변 목록/상세·달력·연결된 사진/음성 열람 | 허용 | 허용 | 거부 |
| 일기·답변 생성, 현재 질문 확인·배정 | 허용 | 허용 | 거부 |
| 본인 글 수정·삭제 | 허용 | 허용 | 거부 |
| 다른 작성자 글 수정·첨부 교체 | 거부 | 거부 | 거부 |
| 다른 작성자 글 삭제 | 가족 계획 Q2의 적용 합의 후 허용 | 거부 | 거부 |
| 반려동물 정보·모드 관리 | pet의 소유주 전용 계약 유지 | 거부 | 거부 |

소유주의 타인 글 삭제는 가족 계획에서 정한 목표다. 구체적인 적용 범위는 아래 [Q2 소유주 타인 글 삭제 계획](#q2-소유주-타인-글-삭제-계획)으로 검토한다. 이 세부 계획의 PR 승인 전에는 기존 작성자 전용 삭제를 유지한다. 첨부 없는 삭제만 먼저 열어 첨부 유무에 따라 권한이 달라지는 배포는 하지 않는다. 질문 답변 첨부도 이미 구현되어 있으므로 질문만 텍스트 단계로 먼저 열지 않으며, [가족 계획](../family/membership.md)의 질문 답변 확인과 4단계도 이 기준으로 맞췄다.

미인증은 401, 존재하는 반려동물의 비가족·권한 회수는 403, 없는 반려동물·기록·아이와 다른 기록 ID는 404, 버전·중복 답변·모드 충돌은 409다. `NONE`만으로 없는 아이와 비가족을 구분할 수 없으므로 각 도메인의 접근 어댑터가 pet의 `GetPetOwnerUseCase`(요청자 검사·잠금 없음, `Optional<GetPetOwnerResult>` 반환)를 함께 사용한다. 이 포트는 #196에서 들어오므로 #196이 develop에 반영된 뒤에 쓸 수 있다. 서비스가 다른 도메인의 저장소를 직접 읽지 않는다. 404 통일은 이번 변경에 포함하지 않는다.

## 헥사고날 경계와 트랜잭션

- diary·question·media의 자체 접근 확인 출력 포트를 유지하고 외부 어댑터가 family 입력 포트를 호출한다. 핵심 계층에 family 엔티티·도메인 역할·JPA 저장소를 노출하지 않는다. 역할이 필요하면 해당 도메인의 계약으로 변환한다.
- 사용자 컨트롤러·경로·인증 방식은 유지한다. 권한은 입력 유스케이스 직접 호출에도 적용한다. 관리자 권한이 개인 기록 접근을 대신하지 않는다.
- 읽기는 각 요청의 DB 멤버십을 확인하고 기존 목록/count·상세/첨부의 스냅샷 일관성을 유지한다. 회수 커밋 이후 시작한 요청은 거부한다. 이미 승인돼 전송 중인 응답이나 내려받은 파일을 회수하지 않는다.
- 쓰기는 같은 트랜잭션에서 pet 행 잠금 → 최신 소유주/멤버십 확인 → 부모 기록·진행 잠금 → 첨부 자산 잠금 순서로 정렬한다. pet의 `LockPetOwnerUseCase`(#196에서 들어오며, 반려동물 행을 `FOR UPDATE`로 읽어 소유주를 돌려준다)는 `Propagation.MANDATORY`라 호출자 트랜잭션 안에서만 부를 수 있다. 기존 포트의 반환값만으로 가족 여부를 추정하지 않는다. 가족 변경도 pet 행을 먼저 잠그므로 먼저 잠금을 얻은 요청이 끝난 뒤 다음 요청이 최신 권한을 확인한다.
- 기존 JPA CRUD, 낙관적 버전, 같은 DB의 첨부 참조·지도 반영 원자성을 유지한다. 일반 CRUD용 JDBC를 추가하지 않는다. 기존 잠금 순서와 달라지는 모든 쓰기 경로를 조사하고 실제 PostgreSQL 경합 검사 후 연결한다.

## 다이어리 연결

목록·달력은 접근 검사 후 `petId`와 날짜로 조회한다. `createdBy = 요청자` 조건을 추가하지 않으며 다른 반려동물의 기록은 섞이지 않는다. 작성자 ID·최초 작성 시각·사건 날짜는 수정하거나 소유주를 이전해도 보존한다.

작성자 표시의 제안 계약은 기존 `createdBy`를 유지하고 `author: {memberId, displayName}`을 상세·목록에 추가하는 것이다. 이름은 member 입력 포트로 가져와 생성 시 스냅샷으로 저장하며 body 값은 거부한다. 기존 행의 이름 스냅샷은 마이그레이션 시 member 입력 계약으로 채우고, 회원이 실제로 없어 조회 불가능한 경우에만 `알 수 없는 작성자`로 표시한다. 저장소 장애를 누락 회원처럼 처리하지 않는다. 회원 탈퇴에 따른 익명화·30일 정리는 별도 탈퇴 계획과 합의하며, 이 문서만으로 스냅샷 영구 보존을 확정하지 않는다. 이 응답·마이그레이션 계약은 계획 PR 승인 후 구현한다.

가족 탈퇴·내보내기는 기존 글과 작성자 ID를 삭제하지 않는다. 나간 작성자도 현재 가족이 아니면 자기 글을 읽거나 수정·삭제하지 못한다. 소유주 이전은 기록의 작성자를 새 소유주로 바꾸지 않는다.

일기 위치는 별도 개인정보다. 가족에게 본문을 공개해도 현재 계약대로 다른 작성자의 `location`은 null이며 지도 핀 열람 범위를 넓히지 않는다. 가족이 자기 일기를 작성할 때 MANUAL/NONE을 사용하는 경로와 지도 입력 포트의 작성자 계약도 함께 검증한다. 타인 글 삭제를 활성화할 때는 원 작성자 핀의 삭제까지 같은 트랜잭션에 포함하고 map 담당과 포트 계약을 확인한다.

## 질문 연결

현재 질문과 진행의 키는 `petId + mode`로 유지한다. 가족별 진행 행을 만들지 않는다. ACTIVE는 일상 질문, GARDEN은 기억 질문이며 답변 전까지 자정·재접속으로 질문을 교체하지 않는다.

첫 답변이 질문 회차를 한 번만 완료하고 다음 배정 대기 상태로 만든다. 다른 가족은 기존 `promptId`에 자기 답변을 추가할 수 있으며 이미 넘어간 현재 진행을 다시 변경하지 않는다. 회차·회원당 답변 하나와 중복 409를 유지한다. answeredAt/answeredDate는 실제 등록 순간의 서버 시각과 Asia/Seoul 날짜이며 수정·삭제로 원 등록일을 바꾸지 않는다.

기존 `author`와 질문 본문 스냅샷을 유지한다. 가족 동시 답변·마지막 답변 삭제도 진행을 되돌리지 않는다. 현재 질문 조회·답변 목록/상세·첨부 권한을 모두 가족 포트에 연결한다. 과거 회차 목록/상세 API와 화면 추가는 별도 계획이며 이번 문서로 새 API를 확정하지 않는다.

## 사진·음성 연결

부모 diary/question의 현재 열람 권한과 실제 첨부 관계를 검사한 뒤 media 입력 포트로 읽는다. 공통 업로드·미연결 READY 자산의 조회·취소는 업로더 권한을 유지한다. 가족이라는 이유로 남의 미연결 자산을 보거나 새 글에 연결하지 못한다.

새 연결은 요청자 업로드·같은 아이·같은 purpose·READY 조건을 유지한다. 부모 권한을 통과한 기존 연결의 조회·유지·해제는 원 업로더와 요청자가 다를 수 있다. 소유주의 타인 글 삭제를 구현한다면 신뢰할 수 있는 부모 경로에서 DB로 읽은 previous와 requested를 구분하는 media 계약을 diary/question과 함께 변경한다. previous를 외부 body로 받거나 업로더 검사를 전체 제거하지 않는다. 이 계약은 #133의 제안이며 현재 `assetIds + purpose` 계약과 동일하다고 가정하지 않는다.

삭제·참조 해제·지도 제거 중 실패하면 부모·참조 수·진행·핀을 전부 롤백한다. 물리 파일은 기존 커밋 후 정리 작업으로 처리하며 공유 파일은 마지막 실제 참조가 사라졌을 때만 정리한다. HEAD·Range·썸네일에도 동일한 가족 권한을 적용한다.

직접 유스케이스 권한 검사와 실제 HTTP 시나리오를 함께 둔다. 가족 초대·가입·나가기·내보내기 API가 준비되면 fixture 권한 검사와 별도로 실제 두 계정 흐름을 실행한다. 프론트가 연결되기 전에는 #31-S19/S20이나 파일 UI 시나리오를 완료로 표시하지 않는다. 검사를 다른 계층으로 옮기거나 줄이면 testing-coverage 대응표를 함께 갱신한다.

## 작업 순서와 PR 경계

1. 계획 승인: 가족 접근 포트와 예외 응답, 작성자 스냅샷·기존 행 보강, Q2 삭제 적용 범위, map 삭제 계약을 관련 담당이 리뷰한다.
2. 공통 권한·첨부 기반: family 포트 반영 후 도메인별 접근 어댑터와 필요한 media 계약을 준비한다. 공용 업로드를 먼저 무제한 개방하지 않는다. Q2를 보류하면 타인 삭제는 차단한 채 가족 조회·본인 작성만 연결한다.
3. 다이어리: 생성·상세·목록·달력·본인 변경, 작성자 응답과 마이그레이션, 첨부·위치 경계를 묶어 검증한다. #32-S30~S32 및 기존 S2/S5/S11/S24 회귀.
4. 질문: 현재 질문·공통 진행·개별 답변·첨부를 연결하고 #31-S30/S31 및 기존 S6/S7/S8/S12/S18을 검증한다. 다이어리 저장소·달력에 영향이 없는지 확인한다.
5. 가족 API 종단 확인: 실제 가입·회수·이전 API로 두 계정과 동시 쓰기를 검증한다. #133 전체 완료 여부는 가족 담당이 관리한다. 각 이슈는 완료된 범위만 체크한다.

## 범위 밖과 담당 확인

초대 코드·가족 목록·가입·내보내기·소유주 이전 API 구현, 가족 UI·프론트 API 연결, 관리자 화면, 사진 GPS/AUTO, 가족 지도 공유, 회원 탈퇴 데이터 영구 삭제, 질문 회차 이력 신규 API는 이번 구현 범위가 아니다.

- family 담당: NONE 처리와 잠금 순서, 회수/이전 실제 API 준비 시점.
- diary/question/media 담당: Q2의 타인 글 삭제 동시 적용과 previous/requested 내부 계약. 승인 전 타인 삭제 허용 금지.
- member 담당: 이름 조회/회원 부재 구분 및 기존 데이터 보강, 탈퇴 표시 정책.
- map 담당: 가족 작성자의 MANUAL/NONE 반영과 소유주 타인 삭제 시 원 작성자 핀 제거. 지도 열람 권한은 확대하지 않는다.


## Q2 소유주 타인 글 삭제 계획

관련 요구사항은 #32-R3와 가족 계획 #133의 소유주 삭제 정책이다. 기존 #32-S31·S32, #31-S31, #33-S20의 미완료 범위를 이어서 구현한다. 이번 계획 작성은 삭제 권한이 이미 적용됐거나 관련 담당의 검토가 끝났음을 뜻하지 않는다.

### 정한 것과 범위

- 현재 소유주는 같은 반려동물의 다른 가족이 쓴 일기와 질문 답변을 삭제할 수 있다. 작성자가 가족에서 나간 뒤에도 동일하다. 가족은 본인 글만 삭제하며, 모든 역할의 타인 글 수정·제목 변경·첨부 교체는 계속 거부한다. 비가족 관리자에게 예외를 주지 않는다. (고침 #133: Q2를 diary·question·media에 함께 적용)
- 기존 DELETE 경로와 `petId`·기대 `version`, 성공 204를 유지한다. 소유주 전용 우회 API, 외부 body의 작성자·역할·첨부 목록은 추가하지 않는다.
- 일기와 질문 답변, 사진·음성 첨부가 있는 경우와 없는 경우를 한 배포에서 동일하게 적용한다. 질문 삭제로 일기/달력에 행을 만들거나 현재 질문·완료 회차를 되돌리지 않는다.
- 삭제 이력 보관·복구·알림·가족 API 구현·소유주 이전 API 구현은 범위 밖이다. 위치 열람 권한도 확대하지 않는다. 프론트 삭제 확인 화면은 별도 연결 작업이며 이 백엔드 단위의 완료에 포함하지 않는다.

### 권한과 헥사고날 경계

1. diary/question의 접근 출력 포트가 삭제 전용 잠금 권한 결과를 제공한다. 결과는 각 도메인의 소유주 여부와 질문의 현재 모드 등 필요한 값으로 한정한다. family의 엔티티·역할 enum·저장소를 핵심 계층에 가져오지 않는다.
2. 외부 접근 어댑터가 기존 pet 행 잠금과 family 접근 입력 포트를 사용해 최신 권한을 확인한다. 같은 트랜잭션에서 pet 잠금 → 멤버십/소유주 확인 → 부모 기록 잠금 → 첨부 자산 잠금 순서를 유지한다. 잠금 전 조회는 사전 오류 확인용이며 삭제 허가의 근거로 재사용하지 않는다.
3. 부모의 petId를 확인하고, 잠근 부모의 작성자와 잠금 후 소유주 결과로 삭제를 허용한다. 비가족/다른 가족의 타인 삭제는 403, 없는 기록·다른 아이의 기록은 기존 404 계약, 오래된 version·질문 모드 충돌은 기존 409 계약을 유지한다.
4. 수정과 삭제가 공유하던 작성자 검사를 분리한다. 삭제 권한 확대가 수정 경로의 `requireAuthor`/`requireEditable` 검사를 완화하지 않도록 한다. 질문 삭제도 기존 모드·버전 검사는 유지한다.

### 첨부 참조와 실제 파일 정리

- `previous`는 삭제 권한 확인 후 DB에서 읽은 해당 부모의 실제 첨부 ID다. 삭제의 `requested`는 빈 목록이다. 요청자가 업로드한 파일 목록이나 클라이언트 입력을 `previous`로 받지 않는다.
- 공통 media 잠금 명령에는 이미 `previous/requested/purpose`가 있다. 현재 업로더 검사 예외는 `PET_PROFILE`의 previous에 한정돼 있으므로, diary/question의 검증된 기존 연결 해제에도 적용하도록 범위를 명시적으로 확장한다. 요청자와 다른 업로더라는 이유만으로 부모 삭제를 막지 않는다.
- 신규 연결은 계속 요청자 업로드·같은 아이·같은 purpose·READY 조건을 만족해야 한다. 기존 연결 예외를 미연결 자산 조회/취소나 다른 글의 파일 신규 연결로 확장하지 않는다. 기존 참조 유지·교체 경로의 영향도 회귀 검사한다.
- 기존 참조 수 감소 및 실제 부모 참조 확인을 유지한다. 다른 일기/답변에서 사용하는 파일은 보존하고 마지막 참조 해제에만 물리 삭제 작업을 예약한다. 공유 파일 여부를 업로더 ID로 판단하지 않는다.
- 부모 삭제·첨부 관계/참조 수 변경·삭제 작업 예약·지도 제거는 같은 DB 트랜잭션이다. 물리 파일 삭제는 커밋 후 기존 작업자가 수행하며 저장소 장애 시 기존 재시도를 사용한다.

### 일기 지도 핀 정리

- 삭제자의 ID가 아니라 저장된 일기의 `createdBy`로 기존 map 반영 포트를 호출한다. 원 작성자의 위치와 다음 revision으로 핀을 제거하며 소유주에게 좌표를 응답하지 않는다.
- 삭제 시 위치 없음·정상 핀·원본/파생 불일치에 대한 기존 reconcile 계약을 유지한다. 지도 DB 실패나 STALE 충돌은 일기·첨부 변경도 롤백한다. 삭제를 위해 새 위치 쓰기 API나 주소/GPS 외부 호출을 만들지 않는다.
- 지도 담당에게 원 작성자 기준 삭제와 같은 트랜잭션 계약의 호환성을 계획 PR에서 확인받는다. 가족 지도 공동 열람은 승인 범위에 포함하지 않는다.
