# 다이어리 텍스트 CRUD

관련 이슈: [#32](https://github.com/likelion-backendschool-9th/pawmento/issues/32). 상위 설계는 [다이어리](README.md), 예외 규칙은 [공통 예외](../backend-exceptions.md)와 [#72](https://github.com/likelion-backendschool-9th/pawmento/issues/72)를 따른다.

첫 구현 단위는 서버에 텍스트 일기를 생성·상세 조회·수정·삭제하는 기능이다. #32 전체 완료를 뜻하지 않는다. 목록·달력, 첨부, 가족 공유, 위치와 프론트 API 연결은 후속 단위다.

## 요구사항과 범위

- #32-R1 중 자유 일기의 텍스트 CRUD와 질문 답변 저장소 분리를 구현한다.
- #32-R3 중 인증된 작성자 저장과 본인 변경 권한을 구현한다. 가족 기능 전에는 실제 반려동물 소유자만 접근할 수 있다. 다른 회원을 가족으로 간주하는 가짜 접근 검사는 만들지 않는다.
- #32-R2 목록·달력, #32-R4 파일 첨부, #32-R5·R6 지도/GPS, R3의 가족 공유·역할 검사는 이 단위에 포함하지 않는다.
- 같은 아이·같은 날짜에 여러 일기를 작성할 수 있다. 일상/정원 전환은 일기를 복제하거나 숨기는 조건이 아니다.

## 사용자와 API 계약

공통 `/api/v1`은 `WebConfig`가 붙인다. 아래 경로에는 중복 작성하지 않는다.

| 요청 | 입력 | 성공 응답 |
| --- | --- | --- |
| `POST /diaries?petId={petId}` | `content`, `recordedDate` | 201, 생성 상세 |
| `GET /diaries/{diaryId}?petId={petId}` | 없음 | 200, 상세 |
| `PATCH /diaries/{diaryId}?petId={petId}` | `content` 또는 `recordedDate` 중 하나 이상, 필수 `version` | 200, 변경 상세 |
| `DELETE /diaries/{diaryId}?petId={petId}&version={version}` | 필수 쿼리 `petId`, `version` | 204, 본문 없음 |

경로 표는 [목록·달력 단계의 전환 계약](list-calendar.md#crud-경로-전환을-먼저-수행)에 맞춘 목표다. PR #89의 실제 코드는 아직 중첩 경로이며, 후속 구현에서 CRUD·테스트를 함께 전환한다. 모든 API의 petId는 쿼리에서만 양의 Long 하나로 받고 기존 작성자·아이·버전 규칙은 유지한다. (고침 #32: PR #94 공통 경로 규칙 반영)

수정은 제공된 필드만 바꾼다. 필드 누락과 명시적 null을 구분하며 `content: null`, `recordedDate: null`은 400이다. `version`만 있는 PATCH와 음수·누락 버전도 400이다. 삭제 버전은 URL 쿼리로만 받고 HTTP 헤더로 대체하지 않는다.

첫 단계에서는 `attachmentIds` 생략 또는 빈 배열, `location` 생략 또는 `{mode: "NONE"}`만 허용한다. 비어 있지 않은 첨부나 AUTO/MANUAL 요청은 아직 지원하지 않는 상태를 409로 알리고 저장하지 않는다. 잘못된 타입·모드·명시적 null은 400이다. 이 요청들을 성공처럼 무시하지 않는다. 첨부·위치의 완전한 계약은 상위 설계를 유지하며 후속 구현에서 확장한다.

미지원 기능의 거부는 애플리케이션 정책으로 관리한다. 웹은 JSON 타입·모드 등의 형식만 검사한 뒤 첨부·위치 요청 여부를 `DiaryWriteFeatures`로 Command에 전달한다. 생성·수정 서비스는 이 값을 검사해 `application/exception/DiaryFeatureUnavailableException`으로 409를 반환하며, 웹을 거치지 않은 입력 포트 호출에도 같은 정책을 적용한다. `InvalidDiaryRequestException`은 HTTP 형식 오류로 웹 어댑터에 유지한다. 첨부·위치 값 자체를 저장하거나 원본 JSON을 핵심 계층에 전달하지 않는다. (고침 #32: PR #89 리뷰에 따라 임시 웹 가드를 애플리케이션 정책으로 이동)

상세는 `diaryId`, `petId`, `createdBy`, `content`, `recordedDate`, `createdAt`, `updatedAt`, `version`을 반환한다. `createdBy`는 인증 회원 ID다. 가족용 `author.displayName` 계약과 회원 탈퇴 후 표시 정책은 후속 가족/작성자 표시 단위에서 연결하며, 현재 ID를 닉네임처럼 표시하지 않는다. ID는 현재 공통 API와 동일하게 Long을 사용한다.

## 데이터와 도메인 규칙

`com.pawmento.diary`에 식별자·생명주기를 가진 순수 자바 `DiaryEntry` class를 둔다. 임시 record·memory 패키지나 엔티티를 복구하지 않는다. 물리 테이블은 `diary_entries`로 제안하며 프론트의 기존 `type=DIARY`를 서버 타입으로 복사하지 않는다.

| 필드 | 규칙 |
| --- | --- |
| `id` | DB에서 발급한 일기 ID. 지도 계약의 `diaryId`와 같은 식별자 |
| `pet_id` | 생성 시 결정, 이후 변경 불가 |
| `created_by` | 인증 회원에서 결정, 이후 변경 불가 |
| `content` | 앞뒤 공백 정리 후 1~3,000자. 첨부 없는 첫 단계이므로 공백만 있는 일기 불가 |
| `recorded_date` | 필수 DATE. Asia/Seoul 기준 오늘 이하, 과거 날짜 허용 |
| `created_at`, `updated_at` | 서버 Clock으로 결정한 UTC 시각. 생성 시 동일, 수정 시 최초 작성 시각 유지 |
| `version` | 생성 시 0, 실제 수정 시 증가. 수정·삭제의 기대 버전으로 검사 |

클라이언트가 보낸 작성자·생성 시각·아이 변경값을 서버 결정값으로 사용하지 않는다. `recordedDate`는 사건의 날짜이며 실제 작성 시각과 다르다. 질문 답변의 실제 등록일 규칙과 혼용하지 않는다.

## 권한과 의존 경계

- diary의 접근 확인 출력 포트를 두고, 첫 어댑터는 pet의 `GetPetUseCase`로 실제 소유자를 확인한다. 다른 도메인의 JPA 엔티티·리포지토리를 직접 읽지 않는다.
- 현재 pet의 비소유자 거부는 403이다. 이 단계에서도 이를 유지하고, 가족 접근 포트가 연결된 뒤에도 존재하는 아이의 비가족은 403, 없는 아이는 404로 유지한다. 이는 모든 회원에게 임시 읽기 권한을 허용하는 단계가 아니다. (고침 #133: 비가족 404 통일을 하지 않음. [가족 연동 계획](family-integration.md#권한-계약))
- 상세·수정·삭제 모두 접근 가능한 아이와 저장된 일기의 `petId`를 대조한다. 요청 아이와 다른 일기 ID는 404로 처리하고 원본을 유지한다.
- 수정·삭제는 저장된 `createdBy`와 인증 회원도 비교한다. 가족 어댑터가 추가되어도 다른 작성자 변경은 403이다.
- 존재하지 않는 일기는 diary 애플리케이션 예외로 404를 반환한다. 도메인 규칙 400, 권한 403, 버전 충돌 409는 공통 기본 예외를 상속하고 전역 핸들러에서 변환한다. diary 전용 Advice나 도메인 예외를 재포장하는 서비스 catch를 추가하지 않는다.

pet의 `HasPetRecordsPort`는 지금 항상 false인 어댑터를 사용한다. 실제 diary 존재 확인 입력 포트를 만들고 pet 어댑터가 이를 호출하게 연결한다. 같은 출력 포트의 빈을 중복 등록하지 않으며 다른 도메인 저장소를 직접 조회하지 않는다. 존재 확인은 일반적인 삭제 요청을 미리 거부하기 위한 것이며, 동시성 보장은 아래 DB 제약으로 처리한다. (고침 #32: PR #87 리뷰에 따라 첫 생성/아이 삭제 경합 보호를 첫 구현에 포함)

### 반려동물 삭제와 첫 일기 생성의 경합

첫 구현의 구체안은 `diary_entries.pet_id → pets.id`의 **NOT DEFERRABLE 외래 키와 ON DELETE RESTRICT**다. CASCADE·SET NULL은 사용하지 않는다. 일기를 조용히 삭제하거나 아이 없는 일기를 남기는 동작을 막기 위해서다. `pet_id`는 NOT NULL이며 조회·삭제 제약 검사를 위해 인덱스를 둔다. FK는 스키마에 명시적으로 생성하고 실제 PostgreSQL 테스트 DB와 배포 DB에 동일하게 적용한다. JPA 엔티티 간 연관관계를 만들지 않고 diary는 계속 Long ID만 보관한다.

```sql
ALTER TABLE diary_entries
  ADD CONSTRAINT fk_diary_entries_pet
  FOREIGN KEY (pet_id) REFERENCES pets(id)
  ON DELETE RESTRICT NOT DEFERRABLE;
CREATE INDEX ix_diary_entries_pet_id ON diary_entries(pet_id);
```

- **생성이 먼저 반영되는 경우**: 일기 INSERT가 FK 참조를 확보한 트랜잭션은 pet DELETE와 경합한다. 생성 커밋 후 삭제는 해당 FK 위반으로 거부하고, pet과 일기를 모두 보존한다. 삭제의 사전 존재 조회가 이미 false를 반환했더라도 같아야 한다.
- **삭제가 먼저 반영되는 경우**: pet DELETE가 먼저 실행되고 커밋되면 후속 일기 INSERT는 해당 FK 위반으로 거부한다. 삭제 전에 통과한 소유자 조회 결과만으로 생성 성공을 반환하지 않는다. pet과 일기 모두 남지 않아야 한다.
- **오류 응답 경계**: pet 영속성 어댑터는 delete 후 flush까지 수행해 이름이 `fk_diary_entries_pet`인 FK 위반만 기록 존재 충돌(409 `CONFLICT`)로 변환한다. diary 영속성 어댑터는 insert/flush에서 같은 FK 위반을 생성 대상 아이 없음(404 `NOT_FOUND`)으로 변환한다. 각각 해당 도메인의 애플리케이션 예외를 사용하고 #72의 공통 기본 예외를 따른다. 모든 `DataIntegrityViolationException`을 이 두 오류로 일괄 변환하지 않는다.
- **트랜잭션 경계**: flush 후에도 최종 성공은 트랜잭션 커밋이 완료된 결과다. 실패 트랜잭션은 롤백하고, 성공 응답 뒤 보상 삭제로 맞추는 방식은 쓰지 않는다. commit 전후 결과는 별도 연결에서 다시 조회해 검증한다.
- **pet 담당과 확인할 변경**: FK의 이름·소유/적용 방식·삭제 제한, pet 삭제 어댑터의 flush/명시적 FK 충돌 매핑, 기존 기록 존재 어댑터 교체를 이 계획의 연동 계약으로 검토한다. 담당자 합의가 끝났다고 간주하지 않으며 코드 착수 전에 이 계약을 확인한다. 경합 보호 구현·검증은 첫 CRUD의 완료 조건이며 후속 작업으로 미루지 않는다.

별도 공통 잠금 방식으로 바꾸려면 생성과 pet 삭제 양쪽이 같은 잠금/트랜잭션 규약을 따라야 한다. 한쪽만 잠그거나 존재 조회를 추가하는 것으로 대체하지 않는다. 변경 시 이 계획과 #32-S22의 양쪽 실행 순서 테스트를 함께 갱신한다.

## 수정·삭제의 동시성

수정·삭제 모두 기대 `version`을 비교한다. 오래된 상세에서 보낸 수정이나 삭제는 409로 거부한다. 버전 확인 후 별도 무조건 갱신·삭제를 하지 않고 DB의 조건부 쓰기 또는 낙관적 잠금으로 경합까지 보호한다. 실제 동시 요청에서 수정/삭제 중 먼저 성공한 결과가 보존되어야 한다.

영속성 어댑터는 기술적인 낙관적 충돌을 diary의 `StateConflictException` 하위 예외로 변환한다. 필요한 flush를 어댑터 안에서 수행해 일반적인 충돌이 변환 경계 밖의 커밋 시점에만 나타나지 않도록 한다. 전체 앱의 커밋 예외 처리 정책을 이 기능에서 일괄 변경하지 않는다. 실패한 수정은 원본 내용·날짜·시각·버전을 유지한다.

| 번호 | 방법 | 이번 단위의 확인 |

| #32-S4 | 테스트 | 같은 아이·날짜에 여러 텍스트 일기 허용. 가족 공유·역할 검사는 후속 |

| #32-S20 | 테스트 | PATCH 누락/명시적 null 구분, 변경 필드 없는 요청·음수/누락 버전 거부, 정상 부분 수정 |

| #32-S22 | 테스트 | 순차 삭제 차단·마지막 일기 삭제 후 pet 삭제 허용과 실제 PostgreSQL 첫 생성/아이 삭제 경합을 양쪽 실행 순서로 검증. 이름 있는 FK·삭제 제한·404/409 매핑·롤백·고아 일기 없음 확인 (고침 #32: PR #87 리뷰의 경합 보호를 첫 범위에 포함) |
| #32-S23 | 테스트 | 첫 단계의 첨부/위치 미연동 요청을 성공으로 무시하지 않음. 빈 첨부·NONE만 허용, 비어 있지 않은 첨부·AUTO/MANUAL은 409 |

#32-S22의 경합 검증은 별도 DB 연결·트랜잭션 두 개와 latch/barrier를 사용한다. 순차 호출·mock·sleep으로 경합을 대신하지 않는다. 첫 일기가 없는 같은 아이에서 두 요청이 접근/존재 확인을 통과한 뒤 DB 쓰기 순서를 제어한다.

1. 생성 INSERT/flush → 삭제 시도 → 생성 커밋: 생성 201, 삭제 409이며 pet·일기가 남고 소유자의 일기 상세 조회가 가능해야 한다.
2. 삭제 DELETE/flush → 생성 시도 → 삭제 커밋: 삭제 204, 생성 404이며 pet과 일기는 없어야 한다.
3. 두 경우 모두 각각의 트랜잭션 종료를 확인하고 새 트랜잭션에서 DB 상태를 검증한다. 두 요청 모두 성공하거나 고아 일기가 남으면 실패다. 제약 이름으로 인식한 FK 위반만 도메인 오류로 변환되는지도 확인한다.

도메인 규칙은 순수 자바 단위 테스트, 조건부 쓰기·트랜잭션·동시성은 PostgreSQL 통합 테스트, 인증·DTO·상태/응답 형식은 웹 테스트로 확인한다. 같은 입력 조합을 모든 계층에서 반복하지 않는다. 검증 결과는 PR 본문에 기록하며 이 문서에 실행 로그를 넣지 않는다.

## 작업 순서

1. 이 계획의 API·삭제 버전·첫 단계 권한/미연동 입력 범위를 확인한다.
2. 도메인과 공통 기본 예외 하위 타입, 도메인 테스트를 구현한다.
3. 동작별 입력 포트(Command/Query/Result)와 접근·저장·조회·삭제 출력 포트를 만든다.
4. 유스케이스 서비스에서 접근 검사·작성자·Clock·트랜잭션을 조율한다.
5. pet 담당과 FK·삭제 제한·오류 변환 계약을 확인하고, 명시적인 스키마 FK와 양쪽 영속성 어댑터의 flush/예외 변환을 구현한다. 버전 충돌·기록 존재 어댑터를 연결하고 #32-S22의 PostgreSQL 경합을 검증한다.
6. 컨트롤러·요청/응답 DTO를 연결하고 관련 단위·DB·웹 테스트를 실행한다.

## 범위 밖과 후속 연결

- 목록·날짜 필터·페이지·월별 달력은 다음 구현 단위다.
- 사진·음성의 참조 획득/해제·첨부 테이블·부모 파일 열람은 미디어 연결 단위에서 구현한다. 이번 텍스트 삭제를 전체 첨부 삭제 완료로 표시하지 않는다.
- 가족 초대·멤버십·공유 열람·표시 이름은 가족 포트가 구현된 뒤 연결한다.
- 지도 입력 포트·GPS 사전 동의·주소 조회·위치 반영은 [위치 설계](../map/photo-location.md)를 따른다. AUTO/MANUAL을 받으면서 조용히 NONE으로 저장하지 않는다.
- 프론트 데모·명칭 이관과 실제 HTTP 연결, 기존 localStorage 데이터 이관은 별도 단위다.
