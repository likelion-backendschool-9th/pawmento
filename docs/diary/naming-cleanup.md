# 다이어리와 질문 답변 이름 정리 (#32)

## 변경 범위

- diary 응답·명령·조회·첨부 관계 및 지도 핀의 일기 식별자는 `diaryId`로 통일한다. 질문 답변 식별자와 섞지 않는다. URL의 실제 `/api/v1/diaries/{숫자}` 형태는 유지하지만 JSON의 `recordId` 필드는 `diaryId`로 변경한다. 호출자는 함께 수정해야 한다.
- map 도메인·저장소·예외·포트의 `RecordLocation`은 `DiaryLocation`, 위치 테이블은 `diary_location`, 일기 FK는 `diary_id`다. `recordedDate`는 일기의 사건 날짜이므로 유지한다. Java의 `record` 문법이나 과거 샘플 삭제 기록은 이름 변경 대상이 아니다.
- 프론트의 혼합 `Memory` 저장 모델을 `DiaryEntry`, `QuestionAnswer`, `QuestionPrompt`로 나눈다. 각각 별도 유스케이스와 컬렉션을 사용하며, 브라우저 저장은 한 번의 localStorage 쓰기로 일관성을 유지하는 v2 스냅샷이다. 화면에서만 `JournalItem`으로 합성한다.
- 자유 일기 경로는 `/pets/{petId}/diary`, `/diary/new`, `/diary/{diaryId}`다. 질문 답변은 `/questions`, `/questions/answers/new`, `/questions/answers/{answerId}`다. 과거 `/timeline`·`/records` 링크와 이전 질문 상세 링크는 새 경로로 이동한다.
- 질문은 반려동물·모드별 배정 스냅샷으로 보관한다. 답변 전까지 날짜가 지나도 유지하고, 첫 답변 후 가족 공통으로 다음 질문으로 진행한다. 가족은 지난 질문에도 각자 답할 수 있으며 같은 작성자·배정 질문의 중복만 막는다. 등록일은 실제 답변 시각으로 기록하고 수정해도 유지한다.
- 엽서의 새 원본 참조는 종류와 ID를 함께 보관한다. 기존 엽서의 종류 없는 원본 ID는 보존하되 종류를 추측해 상세 링크를 만들지 않는다.

기존 관리자 질문 중 모드가 없는 항목은 LEGACY로 남기고, ACTIVE·GARDEN 기본 질문을 별도 ID로 제공한다. 관리자가 과거 항목의 모드를 지정할 수 있다.

## 기존 데이터 이관

`db/diary-naming-migration.sql`을 Hibernate 초기화 전에 실행한다. 기존 `record_location`과 `diary_attachments.record_id`를 이름만 변경하며 행·키·제약을 유지한다. 새 DB와 이관 완료 DB에서 재실행할 수 있다. 구·신 테이블 또는 컬럼이 함께 있으면 임의 삭제·병합 없이 시작을 중단한다. 운영 반영 전 DB 백업과 모든 인스턴스의 동시 버전 전환이 필요하며 구버전과 혼용하지 않는다.

브라우저는 `pawmento.workspace.v1.{accountId}`를 읽어 `v2`로 한 번 저장하며 v1을 복구용으로 남긴다. 기존 `DIARY`는 질문 답변, TEXT/PHOTO/VOICE/VIDEO는 일기로 옮긴다. ID·질문 원문·본문·첨부·알려진 작성자·시각을 보존한다. 기존 선택 날짜는 `legacyRecordedDate`로 보존하고 실제 등록 시각으로 새로 주장하지 않는다. 과거 모드와 알 수 없는 작성자는 추측하지 않는다. 작성자 미상 기록과 기존 영상 기록은 읽기를 보존한다. 새 첨부는 사진·음성으로 제한한다.

v2가 손상돼도 오래된 v1로 조용히 돌아가지 않는다. v2 이관 쓰기에 실패하면 검증된 v1을 메모리에서 변환해 조회를 계속 허용한다. v2가 생길 때까지 재조회 시 이관을 재시도한다. 사용자 변경의 save 실패는 성공으로 처리하지 않고 기존 데이터를 유지하며 오류로 알린다. 기존 회원의 ID·이름이 같으면 로그인 확인 과정에서 life 상태를 재저장하지 않으며 SUSPENDED 상태는 유지한다. 기존 데모 작업 공간으로 다시 진입할 때도 샘플을 자동 생성·저장하지 않고 바로 인증·기록 조회를 진행한다. 또한, 초기화 후에도 v2 빈 상태를 우선해 v1이 되살아나지 않게 한다.

## 범위의 한계

프론트의 질문·가족 기록은 기존 브라우저 데모다. 이번 정리가 서버 질문 API나 가족 멤버십 연동을 새로 완성하는 것은 아니다. 백엔드 diary와 map은 기존 헥사고날 계층을 유지하며 이름만 정리한다. 위치 수동 입력 등 후속 계획에서도 `diaryId` 명칭을 사용한다.

## 확인 시나리오

- #32-S28 [테스트] PostgreSQL 이름 이관 시 기존 행·ID·FK·유니크·시퀀스를 보존하고 재적용 가능하며 구/신 테이블 동시 존재 시 중단한다. 기존 #32-S1 CRUD 번호를 재사용하지 않는다.
- #32-S29 [테스트] 브라우저 v1→v2 이관에서 ID·작성자·질문 스냅샷·기존 영상과 엽서 원본 참조를 보존한다. 저장 한도 때문에 복사본을 만들지 못해도 v1 기록 조회는 허용하고 사용자 쓰기 실패는 알린다. 질문 풀 이관이 필요한 512바이트 여유 저장소에서도 기존 회원 확인·공유 작업 공간 조회가 성공하며 이름 변경 실패·SUSPENDED 유지도 확인한다. 이후 공간 확보 시 이관 재시도, 손상 v2 우회 금지, 초기화 후 v1 부활 금지를 검사한다. 기존 #32-S2 인증·범위 번호를 재사용하지 않는다.
