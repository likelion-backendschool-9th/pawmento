# 다이어리 제목

관련 이슈: [#32](https://github.com/likelion-backendschool-9th/pawmento/issues/32). 상위 설계는 [다이어리](README.md), 작성자·가족 권한은 [가족 연동](family-integration.md)을 따른다.

## 목표와 요구사항

- #32-R7 일기에 본문과 별개인 제목을 입력·저장·조회·수정한다. 신규 작성과 수정 저장에는 제목을 반드시 입력한다. 기존 무제목 일기는 조회를 허용하되 수정 시 유효한 제목을 함께 제출한다. (고침 #32: 사용자 요청으로 제목 필수화)
- 제목은 사진·음성 첨부, 작성자 이름, 질문 본문과 다른 필드다. 질문 답변에 제목을 추가하거나 일기 본문의 첫 줄을 제목으로 자동 복사하지 않는다.
- 승인된 제목 계획을 구현하며 질문 회차 조회 기능과 별도로 진행한다. 제목 필수 정책은 후속 사용자 결정에 따른다.

## 제목 규칙

- title은 앞뒤 공백을 정리한 한 줄 텍스트로 최대 100자다. 문자 수는 유니코드 코드 포인트 기준으로 계산하고 UI 글자 수도 동일하게 센다. 저장 길이는 varchar(100)으로 맞춘다.
- 신규 제목의 생략/null/빈 문자열/공백은 400이다. 기존 무제목 행만 null로 조회한다. 문자열 외 JSON 타입은 400으로 거절한다.
- 문자열 제목은 다음 순서로 처리한다. 구현과 테스트는 이 순서를 바꾸지 않는다.
  1. 정리하기 전의 원본에 개행·탭 등 제어문자(유니코드 `Cc`), 줄 구분자 `U+2028`(`Zl`), 문단 구분자 `U+2029`(`Zp`), 짝이 없는 UTF-16 surrogate가 하나라도 있으면 400으로 거절한다. 정상적인 이모지 surrogate 쌍은 허용한다. 앞뒤뿐 아니라 가운데에 있어도 거절하며 `String.strip()`보다 먼저 검사한다. (고침 #32: Cc에 속하지 않는 유니코드 줄/문단 구분자도 한 줄 제목에서 제외)
  2. 앞뒤 공백을 정리한다(`String.strip()` 기준).
  3. 정리한 값이 비어 있으면 쓰기를 400으로 거절한다.
  4. 정리한 값이 100자를 넘으면 400으로 거절한다.
- 그래서 `""`·`"   "`도 400이고, `"\t"`·`"제목\n"`·`"제\n목"`·`"앞\u2028뒤"`·`"앞\u2029뒤"`는 400이다.
- 제목은 일기의 최소 내용 조건을 대체하지 않는다. 제목만 있고 본문·유효 첨부가 모두 없는 일기는 기존 규칙대로 400이다. 사진/음성이 있어도 제목은 필수다.
- 제목을 입력하지 않았을 때 본문 첫 줄이나 날짜로 새 제목을 저장하지 않는다. 화면의 `제목 없는 일기`는 표시용 대체 문구이며 DB 값이 아니다.

## API 계약

| 경로 | title 입력 | 동작 |
| --- | --- | --- |
| `POST /api/v1/diaries?petId=` | 생략/null/빈 문자열/공백 | 400, 생성하지 않음 |
| 같은 POST | 유효 문자열 | 정규화한 제목으로 생성 |
| `PATCH /api/v1/diaries/{diaryId}?petId=` | 생략 | 기존 유효 제목 유지; 기존 null이면 400 |
| 같은 PATCH | null/빈 문자열/공백 | 400, 제목 제거 불가 |
| 같은 PATCH | 유효 문자열 | 제목 변경 |

생성·수정·상세·목록의 일기 항목에 `title: string | null`을 추가한다. ID·작성자·날짜·본문·첨부·위치 필드와 API 경로를 바꾸지 않는다. 달력은 기존 날짜별 건수와 해당 날짜의 일기 목록 계약을 유지하며 제목 수정만으로 날짜별 건수가 바뀌지 않는다.

- PATCH의 version은 계속 필수다. title만 변경하는 PATCH도 허용한다. 같은 유효 값을 명시해 보내는 요청도 기존 명시적 본문 수정처럼 updatedAt과 version을 갱신한다. version만 보내고 변경 필드가 없는 요청은 계속 400이다.
- title의 생략과 명시적 null을 구분해 Command로 전달한다. 단순 nullable String 하나로 PATCH의 유지/변경 의미를 합치지 않는다. 원본 JsonNode를 핵심 계층에 넘기지 않는다.
- 제목·본문·첨부·위치가 함께 변경되면 일기 버전은 한 번만 갱신하고 기존 트랜잭션 안에서 함께 저장한다. 실패하면 제목을 포함한 전체 변경을 롤백한다.
- 제목만 바꾸는 PATCH도 별도 경로를 만들지 않고 기존 수정 경로를 그대로 탄다. 위치를 생략한 수정과 같이 `DiaryLocationManager`가 저장 전에 핀의 `source_revision`과 일기 version이 맞는지 확인하고, 저장 뒤 핀을 새 version으로 동기화한다. 핀의 좌표·장소 이름·출처(`source`·`source_asset_id`)는 바꾸지 않고 `source_revision`만 새 version으로 맞춘다. 일기 version만 올리고 핀을 그대로 두면, 위치가 있는 일기의 다음 일반 수정이 정합성 오류로 실패한다.
- 현재 가족 접근 검사·작성자 본인 수정·기대 버전 409·타인 location 숨김을 유지한다. 제목 변경이 소유주의 타인 일기 수정 권한을 새로 부여하지 않는다.

## 도메인·저장·호환성

- DiaryEntry의 제목 값과 불변 제목 규칙을 domain에 둔다. application 입력 계약에는 PATCH의 제목 변경 의도를 표현하고, 웹은 JSON 형식과 생략/null 구분을 담당한다.
- DiaryEntryJpaEntity·기존 DiaryEntryPersistenceAdapter와 버전 조건부 갱신 쿼리를 확장한다. 새 저장소나 JDBC CRUD를 만들지 않는다. 기존 초안 검증도 제목을 확인해 잘못된 제목으로 외부 주소 조회·첨부 변경을 진행하지 않게 한다.
- 기존 diary_entries에 nullable title 열을 추가한다. 기존 행은 null을 유지하고 본문·작성자·날짜·시각·version·첨부·지도 핀을 보강하거나 바꾸지 않는다. 반복 초기화에서도 직접 작성한 제목을 덮어쓰지 않는다.
- 신규 생성의 title 생략은 더 이상 호환되지 않는다(400). Java 생성 호출부도 제목을 명시한다. 수정 생략은 KEEP이지만 기존 제목이 null이면 제목을 입력해야 저장할 수 있다. 쓰지 않는 임시 호환 코드나 제목 기본값 자동 생성을 남기지 않는다.
- 저장된 제목이 규칙을 위반하면 DB 복원 경계에서 저장 데이터 오류(500)로 구분한다. 사용자의 제목 형식·길이 오류(400)와 섞지 않는다. 복원 시 원본과 정규화 결과가 다르면(앞뒤 공백·공백만·빈 문자열) 500으로 거절하고 DB를 고치지 않는다. 기존 null만 예외로 허용한다. (고침 #32: #218 저장값 정규화·surrogate 리뷰 반영)

## 화면 계약

프론트 디자인 정리·API 연결 시 작성/수정 화면의 본문 위에 `제목 (필수)` 입력칸을 둔다. 입력 예시는 `오늘의 산책을 기억하며`처럼 짧은 문구를 쓰고 최대 길이를 안내한다. 기존 데이터 수정 화면에서 제목이 null이면 빈 입력칸으로 보여 주고 저장 전에 제목 입력을 요구한다.

목록과 상세는 제목이 있으면 제목을 표시하고, 없으면 `제목 없는 일기`를 표시한다. 작성자·사건 날짜·본문 미리보기는 별도로 유지한다. 입력·API 전달만 프론트가 담당하고 제목 정규화·검증·영속 저장은 백엔드가 담당한다. 화면 입력칸만 추가하고 저장되는 기능으로 표시하지 않는다.

## 시나리오

기존 번호는 유지한다. S33~S35·S37~S38은 제목 필수화 및 #218 경계 검증에 맞춰 고쳤다. (고침 #32: 사용자 정책 결정과 리뷰 반영) 다음은 제목의 시나리오다. 구현 전 완료로 체크하지 않는다.

| 번호 | 확인 방법과 기대 결과 |
| --- | --- |
| #32-S33 | [테스트] 제목이 있는 생성 응답·재조회·목록에 같은 정규화 제목을 반환한다. 생략/null/빈 제목/공백은 400이며 제목만으로 빈 일기를 만들 수 없다. |
| #32-S34 | [테스트] 제목만 수정, 생략 유지, null/공백 제거 거절, 같은 값 재전송과 복합 변경의 version/updatedAt을 확인한다. 최초 작성자·작성 시각·사건 날짜·작성자 이름 스냅샷은 보존한다. 위치가 있는 일기에서 제목만 바꾸면 핀의 좌표·장소 이름·출처는 그대로이고 `source_revision`이 새 version과 같으며, 이어서 위치를 생략한 본문 수정도 성공한다. |
| #32-S35 | [테스트] 100자·101자·한글·이모지와 문자열 외 타입을 검사한다. 처리 순서가 어긋나면 잡히도록 `"   "`(400)과 `"\t"`·`"제목\n"`·`"제\n목"`·`"앞\u2028뒤"`·`"앞\u2029뒤"`(400)을 나눠 확인한다. 유니코드 줄/문단 구분자와 짝이 없는 surrogate를 원본 검사에서 거절하고 정상 이모지는 재조회까지 보존한다. 앞뒤 공백·공백만 남은 저장값은 조회와 KEEP 수정 모두 500이며 DB 원문은 유지한다. (고침 #32: Cc 밖 줄 구분자 경계 예시 추가) HTTP 형식 오류와 직접 입력 유스케이스의 제목 규칙을 구분하며 제목 오류가 DB/첨부/지도 쓰기를 남기지 않는다. |
| #32-S36 | [테스트] 가족 공동 열람과 본인 제목 변경을 허용하고 타인 변경·회수 후 변경은 403, 오래된 version은 409다. 첨부/핀 반영 실패 시 제목도 롤백하며 제목 수정으로 달력 건수가 바뀌지 않는다. |
| #32-S37 | [테스트] 기존 스키마 업그레이드·재실행 후 제목 없는 일기를 읽을 수 있다. 제목 없이 수정하면 400이며 유효 제목을 넣어 수정하면 성공한다. 기존 제목·본문·ID·작성자·날짜·시각·버전·첨부·핀을 보존하고 기존 유효 제목의 PATCH 생략 유지도 확인한다. (고침 #32: 제목 필수화와 기존 null 조회 호환) |
| #32-S38 | [직접] 프론트 연결 후 제목 입력·수정·빈 제목 저장 차단·저장 실패 시 입력 유지, 제목 없는 기존 일기 표시와 목록/상세 전환을 확인한다. 백엔드 검사만으로 완료 표시하지 않는다. |

## 작업 순서와 범위 밖

1. 필수 입력·100자·PATCH 유지/변경 및 기존 null 조회 호환 계약을 따른다.
2. 도메인·JPA/스키마·입력/응답 계약을 확장하고 S33~S37을 검사한다. 기존 가족·첨부·지도·작성자·달력 회귀를 함께 확인한다.
3. 프론트 디자인 정리 단계에서 입력칸과 제목 표시를 적용하고 실제 API 연결 후 S38을 확인한다.

제목 검색·필터·정렬, 질문 답변 제목, 본문에서 제목 자동 생성, 프론트 디자인 전면 개편, 가족 API, 타인 글 삭제 권한 변경은 이 단위에서 하지 않는다.
