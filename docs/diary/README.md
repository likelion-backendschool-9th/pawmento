## 사용자 경험과 범위

- 선택한 아이의 자유 기록을 작성하고 상세 조회·수정·삭제한다. 같은 날짜에 여러 개를 남길 수 있다.
- ‘다이어리’는 ‘일기 / 달력’ 두 탭이다. 일기는 목록과 상세, 달력은 날짜별 건수와 해당 날짜 목록을 제공한다.
- 오늘의 질문과 답변은 별도 이력이다. 자유 다이어리 조회·달력·첨부 집계에 섞지 않는다.
- ACTIVE/GARDEN에서 같은 기록을 조회한다. 모드를 바꿔도 기록을 복제하거나 삭제하지 않는다.
- 사진·음성 녹음을 첨부한다. 업로드·검증·비공개 열람·미사용 정리·삭제 재시도까지 이번 범위에 포함한다.
- 내용은 3,000자 이하이며 텍스트 또는 READY 첨부가 하나 이상 있어야 한다.
- 가족 구성원이 각자 작성하고 작성자 이름을 표시할 수 있도록 멤버십·작성자 계약을 둔다. 가족 역할·초대 API는 가족 담당과 연결한다. 질문의 가족 다중 답변은 별도 question 도메인에서 처리한다.

## 도메인 경계

자유 일기의 생성·조회·수정·삭제, 목록·달력은 `diary` 도메인이 소유한다. PR #64에서 임시 `com.pawmento.record`·`com.pawmento.memory` 샘플과 `/records`·`/memories` API를 제거했다. 삭제된 샘플 패키지·엔티티·입력 포트를 재사용하거나 별도 record 저장소를 앞에 두지 않는다. (고침 #80: 폐기된 샘플 대신 실제 diary 도메인을 연동 기준으로 통일)

| 영역 | 책임 |
| --- | --- |
| `diary` | 자유 일기의 서버 발급 기록 ID, 아이·작성자, 내용·날짜·시각, 접근 검사, 첨부 참조, CRUD·목록·월별 달력 |
| `question` | 모드별 질문 풀·가족 공통 진행·개별 답변. diary 행을 생성하지 않으며 독립 ID를 사용 |
| `media` | 파일 업로드·검증·저장·비공개 열람과 파일 메타데이터 |
| `map` | diary의 기록 ID에 위치를 연결하고 핀 조회 제공. 기록 본문·첨부를 복제하지 않음 |

`diaryId`는 **실제 diary 일기의 서버 발급 ID**다. diary 응답·Command/Query·첨부 관계·지도 핀과 내부 위치 포트에서 같은 이름을 사용한다. 위치 모델은 `DiaryLocation`, 저장소는 `diary_location.diary_id`다. 질문 답변은 독립된 `answerId`를 사용한다. 프론트 저장 모델도 자유 일기 `DiaryEntry`, 질문 답변 `QuestionAnswer`로 분리한다. 기존 DB 이름은 [이름 정리](naming-cleanup.md)의 이관 규칙을 따른다. (고침 #32: ID·저장 모델 이름 통일)

도메인 간 연결은 애플리케이션 포트로 한다. diary가 현재 회원의 아이 접근·작성/수정/삭제 권한과 부모 버전을 검사한 뒤 map 입력 포트로 `diaryId`, `petId`, 원 작성자 `createdBy`, `revision`, nullable 위치를 전달한다. map은 같은 DB 트랜잭션에 참여하며 diary를 역호출해 작성자를 확인하지 않는다. 다른 도메인의 JPA 엔티티·리포지토리를 직접 참조하지 않는다. 상세한 위치 반영 계약은 [위치 연동](../map/photo-location.md)을 따른다.

## 데이터 구조 제안

실제 diary 저장소에 아래 필드를 설계한다. 삭제된 샘플 `records` 테이블을 확장한다는 전제는 두지 않으며 물리 테이블·제약 이름은 공통 네이밍 기준에 맞춘다. (고침 #80: 샘플 확장 전제 제거)

| 컬럼 | 의미 |
| --- | --- |
| `id` | 자유 다이어리의 서버 발급 기록 ID. 질문 답변 ID와 별개 |
| `pet_id` | 대상 아이. 생성 이후 변경 불가 |
| `created_by` | 인증된 작성자 ID. 요청 본문에서 받지 않음 |
| `content` | 자유 일기 내용, 최대 3,000자 |
| `recorded_date` | 사용자가 선택한 기록 날짜(DATE). 자유 기록은 수정 가능 |
| `created_at`, `updated_at` | 서버 생성 UTC 시각 |
| `version` | 동시 수정 충돌 확인용 버전 |

- 질문 ID·질문 본문·답변은 question의 독립 테이블에만 저장한다. 다이어리 생성·삭제와 question 생명주기를 연결하지 않는다.
- 자유 기록은 내용이 비어 있으면 유효한 첨부가 필수다. 공백은 저장 전 정리한다.
- 질문의 답변 등록일은 실제 저장 날짜로 고정한다. 자유 일기의 `recorded_date`는 회상한 사건의 날짜로 별도 유지하고 `created_at`은 실제 작성 시각으로 표시하는 안을 제안한다. 질문 날짜와 혼용하지 않는다.
- 미래 기록 날짜는 첫 범위에서 거부하는 안을 제안한다. 과거 날짜는 허용한다. ‘오늘’은 서버 Asia/Seoul 기준이다.
- 목록 인덱스 후보는 `(pet_id, recorded_date DESC, id DESC)`다. 가족 멤버십을 먼저 검사한 뒤 아이 단위로 조회하고 달력도 이 조건으로 집계한다. 작성자 필터가 있으면 추가 인덱스를 검토한다. 실제 데이터로 실행 계획을 확인한다.
- 폐기된 record·memory 샘플 데이터는 diary의 이관 원본으로 간주하지 않는다. 실제 데이터 이관이 필요하면 별도 이관안에서 출처·아이·작성자를 검증하며, 작성자를 추측해 채우지 않는다. (고침 #80: 샘플 데이터 백필 전제 제거)

### 첨부 계약

- 공통 파일 동작·메타데이터·형식·개수·용량·상태·TTL은 [media 설계](../media/README.md)를 단일 기준으로 삼는다. 파일 업로드를 별도 담당이 만들기를 기다리는 범위 밖 작업으로 두지 않는다.
- `diary_attachments`: `id`, `diary_id`, `asset_id`, `sort_order`. 부모+파일과 부모+순서 중복을 DB에서 막는다. 실제 파일 정보는 media가 소유한다.
- 사진 선택 및 음성 녹음 → 업로드 세션 → 바이너리 업로드 → 서버 검증 READY → 일기 JSON의 `attachmentIds` 연결 순서다. blob/data URL을 DB에 저장하지 않는다.
- 새 첨부는 본인 업로드·해당 아이·`DIARY_ATTACHMENT` 용도·READY를 검사한다. 수정 시 기존 첨부 유지와 새 첨부 추가를 구분한다. `attachmentIds`는 전체 교체 목록이고 중복 ID는 거부한다.
- 일기·첨부 행·media 참조 수 변경은 같은 DB 트랜잭션이다. 연결 실패 시 전체를 롤백하고 입력·기존 첨부를 보존한다. 본문이 비어 있으면 READY 첨부가 반드시 하나 이상 남아야 한다.
- 상세의 `attachments`는 `assetId`, `type`, `filename`, `mimeType`, `sizeBytes`, `durationMs`, `width`, `height`, `sortOrder`를 반환한다. 부모 첨부 content API에서 현재 열람 권한을 확인한 뒤 파일을 스트리밍한다. 파일당 15MiB 추천안·Docker volume 저장은 media 문서를 따른다.
- 썸네일은 첫 이미지로 제안한다. 파일 종류가 섞여도 일기 개체를 PHOTO/VOICE로 나누지 않는다. 이미지 축소본은 media가 제공하고 음성 자동 재생은 하지 않는다.
- 첨부 제거·일기 삭제 시 연결 해제·참조 수 변경·삭제 작업 등록까지 트랜잭션에 포함한다. 실제 저장소 삭제는 비동기 재시도하고, 다른 글에서 쓰는 자산은 지우지 않는다.

## API 제안

경로는 공통 `/api/v1` 접두사를 제외했다. 최신 `WebConfig`가 접두사를 적용하므로 컨트롤러에 중복 작성하지 않는다.

| 요청 | 입력 | 응답 |
| --- | --- | --- |
| `POST /diaries?petId={petId}` | `content`, `recordedDate`, `attachmentIds`, 선택 `location` | 201, 자유 기록 상세 |
| `GET /diaries?petId={petId}` | `date` 또는 `from/to`, `page`, `size` | 200, 자유 기록 목록 |
| `GET /diaries/calendar?petId={petId}` | `month=YYYY-MM` | 200, 해당 월 날짜별 건수 |
| `GET /diaries/{diaryId}?petId={petId}` | 없음 | 200, 자유 기록 상세 |
| `PATCH /diaries/{diaryId}?petId={petId}` | `content`, `recordedDate`, `attachmentIds`, `location`, `version` | 200, 변경 상세 |
| `DELETE /diaries/{diaryId}?petId={petId}&version={version}` | 필수 쿼리 `version` | 204 |

위 표는 [공통 API 경로 규칙](../backend-architecture.md#api-경로)에 맞춘 목표 계약이다. petId는 모든 API의 필수 양의 Long 쿼리이며 헤더·본문으로 대신하지 않는다. PR #89의 중첩 CRUD 경로는 아직 코드에 남아 있으므로 [다음 구현의 선행 작업](list-calendar.md#crud-경로-전환을-먼저-수행)에서 웹/경합 테스트와 함께 전환하고, 이전 경로를 호환 별칭으로 남기지 않는다. (고침 #32: PR #94 경로 리뷰 반영)

생성·수정의 `location`은 [지도와의 단일 위치 저장](#지도와의-단일-위치-저장)의 AUTO/MANUAL/NONE 계약을 따른다. 생략 시 생성은 NONE, 수정은 기존 모드 유지이며 별도 위치 쓰기 API를 두지 않는다. (고침 #80: 기존 #53 위치 계약을 API 입력 표에도 반영)

PATCH는 제공한 필드만 바꾼다. 변경 필드 하나 이상과 `version`이 필수이며, 필수 필드의 명시적 null은 400이다. `attachmentIds: []`는 첨부 전체 제거다. 변경 후 텍스트·첨부가 모두 비면 거부한다. 질문 답변 API는 [질문 문서](../question/README.md)에서 별도로 정의한다.

상세 응답 예시(제안):

```json
{
  "diaryId": 123,
  "petId": 10,
  "author": {"memberId": 1, "displayName": "보리 가족"},
  "content": "오늘도 공원에서 즐겁게 뛰었어요.",
  "recordedDate": "2026-11-17",
  "attachments": [],
  "createdAt": "2026-11-17T02:30:00Z",
  "updatedAt": "2026-11-17T02:30:00Z",
  "version": 0
}
```

목록은 `recordedDate DESC, diaryId DESC` 정렬, `page`는 0부터, `size` 기본 20·최대 100이다. 응답은 `items`, `page`, `size`, `totalElements`, `totalPages`다. `date`와 `from/to` 동시 지정은 거부하고 기간 양 끝은 포함한다. 날짜 형식·역전·페이지 범위를 검증한다. 첫 범위는 날짜 필터이며 텍스트 검색·미디어 전용 탐색은 후속 이슈로 둔다.

달력 응답은 `{petId, month, days: [{date, count}]}`로 제안한다. 기록이 있는 날짜만 반환하고 프론트가 빈 날짜를 채운다. 질문 답변 저장소를 조회하거나 합산하지 않는다. 월 범위는 DATE의 월 첫날 이상·다음 달 첫날 미만이다. 날짜 클릭은 동일 목록 API의 `date`로 연결한다.

ID는 서버에서 Long으로 발급하되 JavaScript의 정수 범위를 넘을 가능성을 고려해 JSON ID를 문자열로 통일할지 공통 응답 담당과 합의한다. 프론트 연결 어댑터가 타입을 한 번만 변환한다.

## 인증·권한·오류

- 컨트롤러의 `@LoginMember`로 회원 ID를 받는다. 클라이언트의 `ownerId`, `createdBy`는 신뢰하지 않는다.
- pet/가족 입력 포트로 해당 회원의 멤버십·읽기/쓰기 권한을 확인한다. OWNER·FAMILY 모두 조회·작성할 수 있다. 수정은 작성자 본인만 허용하고 삭제도 우선 동일하게 유지한다. 소유주의 타인 글 삭제는 가족 계획 Q2 적용 합의 후 첨부·지도 정리와 함께 반영한다. (고침 #133: 가족 역할과 삭제 적용 조건 반영) 접근 시 기존 기록의 `petId`, `createdBy`까지 검사한다. 경로의 petId만 확인하고 임의 diaryId를 수정하는 경로가 없어야 한다.
- 가족은 아이의 일기를 함께 읽고 답변과 동일하게 작성자 회원 ID·표시 이름을 본다. 이름 스냅샷과 탈퇴 후 표시 정책은 question과 맞춘다. 멤버십 회수 후에는 조회·변경을 거부한다.
- 미인증 401, 입력 오류 400, 없는 아이/기록·다른 아이의 기록 404, 비가족·권한 회수·다른 작성자 수정 403, 버전 충돌 409. 관리자라는 이유로 개인 기록 열람 권한을 자동 부여하지 않는다.
- 에러는 기존 `{code, message}`를 따른다. 저장 실패 시 DB 상태를 되돌리고 프론트는 입력을 유지한다.
- 새 diary 구현은 [공통 예외 규칙](../backend-exceptions.md)과 [#72](https://github.com/likelion-backendschool-9th/pawmento/issues/72)를 따른다. 도메인·애플리케이션 예외는 해당 계층의 `exception` 패키지에서 공통 기본 예외를 상속하고 `GlobalExceptionHandler`가 응답으로 변환한다. 서비스에서 도메인 예외를 다른 예외로 포장하거나 diary 전용 Advice를 만들지 않는다. #72의 기존 record→memory 전환 항목은 PR #64에서 삭제된 샘플에 관한 것으로, 새 diary 구현이나 예외 전환의 선행 작업이 아니다. (고침 #80: 폐기 샘플과 신규 도메인의 예외 전환 범위 구분)
- 수정은 요청 버전으로 조건부 갱신한다. 삭제도 경합 시 재확인이 필요하도록 버전 전달 방식을 구현 이슈에서 정한다.

## 지도와의 단일 위치 저장

세부 계약은 [위치 연동 #44](../map/photo-location.md)를 따른다. diary는 지도에 작성자 확인용 입력 포트를 추가로 제공하지 않는다. 현재 회원의 아이 접근·본인 수정 권한을 검사한 뒤 원 작성자·아이·기록 ID를 map 입력 포트에 전달한다. 지도 조회의 인증·작성자 필터는 유지한다. (고침 #53: 작성 권한 책임을 diary로 통일)

- 일기 생성·수정 body의 `location: {mode: AUTO|MANUAL|NONE}`만 위치 쓰기 경로다. MANUAL은 좌표·선택 장소명을 받고, AUTO는 사전 동의된 READY 첨부에서만 첫 유효 GPS를 선택한다. 별도 지도 위치 PUT/DELETE는 만들지 않는다.
- **생성에서 location 생략은 NONE**, 수정에서 생략은 기존 모드 유지다. 기존 AUTO에서 사진/순서가 바뀌면 동의된 후보로 재계산하고 MANUAL/NONE은 유지한다. 미동의 사진만으로 AUTO를 요청하면 거부한다.
- 업로드 동의는 media 세션 생성/파일 전송 전에 받는다. 미동의 사진은 프론트에서 GPS 제거본만 전송한다. 동의 문구·범위·철회/재동의 정책은 확정이 필요하며, 미확정을 자동 동의로 취급하지 않는다.
- `ApplyDiaryLocationUseCase`에 `diaryId`, `petId`, `createdBy`, `revision`, nullable 위치(source/sourceAssetId 포함)를 전달한다. APPLIED/DUPLICATE/STALE을 받고 정상 반영/중복은 성공, STALE은 409로 부모 저장도 롤백한다. (고침 #53: 무시 사유를 명확히 구분)
- diary는 **저장 트랜잭션을 열기 전에** map 주소 조회 포트로 `placeName`을 구한다. 비트랜잭션 조정 메서드와 DB 저장 서비스를 분리하고 저장 시 권한·첨부·기대 버전을 재검사한다. map apply는 외부 호출을 하지 않는다. (고침 #53: 주소 조회 실행 경계 확정)
- diary·첨부·media 참조·위치 모드/revision·map 행을 **동일 DataSource/트랜잭션 매니저의 REQUIRED 트랜잭션**으로 저장한다. 지도 DB 실패는 전체 롤백, 외부 주소 조회 실패는 주소 없는 좌표 저장으로 구분한다.
- 지도용 outbox·PENDING/SYNCED/FAILED·location-sync API는 제거한다. 일기 성공 응답은 지도 DB 반영까지 완료된 결과다. (고침 #53: 같은 앱/DB에서 불필요한 비동기 동기화 제거)
- AUTO 후보 없음/NONE/일기 삭제는 같은 트랜잭션에서 map 행을 실제 삭제한다. 행이 없으면 아무 작업도 하지 않는다. 오래된 수정과 삭제 경합은 모든 diary 쓰기의 부모 잠금/기대 버전 검사로 거부하며 map 변경도 롤백한다. 삭제 표시와 tombstone은 두지 않는다. (고침 #53: 동기 저장에서 불필요한 삭제 표시 제거)
- 물리 파일 삭제만은 [media](../media/README.md)의 작업 등록·재시도를 유지한다. DB 삭제·파일 참조 해제·작업 등록은 원자적으로 저장하지만 파일 I/O는 그 트랜잭션 밖이다.
- 질문·답변은 지도 연동 대상이 아니다. 가족 일기 열람 권한은 작성자 본인만 보는 지도 위치 권한을 자동 확대하지 않는다.

## 구현 순서 제안

1. diary 도메인의 pet/가족 접근 계약·지도 입력/조회 경계·공통 API 접두사를 확인하고 구현 이슈를 작성한다. 삭제된 record 입력 포트에 의존하지 않는다. (고침 #80: 실제 도메인 기준)
2. diary 자체의 기록 필드·접근 검사·저장소와 텍스트 생성/상세/수정/삭제를 구현한다. 폐기된 샘플 API의 제거·전환을 선행 작업으로 다시 계획하지 않는다. (고침 #80: 제거 완료 상태 반영)
3. 자유 기록 목록·날짜 필터·달력 집계, [위치 연동 #44](../map/photo-location.md)의 단일 body·권한 검사·map 입력 포트·같은 DB 트랜잭션 연결.
4. 가족 멤버십·작성자 표시와 권한 검증, question과 저장소·조회 분리 확인.
5. [media 구현 순서](../media/README.md)에 따라 업로드·검증·열람·삭제를 구현하고 첨부 참조 트랜잭션·소유권 검사와 연결한다. 텍스트 CRUD만으로 전체 기능 완료로 표시하지 않는다.
6. 프론트 공통 업로더·음성 녹음·재생과 HTTP 어댑터를 연결한다. 기존 데모 데이터는 서버에 자동 업로드하지 않는다.

## 범위 밖과 아직 정하지 않은 것

- 한 일기를 가족이 공동 편집하는 기능, 지도 SDK 자체 구현(사진 핀 연동은 #44와 연결), 커뮤니티 공개, AI 엽서, 정원 쪽지·편지, 음성 전사, 전문 검색, 휴지통 복원은 이 범위 밖이다.
- 파일 업로드는 이번 구현 범위다. 형식·용량·TTL·저장소·검증 도구의 세부 제안은 media 문서에서 확정한다. 미래 날짜·작성 가능한 과거 범위와 일기 삭제 경합 정책은 별도 확인한다.
- 반려동물 삭제와 첫 일기 생성의 경합 보호는 [텍스트 CRUD 첫 계획](basic-crud.md#반려동물-삭제와-첫-일기-생성의-경합)에 포함한다. 이름 있는 비지연 FK·ON DELETE RESTRICT와 pet/diary의 flush·오류 매핑을 pet 담당과 확인하고 #32-S22의 PostgreSQL 양방향 경합 테스트를 완료해야 한다. 이를 단순 존재 조회나 후속 작업으로 대체하지 않는다. 회원 삭제 시 기록 보존 정책과 위치 연관 삭제는 각 담당과 별도로 합의한다. (고침 #32: PR #87 리뷰의 첫 생성/아이 삭제 경합 보호 반영)
- 프론트 자유 기록의 TEXT/PHOTO/VOICE는 `DiaryEntry`와 첨부 메타데이터로 정리하고 새 VIDEO 생성·첨부 UI는 제거한다. 기존 데모 VIDEO는 자동 삭제하거나 사진/음성으로 오인 변환하지 않고 이전 데모 자료로 분리해 보존한다. 서버로 자동 이관하지 않는다. 잘못 이름 붙은 `type=DIARY`는 `QuestionAnswer` 저장소로 이관하며 자유 일기로 취급하지 않는다. 프론트의 저장소·URL·상세·검증도 함께 분리한다.
- `/records`·`/memories` 샘플 API는 PR #64에서 제거했으며 호환 API로 복구하지 않는다. 새 일기 API는 위 diary 계약으로 구현한다. (고침 #80: 샘플 제거 시점 미결 항목 해소)
