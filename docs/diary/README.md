## 사용자 경험과 범위

- 선택한 아이의 자유 기록을 작성하고 상세 조회·수정·삭제한다. 같은 날짜에 여러 개를 남길 수 있다.
- ‘다이어리’는 ‘일기 / 달력’ 두 탭이다. 일기는 목록과 상세, 달력은 날짜별 건수와 해당 날짜 목록을 제공한다.
- 오늘의 질문과 답변은 별도 이력이다. 자유 다이어리 조회·달력·첨부 집계에 섞지 않는다.
- ACTIVE/GARDEN에서 같은 기록을 조회한다. 모드를 바꿔도 기록을 복제하거나 삭제하지 않는다.
- 이미지·영상·음성 녹음을 첨부한다. 업로드·검증·비공개 열람·미사용 정리·삭제 재시도까지 이번 범위에 포함한다.
- 내용은 3,000자 이하이며 텍스트 또는 READY 첨부가 하나 이상 있어야 한다.
- 가족 구성원이 각자 작성하고 작성자 이름을 표시할 수 있도록 멤버십·작성자 계약을 둔다. 가족 역할·초대 API는 가족 담당과 연결한다. 질문의 가족 다중 답변은 별도 question 도메인에서 처리한다.

## 도메인 경계 제안

문서의 사용자 기능 이름은 `diary`로 유지한다. 다만 기존 `record` 샘플과 지도 #19의 기록 ID는 자유 다이어리에 사용하는 안을 제안한다. 같은 일기를 별도 diary 테이블에 복제하지 않는다. 질문 답변은 여기에 포함하지 않고 question 테이블과 독립 ID를 갖는다.

| 영역 | 책임 |
| --- | --- |
| `record` | 자유 다이어리의 기록 ID, 아이·작성자, 내용·날짜·시각, 접근 검사, 첨부 참조와 CRUD |
| `diary` | 자유 다이어리 목록·월별 달력 조회 계약. 초기에는 record의 조회 유스케이스로 구현 가능 |
| `question` | 모드별 질문 풀·가족 공통 진행·개별 답변. record/diary 행을 생성하지 않음 |
| `map` | 기존 record ID에 위치를 연결. record의 접근 확인 입력 포트 사용 |

프론트의 개체명은 자유 일기 `DiaryEntry`, 질문 답변 `QuestionAnswer`로 분리한다. 구현 전 백엔드 도메인 이름을 합의한다. 이 초안은 `com.pawmento.record`를 유지하는 안이며 단순 명칭 변경 때문에 기존 지도 계약을 깨지 않는다. 별도 `diary` 패키지를 만든다면 record 입력 포트만 호출하고 JPA 엔티티·리포지토리를 직접 참조하지 않는다.

## 데이터 구조 제안

기존 `records`의 `id`, `pet_id`, `content`를 다음과 같이 확장한다.

| 컬럼 | 의미 |
| --- | --- |
| `id` | 자유 다이어리의 서버 발급 기록 ID. 질문 답변 ID와 별개 |
| `pet_id` | 대상 아이. 생성 이후 변경 불가 |
| `created_by` | 인증된 작성자 ID. 요청 본문에서 받지 않음 |
| `content` | 자유 일기 내용, 최대 3,000자 |
| `recorded_date` | 사용자가 선택한 기록 날짜(DATE). 자유 기록은 수정 가능 |
| `created_at`, `updated_at` | 서버 생성 UTC 시각 |
| `version` | 동시 수정 충돌 확인용 버전 |

- 질문 ID·질문 본문·답변은 question의 독립 테이블에만 저장한다. 다이어리 생성·삭제와 question 생명주기를 연결하지 않는다.
- 자유 기록은 내용이 비어 있으면 유효한 첨부가 필수다. 공백은 저장 전 정리한다.
- 질문의 답변 등록일은 실제 저장 날짜로 고정한다. 자유 일기의 `recorded_date`는 회상한 사건의 날짜로 별도 유지하고 `created_at`은 실제 작성 시각으로 표시하는 안을 제안한다. 질문 날짜와 혼용하지 않는다.
- 미래 기록 날짜는 첫 범위에서 거부하는 안을 제안한다. 과거 날짜는 허용한다. ‘오늘’은 서버 Asia/Seoul 기준이다.
- 목록 인덱스 후보는 `(pet_id, recorded_date DESC, id DESC)`다. 가족 멤버십을 먼저 검사한 뒤 아이 단위로 조회하고 달력도 이 조건으로 집계한다. 작성자 필터가 있으면 추가 인덱스를 검토한다. 실제 데이터로 실행 계획을 확인한다.
- 기존 샘플 데이터의 작성자를 추측해 채우지 않는다. 개발 데이터 초기화 또는 명시적인 백필 후 NOT NULL을 적용하는 이관안을 정한다.

### 첨부 계약

- 공통 파일 동작·메타데이터·형식·개수·용량·상태·TTL은 [media 설계](../media/README.md)를 단일 기준으로 삼는다. 파일 업로드를 별도 담당이 만들기를 기다리는 범위 밖 작업으로 두지 않는다.
- `record_attachment`: `id`, `record_id`, `asset_id`, `sort_order`. 부모+파일과 부모+순서 중복을 DB에서 막는다. 실제 파일 정보는 media가 소유한다.
- 이미지·영상 선택 및 음성 녹음 → 업로드 세션 → 바이너리 업로드 → 서버 검증 READY → 일기 JSON의 `attachmentIds` 연결 순서다. blob/data URL을 DB에 저장하지 않는다.
- 새 첨부는 본인 업로드·해당 아이·`DIARY_ATTACHMENT` 용도·READY를 검사한다. 수정 시 기존 첨부 유지와 새 첨부 추가를 구분한다. `attachmentIds`는 전체 교체 목록이고 중복 ID는 거부한다.
- 일기·첨부 행·media 참조 수 변경은 같은 DB 트랜잭션이다. 연결 실패 시 전체를 롤백하고 입력·기존 첨부를 보존한다. 본문이 비어 있으면 READY 첨부가 반드시 하나 이상 남아야 한다.
- 상세의 `attachments`는 `assetId`, `type`, `filename`, `mimeType`, `sizeBytes`, `durationMs`, `width`, `height`, `sortOrder`를 반환한다. 부모 첨부 content API에서 현재 열람 권한을 확인한 뒤 파일을 스트리밍한다. 파일당 15MiB 추천안·Docker volume 저장은 media 문서를 따른다.
- 썸네일은 첫 이미지로 제안한다. 파일 종류가 섞여도 일기 개체를 PHOTO/VIDEO/VOICE로 나누지 않는다. 영상 썸네일은 media가 제공하고 오디오 자동 재생은 하지 않는다.
- 첨부 제거·일기 삭제 시 연결 해제·참조 수 변경·삭제 작업 등록까지 트랜잭션에 포함한다. 실제 저장소 삭제는 비동기 재시도하고, 다른 글에서 쓰는 자산은 지우지 않는다.

## API 제안

경로는 공통 `/api/v1` 접두사를 제외했다. 최신 `WebConfig`가 접두사를 적용하므로 컨트롤러에 중복 작성하지 않는다.

| 요청 | 입력 | 응답 |
| --- | --- | --- |
| `POST /pets/{petId}/diaries` | `content`, `recordedDate`, `attachmentIds` | 201, 자유 기록 상세 |
| `GET /pets/{petId}/diaries` | `date` 또는 `from/to`, `page`, `size` | 200, 자유 기록 목록 |
| `GET /pets/{petId}/diaries/calendar` | `month=YYYY-MM` | 200, 해당 월 날짜별 건수 |
| `GET /pets/{petId}/diaries/{recordId}` | 없음 | 200, 자유 기록 상세 |
| `PATCH /pets/{petId}/diaries/{recordId}` | `content`, `recordedDate`, `attachmentIds`, `version` | 200, 변경 상세 |
| `DELETE /pets/{petId}/diaries/{recordId}` | 없음 | 204 |

PATCH는 제공한 필드만 바꾼다. 변경 필드 하나 이상과 `version`이 필수이며, 필수 필드의 명시적 null은 400이다. `attachmentIds: []`는 첨부 전체 제거다. 변경 후 텍스트·첨부가 모두 비면 거부한다. 질문 답변 API는 [질문 문서](../question/README.md)에서 별도로 정의한다.

상세 응답 예시(제안):

```json
{
  "recordId": 123,
  "petId": 10,
  "author": {"memberId": 1, "displayName": "보리 가족"},
  "content": "오늘도 공원에서 즐겁게 뛰었어요.",
  "recordedDate": "2026-11-17",
  "attachments": [],
  "createdAt": "2026-11-17T02:30:00Z",
  "updatedAt": "2026-11-17T02:30:00Z",
  "version": 0
}
```

목록은 `recordedDate DESC, recordId DESC` 정렬, `page`는 0부터, `size` 기본 20·최대 100이다. 응답은 `items`, `page`, `size`, `totalElements`, `totalPages`다. `date`와 `from/to` 동시 지정은 거부하고 기간 양 끝은 포함한다. 날짜 형식·역전·페이지 범위를 검증한다. 첫 범위는 날짜 필터이며 텍스트 검색·미디어 전용 탐색은 후속 이슈로 둔다.

달력 응답은 `{petId, month, days: [{date, count}]}`로 제안한다. 기록이 있는 날짜만 반환하고 프론트가 빈 날짜를 채운다. 질문 답변 저장소를 조회하거나 합산하지 않는다. 월 범위는 DATE의 월 첫날 이상·다음 달 첫날 미만이다. 날짜 클릭은 동일 목록 API의 `date`로 연결한다.

ID는 서버에서 Long으로 발급하되 JavaScript의 정수 범위를 넘을 가능성을 고려해 JSON ID를 문자열로 통일할지 공통 응답 담당과 합의한다. 프론트 연결 어댑터가 타입을 한 번만 변환한다.

## 인증·권한·오류

- 컨트롤러의 `@LoginMember`로 회원 ID를 받는다. 클라이언트의 `ownerId`, `createdBy`는 신뢰하지 않는다.
- pet/가족 입력 포트로 해당 회원의 멤버십·읽기/쓰기 권한을 확인한다. OWNER·EDITOR는 작성 가능, VIEWER는 조회만 가능하도록 제안한다. 수정·삭제는 작성자 본인만 허용하고 기존 기록의 `petId`, `createdBy`까지 검사한다. 경로의 petId만 확인하고 임의 recordId를 수정하는 경로가 없어야 한다.
- 가족은 아이의 일기를 함께 읽고 답변과 동일하게 작성자 회원 ID·표시 이름을 본다. 이름 스냅샷과 탈퇴 후 표시 정책은 question과 맞춘다. 멤버십 회수 후에는 조회·변경을 거부한다.
- 미인증 401, 입력 오류 400, 없는 아이/기록 또는 비가족 자원 404, 열람자 쓰기·다른 작성자 수정 403, 버전 충돌 409. 관리자라는 이유로 개인 기록 열람 권한을 자동 부여하지 않는다.
- 에러는 기존 `{code, message}`를 따른다. 저장 실패 시 DB 상태를 되돌리고 프론트는 입력을 유지한다.
- 수정은 요청 버전으로 조건부 갱신한다. 삭제도 경합 시 재확인이 필요하도록 버전 전달 방식을 구현 이슈에서 정한다.

## 지도 담당에게 제공할 입력 포트

후보: `GetRecordAccessUseCase` / `GetRecordAccessQuery(memberId, recordId)` / `GetRecordAccessResult(recordId, petId, createdBy)`.

record 서비스가 접근을 확인한 결과만 반환하고, map은 record의 엔티티나 저장소를 직접 참조하지 않는다. 조회 전용 포트다. 지도 #19의 위치 저장·삭제 구현보다 먼저 제공해야 한다. 질문 답변은 이 포트의 대상이 아니다. 지도 #19는 작성자 본인만 위치를 관리하는 기존 정책이 있으므로 가족 일기 조회 권한이 지도 위치 권한을 자동 확대하지 않도록 별도 계약을 합의한다.

일기 삭제 시 위치·일기 첨부 참조를 정리한다. 독립된 질문·답변 데이터는 삭제하지 않는다. 같은 DB의 위치 정리는 map 입력 포트를 호출하는 트랜잭션 또는 이벤트로 구현할지 합의한다. 파일 정리는 [media 설계](../media/README.md)의 참조 해제·삭제 작업 등록 계약으로 처리한다. 실제 삭제 실패로 일기를 되살리거나 다른 글의 참조 파일을 지우지 않는다.

## 사진 위치 자동 연결

사진의 위치 데이터로 지도 핀을 만드는 흐름을 이번 설계에 포함한다. 세부 API·기록당 대표 위치·위치 해제/수정 우선순위·outbox·버전/삭제 경합은 [사진 위치 연동 #44](../map/photo-location.md)를 따른다.

- 업로드만으로 핀을 만들지 않는다. READY 사진의 서버 검증 GPS 후보를 사용하고 **일기 저장 성공 후** 기록 ID와 연결한다. GPS가 없으면 일기는 정상 저장하고 자동 핀은 만들지 않는다.
- 생성/수정 요청에 `location: {mode: AUTO|MANUAL|NONE}`를 추가하고 MANUAL만 좌표·선택 주소를 받는다. 생성 생략은 AUTO, 수정 생략은 기존 정책 유지다. 기존 AUTO에서는 사진 변경 시 재계산한다.
- 여러 사진은 첨부 순서상 첫 유효 GPS 하나를 대표로 삼는 안이다. 명시적 수동 지정과 NONE은 자동 작업이 덮어쓰지 않는다.
- 일기/첨부/위치 의도/outbox를 한 트랜잭션에 기록한다. 지도 저장은 비동기 재시도로 분리하고 응답의 `location: {mode, syncStatus}`로 반영 중·실패를 구분한다. 지도 실패는 일기 저장을 취소하지 않는다.
- 기록 삭제·사진 변경 이벤트는 최신 revision만 반영하며 제거한 핀이 오래된 이벤트로 재생성되지 않도록 한다. 핀을 클릭하면 해당 다이어리 상세로 이동한다.
- 좌표 후보는 일반 첨부 메타데이터에 넣지 않는다. 지도 권한은 #19의 작성자 본인 정책을 유지하며 가족 일기 열람으로 자동 확대하지 않는다.

## 구현 순서 제안

1. record/diary 명칭·pet 접근·지도 조회 포트·공통 API 접두사 합의, 기능 이슈 작성.
2. 기록 공통 필드·접근 검사와 텍스트 생성/상세/수정/삭제. 기존 샘플 API 처리와 DB 이관 포함.
3. 자유 기록 목록·날짜 필터·달력 집계, 지도용 접근 조회 포트와 [사진 위치 연동 #44](../map/photo-location.md)의 위치 의도·이벤트 연결.
4. 가족 멤버십·작성자 표시와 권한 검증, question과 저장소·조회 분리 확인.
5. [media 구현 순서](../media/README.md)에 따라 업로드·검증·열람·삭제를 구현하고 첨부 참조 트랜잭션·소유권 검사와 연결한다. 텍스트 CRUD만으로 전체 기능 완료로 표시하지 않는다.
6. 프론트 공통 업로더·음성 녹음·재생과 HTTP 어댑터를 연결한다. 기존 데모 데이터는 서버에 자동 업로드하지 않는다.

## 범위 밖과 아직 정하지 않은 것

- 한 일기를 가족이 공동 편집하는 기능, 지도 SDK 자체 구현(사진 핀 연동은 #44와 연결), 커뮤니티 공개, AI 엽서, 정원 쪽지·편지, 음성 전사, 전문 검색, 휴지통 복원은 이 범위 밖이다.
- 파일 업로드는 이번 구현 범위다. 형식·용량·TTL·저장소·검증 도구의 세부 제안은 media 문서에서 확정한다. 미래 날짜·작성 가능한 과거 범위와 일기 삭제 경합 정책은 별도 확인한다.
- 반려동물·회원 삭제 시 기록 보존 정책, 위치 연관 삭제 방식과 FK 책임을 담당자끼리 합의해야 한다.
- 프론트 자유 기록의 TEXT/PHOTO/VIDEO/VOICE는 `DiaryEntry`와 첨부 메타데이터로 정리한다. 잘못 이름 붙은 `type=DIARY`는 `QuestionAnswer` 저장소로 이관하며 자유 일기로 취급하지 않는다. 프론트의 저장소·URL·상세·검증도 함께 분리한다.
- 현재 샘플 POST `/records`는 새 계약과 중복되지 않도록 제거·전환 시점을 합의한다. 기존 API를 조용히 남겨 권한 검사를 우회하게 해서는 안 된다.
