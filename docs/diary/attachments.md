# 다이어리 사진·음성 첨부

관련 이슈: #32, 미디어 #33. 선행: 텍스트 CRUD #89, 목록·달력 #100.

## 한눈에

- 끝나면: 업로드·검증된 사진과 음성을 일기에 연결하고, 상세에서 열람하며 교체·삭제한다. 본문 없는 첨부 일기도 허용한다.
- 결정 필요: 이 계획의 첨부 참조·부모 권한 열람 계약 승인. 가족·지도·프론트는 이번 범위에 포함하지 않는다.
- 규모: 참조 관리 → 일기 저장 → 부모 권한 열람 → 삭제·경합 검증 순서로 구현한다.

## 요구사항

- #32-R1 본문 또는 첨부가 하나 이상인 일기를 저장한다. 본문과 첨부가 모두 없으면 거부한다. 본문 최대 3,000자·미래 사건 날짜 거부는 유지한다.
- #32-R4 `attachmentIds`의 순서를 보존하며 사진·음성만 연결한다. 신규 생성에서 생략은 빈 목록, 수정에서 생략은 기존 첨부 유지, 빈 배열은 전체 해제다. 중복 ID는 거부한다. 용량·형식 검증은 기존 media 정책을 재사용한다.
- #33-R4 부모 일기·첨부 행·media 참조 수를 동일 DB 트랜잭션으로 저장한다. 자산의 업로더·아이·DIARY 용도·READY 상태와 미연결 만료 여부를 서버에서 확인한다.
- #33-R5 다른 일기에 재사용 중인 파일은 연결 하나를 지웠다고 삭제하지 않는다. 마지막 참조 해제 시 삭제 작업을 등록하고 물리 삭제는 기존 작업자가 트랜잭션 밖에서 수행한다.
- #32-R3 현재 pet 소유자와 작성자 규칙을 유지한다. 실제 가족 공유·역할·표시 이름은 가족 도메인 연결 전 완료로 표시하지 않는다.

## 경계와 API

- 기존 `/api/v1/diaries?petId=...` 생성 및 `/api/v1/diaries/{recordId}?petId=...` 수정 body에 `attachmentIds`를 추가한다. 작성자·서버 시각·기대 버전 규칙을 유지한다.
- JSON 필드의 생략과 명시적 null은 웹 경계에서 구분한다. 아래 본문 계약은 이번 첨부 단계의 변경 제안이며 기존 텍스트 전용 동작이 이미 지원한다고 표시하지 않는다.

| 필드 | POST 생성 | PATCH 수정 |
| --- | --- | --- |
| `content` 생략 | 본문 없음(`""`)으로 정규화. 최종 첨부가 하나 이상이어야 함 | 기존 본문 유지 |
| `content: null` | 400, 문자열만 허용 | 기존과 같이 400, 생략으로 취급하지 않음 |
| `content: ""` 또는 공백 문자열 | strip 후 `""`로 저장. 첨부 없으면 400 | 본문 비우기. 최종 첨부 없으면 400 |
| `content` 비어 있지 않은 문자열 | strip 후 저장, 최대 3,000자 | 동일 검증 후 변경 |
| `attachmentIds` 생략 | 빈 목록 | 기존 첨부 유지 |
| `attachmentIds: null` | 400, 배열만 허용 | 400, 생략으로 취급하지 않음 |
| `attachmentIds: []` | 첨부 없음 | 전체 해제, 최종 본문도 없으면 400 |

- `version`을 포함한 attachmentIds만의 PATCH를 허용한다. content·recordedDate를 함께 보내도록 강제하지 않는다. 서버가 기존 본문과 요청의 최종 첨부를 합쳐 유효성을 검사하고, 첨부만 수정해도 부모 version과 updatedAt을 갱신한다. version 외 수정 필드가 모두 생략된 요청은 기존처럼 400이다. recordedDate의 생략/명시적 null 규칙은 기존대로 유지한다.
- 상세 응답은 정렬된 자산 ID·종류·안전한 파일 메타데이터·부모 권한 열람 경로를 반환한다. 파일 시스템 경로·저장 키·GPS를 노출하지 않는다. 목록은 첨부 메타데이터를 일괄 조회해 N+1을 피한다.
- 부모별 GET/HEAD `/api/v1/diaries/{recordId}/attachments/{assetId}?petId=...` 및 이미지 썸네일 경로를 제공한다. 매 요청에서 현재 부모 접근과 실제 첨부 관계를 확인하고 기존 media 파일 읽기·Range·캐시 정책을 재사용한다. 미연결 미리보기 API를 첨부 파일 열람으로 우회하지 않는다.
- diary 서비스는 diary 출력 포트로 첨부·자산 참조를 조율한다. `diary/adapter/out/media`가 media 입력 포트를 호출하며 서비스에서 media 저장소나 JPA 엔티티에 접근하지 않는다. media 입력 포트는 자산 잠금·참조 획득/해제·열람을 제공하고 내부 저장 구현을 감춘다.
- diary 첨부 테이블은 부모+자산 및 부모+순서를 유일하게 한다. 버전 조건부 갱신 성공 뒤 첨부를 변경하고, 중간 실패는 부모 변경도 롤백한다. 자산 잠금은 ID 순으로 획득해 교체 요청 간 교착 위험을 줄인다.
- 첨부 전체 교체는 기존/요청 자산 ID의 차집합으로 처리한다. 유지 집합은 참조 해제·재획득하지 않고 순서만 변경하며, 제거 집합만 해제하고 신규 집합만 획득한다. 유지 자산의 referenceCount·READY 상태·삭제 작업은 변하지 않는다. 동일 배열 재전송도 참조 변경이나 삭제 작업을 만들지 않는다.
- 부모 버전 검사와 필요한 자산 잠금 뒤 동일 트랜잭션에서 최종 집합을 검증한다. 순서 유일 제약과 충돌하지 않도록 기존 첨부 관계 행을 삭제·flush한 후 최종 순서로 재삽입할 수 있으나, 이는 관계 행 교체일 뿐 유지 자산의 media 참조 해제는 호출하지 않는다. 중간 실패는 관계 행·부모 version/updatedAt·참조 수·상태·삭제 작업을 모두 이전 상태로 롤백한다.
- 정리 작업의 실제 참조 확인에 diary 첨부 저장소를 연결한다. 참조 수만 믿고 연결된 파일을 삭제하지 않는다. question은 아직 연결하지 않으며 질문 첨부가 구현된 것으로 표시하지 않는다.

## 시나리오

- #32-S3 [테스트] POST에서 content 생략·빈 문자열·공백은 유효 첨부가 있으면 성공하고 없으면 400이다. content 명시적 null·문자열 외 타입, attachmentIds 명시적 null·중복·잘못된 ID와 기존 본문 길이·날짜 오류는 거부한다. PATCH content 명시적 null은 생략과 달리 400이다. (고침 #32: #105 리뷰의 입력 계약 구분)
- #32-S8 [테스트] 오래된 버전 수정·삭제에서 부모와 첨부·참조 수가 유지된다. 본문 없는 `[11]` 일기에 `{"version":v,"attachmentIds":[]}`를 보내면 400이며 본문·첨부·부모 버전·참조 수·READY 상태·삭제 작업이 그대로다. 본문과 마지막 첨부를 동시에 비우는 요청도 같은 방식으로 거부한다. (고침 #32: #105 리뷰의 마지막 첨부 제거 검증)
- #32-S9 [테스트] READY 사진·음성을 요청 순서대로 생성·열람하고 본문 없는 첨부 일기를 허용한다. 수정 생략은 유지, 배열은 전체 교체, 빈 배열은 해제다. 아래 사례를 웹 경계와 실제 PostgreSQL 저장 결과로 검증한다. (고침 #32: #105 리뷰의 첨부 전용 전환·교집합 검증)
  - 날짜 등 필수 필드를 갖춘 POST `{"attachmentIds":[11]}`는 content 생략을 `""`로 저장한다. content 빈 문자열·공백도 같은 결과이며 null은 S3의 400이다.
  - 텍스트 일기에 `{"version":v,"content":"","attachmentIds":[11]}`를 보내 첨부 전용으로 바꾼다. 이후 `{"version":v+1,"attachmentIds":[12]}`로 본문·날짜 없이 첨부만 바꾸면 본문과 날짜는 유지되고 version/updatedAt은 갱신된다. attachmentIds 생략은 기존 연결을 유지한다.
  - `[11,12]` → `[12,11]`: 부모+순서 유일 제약 아래 교환이 성공하고 응답·저장 순서가 일치한다. 두 자산은 각각 이 일기에만 연결된 fixture로 두어 referenceCount=1·READY·삭제 작업 수 불변을 검사한다.
  - `[11,12]` → `[12,13]`: 12는 참조·상태·삭제 작업 불변, 11만 해제, 13만 획득한다. 11이 마지막 참조일 때만 삭제 예약하고, 다른 일기에도 연결돼 있으면 보존한다. 동일 배열 재요청도 참조 수가 변하지 않는다.
  - 관계 행 삭제/재삽입 또는 참조 변경 도중 실패를 주입해 기존 순서·부모 버전·참조 수·상태·삭제 작업 전체가 롤백되는지 확인한다.
- #32-S10 [테스트] 타인·다른 아이·다른 용도·미완료/만료·삭제 중 자산 연결을 거부한다. 여러 자산 중 하나라도 실패하면 부모·첨부·참조 수 전체를 롤백한다.
- #32-S11 [테스트] 현재 소유자 범위에서 부모 권한과 실제 연결을 검사한다. 재사용 중인 파일은 보존하고 마지막 참조 해제만 정리 대상으로 만든다. 가족 열람·권한 회수 부분은 미완료로 남긴다.
- #32-S13 [테스트] 일기 삭제와 첨부 해제·삭제 작업 등록을 원자적으로 처리한다. 물리 삭제 실패는 기존 작업 재시도 규칙으로 복구한다.
- #32-S10·S11 [테스트] 자산 연결과 만료 정리의 양방향 경합, 동일 자산 재사용·교체·일기 삭제 경합을 실제 PostgreSQL에서 검증한다. 참조 수 불일치 시 실제 연결 파일을 보존한다.
- #32-S14·S15 [직접] 프론트 연동 전에는 완료 처리하지 않는다.

## 작업 순서

1. media 참조 획득/해제·부모 열람 입력 계약과 도메인 규칙, diary 첨부 저장소·명시적 제약을 구현한다.
2. 생성·수정·삭제에 첨부와 참조 관리를 연결하고 버전·원자성 회귀 검사를 추가한다.
3. 상세·목록 응답과 부모 권한 파일/썸네일 열람을 연결한다.
4. 정리 작업의 실제 참조 확인과 경합·물리 삭제 재시도를 검증한다.

## 확인 방법

- 도메인 규칙은 단위 테스트, FK·유일성·동시성·전체 롤백은 PostgreSQL 통합 테스트, 파일 열람 인증·Range·HEAD는 웹 테스트로 나눈다.
- 바뀐 diary/media 테스트와 헥사고날 경계 검사만 로컬 실행하고 전체 검사는 CI에 맡긴다. 실제 외부 API나 사용자 파일을 사용하지 않는다.
- 테스트 실행 결과는 PR에 기록하며 완료한 범위만 #32·#33에 체크한다.

## 범위 밖

- 가족 멤버십, 질문 답변 첨부, 지도 입력 포트·위치 동의·GPS 추출, 프론트 업로더·녹음 UI, 기존 데모 파일 자동 이관.
- media의 위치 동의 차단을 해제하지 않는다. 영상 신규 업로드는 계속 거부한다.
- 사용자·일기·기존 파일 초기화, 업로드 용량 변경, 공통 예외 종류 추가.
