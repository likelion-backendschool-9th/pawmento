# 다이어리 목록·달력 조회

관련 이슈: [#32](https://github.com/likelion-backendschool-9th/pawmento/issues/32). [다이어리 전체 설계](README.md)의 두 번째 구현 단위다. [텍스트 CRUD 계획](basic-crud.md)과 PR #89의 기록을 조회하며 기존 생성·수정·삭제 계약은 바꾸지 않는다.

## 요구사항과 범위

- #32-R2: 반려동물별 일기 목록, 날짜/기간 필터, 페이지 조회, 월별 달력의 날짜별 건수를 구현한다. 질문 답변 저장소는 조회·합산하지 않는다.
- #32-R3 중 작성자 구분 기반: 목록의 각 일기에 서버 저장값 `createdBy`를 포함한다. 접근 권한과 조회할 작성자를 혼동하지 않는다. 소유자 ID로 작성자를 제한하지 않고 해당 아이의 일기를 함께 조회한다.
- 현재는 실제 pet 소유자만 접근한다. 가족 멤버십·역할·표시 이름은 후속 단위이며 임의 회원을 가족으로 허용하지 않는다.
- ACTIVE/GARDEN은 같은 기록을 사용한다. 모드 전환은 목록·달력 필터가 아니다.

## 사용자 경험

‘다이어리’의 **일기 / 달력** 탭에서 사용할 서버 API를 제공한다. 목록에서는 작성자 ID로 기록을 구분하고, 달력 날짜 선택은 같은 목록 API의 `date`로 연결한다. 이번에는 프론트 데모를 실제 서버 호출로 바꾸지 않는다.

가족 연결 이후에도 조회 구조는 동일하다. 가족 접근 검사를 통과한 뒤 반려동물 기준으로 조회하고, 목록의 각 일기는 원 작성자 정보를 유지한다. 실제 여러 가족의 생성·열람과 탈퇴 후 접근 차단은 가족 단계에서 검증한다.

## API와 입력 규칙

공통 `/api/v1`은 설정에서 붙인다.

| 요청 | 입력 | 응답 |
| --- | --- | --- |
| `GET /pets/{petId}/diaries` | 선택 `date` 또는 `from`/`to`, `page`, `size` | 200, 페이지 목록 |
| `GET /pets/{petId}/diaries/calendar` | 필수 `month=YYYY-MM` | 200, 해당 아이의 월별 날짜·건수 |

쿼리는 URL에서만 받는다. 헤더·본문으로 필수 쿼리를 대신 채우지 않는다. 생략과 빈 값을 구분하고 같은 키의 중복은 400으로 거부한다. 웹 입력 오류는 공통 기본 예외를 상속하는 웹 예외와 전역 핸들러로 처리하며, 모든 MVC 요청의 전역 정책을 변경하지 않는다.

### 일기 목록

- 필터 생략은 해당 아이의 전체 자유 일기다. 특정 작성자 필터는 이번 API에서 제공하지 않는다.
- `date`는 정확한 `YYYY-MM-DD`이고 해당 사건 날짜(`recordedDate`)의 일기를 조회한다. 실제 작성 시각(`createdAt`)이나 질문 답변 날짜로 필터하지 않는다.
- `from`·`to`는 각각 선택이며 한쪽만 있어도 허용한다. 양쪽이 있으면 `from <= to`여야 하며 경계 날짜를 포함한다.
- `date`와 `from` 또는 `to`를 동시에 보내면 400이다. 잘못된 날짜·빈 값·역전 범위도 400이다.
- `page`는 0부터 시작하고 기본 0, `size`는 기본 20·허용 1~100이다. 음수·소수·문자·정수 범위 초과·빈 값·중복은 400이며 범위를 조용히 보정하지 않는다.
- 정렬은 `recordedDate DESC, recordId DESC`로 고정한다. 같은 사건 날짜에도 ID로 순서를 고정한다.
- 범위를 벗어난 페이지와 일기 없는 아이는 `items: []`를 반환한다. `totalElements`와 `totalPages`는 페이지 오프셋이 아니라 같은 아이·날짜 조건의 전체 결과를 기준으로 계산한다.
- 미래 날짜/기간도 조회 형식이 유효하면 허용하며 데이터가 없으면 빈 목록이다. 생성 시 미래 날짜를 거부하는 규칙과 조회의 빈 결과를 혼동하지 않는다.

응답 예시:

```json
{
  "items": [{
    "recordId": 123,
    "petId": 10,
    "createdBy": 1,
    "content": "공원에서 함께한 오후",
    "recordedDate": "2026-11-17",
    "createdAt": "2026-11-18T01:00:00Z",
    "updatedAt": "2026-11-18T01:00:00Z",
    "version": 0
  }],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

각 항목은 현재 상세 응답과 동일한 스냅샷이다. 본문 3,000자 제한 안에서 전체 내용을 반환하고 새 요약 필드를 만들지 않는다. `createdBy`는 회원 ID이며 닉네임·가족 역할로 표시하지 않는다. 이름을 확인할 수 없는데 가짜 표시 이름을 채우거나 member JPA 저장소를 직접 조인하지 않는다. 가족 단계에서 실제 이름 조회/탈퇴 후 표시 정책을 연결한다.

### 달력

- `month`는 필수이며 정확한 `YYYY-MM`이다. 누락·빈 값·잘못된 월·중복은 공통 400이다.
- 사건 날짜 기준으로 월 첫날 이상·다음 달 첫날 미만을 집계한다. 생성 시각·시간대 변환으로 DATE 경계가 이동하지 않게 한다.
- 기록이 있는 날짜만 `{date, count}`로 날짜 오름차순 반환한다. 빈 날짜는 프론트에서 채우며 일기가 없는 월은 `days: []`다.
- 같은 날짜의 여러 작성자 일기도 모두 합산한다. 해당 날짜의 `date` 목록 전체 건수와 달력 건수가 일치해야 한다.

```json
{
  "petId": 10,
  "month": "2026-11",
  "days": [{"date": "2026-11-17", "count": 2}]
}
```

## 권한과 작성자 구분

목록·달력 모두 먼저 `CheckDiaryPetAccessPort`로 해당 아이의 현재 접근 권한을 확인한다. 첫 어댑터는 기존 pet 입력 포트의 소유자 검사이며 미인증 401, 비소유자 403, 없는 아이 404를 유지한다. 잘못된 아이 ID·조회 조건은 400이다. 일기 없는 아이와 접근할 수 없는 아이를 같은 빈 목록으로 처리하지 않는다.

DB 조회 조건은 **대상 `petId`와 날짜**다. 인증 회원 ID는 접근 검사에 사용하며 `createdBy = memberId` 필터로 결과를 제한하지 않는다. 별도 아이의 기록은 섞이지 않아야 한다. 이 구조는 가족 쓰기 권한을 미리 부여하는 것이 아니며 생성·수정·삭제의 기존 소유자/작성자 검사는 유지한다.

## 헥사고날 경계와 저장소

- 기존 `DiaryController`에 목록·달력 메서드를 추가한다. 별도 도메인 컨트롤러나 도메인 전용 Advice를 만들지 않는다.
- 입력 포트는 `ListDiaryEntriesUseCase`, `GetDiaryCalendarUseCase`로 분리하고 각각 Query/Result를 사용한다. 페이지·날짜 집계 결과는 Spring `Page` 대신 자체 값 타입으로 전달한다.
- 서비스는 접근 검사와 조회를 조율하고 읽기 트랜잭션을 사용한다. 회원 정보·Spring Security·웹 요청을 핵심 계층으로 전달하지 않는다.
- 출력 포트는 페이지 조회와 날짜별 건수 조회로 분리하며 기존 `DiaryEntryPersistenceAdapter`가 구현한다. 다른 도메인의 JPA 저장소는 참조하지 않는다.
- 페이지 조회·총 건수는 같은 아이/날짜 조건을 사용한다. 한 요청의 항목과 총 건수는 같은 읽기 스냅샷을 사용하도록 목록 트랜잭션을 PostgreSQL REPEATABLE READ로 실행한다. 서로 다른 페이지 요청 사이의 동시 추가/삭제까지 스냅샷을 보존한다는 뜻은 아니다.
- 월별 집계는 DB의 GROUP BY로 수행한다. 모든 일기를 애플리케이션 메모리에 불러와 집계하거나 날짜마다 별도 조회하지 않는다.
- 인덱스 후보는 `(pet_id, recorded_date DESC, id DESC)`다. 기존 pet 외래 키·삭제 제한을 유지하며 인덱스 적용과 조회 조건을 함께 검증한다. 작은 테스트 데이터에서 특정 실행 계획을 강제하지 않는다.

## 확인 시나리오

기존 시나리오 번호를 유지하고 작성자 통합 조회 및 쿼리 경계의 새 검증만 추가한다. 가족·질문 전체 기능이 구현되었다고 표시하지 않는다.

| 번호 | 방법 | 이번 단위의 확인 |
| --- | --- | --- |
| #32-S5 | 테스트 | 현재 접근 계약의 비소유자·없는 아이 거부, 다른 아이 결과 미노출. 가족 탈퇴/역할 검사는 후속 |
| #32-S6 | 테스트 | 실제 PostgreSQL의 월말·윤년·다음 달 경계 집계, 생성 시각과 사건 날짜가 다른 기록의 월 선택, 빈 월·일기 수정/삭제 후 건수 반영. 질문 행과의 독립 저장소 경계 확인 |
| #32-S7 | 테스트 | 날짜·양쪽/한쪽 기간·포함 경계·역전·동시 필터 검증, 같은 날짜 ID 역순, 페이지 기본/최대/빈 결과/총 건수 |
| #32-S24 | 테스트 | 같은 아이에 작성자가 다른 fixture를 저장하고 목록이 두 작성자를 `createdBy`로 구분하며 달력도 합산하는지 확인. 접근은 실제 소유자로 수행하고 다른 아이는 제외. 가족 생성/가입 권한 검증을 대체하지 않음 |
| #32-S25 | 테스트 | URL 쿼리 전용 입력, 헤더만 보낸 month 누락, 빈 값·중복·타입/날짜/월 오류를 공통 400으로 거부. 기본값은 생략에만 적용 |
| #32-S26 | 테스트 | 목록 항목/총 건수의 동일 조회 조건과 읽기 스냅샷을 실제 PostgreSQL에서 검증. 병렬 추가/삭제 뒤 다른 요청에는 변경 결과가 반영됨 |

조회·집계·스냅샷과 아이별 격리는 PostgreSQL 통합 테스트, HTTP 인증·입력·응답은 웹 테스트, 순수한 기간/페이지 규칙은 필요한 단위 테스트로 나눈다. 기존 CRUD·버전·반려동물 삭제 경합은 변경 영향 범위의 회귀 대상으로 유지한다. 실행 결과는 PR 본문에 기록한다.

## 작업 순서

1. 날짜/기간·페이지·작성자 응답·현재 권한·월 집계 계약을 확인한다.
2. 조회 조건 값 타입과 Query/Result·입력/출력 포트를 만든다.
3. 조회 서비스와 기존 소유자 접근 어댑터를 연결한다.
4. DB 목록/건수·월 집계·인덱스를 구현하고 PostgreSQL 조회/경계 검사를 실행한다.
5. 웹 쿼리 해석·응답 DTO를 연결하고 목록·달력 입력과 인증 검사를 실행한다.
6. 기존 CRUD와 pet 연동의 영향 범위 회귀를 확인한다.

## 범위 밖과 후속 연결

가족 초대·멤버십·역할·작성자 표시 이름, 사진·음성 첨부/미디어 전용 조회, 위치/GPS, 질문 답변 CRUD, 텍스트 검색·작성자 필터·임의 정렬, 프론트 API 연결은 이번 단위에 포함하지 않는다. 반려동물별 모아보기와 작성자 ID 구분은 지금 구현하고, 가족의 실제 접근 허용과 공동 사용 검증은 가족 단계에서 연결한다.
