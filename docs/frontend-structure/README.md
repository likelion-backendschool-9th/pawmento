# 프론트엔드 책임과 폴더 구조 개편

## 한눈에

프론트엔드는 화면 표시·사용자 상호작용·서버 요청을 담당하고, 업무 규칙과 실제 데이터 저장은 백엔드만 담당한다. 프론트의 헥사고날 구조를 기능별 화면 구성으로 바꾸고, 목업 데이터와 응답 대역은 별도 폴더로 모은다.

이 문서는 사용자 요청에 따른 **구조 개편 검토안**이다. 지금은 제품 코드·폴더·데이터·의존성을 변경하지 않는다. 구현 전에 작업 이슈를 연결하고 이 문서 PR에서 범위와 계약을 승인받는다. 구현 이슈의 요구사항·시나리오 번호는 이슈 생성 후 부여하며 기존 #12·#52 등의 번호를 새 의미로 재사용하지 않는다.

관련 기준: [문서 규칙](../README.md), [백엔드 구조](../backend-architecture.md), [기존 데모 계획](../app-demo/README.md), [검증 기준](../testing.md).

## 1. 사용자가 정한 방향

- 프론트에서 별도 업무 규칙·비즈니스 유스케이스·실제 데이터 저장소를 구현하지 않는다.
- 업무의 성공 여부, 권한, 질문 진행, 기록 저장과 최종 데이터는 백엔드 응답을 기준으로 한다.
- 프론트 전체 폴더 구조를 바꾸고 목업 데이터는 목업끼리 분리한다. 폴더 이름만 바꾸고 기존 브라우저 업무 로직을 그대로 옮기는 작업으로 끝내지 않는다.
- 코드 수정 전에 문서로 개편 범위·순서·검증 방법을 정한다.
- 백엔드의 헥사고날/JPA 구조는 유지한다. 디자인 개편이나 API 계약 변경을 자동으로 포함하지 않는다.

이 문서를 승인하면 **프론트 구조**에 대해서는 아래 기준을 우선한다. 기존 헥사고날 청사진과 브라우저 데모 계획은 과거 설계·데이터 호환의 참고 자료로 남긴다. 기존 업무 동작, 보안, API 계약, 테스트 요구를 폐기한다는 뜻은 아니다.

## 2. 프론트와 백엔드의 책임

| 항목 | 프론트 | 백엔드 |
| --- | --- | --- |
| 화면·탐색 | 반응형 레이아웃, 모달·탭, 접근성, 선택 날짜·검색 조건 | 필요한 조회 API 제공 |
| 입력 폼 | 입력 중 값, 필수 안내·입력 형식의 즉시 피드백, 제출/중복 클릭 방지 | 업무 유효성 최종 판단, 저장 충돌 처리 |
| 인증·권한 | 현재 회원 조회, 서버 상태에 따른 안내·화면 이동·버튼 표시 | 로그인, 역할·가족 권한 검사, 토큰·세션 발급/폐기 |
| 반려동물·모드 | 선택한 아이의 서버 정보 표시, 변경 요청 | 소유권·모드 변경 가능 여부와 저장 |
| 질문 | 서버가 배정한 질문·답변 표시, 답변 입력 | 모드별 질문 선택, 미답변 유지, 최초 답변 완료와 가족 공통 진행 |
| 다이어리·달력 | 폼, 목록·달력 렌더링, 조회 조건 | 등록일·작성자·정렬·페이지·날짜 집계·CRUD |
| 파일·음성 | 파일 선택, 메모리 미리보기, 마이크 권한·녹음, 업로드 진행 | 형식/용량 최종 검증, 자산 상태·참조·비공개 저장·삭제 작업 |
| 위치·산책 | 위치 권한, 좌표 수집·전송 버퍼, 경로 그리기 | 위치 저장·중복 제거·상태·거리·시간 최종 집계 |
| 엽서·커뮤니티·가족 | 서버 결과 표시와 요청, 처리 중/실패 안내 | 생성·제한·공개 범위·초대·역할·저장 |
| 사용자 설정 | 현재 선택을 메모리에 반영 | 재접속 후 유지할 설정 저장·조회 |

### UI 로직과 업무 로직을 구분하는 기준

- 프론트에 남김: 포커스·스크롤, 날짜/숫자 표시, 화면용 지도 좌표 변환, 오디오 재생, 업로드 중 버튼 비활성화, 미저장 입력 경고, 네트워크 요청 취소·오래된 응답 무시.
- 백엔드로 통일: 권한 승인, 질문 뽑기·진행 전환, 등록일 확정, 작성자 결정, 가족 초대/역할 변경, 하루 생성 제한, 참조 수·삭제 판단, 업무상 모드 전환 조건.
- 브라우저에서 파일 크기나 입력 길이를 미리 안내할 수 있지만 서버 검증을 대신하거나 별도 정책을 정하지 않는다. 서버 거절을 최종 결과로 처리한다.
- 위치 미동의 사진의 **전송 전 GPS 제거와 제거 실패 시 업로드 중단**, 위치/마이크 권한 요청은 기존 개인정보 처리 계약을 지키는 브라우저 작업이다. 사진 위치에 동의하지 않았다는 이유만으로 GPS 제거에 성공한 사진의 업로드까지 막지 않는다. “업무 로직 제거”를 이유로 이 전처리를 삭제하거나 서버 도착 후 제거로 대체하지 않는다.
- 서버 요청의 입력/응답 타입은 남기되 프론트 전용 QuestionProgress·가족 권한 엔진 같은 상태 모델을 다시 만들지 않는다.

## 3. 데이터 저장과 화면 상태

### 실제 데이터

- 회원·아이·일기·답변·가족·산책·엽서·첨부·사용자 설정의 원본은 서버에만 저장한다.
- localStorage·sessionStorage·IndexedDB·브라우저 DB에 업무 데이터, 로그인 토큰, 역할, 초대 코드, 임시 업무 ID를 저장하지 않는다.
- API 오류·미구현·타임아웃을 브라우저 저장 성공으로 바꾸지 않는다. 요청 실패는 실패로 표시하고 입력을 유지한다.
- 서버에서 ID·등록일·권한·상태를 받은 후 결과를 반영한다. 클라이언트가 만든 임시 UUID를 저장된 업무 ID로 사용하지 않는다.
- 인증은 기존 서버의 HttpOnly 쿠키 계약을 유지한다. 브라우저 JS가 로그인 토큰을 읽거나 별도로 저장하지 않는다. 명시적인 UI의 목업 모드와 실제 로그인 세션도 합치지 않는다.

### 일시적 상태

- React state/ref/context에는 폼 초안, 모달, 선택한 아이·날짜, 업로드/조회 진행, API 응답의 메모리 캐시를 둘 수 있다. 이는 업무 데이터의 영구 저장소가 아니다.
- URL에는 라우트·공유 가능한 조회 조건만 둔다. 인증정보·복구 토큰·파일 바이트·민감한 본문을 URL에 넣지 않는다.
- File/Blob, 녹음 조각, 전송 대기 좌표는 메모리에만 두고 사용 후 해제한다. Object URL은 미리보기 수명에 맞춰 revoke하며 DB 주소로 취급하지 않는다.
- 새로고침 후 복원은 서버 조회로 한다. 진행 중인 산책 복원 등 필요한 API가 없으면 별도 서버 계약을 먼저 준비한다. 기존 LocalActiveWalkStore를 지우면서 복원 기능이 유지된다고 주장하지 않는다.
- 메모리에서 아직 전송하지 않은 데이터는 새로고침/탭 종료 시 유실될 수 있다. UI 경고·작업 취소/종료 흐름을 준비하며 오프라인 영구 큐는 이번 범위에 두지 않는다. 백엔드의 진행 중 산책 만료/중단 정책과도 맞춘다.
- 로그아웃·계정 변경·권한 회수 시 조회 캐시와 민감한 입력·버퍼를 비운다. 요청의 서버 권한 검사는 항상 별개로 유지한다.

## 4. 제안 폴더 구조

Next.js App Router·React·TypeScript를 유지한다. 새로운 상태 관리·쿼리·목업 라이브러리 도입을 이번 문서만으로 확정하지 않는다.

```text
frontend/
├─ src/
│  ├─ app/                       # Next 라우트·layout·전역 스타일·최상위 UI provider
│  │  ├─ (auth)/                 # 기존 공개 인증 URL 유지
│  │  └─ (app)/                  # 기존 로그인 화면 URL 유지
│  ├─ features/
│  │  ├─ member/                 # 로그인·내 정보·복구 화면
│  │  ├─ pet/                    # 반려동물 관리·모드 선택
│  │  ├─ diary/
│  │  │  ├─ components/          # 일기 폼·목록·달력·상세
│  │  │  ├─ hooks/               # UI 상태와 API 호출 수명 관리
│  │  │  ├─ api/                 # diary API 함수·요청/응답 변환
│  │  │  ├─ types/               # 서버 DTO와 화면 props 타입
│  │  │  └─ utils/               # diary 표시·입력 보조만
│  │  ├─ question/
│  │  ├─ media/                  # 업로드/녹음 UI·브라우저 작업
│  │  ├─ map/                    # 지도 표시·산책 상호작용
│  │  ├─ family/
│  │  ├─ community/
│  │  ├─ admin/                  # 여러 관리 기능을 조합하는 화면
│  │  └─ mypage/
│  ├─ components/                # 공통 버튼·모달·레이아웃·브랜드 UI
│  ├─ hooks/                     # 공통 UI 훅·미저장 경고 등
│  ├─ lib/
│  │  ├─ http/                   # 공통 fetch·오류·요청 취소·인증 쿠키 전송
│  │  └─ browser/                # 파일·음성·위치 API 등 기술 보조
│  ├─ types/                     # 실제로 공통인 API 오류·페이지 응답 등
│  └─ styles/                    # 디자인 토큰·공통 스타일
├─ mocks/                        # 운영 기능에서 독립된 목업 전용 영역
│  ├─ fixtures/                  # member/pet/diary/question/... 고정 응답 데이터
│  ├─ scenarios/                 # 빈 목록·오류·권한 거부·처리 중 등 응답 조합
│  ├─ handlers/                  # API 요청에 정해진 응답을 돌려주는 대역
│  ├─ assets/                    # 목업 전용 이미지·음성, 브랜드 원본과 분리
│  └─ setup.ts                   # 개발/테스트의 명시적 목업 활성화·초기화
├─ public/                       # 실제 서비스 정적 자산·브랜드 이미지
└─ tests/                        # UI/API 연결·브라우저 상호작용·경계 검사
```

모든 기능에 다섯 하위 폴더를 의무적으로 만들지 않는다. 실제 파일이 생길 때 필요한 폴더만 추가한다. 도메인 폴더 이름은 문서·백엔드의 `member`, `pet`, `diary`, `question` 등과 맞춘다. URL의 `/pets`, `(auth)` 등은 API/라우트 계약이므로 폴더 이름 통일을 이유로 바꾸지 않는다.

질문 원본 관리 화면은 question 기능을 사용하고 `/questions/admin` API를 호출한다. admin 아래에 별도 질문 원본 API나 저장소를 중복 구현하지 않는다.

### 호출과 의존 방향

```text
app 라우트 → 기능 화면·훅 → 기능 API 함수 → 공통 HTTP → 백엔드
                    └→ 브라우저 API·표시 보조
```

- app은 화면 조합·라우팅·provider만 담당한다. 업무 유스케이스 조립용 composition root를 새 이름으로 옮기지 않는다.
- 화면/훅은 필요한 기능 API 함수를 호출할 수 있다. HTTP 함수는 React를 몰라야 하며 검증·정책 엔진을 포함하지 않는다.
- hooks는 상태/수명/호출 순서의 UI 편의를 제공하며 createDiaryUseCases 같은 업무 서비스를 대체하는 이름이 아니다.
- 기능 간에는 꼭 필요한 공개 화면·타입·API만 참조한다. 여러 기능을 조합하는 화면은 app이나 해당 조합 화면에서 구성하고 거대한 전역 업무 state를 두지 않는다.
- 공통 components/hooks/lib는 features나 mocks의 업무 데이터에 의존하지 않는다. 공유 여부가 분명하지 않은 코드는 먼저 기능 내부에 둔다.
- Next 서버 컴포넌트·Route Handler·Server Action에 저장·권한·질문 진행을 옮겨 “프론트 백엔드”를 만들지 않는다. 업무 실행은 기존 백엔드 API로 보낸다.

## 5. 목업 데이터와 응답 대역

### 정상 실행과 목업 실행의 분리

- 기본 실행은 실제 API다. 목업은 개발·테스트에서 명시적으로 켠 경우에만 사용하고, 운영 빌드는 목업 활성 설정을 허용하지 않는다.
- 활성화는 초기 진입 지점 한곳에서 처리한다. 일반 화면·API 모듈은 fixture를 import하거나 사용자 ID 형식으로 서버/목업을 선택하지 않는다.
- 일반 계정·숫자가 아닌 petId·서버 오류를 목업 활성 신호로 사용하지 않는다. 실제 요청이 실패했다고 목업 목록이나 성공 응답을 대신 보여 주지 않는다.
- 로컬 미구현 기능을 개별 목업으로 표시하려면 기능/엔드포인트 허용 목록을 setup에서 명시하고, 화면에 목업임을 표시한다. 실데이터와 목업 데이터를 한 목록에 합치거나 실제 ID로 목업 쓰기를 처리하지 않는다.
- 개발 목업과 실제 로그인/서버 쿠키는 함께 사용하지 않는 모드를 기본으로 한다. 모드 전환 시 요청·캐시·메모리 fixture 상태를 초기화하며 운영 서버를 잘못 호출하지 않게 한다.
- 운영에서 누구나 쓰는 체험 모드가 필요하다면 별도 제품 요구와 서버/인프라 계약을 정한다. 이 문서가 브라우저 기반 운영 데모 저장소의 존속을 승인하는 것은 아니다.

### 목업 내부의 기준

- 데이터와 응답은 기능별 fixture에 두고 페이지·컴포넌트·실제 API 함수에 하드코딩하지 않는다.
- 목록·상세·작성 결과·빈 상태·403·409·처리 중 등을 미리 정의한다. 실제 API와 같은 DTO를 사용해 화면 계약을 확인한다.
- 질문 배정·가족 권한·하루 제한·업무 날짜 판단을 목업에서 다시 구현하지 않는다. 해당 결과를 fixture/시나리오로 선택한다.
- 폼 상호작용 확인용 임시 메모리 변경은 목업 내부에서만 허용한다. 실제 업무 처리·영구 저장의 성공으로 표시하지 않으며 새로고침/초기화로 사라진다. localStorage 등에 목업 업무 데이터를 저장하지 않는다.
- 테스트 시나리오마다 fixture 상태를 초기화해 계정·테스트 간 상태가 섞이지 않게 한다. 목업 정리 중 실제 서버 데이터 삭제 API를 호출하지 않는다.
- 목업 전용 자산은 mocks/assets에 모으고 public의 브랜드 로고·실서비스 정적 이미지는 유지한다. 기존 자산의 실사용 여부를 확인하지 않고 일괄 이동/삭제하지 않는다.

## 6. 현재 코드에서 무엇을 바꿀지

아래는 현 구조를 조사한 이동·제거 기준이며 지금 파일을 옮긴다는 뜻은 아니다.

| 현재 영역 | 개편 방향 |
| --- | --- |
| `src/*/adapters/inbound` | 기능 화면은 features/<도메인>/components, UI 훅은 hooks, 실제 공통 요소만 공통 폴더로 이동 |
| `src/*/adapters/outbound/Http*` | 요청/응답 변환을 기능 api 함수로 단순화. 불필요한 Repository 인터페이스·위임 계층 제거 |
| `src/*/domain`, `application`, `ports`, `useCases` | 타입·표시/브라우저 보조는 새 위치로 분류. 업무 판단은 서버 계약으로 이전하고 운영 프론트에서 제거 |
| `workspace` | 아이 선택·공통 레이아웃과 diary/question/pet UI로 해체. 별도 공통 기록 저장소를 만들지 않음 |
| `life` | community/family/member/엽서 등 실제 기능으로 해체. 공유 업무 state나 통합 브라우저 저장소를 유지하지 않음 |
| `auth`, `pets` | 인증 UI는 member, 아이 관리 UI는 pet. 실제 API 호출과 현재 세션 표시 분리 |
| `BrowserWorkspaceRepository`, `BrowserLifeRepository`, `SharedWorkspaceRepository` | 실제 기능의 로컬 CRUD/권한 처리를 제거. 화면용 샘플만 mocks로 이동하고 업무 규칙 자체는 옮기지 않음 |
| `Demo*Repository`, `demoQuestions`, `demoWalkSamples`, 샘플 엽서 | mocks/fixtures·scenarios·handlers로 모으고 사용자 계정에 따른 자동 분기 제거 |
| `SessionAuthRepository`, `PetScoped*Repository` | 정상 기능의 저장소/세션 출처 혼합 제거. 실제 API와 명시적 목업 실행 분리 |
| `LocalActiveWalkStore`, 브라우저 저장 이관 코드 | 서버 복원 계약·기존 데모 데이터 처리 확인 후 운영 저장 경로 제거 |
| `shared/ui`, 스타일·브라우저 보조 | 실제 역할에 따라 components/styles/lib/browser로 분류. 디자인 토큰 값과 화면 동작은 구조 이동만으로 바꾸지 않음 |
| `app/composition.ts`, 거대한 AppProvider | 업무 의존성 조립 제거. 인증 조회·선택 상태·알림 같은 UI provider만 필요한 범위에 둠 |

유틸리티·타입·사용 중인 UI를 “헥사고날 폴더에 있었다”는 이유만으로 삭제하지 않는다. 현재 호출부, 동작, 서버 대체 경로를 확인한 뒤 이동·대체·제거를 결정한다.

## 7. 단계별 전환 순서와 선행 조건

1. **인벤토리와 API 대응표**
   - 화면별 라우트, 업무 동작, 호출 코드, 브라우저 저장 키, 데모 데이터, 보유 테스트, 대응 서버 API를 목록화한다.
   - 서버 API가 없는 기능은 담당자·계약·구현 이슈를 연결한다. 화면이 있다는 이유로 백엔드 구현 완료로 판단하지 않는다.
   - 기존 URL·일상/정원 레이아웃·반응형·질문/다이어리 분리·카테고리 선택 같은 사용자 동작을 보존 기준으로 기록한다.
2. **공통 HTTP·UI 경계와 목업 부트스트랩**
   - 실제 API와 목업 실행을 분리하고 공통 오류/401/403 처리·요청 취소를 연결한다.
   - 기존 화면이 참조하는 코드는 이동 단계에서 한 개의 임시 재export를 쓸 수 있으나, 양방향 import·새 로컬 저장 기능은 금지한다. 해당 기능 이전 PR에서 호출부까지 정리해 임시 경로를 제거한다.
3. **인증·아이 화면부터 기능별 이전**
   - 서버 계약이 준비된 기능부터 components/hooks/api/types로 옮긴다. 라우트는 유지하고 실제 API 결과를 표시한다.
   - 기능 단위로 기존 계층·로컬 업무 처리·fixture 직접 참조를 제거하고 같은 역할을 두 위치에 남기지 않는다.
4. **질문·다이어리·업로드·지도 등으로 확대**
   - 실제 업로드→검증 상태 확인→본문 저장 흐름을 연결한다. 실패 시 입력 유지·허위 성공 방지·인증된 파일 열람을 확인한다.
   - 지도 수동 위치·사진 동의·산책 버퍼/복원은 기존 계약과 서버 준비 상태에 맞춰 연결한다.
5. **나머지 기능·레거시 경로 정리**
   - 가족·커뮤니티·엽서·관리자·마이페이지를 각 담당 API와 연결한다. API가 없는 동작은 목업 전용 화면이나 명시적 미지원으로 구분하고 실제 모드에서 성공시켜 두지 않는다.
   - 기존 헥사고날 경로·미사용 포트·대체 완료된 브라우저 저장·목업 혼합 코드를 정리한다.
6. **문서·테스트·운영 경계 확인**
   - 기존 청사진의 구조 기준, 소스 링크, 경계 테스트를 새 구조에 맞춘다. 테스트 범위 대응표와 실제 확인 결과를 작성한다.
   - 최종적으로 운영 경로가 목업과 브라우저 업무 저장소를 사용하지 않는지 확인한다.

각 단계는 작은 PR로 나눈다. 구조 이동과 신규 백엔드 기능 개발·디자인 변경을 한 PR에 섞지 않는다. 서버가 준비되지 않은 기능을 당장 삭제하지 않고, 전환 전제와 남은 의존성을 이슈에 공개한다.

### 기존 브라우저 데이터 처리

이 문서는 기존 사용자의 브라우저 데이터를 삭제하거나 서버로 자동 업로드할 권한을 부여하지 않는다. 데이터 키·이관 테스트를 조사하고 실제 사용 데이터인지 확인한 뒤 별도 정책을 승인받는다. 새 운영 코드가 해당 값을 읽거나 쓰는 경로는 제거하되, 보존/내보내기/사용자 동의 이관/삭제 중 어떤 처리를 할지는 구현 전 확정한다. 기존 브라우저 데이터가 서버에 옮겨졌다고 안내해서는 안 된다.

## 8. 완료 조건과 검증 범위

| 확인 항목 | 확인 방법 |
| --- | --- |
| 라우트·레이아웃·접근성 유지 | 주요 PC/모바일 화면과 키보드 흐름 직접 확인. 이동 전후 경로·빈/로딩/오류 상태 비교 |
| 실제 저장은 서버만 수행 | 브라우저 저장 API·로컬 CRUD·클라이언트 업무 ID 생성의 호출부 검색 + 실제 API 저장/실패 흐름 검사 |
| 업무 규칙 중복 제거 | 권한·질문 선택·등록일·가족 역할·생성 제한을 실행하는 운영 코드가 없는지 검토. 실제 업무 검증은 해당 백엔드 테스트로 확인 |
| UI 상태·요청 수명 | 폼 입력/미저장 경고, 취소·중복 클릭·계정/아이 전환·오래된 응답 방지 테스트 |
| API 연결 | 요청 method/path/query/body, DTO 변환, 401/403/409/503 처리, 재조회·캐시 초기화 검사 |
| 목업 분리 | 일반 실행의 API 실패/로컬 ID에서 fixture가 나오지 않고, 목업 초기화 후 상태가 비며 운영 모드에서는 활성화가 거부되는지 검사 |
| 첨부·음성·산책 | 파일 미리보기 해제·동의/GPS 전처리·녹음 중단·전송 재시도·새로고침 복원/미전송 유실 안내 확인 |
| 이전 구조 제거 | 신규 운영 코드에서 domain/application/ports/adapters·Browser*Repository·Demo* 혼합 경로 import와 남은 미사용 코드 확인 |

기존 `hexagonal-architecture.test.ts`는 파일을 지웠다고 끝내지 않고 새 의존/목업/저장 경계 검사로 대체한다. 기존 workspace/life/question/산책 등의 테스트도 업무 검증·목업 시나리오·UI/브라우저 동작으로 분류한다. 프론트 업무 테스트를 없애는 경우 대응하는 실제 백엔드 검사와 API 연결 확인 위치를 [검증 범위 대응표](../testing-coverage.md)에 기록하고, 단순 fixture 성공을 업무 시나리오 검증으로 주장하지 않는다. 자동 확인에서 빠지는 동작도 명시한다.

변경 범위에 맞는 `npm run lint`, `npx tsc --noEmit`, 관련 테스트를 실행한다. 폴더/모듈 경계·설정 변경 단계에서는 Next 빌드로 라우트/서버·클라이언트 경계가 유지되는지 확인하고, 전체 반복 검사는 [검증 기준](../testing.md)을 따른다. Next 코드 변경 전에는 [frontend/AGENTS.md](../../frontend/AGENTS.md)가 지정하는 설치된 버전의 로컬 가이드를 읽는다.

## 9. 구현 전 확인할 사항

- 기능별 실제 API 준비 상태와 각 담당의 연결 일정. 가족 API는 가족 담당 범위이며 프론트 구조 작업에서 새로 구현하지 않는다.
- 진행 중 산책의 서버 복원과 미전송 데이터 유실 UX, 아직 없는 조회 계약.
- 브라우저 기존 데이터 보존·이관 정책. 사용자의 별도 동의 없는 자동 업로드/삭제는 하지 않는다.
- 목업 실행 수단·설정 이름·운영 차단 방법. 의존성 추가가 필요하면 선택 근거와 영향 범위를 구현 계획에서 정한다.
- 운영 체험 모드 존속 여부. 기본 제안은 mocks를 개발·테스트 전용으로 제한하는 것이며, 기존 체험 기능 전환은 제품 담당 확인 후 진행한다.

지금 확정한 것은 프론트/백엔드 책임과 구조 개편 방향이다. 위 확인 사항은 현재 제품 코드를 즉시 제거해도 된다는 승인이 아니며, 구현 착수 전에 이슈·PR로 구체화한다.
