# 모바일 화면을 공통으로 사용하는 전체 프론트 디자인 개편

관련 이슈: [#233](https://github.com/likelion-backendschool-9th/pawmento/issues/233).

## 목표와 확정 사항

전체 프론트의 화면·탐색·상태 표현을 점검하고 누락된 화면을 디자인한다. **이번 작업은 디자인과 목업 상호작용이며 새 API 연결은 하지 않는다.** 이전의 다이어리·질문 우선/API 연결 계획을 아래 사용자 결정으로 대체한다. 기존에 연결된 API를 끊거나 목업으로 교체한다는 뜻은 아니다. (고침 #233: 전체 디자인으로 확대, API 연결은 후속으로 분리)

- #233-R1 PC에서도 모바일과 같은 화면·폭·탐색·배치를 표시한다. PC 전용 사이드바·다열 대시보드·목록/상세 분할 화면을 만들지 않는다. (고침 #233: PC 확장 배치 대신 모바일 화면 그대로 사용)
- #233-R2 상단/사이드 전역 nav를 제거하고 모바일 하단 메뉴바를 모든 화면 크기에서 유지한다. 하단 ‘더보기’ 자리는 **정보 지도**로 정한다. 상세 뒤로 가기·프로필·아이 선택 같은 화면 동작은 필요한 위치에 유지한다.
- #233-R3 다이어리와 오늘의 질문은 독립 화면이며 현재 메뉴 하나만 활성화한다. 다이어리 진입 시 오늘의 질문까지 활성화되는 문제를 수정한다.
- #233-R4 가든 홈의 첫 화면은 사용자 제공 첫 번째 이미지(코기가 밤하늘을 바라보는 그림)로 가득 채운다. 기존 홈 내용은 아래로 이동한다. 빛나는 작은 나비를 누르면 선택한 아이의 일기 또는 질문·답변 기억을 무작위로 보여 준다.
- #233-R5 브랜드 로고는 사용자 제공 두 번째 이미지(책 위 여러 동물·잎·별 로고)로 교체한다. 기존 모드별 코기/정원 로고 교체 규칙을 대신하며 새 이미지를 재생성하지 않는다.
- #233-R6 기존 설계에 있는 화면에 한정하지 않고 인증·홈·반려동물·다이어리·질문·미디어·엽서·지도·가족·커뮤니티·마이·설정·관리자의 디자인과 누락 UI를 포함한다.
- #233-R7 실제로 불필요해진 코드·스타일만 정리한다. 현재 기능·데모·호환 URL·다른 담당의 API 연결을 보존한다.

이 문서는 구현 전 검토안이며 문서 PR 승인 후 제품 코드를 수정한다. 이번 계획에서 새 서버 기능·권한·저장 정책을 결정하지 않는다. [프론트 책임과 목업 분리](README.md)는 유지하고, 예전 디자인과 충돌하면 이 문서의 사용자 확정 사항을 우선한다.

## 코드 점검과 범위

계획 작성 시 Next 라우트·레이아웃, 기능별 화면 컴포넌트, composition/provider, 공통 UI·테마, API 모듈, 목업 구성과 정적 import 관계를 확인했다. 이 점검은 모든 런타임 분기·브라우저 동작을 검증한 결과가 아니다. 기능별 실제 사용과 디자인 회귀는 구현 단계에서 확인한다.

- AppShell의 navigationRoute와 SpaceShell의 질문 active 조건 모두 diary 경로를 질문에 포함한다. 하단 메뉴의 활성 규칙을 하나로 통합하고 일기/질문이 겹치지 않게 한다.
- SpaceShell은 모드에 따라 우체통을 목록 중간에 삽입한 뒤 앞 네 개와 지도를 선택한다. 그 결과 모드에 따라 주요 메뉴가 밀릴 수 있어 고정 항목으로 교체한다. 현재 코드의 마지막 칸은 이미 지도이므로 이름을 정보 지도로 명확히 하고 ‘더보기’가 남은 다른 분기도 함께 확인한다.
- frontend/README와 일부 문구에는 과거 헥사고날·EDITOR/VIEWER·영상 데모 설명이 남아 있다. 실제 코드/보존할 데모와 대조해 범위가 맞지 않는 안내를 갱신한다.
- 다이어리 타입·공유 편집기에는 필수 제목이 없고 질문 이력은 데모 답변 중심이다. 서버 계약에 맞는 **필드와 누락 화면**을 먼저 디자인하되 이번 단계에서 실제 저장 API를 연결하지 않는다.
- AppProvider/composition은 인증·반려동물·지도 등 서버 연결과 workspace/life 목업이 공존한다. 기존 세션·저장 방식의 변경은 이번 디자인 작업에 포함하지 않는다.
- 앱 진입점에서 정적 참조를 추적한 결과 기능·공통 UI 파일 중 미참조라고 확정할 후보는 나오지 않았다. 도달 가능성이 파일 내부의 모든 함수/스타일 사용을 뜻하지는 않는다. “오래된 파일”이라는 이유로 삭제하지 않는다.

## 모바일 화면과 공통 탐색

### PC도 같은 화면

- 앱 폭은 최대 480px을 초기 디자인 기준으로 하고 좁은 화면에서는 100%를 사용한다. PC에서는 같은 앱 화면을 중앙에 두고 바깥은 중립 배경으로 채운다. 기기 테두리·가짜 상태바는 넣지 않는다.
- PC에서도 상단 nav·사이드바·두 열 편집기를 추가하지 않는다. 페이지·폼·바텀시트·하단 메뉴의 위치와 순서가 모바일과 같다.
- 고정 헤더/메뉴·시트는 브라우저 전체 폭이 아니라 앱 컨테이너 폭을 따른다. 지도·이미지도 앱 밖으로 늘어나지 않는다.
- 실제 화면 높이는 svh/dvh 및 safe-area를 고려한다. 키보드가 열리면 입력과 저장 버튼을 볼 수 있고, 내부 이중 스크롤과 불필요한 가로 스크롤을 피한다.

### 하단 메뉴와 제거되는 nav

- 상단 가로 전역 메뉴·사이드 메뉴·전체 메뉴 드로어를 제거한다. 화면 제목·뒤로 가기·브랜드·프로필·선택한 아이 버튼은 nav를 대신하는 긴 메뉴 목록으로 만들지 않는다.
- 하단 메뉴는 초기안으로 **홈 / 다이어리 / 오늘의 질문 / 커뮤니티 / 정보 지도** 5개를 두고 일상/가든에서 항목·순서를 고정한다. 확정 사항은 하단 유지·더보기→정보 지도이며 나머지 항목은 이 문서 PR에서 검토한다.
- 다이어리·달력·미디어·호환 기록 경로는 다이어리만 활성화한다. 질문 회차·질문 답변·답변 작성/수정은 오늘의 질문만 활성화한다. 정보 지도 `/places`는 마지막 항목이며 개인 기록 지도는 원본 기록 진입 관계에 맞춰 별도로 표시한다.
- 프로필 버튼은 마이로 연결하고 마이 안에 반려동물·가족·설정·설치·활동·관리자 진입을 제공한다. ‘더보기’ 탭 삭제 때문에 이 기능들이 사라지지 않게 한다.
- 우체통은 가든 홈의 아래 영역과 마이/아이별 기능에서 접근하고 하단 메뉴 중간에 끼워 다른 항목을 밀어내지 않는다. 일상에서는 가든 전용 기능을 노출하지 않는다.
- 반려동물별 모드 전환은 관리 화면에서만 제공한다. 모드는 색·문구로도 식별하며 색만으로 구분하지 않는다.

## 가든 홈: 밤하늘과 나비의 기억

### 사용자 제공 이미지

- 첫 번째 이미지: 세로 밤하늘·꽃·코기 그림을 가든 홈의 기본 배경으로 그대로 사용한다. 비슷한 새 그림·AI 이미지·CSS 대체 그림을 만들지 않는다.
- 두 번째 이미지: 책·강아지·고양이·새·작은 동물·별이 있는 로고를 공통 브랜드로 사용한다. ACTIVE/GARDEN 및 인증/앱 화면에서 동일한 브랜드 원본을 쓴다.
- 구현 시 원본 파일 경로를 확인하고, 브랜드·배경·PWA 아이콘의 쓰임을 구분한다. 첨부 이미지와 일치하는 파일을 확인하기 전 임의 파일로 대체하지 않는다.
- 로고의 주변 여백이 많으므로 표시 영역/크롭을 검토하되 원본을 덮어쓰지 않는다. PWA 아이콘·maskable 용도는 별도 출력 규격을 확인하며 공통 로고 교체와 혼동하지 않는다.

### 첫 화면과 아래 영역

- 첫 화면은 밤하늘 배경을 앱의 가로·세로 공간에 가득 채운다. PC에서도 동일한 모바일 폭에서 같은 그림이 보인다.
- 코기·밤하늘·꽃을 가리는 큰 카드·통계·긴 문구는 첫 화면에서 내린다. 로고·아이 선택/프로필은 작게 배치하고 필요하면 대비를 위한 최소한의 반투명 배경을 사용한다.
- 배경은 비율을 유지한 cover를 기준으로 코기와 주요 영역이 살아 있는 위치를 조정한다. 이미지 안에 원래 그려진 나비는 시각 요소이고, 눌리는 위치에는 실제 버튼을 배치한다. 화면 크기마다 그림의 나비와 버튼이 어긋나는 문제를 직접 확인한다.
- 하단 메뉴는 계속 조작할 수 있게 유지하며 나비/그림의 주요 요소와 겹치지 않게 한다.
- 기존 홈의 질문·최근 일기·우체통 등 유효 기능은 첫 화면 아래 스크롤 영역에 정리한다. 삭제하거나 별도 PC 대시보드로 만들지 않는다.

### 나비를 눌렀을 때

1. 선택한 아이의 일기와 질문·답변 목업 중 열람 가능한 기억을 모은다. 다른 아이·계정의 데이터를 섞지 않는다.
2. 작게 빛나는 나비를 탭/클릭하거나 키보드로 실행하면 한 기억을 무작위로 골라 바텀시트로 보여 준다. PC도 같은 시트를 사용한다.
3. 일기는 제목·본문·사건 날짜·작성자·사진/음성 요약, 질문 답변은 질문 스냅샷+답변·실제 등록일·작성자·첨부를 표시한다. 두 종류를 혼동하지 않게 이름을 붙인다.
4. ‘원문 보기’는 정확한 diaryId/answerId 상세로 이동한다. ‘다른 기억’은 시트 안에서 다른 항목을 고르고 닫으면 원래 홈/스크롤/포커스로 돌아간다.
5. 항목이 여러 개면 직전 기억의 즉시 반복을 피한다. 하나뿐이면 그 기억을 보여 주며, 없으면 허위 샘플을 실제 기록으로 꾸미지 않고 빈 상태와 기록하기 진입을 제공한다.

이 무작위 선택은 **화면 데모 인터랙션**이며 서버 질문 배정·AI 생성·진행 완료·데이터 저장을 하지 않는다. API 연결 시에는 별도 계획에서 서버 접근/조회 범위를 확정한다.

### 기억 데이터 출처와 원문 이동

아이/기억 ID가 같아 보이는 것만으로 원문을 열지 않는다. 화면에 공급하는 항목은 출처(기존 데모·화면 프리뷰·서버), 세션/계정 범위, petId, 기억 종류, 원문 ID를 구분한다. ID 형식이나 API 실패 여부로 출처를 추측하지 않는다. (고침 #233: #235 리뷰의 데이터 출처별 상세 이동 보완)

| 출처 | 나비 후보·원문 보기 |
| --- | --- |
| 현재 세션에서 읽을 수 있는 기존 데모 기록 | 선택한 아이·현재 계정/기존 데모 공유 범위 안의 항목만 후보로 사용한다. 상세가 같은 출처의 같은 종류·아이·ID를 읽을 수 있을 때만 기존 diary/answer URL로 이동한다. |
| 새 디자인용 프리뷰 fixture | 명시적 프리뷰에서만 노출하고 ‘예시 기억’으로 식별한다. ‘원문 보기’는 같은 fixture를 읽는 프리뷰 상세/시트로 연결한다. 그런 상세가 아직 없으면 버튼을 숨기고 프리뷰임을 안내한다. 저장된 실제 기록처럼 기존 상세 URL에 임의 ID를 넣지 않는다. |
| 서버 기록 | 이번 디자인 단계에서 새로 가져오지 않는다. 이미 공급되는 서버 항목이 있어도 현재 상세 화면이 서버 출처를 지원하지 않으면 나비 후보에서 제외한다. 서버 상세 연결 전에는 로컬 상세 URL로 보내거나 같은 ID의 데모 기록을 대신 열지 않는다. |
| 삭제됨·출처 불명·아이/계정 불일치·접근 회수 | 후보에서 제외한다. 시트를 연 뒤 상태가 바뀌면 원문 버튼을 숨기고 이용할 수 없음을 안내한다. 후보가 없어지면 빈 상태로 돌아가며 새 API 호출/다른 계정 데이터로 보충하지 않는다. |

- 상세 링크를 그리는 시점과 실행하는 시점에 현재 출처·세션·아이 및 목적지의 열람 가능 상태를 확인한다. 계정/아이 전환 시 이전 후보와 열린 기억을 비운다. 이 UI 확인은 서버 권한 검사를 대체하지 않는다.
- 기존 데모 항목이 없다는 이유로 실제 로그인 화면에 프리뷰 fixture를 자동 주입하지 않는다. 서버/데모/프리뷰 ID가 우연히 같아도 같은 기억으로 취급하지 않는다.
- 프리뷰 상세의 URL/시트 구현 방식은 화면 구현 PR에서 정하되, 기존 실제 기록 라우트와 출처를 섞지 않는 위 기준을 지킨다. 모든 출처에 같은 ‘원문 보기’ URL을 무조건 붙이는 구현은 허용하지 않는다.

- 인터랙티브 나비는 장식 배경과 구분되는 작은 빛·포커스 링·눌림 상태를 가진 실제 button이다. 보이는 나비는 작아도 터치 영역은 44px 이상 확보하고 서로/메뉴와 겹치지 않는다.
- 빠른 반복 탭은 여러 시트를 쌓지 않는다. 시트의 포커스 진입·닫기·ESC·스크린리더 이름·음성 자동 재생 금지를 확인한다.
- 잔잔한 움직임과 빛은 허용하되 빠른 점멸을 피하고 prefers-reduced-motion에서는 정지시킨다. 캔버스나 이미지 클릭만으로 조작을 한정하지 않는다.

## 화면별 디자인·목업 상호작용

### 다이어리와 질문

- 다이어리는 `일기 / 달력`을 유지하고 목록·상세·작성/수정에 제목·작성자·날짜·첨부를 반영한다. 필수 제목·기존 무제목 조회/수정 보완 상태를 목업으로 표현한다.
- 질문은 현재 질문·미배정·회차 이력·회차 상세·가족 답변 페이지·내 답변 여부와 답변 가능 상태를 디자인한다. 신규 회차 상세 URL은 `/pets/[petId]/questions/prompts/[promptId]`로 제안한다.
- 답변 작성은 질문+본문+사진/음성이며 일기 제목·사건 날짜 입력을 섞지 않는다. 질문 등록일은 서버 계약 기준 안내를 사용하고 화면에서 임의로 변경하는 입력을 만들지 않는다.
- 폼에 기존 공유 편집기를 사용하더라도 화면별 책임을 분리하고 공통 파일 선택·녹음·이탈 확인 UI만 재사용한다.

### 목업 제목 입력과 현재 일기 API의 구분

[다이어리 제목 계약](../diary/title.md)은 이미 적용된 백엔드 기준이다. POST의 title은 필수이며 생략/null/빈 문자열/공백은 400이다. PATCH에서 기존 유효 제목의 생략은 유지이고 명시적 빈 값은 거절한다. 기존 무제목은 조회할 수 있지만 수정 저장에는 유효 제목을 제출해야 한다. 이번 디자인 계획으로 이 기준을 새로 결정하거나 변경하지 않는다. (고침 #233: #235 리뷰의 현재 서버 계약과 목업 범위 구분)

- 새 화면의 ‘제목 필수’는 이 계약에 맞춘 입력·검증 메시지·비활성/오류 상태의 목업 표현이다. 목업 완료는 실제 POST/PATCH 저장이나 서버 검증 통과를 의미하지 않는다.
- 기존 무제목 데모/fixture는 조회 시 ‘제목 없는 일기’로 표시하고 편집 시 제목 보완 상태를 보여 준다. 디자인 편의를 위해 기존 데이터에 본문 첫 줄·날짜로 제목을 자동 생성하거나 일괄 저장하지 않는다.
- 신규 화면 프리뷰의 저장/완료는 목업임을 구분하고 새 API 호출·실제 저장소 쓰기를 추가하지 않는다. 기존에 동작하는 데모 저장 흐름을 바꿀 필요가 생기면 해당 데이터 계약과 보존 범위를 구현 PR에서 따로 확인한다.
- 후속 실제 API 연결 단계에서 title·version 전달과 서버 400/409 처리까지 별도로 검증한다. 이번 목업 검사로 서버 연결 완료를 표시하지 않는다. 질문 답변에는 제목 필드를 추가하지 않는다.

### 나머지 화면과 빠진 상태

- 전체 점검표의 각 화면에서 모바일 목록→상세→작성/수정→완료/실패 흐름을 준비한다. 현재 API가 있어도 화면이 없으면 목업으로 새 화면과 진입 경로를 만든다.
- 로딩·빈 목록·필터 결과 없음·권한 없음·삭제된 항목·처리 중·재시도·업로드 실패·저장 충돌·연결 끊김 상태를 디자인한다.
- 기존 서버 연동 화면은 현재 요청/응답·세션 분기를 유지하며 JSX/CSS와 표시용 UI 상태만 바꾼다. 새 기능은 명시적 프리뷰/목업으로 식별하고 서버 저장 성공을 표시하지 않는다.
- 실제 API와 맞지 않는 목업 정책은 새 서버 기능처럼 확정하지 않는다. 가족 OWNER/FAMILY, 엽서 한도/처리 상태 등은 도메인 계약을 참고하되 업무 로직 변경·새 API 호출은 하지 않는다.
- 커뮤니티에 전체 카테고리를 되살리지 않고 추모 관련 카테고리를 의도치 않게 섞지 않는다. 엽서는 수채화·앞/뒷면·우표·종이 느낌을 유지한다.

## PWA·접근성·검증

- manifest/설치 안내/오프라인 안내와 기존 서비스워커 동작을 유지한다. 새 데이터 캐시·오프라인 쓰기·영구 업로드 큐는 도입하지 않는다.
- 360/390px 모바일·768px 태블릿·1440px PC에서 동일한 앱 폭/레이아웃·하단 메뉴를 확인한다. 긴 한국어·작성자·오류·키보드·safe-area·화면 회전에서 잘림/겹침이 없어야 한다.
- 화면 이동·모달·바텀시트·나비 버튼은 키보드와 화면 리더로 조작할 수 있어야 한다. focus-visible·대비·prefers-reduced-motion·음성 자동 재생 금지를 확인한다.
- 파일·녹음 프리뷰는 메모리 Blob/Object URL을 적절히 해제한다. 목업 단계의 업로드 진행/실패가 실제 파일 전송처럼 보이지 않게 한다.
- 테스트 결과와 화면별 스크린샷은 구현 PR에 둔다. 계획 문서 자체를 화면/실제 연동 완료 기록으로 쓰지 않는다.

## 구현 순서와 범위 밖

1. 전체 범위·하단 메뉴·PC 동일 화면·가든 나비·새 로고·API 제외를 이 문서 PR에서 확인한다.
2. 브랜드·공통 토큰·앱 폭·하단 메뉴·활성 상태를 정리한다.
3. 가든 홈과 나비 기억 시트를 먼저 구현해 실제 모바일/PC 화면을 확인한다. 일상 홈과 아래 영역도 함께 정리한다.
4. 다이어리·질문 누락 화면과 폼을 목업으로 완성한다.
5. 전체 화면 점검표의 나머지 화면을 같은 디자인으로 맞추고 누락 UI/상태·진입 경로를 보강한다.
6. 교체된 코드·스타일·문서·토큰·스크린샷을 정리하고 회귀 검증한다.

공통 레이아웃/브랜드, 가든 홈, 일기·질문, 나머지 화면을 나눠 리뷰 가능한 단위로 구현한다. 한 PR에 모든 화면을 무조건 묶지 않는다.

범위 밖: 새 API 연결·백엔드 수정·실제 데이터 이관/삭제·실제 AI 생성·가족 업무 구현·오프라인 동기화·서버 권한/질문 진행 정책 변경. 기존 연결된 API 보존과 디자인 회귀 점검은 포함한다.
