# 사진·음성 파일 업로드

질문·다이어리와 함께 구현할 공통 파일 도메인의 개발 설계 초안이다. 사용자는 두 기능에서 사진·음성 녹음을 첨부할 수 있어야 한다고 정했다. 저장소는 사용자 선택에 따라 Docker named volume으로 한다. 파일 크기는 사진·음성 모두 15MiB를 추천안으로 정리했고 나머지 제한·유효 시간은 검토할 제안이며, 업로드 자체는 후속 범위가 아니라 이번 구현 범위다.

## 범위와 책임

- 사진 선택과 브라우저 음성 녹음 결과를 파일로 업로드한다. 녹음도 하나의 AUDIO 파일이며 별도의 답변 본문 형식으로 저장하지 않는다.
- 실제 파일은 Docker volume의 비공개 파일 저장소, DB에는 메타데이터와 첨부 관계를 저장한다. base64/data URL·브라우저 blob URL을 영구 파일 주소로 저장하지 않는다.
- 업로드·검증·미리보기·가족 열람·미사용 파일 정리·삭제 재시도를 이번 범위에 포함한다.
- `media`는 파일 상태·검증·저장·조회 URL을 담당하고, diary/question은 각각 본문·작성자·첨부 순서와 부모 자원 권한을 담당한다. 질문과 다이어리 저장소는 통합하지 않는다.
- 프론트 새 첨부 메뉴는 사진 선택과 음성 녹음만 제공한다. 영상 선택·촬영·업로드 동작은 제거한다. 서버 허용 목록도 IMAGE/AUDIO로 맞춘다.
- 초기 대상은 `DIARY_ATTACHMENT`, `QUESTION_ANSWER_ATTACHMENT`다. 프로필·커뮤니티·AI 생성물은 별도 정책을 정한 뒤 확장한다.

## 저장 방식

**Docker named volume을 백엔드 컨테이너의 `/var/lib/pawmento/media`에 마운트한다.** PostgreSQL에는 자산 정보·연결 관계·검증/삭제 작업만 저장한다. S3 버킷·presigned URL·브라우저의 저장소 직접 PUT은 이번 구현에서 사용하지 않는다.

업로드는 JSON 세션 생성 → **파일 한 개씩 백엔드 multipart 업로드** → 검증 → READY → 일기/답변에 파일 ID 연결 순서다. 로컬·테스트는 동일한 저장소 포트의 임시 디렉터리/가짜 어댑터를 사용한다. 향후 S3로 옮길 수 있도록 물리 파일 접근은 `adapter/out/storage` 뒤에 둔다.

### 볼륨·배포 설정안

```yaml
services:
  backend:
    volumes:
      - pawmento_media:/var/lib/pawmento/media
    environment:
      PAWMENTO_MEDIA_ROOT: /var/lib/pawmento/media
volumes:
  pawmento_media:
    external: true
    name: pawmento-media
```

이 예시는 설계안이다. 실제 compose 서비스·배포 설정은 담당 파일과 맞춰 구현한다. external volume은 서버에서 한 번 준비하고 없으면 기동을 실패시킨다. 컨테이너의 비 root 실행 UID/GID에 쓰기 권한을 부여하고, 공개 static/nginx alias로 이 경로를 노출하지 않는다. `tmp/`, `files/`, `thumbnails/`를 서버 생성 상대 키로 구분한다.

Docker volume은 컨테이너 교체와 별개로 데이터를 보존하지만 서버 디스크 자체의 유실을 막아주는 백업은 아니다. 이 앱은 우선 **단일 호스트**를 전제로 하고 DB와 volume을 함께 백업·복구하는 절차를 둔다. 여러 서버로 확장할 때는 이 volume이 자동 공유되지 않으므로 저장 어댑터/인프라를 다시 정한다. [Docker 공식 문서](https://docs.docker.com/engine/storage/volumes/)

## 업로드부터 저장까지

1. OWNER/EDITOR가 대상 아이·용도·파일명·신고 MIME·예상 크기를 JSON으로 요청한다. 현재 가족 권한·파일당 제한·업로더의 미완료 건수/용량 한도를 검사한다.
2. 서버가 `assetId`, 재사용하지 않는 임시 파일 키와 세션 만료를 생성해 PENDING을 저장한다. 클라이언트 파일명·경로를 실제 저장 경로로 쓰지 않는다.
3. 브라우저가 파일 한 개를 multipart로 전송한다. 서버는 업로더·아이·현재 권한·세션을 확인하고 PENDING을 UPLOADING으로 조건부 변경한다. 전송 바이트 수를 제한하며 임시 파일에 스트리밍하고 전체를 메모리에 올리지 않는다.
4. 파일 수신 완료 후 PROCESSING과 검증 작업을 같은 DB 트랜잭션으로 저장한다. 응답은 202다. 처리 중 재업로드·다른 바이트 덮어쓰기는 409로 막는다. 응답 유실 시 상태 GET으로 먼저 확인한다.
5. 작업자는 임시 파일의 실제 크기·시그니처·파싱·재생 시간·이미지 픽셀 수를 검증한다. GPS 추출 후 이미지 서비스본 EXIF를 제거한다. 정상 파일은 같은 volume의 서버 전용 최종 경로로 저장하고 성공 후 READY로 갱신한다. 실패는 REJECTED와 정리 대상으로 바꾼다.
6. 파일 I/O/파싱 중 DB 잠금을 오래 잡지 않는다. 검증한 입력/생성한 서비스본만 최종 저장하며 READY 파일을 같은 키로 덮어쓰지 않는다. 파일 처리 중단·디스크 부족·DB 갱신 실패는 작업 임대·재시도·고아 파일 정리로 복구한다.
7. 프론트는 상태 GET에서 READY를 확인한 뒤 `attachmentIds`를 일기/답변 JSON에 보낸다. 녹음/전송/검증 중에는 저장 완료로 표시하지 않는다. 실패 시 입력·다른 첨부를 유지한다.
8. diary/question은 현재 가족·부모 권한, 자산의 업로더·아이·용도·READY를 다시 검사한다. 부모·첨부·media 참조 수 변경을 같은 DB 트랜잭션에 저장한다.
9. 질문 답변은 부모 저장 성공 시각이 등록일이다. 파일 업로드 시각과 다르며 첨부 연결 실패 시 답변·참조·가족 질문 진행을 모두 롤백한다.

수신이 끊긴 UPLOADING 파일은 작업 임대/만료 후 정리한다. 중간부터 이어 올리기는 이번 범위에 두지 않고 실패 파일만 새 세션으로 재업로드한다. 최종 파일 생성 후 DB 실패도 추적 가능한 키로 정리한다.

## 데이터 구조와 상태

`com.pawmento.media`의 `MediaAsset`과 `media_asset`을 둔다.

| 필드 | 의미 |
| --- | --- |
| `id` | 외부에 노출하는 파일 ID |
| `uploader_member_id`, `pet_id`, `purpose` | 누가, 어느 아이의 어떤 기능에 올렸는지. 생성 후 변경 불가 |
| `media_type` | IMAGE / AUDIO만 허용. 실제 검증 결과로 확정하며 영상 트랙은 거부 |
| `original_filename` | 화면 표시용 이름. 경로로 사용하지 않음 |
| `declared_mime_type`, `declared_size_bytes` | 업로드 요청값. 검증 완료 전 신뢰하지 않음 |
| `mime_type`, `size_bytes`, `duration_ms`, `width`, `height` | 실제 파싱한 값. 해당하지 않는 항목은 null |
| `temporary_storage_key`, `storage_key`, `checksum` | volume 루트 기준 서버 생성 상대 키와 검증 바이트 해시. 절대 경로·클라이언트 경로·URL 저장 안 함 |
| `status`, `failure_reason`, `version` | 상태·사용자 안내 가능한 실패 사유·조건부 갱신 버전 |
| 비공개 `media_asset_location` | `asset_id`, `latitude`, `longitude`, `source=EXIF`. 다이어리 사진만 추출하고 일반 자산 응답에서 제외 |
| `reference_count` | 일기/답변 첨부 연결 수. 0일 때만 미사용 정리 가능 |
| `created_at`, `upload_expires_at`, `ready_at`, `unattached_expires_at` | 세션·미연결 파일 수명 |
| `deletion_requested_at`, `deleted_at` | 삭제 작업 이력. 상세 재시도는 작업 테이블에 보관 |

상태는 `PENDING → UPLOADING → PROCESSING → READY`, 실패하면 `REJECTED`, 정리 대상은 `DELETING → DELETED`다. READY가 ‘글에 연결됨’을 뜻하지는 않는다. 연결은 `reference_count`와 도메인별 첨부 테이블로 구분한다.

- diary의 `record_attachment(record_id, asset_id, sort_order)`와 question의 `question_answer_attachment(answer_id, asset_id, sort_order)`를 유지한다. 각 테이블에 부모+파일 중복 및 부모+순서 유니크 제약을 둔다.
- 참조 수 변경은 media 입력 포트를 통해 호출하고 부모·첨부 행 변경과 같은 DB 트랜잭션으로 수행한다. 파일 I/O은 이 트랜잭션 밖이다. 실패 시 카운트만 남지 않아야 한다.
- 참조 획득과 정리 작업은 같은 자산 행의 잠금/조건부 갱신 규약을 따른다. 정리가 먼저 DELETING으로 바꾸면 연결을 거부하고, 연결이 먼저 성공하면 정리는 건너뛴다.
- 초기에는 같은 자산을 같은 아이·같은 용도·같은 업로더의 여러 글에 재사용할 수 있도록 제안한다. 다른 용도/아이로 복사하려면 새 업로드가 필요하다. 여러 연결 중 하나를 삭제했다고 원본을 지우면 안 된다.
- 참조 수와 실제 연결의 정합성 확인·복구 작업을 둔다. 잘못된 카운트만으로 실제 참조 파일을 삭제하지 않도록 삭제 직전 각 도메인의 참조 확인 포트를 사용한다.

## API 계약 제안

공통 `/api/v1` 접두사는 `WebConfig`가 적용한다. 컨트롤러에는 아래 나머지 경로만 쓴다.

| 요청 | 입력 | 응답 |
| --- | --- | --- |
| `POST /pets/{petId}/media/uploads` | JSON: `purpose`, `filename`, `mimeType`, `sizeBytes` | 201: `assetId`, `status=PENDING`, `expiresAt`, 인증 업로드 경로 |
| `POST /pets/{petId}/media/{assetId}/content` | multipart, 파일 파트 `file` **한 개만** | 202: PROCESSING과 검증 상태 경로 |
| `GET /pets/{petId}/media/{assetId}` | 없음 | 200: 상태·검증된 메타데이터·실패 사유. 업로더만 조회 |
| `GET /pets/{petId}/media/{assetId}/preview` | 없음 | 미연결 READY의 업로더용 파일 응답 |
| `DELETE /pets/{petId}/media/{assetId}` | 없음 | 미연결 파일 취소/정리 예약 202. 연결 파일은 409 |

가족의 파일 열람 경로는 다음과 같다. 부모 도메인이 매 요청마다 현재 읽기 권한·실제 첨부 관계·READY를 확인하고 media 포트로 파일을 스트리밍한다.

- `GET /pets/{petId}/diaries/{recordId}/attachments/{assetId}/content`
- `GET /pets/{petId}/question-answers/{answerId}/attachments/{assetId}/content`

일기/답변 `attachments`는 `assetId`, `type`, `filename`, `mimeType`, `sizeBytes`, `durationMs`, `width`, `height`, `sortOrder`를 반환한다. 프론트는 인증된 같은 출처 파일 경로로 표시·재생한다. 물리 경로를 반환하지 않는다. 정적 공개 파일 경로나 일회성 서명 URL을 DB에 저장하지 않는다.

파일 응답은 정확한 Content-Type·Content-Length, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`를 적용하고 `Range`/206·범위 오류 416·HEAD를 지원해 음성 탐색 재생을 검증한다. 가족 탈퇴 이후 새 요청은 거부하지만 이미 내려받은 파일과 이미 시작한 전송을 회수하는 기능은 아니다.

- 업로드 세션 10분·미연결 READY 24시간은 제안값이며 설정으로 관리한다.
- multipart는 JSON 전용이라는 기존 CSRF 전제와 다르다. 업로드 요청에 `X-Pawmento-Upload: 1`을 필수로 요구하고, 허용된 같은 출처의 요청만 받는다. 서버는 누락 헤더·다른 Origin을 거부하며 인증/헤더 검사를 multipart 파싱 전에 수행하도록 필터 순서를 검증한다. credential CORS를 임의 출처에 허용하지 않는다. 인증 담당과 이 변경을 함께 구현한다.
- 공통 `{code, message}` 에러를 유지한다. 401 로그인 없음, 403 쓰기/업로더/출처 거부, 404 비가족·없는 자원·무관한 첨부, 400 입력/파트 수 오류, 409 상태·용도·참조 충돌, 413 파일/요청 크기 초과, 415 형식 미지원이다. 비동기 검증 실패는 REJECTED로 조회한다.

### 요청 크기 설정안

파일 자체는 **15MiB = 15,728,640바이트 이하**이며 정확히 경계값은 허용한다. 초과는 1바이트라도 거부한다. 화면 표기는 ‘파일당 최대 15MB’로 단순화하되 도움말·API·검사는 이 바이트 값을 기준으로 통일한다. 15,000,000바이트를 뜻하는 decimal MB로 정하려면 전 계층을 함께 바꾼다.

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 15728640B
      max-request-size: 16777216B
      file-size-threshold: 0B
      location: /var/lib/pawmento/media/tmp/multipart
```

요청당 파일 하나를 받아 파일 제한 15MiB와 multipart 헤더 여유를 포함한 요청 제한 16MiB를 분리한다. 애플리케이션의 실제 읽기·검증도 15MiB를 검사한다. 생성된 서비스본도 15MiB를 넘으면 재처리하거나 거부한다. 설정 예시는 문서이며 아직 실제 application.yml은 바꾸지 않았다. [Spring Boot 공식 설정](https://docs.spring.io/spring-boot/appendix/application-properties/)

프록시/nginx도 최대 요청 본문 16MiB 이상으로 맞춘다(예: 20m). 여러 장을 한 요청에 합치지 않으므로 5장 합계가 75MiB여도 프록시 요청 하나가 75MiB가 되지 않는다. 두 nginx를 거치는 배포라면 양쪽을 확인하고 프록시의 413도 사용자에게 안내한다.

## 형식·크기·녹음 처리

| 분류 | 초기 허용안 | 제한 제안 |
| --- | --- | --- |
| IMAGE | JPEG, PNG, WebP | 파일당 15MiB, 최대 4천만 픽셀. 방향 보정·EXIF 위치 정보 제거한 서비스본 생성 |
| AUDIO | WebM/Opus, Ogg/Opus, MP4/AAC(M4A), MP3 | 파일당 15MiB, 재생 5분 |
| 공통 | 한 일기/답변에 종류 합쳐 최대 5개 | 첨부 합계 최대 75MiB(5 × 15MiB) |

파일당 15MiB는 사용자가 제안한 15MB를 바이트 단위로 명확히 한 추천안이다. 최대 5개·음성 5분·이미지 픽셀 수는 별도 제안이다. 용량과 시간 중 하나라도 초과하면 거부한다. 영상 업로드·재생·압축은 이번 구현 범위에서 제외한다. 프론트 localStorage의 2MB/30초 제한을 서버 규칙으로 복사하지 않는다.

- 확장자·신고 MIME·실제 컨테이너/코덱을 구분한다. SVG/HTML·실행 파일·파싱 실패·정책 초과 파일은 거부한다. 임시 디스크·파서 실행 시간·메모리 한도도 둔다.
- 녹음은 브라우저가 지원하는 MIME으로 생성한다. 실제 `Blob.type`을 요청하고 파일 확장자만 임의로 mp3로 바꾸지 않는다. 서버가 미지원 형식이면 녹음 전 안내하거나 지원 형식으로 다시 녹음한다.
- 다이어리 이미지의 GPS는 **EXIF 제거 전에** 서버에서 추출·검증해 비공개 `media_asset_location`에 보관한다. 범위·유한값·남북/동서 부호를 검사하고 0도도 유효 좌표로 취급한다. 위치 없음/손상은 후보 없음으로 처리하며 지원 이미지 자체가 정상이면 업로드는 성공한다. 일반 자산 응답·질문 답변 업로드는 GPS를 노출/활용하지 않는다. 지도는 업로드만으로 생성하지 않고 일기 저장 이후 연결한다. 자세한 계약은 [#44 사진 위치 연동](../map/photo-location.md)을 따른다.
- 이미지 서비스본의 메타데이터 제거·방향 보정을 포함한다. 음성의 위치/기기 메타데이터 제거는 파서·리먹싱 도구로 수행하고 정책을 검증한다. 일반 조회로 원본을 공개하지 않는다.
- 영상은 허용하지 않는다. `video/*` 신고값뿐 아니라 실제 영상 트랙이 있는 파일도 거부한다. 오디오용 MP4/WebM 컨테이너는 오디오만 있을 때 허용하고 영상 파일을 AUDIO로 신고하는 우회를 막는다. 음성의 지원 코덱 재생은 실제 PC·모바일에서 확인한다.
- 썸네일은 이미지 축소본만 만든다. 오디오 파형·전사는 후속이며 음성 파일·재생 시간과 재생 기능은 이번 범위다.

## 가족 권한과 보관

- 업로드 세션 생성·완료·글 저장 때마다 현재 멤버십과 쓰기 권한을 검사한다. 업로더 ID는 인증 회원에서 정하고 요청 본문으로 받지 않는다.
- 새 첨부는 본인 업로드만 연결한다. 수정 시 기존에 유효하게 연결된 첨부를 유지하는 동작과 타인의 새 파일을 추가하는 동작을 구분한다.
- 가족은 접근 가능한 일기/답변에 연결된 파일만 읽는다. 업로드 중·미연결 파일은 업로더만 볼 수 있다. 작성자와 업로더는 서로 다른 책임으로 보관한다.
- 가족 탈퇴 후 스트리밍·미리보기·업로드·새 첨부 연결 요청은 현재 멤버십으로 거부한다. 일반 사용자에게 volume 경로를 공개하지 않는다.
- 서버 생성 상대 키만 사용하고 루트 밖 경로·경로 순회·심볼릭 링크 추적을 거부한다. 저장 루트의 최소 파일 권한과 비 root 쓰기 권한을 적용한다.

## 취소·삭제·실패 복구

- 글 저장 전 취소는 미연결 파일 삭제 API로 예약하고, 호출이 없더라도 만료 배치가 정리한다. 취소는 일기·질문 답변 데이터를 만들지 않는다.
- 첨부 변경은 ID 전체 목록으로 교체한다. 유지·추가·제거 차이를 계산해 참조 수를 조정한다. 글 저장 실패 시 원래 연결과 참조 수를 유지한다.
- 글 삭제는 부모·첨부 연결 삭제와 참조 감소·삭제 작업 등록을 같은 DB 트랜잭션으로 수행한다. 작업 등록에는 outbox/삭제 작업 테이블을 사용해 프로세스 중단에도 누락되지 않게 한다.
- 자산 삭제 시 비공개 GPS 후보도 정리한다. 이 위치를 쓰는 일기의 수정/삭제와 지도 정리는 별도 최신 기록 이벤트로 처리하며, 자산 삭제 작업에서 임의로 다른 글의 핀을 지우지 않는다.
- 마지막 참조가 사라지면 자산을 DELETING으로 표시하고 작업자가 최종 파일·썸네일·임시 파일를 삭제한다. 저장소 장애는 재시도하며 글을 되살리지 않는다. 이미 없는 파일 삭제는 성공으로 취급한다.
- 만료 PENDING, 장시간 PROCESSING, 미연결 READY, REJECTED, volume에만 남은 고아 파일를 정리한다. 작업 임대·시도 횟수·최종 오류를 기록하고 영구 실패는 운영자가 확인할 수 있게 한다.
- 임시 디렉터리/고아 파일 정리는 앱의 배치로 관리한다. DB 정합성 확인 없이 최종 디렉터리 전체를 만료 삭제하지 않는다. 디스크 사용률·미완료 업로드 수·업로더별 임시 사용량·동시 업로드 수를 제한/관찰하고, 용량 부족 시 새 업로드를 거부하되 기존 파일과 글은 보존한다.
- 배포 때 미디어 volume을 초기화하거나 다른 Compose 프로젝트 이름으로 새 volume을 만들지 않는다. 서비스 파일·썸네일·GPS 후보/메타데이터의 DB를 일관되게 백업하고 실제 복구를 확인한다.

## 헥사고날 경계·구현 순서

`com.pawmento.media` 아래 domain/application/adapter 규칙을 따른다. JPA 엔티티·파일 시스템 경로·MultipartFile·브라우저 MIME 처리 객체가 핵심 계층으로 새지 않도록 한다.

1. 개발 이슈·형식/용량·권한·저장소 계약 확정. 실제 named volume 준비·권한·백업 절차는 배포 담당과 연결한다.
2. `MediaAsset` 상태·저장소 포트·volume/테스트 어댑터, JSON 업로드 세션·multipart 파일 전송·15MiB 제한·CSRF 검사·만료 처리.
3. 검증 작업자·완료/상태 조회·불변 최종 저장·썸네일·비공개 열람.
4. `AcquireMediaReferencesUseCase`, `ReleaseMediaReferencesUseCase` 등 내부 포트와 트랜잭션 규약을 정의해 diary/question 첨부 저장과 연결.
5. 취소·미사용 정리·outbox 삭제·실패 재시도·참조 정합성 검사.
6. 프론트 공통 업로더·미리보기·녹음·재생과 일기/답변 저장 흐름 연결.

media에서 부모 참조 확인이 필요하면 출력 포트와 각 도메인의 입력 포트를 조합하는 어댑터를 사용한다. 도메인끼리 서로의 JPA 저장소를 직접 참조하거나 Spring 서비스 빈을 순환 주입하지 않는다. 같은 DB 트랜잭션을 공유할 내부 포트와 정리 검사의 의존 방향을 구현 이슈에서 명시한다.

## 아직 정하지 않은 것과 범위 밖

- 저장소는 Docker volume으로 정했다. 15MiB 단위·최대 5개·재생 시간·TTL의 추천값과 실제 volume 이름·UID/GID·디스크 경보·백업 일정을 확정한다.
- 악성코드 검사 도구·미디어 파서·EXIF 제거 도구·이미지 썸네일 도구와 배포 자원 한도를 정한다. 선택한 실제 라이브러리·도구의 공식 문서와 라이선스는 구현 이슈에서 확인한다.
- 영상 업로드·재생·썸네일·트랜스코딩/HLS, S3 multipart/이어 올리기, CDN, 음성 전사·파형 분석은 초기 범위 밖이다. 사진과 음성 녹음 업로드·열람/재생만 포함한다.
- 아이/회원 삭제와 가족 탈퇴 시 파일·작성자 데이터 보존은 각 도메인 정책과 맞춘다. 파일은 현재 권한을 확인하는 인증 스트리밍으로 제공하며 이미 내려받은 파일 회수는 범위 밖이다.
