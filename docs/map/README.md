## 정한 것

- 지도는 별도의 산책 앱이 아니라 기록을 보는 방식의 하나다. 기록(일기·사진)에 장소를 붙이고 지도에서 다시 본다. (#19)
- 위치는 다이어리(기록)와 연동한다. 지도 쪽에는 기록 id와 위치에 관한 값만 저장하고 기록의 내용과 사진은 다이어리가 가진다. 지도에서 필요한 값을 사용자가 다시 입력하거나 같은 데이터가 두 곳에 생기지 않게 하기 위해서다. 여기서 기록 ID(`diaryId`)는 실제 diary 일기의 서버 발급 ID이며 질문 답변 ID와 별개다. PR #64에서 임시 record·memory 패키지와 `/records`·`/memories` API를 제거했으므로 샘플 엔티티나 입력 포트에 의존하지 않는다. ([다이어리 경계](../diary/README.md#도메인-경계), 고침 #80: 폐기된 샘플 전제 제거)
- 핀 모양은 반려동물의 모드를 따른다. ACTIVE는 발자국, GARDEN은 꽃이다. 데이터는 같고 보여 주는 방식만 다르다. 핀 이미지는 디자인에서 정한다. (#19)
- 위치는 민감한 정보라서 기본은 비공개다. 1단계에서는 기록 작성자 본인만 자기 기록의 핀을 볼 수 있다. 가족 공유가 생기면 반려동물 접근 권한으로 넓힌다. (#19)
- 지도 화면은 NAVER Cloud Platform Maps의 Dynamic Map을 쓰고, 서버는 좌표와 주소 변환을 맡는다. 서버에서 쓰는 Client Secret은 프론트엔드로 내려가지 않게 한다. 키는 저장소에 두지 않고 환경 변수로만 받는다. (#19)
- 위치는 좌표(위도·경도)가 필수이고 장소 이름·주소는 선택이다. 주소 조회가 실패해도 위치 저장은 성공한다. 외부 서비스 장애 때문에 기록을 못 남기게 하지 않기 위해서다. (#19)
- 한 기록에는 위치를 하나만 붙인다. 위치 쓰기는 diary body의 AUTO/MANUAL/NONE 한 경로로 받고 map은 내부 입력 포트·핀 조회만 제공한다. (고침 #53: 위치 쓰기 책임 통일)
- #19의 수동 위치 1단계 범위는 유지한다. 사진 GPS 자동 연결은 [별도 확장 #44](photo-location.md)로 설계한다. 업로드 전 동의한 사진만 EXIF 제거 전에 후보를 추출하고 다이어리와 같은 DB 트랜잭션에서 지도에 연결한다. 서비스 이미지에는 GPS를 남기지 않는다. (고침 #44: 사진 장소가 있으면 지도 핀으로 연동하는 사용자 요구 반영)
- 지도 화면은 다이어리의 보기 방식(일기·달력·지도)의 하나로 `/pets/[petId]/map`에 둔다. 하단 탐색에는 새 칸을 만들지 않는다. 지도 그림은 네이버 지도이고, 핀·경로·카드는 우리 디자인(`tokens.css`)이다. (#19)
- 프론트엔드의 네이버 지도 키는 Client ID만 `NEXT_PUBLIC_NAVER_MAP_CLIENT_ID`로 받는다. 이 값은 빌드할 때 번들에 들어가 브라우저에 공개되므로 이미지를 빌드할 때 빌드 인자로 넘긴다. CI는 저장소 Variables의 `NAVER_MAP_CLIENT_ID`를, 로컬 `docker compose`는 `.env`의 `NAVER_MAP_CLIENT_ID`를, `npm run dev`는 `frontend/.env.local`을 쓴다. Client Secret은 프론트엔드 코드에 두지 않는다. 키가 없거나 지도를 불러오지 못하면(등록하지 않은 주소 포함) 움직이지 않는 예시 지도를 보여 준다. (#19)
- 서버의 반려동물 id(양의 정수)만 핀 조회 API에 묻는다. 데모 계정의 반려동물은 브라우저에서 만든 UUID라서 서울숲 근처의 예시 핀을 보여 주고, 예시 기억에서는 일기 상세로 가는 링크를 숨긴다. 예시 핀은 데모 세션이 만든 계정에만 보이고, 일반 계정의 브라우저 반려동물에는 섞지 않는다. 데모 여부는 이메일 모양이 아니라 인증 세션의 출처로 판단한다. (#19, 고침 #19: 일반 계정에 예시 핀이 섞이는 문제와 이메일로 데모를 판별하던 문제 수정, #19-S10)
- 핀을 누르면 장소 이름만 보여 준다. 핀 응답에 사진·날짜·본문이 없어서 미리보기는 다이어리 상세를 서버에서 읽는 연결이 생긴 뒤에 더한다. 상세 화면이 지금은 브라우저에 저장된 기록만 찾아서, "기억 펼쳐보기" 링크는 브라우저에 있는 기록의 핀에만 열고 서버 핀에는 준비 중 안내를 보여 준다. (고침 #19: 서버 일기로 이동하면 404가 되는 링크를 막음)
- 산책로는 날짜별 산책 경로를 지도에 그리는 기능이다. 좌표가 시간순으로 쌓이는 데이터라서 `diary_location`과 따로 저장하고, 경로 데이터는 지도 도메인에서만 관리해 다이어리와 겹치지 않게 한다. 산책의 시작과 끝은 보호자가 직접 누르고, 화면을 켠 상태에서 일정 간격으로 좌표를 보낸다. 집 위치는 기기에만 저장하고 서버에는 보내지 않는다. ([계획](walk-route.md)) (#73)
- 정보 지도 화면은 `/places`이고 모바일 하단 메뉴의 마지막 칸(예전 "더보기" 자리)에 둔다. 전체 메뉴는 머리글의 ☰ 버튼과 PC 위쪽 메뉴, 전체 메뉴 목록에 "지도"를 더해 접근한다. 하단은 주요 링크 네 개와 지도다. (#172, 팀 결정)
- 정보 지도는 기록과 별개로, 공공데이터의 동물병원·동물미용·동물보호센터를 우리 DB(`places`)에 적재해 지도 영역으로 조회한다. 로그인한 회원만 쓰고, 인허가 좌표는 도쿄 측지계 보정을 적용해 WGS84로 바꾸며, 인증키는 환경변수로만 받는다. ([계획](animal-places.md)) (#172)

### 다이어리 연동 경계

- **작성 권한과 입력 계약**: diary가 작성자/아이 접근을 검사하고 map 입력 포트에 서버 결정 ID·작성자·revision·nullable 위치를 전달한다. map은 기록 작성자 역조회나 별도 위치 PUT/DELETE를 두지 않는다. 지도 조회의 인증·작성자 범위 검사는 유지한다. (고침 #53: 단일 쓰기 경로와 내부 포트 확정)
- **주소 조회 실행 위치**: 서버 diary가 저장 트랜잭션 시작 전 map 주소 조회 입력 포트를 호출한다. apply는 DB 쓰기만 하고 외부 API를 부르지 않는다. 실패/타임아웃은 주소 없이 저장한다. (고침 #53: DB 트랜잭션의 외부 응답 대기 제거)
- **기록 삭제**: diary가 부모 존재/권한·버전을 검사하고 같은 트랜잭션에서 null 위치를 전달해 map 행을 실제 삭제한다. 없으면 무시하며 map에는 tombstone을 두지 않는다. (고침 #53: 동기 저장과 부모 버전 검사로 보호)

지도 입력은 인증된 HTTP 요청을 직접 받는 위치 쓰기 API가 아니라 diary가 호출하는 내부 포트다. diary가 기록 ID·아이·원 작성자·버전을 서버에서 결정하고, map은 `diaryId`, `petId`, `createdBy`, `revision`, nullable 위치를 같은 DB 트랜잭션에서 반영한다. 삭제된 record 접근 확인 포트는 사용하지 않는다. 지도 핀에서 전달하는 `diaryId` 역시 해당 diary 일기를 식별하며, 일기 상세는 diary API가 자체 권한 검사 후 제공한다. (고침 #80: 기록 소유권과 연동 방향 통일)

기존 map의 예외 전환은 [#72](https://github.com/likelion-backendschool-9th/pawmento/issues/72)와 [공통 예외 규칙](../backend-exceptions.md)을 따른다. diary가 map에서 올라온 업무 예외를 잡아 다른 예외로 포장하지 않으며, 공통 기본 예외와 전역 핸들러로 응답을 통일한다. 삭제된 record·memory 샘플의 예외 전환이나 입력 포트 복구를 지도 연동의 선행 조건으로 두지 않는다. (고침 #80: #72와 연동 책임 구분)

## 데이터 구조 요약

`diary_location` 테이블

| 컬럼                        | 설명                                                                                                                                                                                                                                                                      |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                        | 위치 id. 자동 증가                                                                                                                                                                                                                                                        |
| `diary_id`                  | 실제 diary 일기의 서버 발급 ID(`diaryId`). 유니크(일기 하나에 위치 하나). 질문 답변 ID와 별개이며 다른 도메인의 엔티티를 참조하지 않고 ID만 저장한다 (고침 #80: ID 의미 통일)                                                                                             |
| `pet_id`                    | 반려동물 id. 핀 조회를 위해 함께 저장한다                                                                                                                                                                                                                                 |
| `created_by`                | diary가 전달한 일기의 원 작성자 회원 ID. 요청 본문에서 받지 않으며 1단계 핀 조회의 접근 기준이다                                                                                                                                                                          |
| `latitude`, `longitude`     | 위도, 경도                                                                                                                                                                                                                                                                |
| `place_name`                | 장소 이름 또는 주소. 비어 있을 수 있다                                                                                                                                                                                                                                    |
| `source`, `source_asset_id` | 위치의 출처와 사진 자산 ID. 지금은 `MANUAL`(직접 고른 위치)만 있고 `source_asset_id`는 비어 있다. 사진 GPS에서 고른 위치(`PHOTO_EXIF`)는 위치 동의 정책이 정해진 뒤에 더한다. `source`는 NOT NULL이고 기존 행을 채우도록 기본값 `MANUAL`을 둔다 (고침 #44: 열 추가)       |
| `source_revision`           | 이 위치를 마지막으로 반영한 revision(다이어리가 확정한 버전). NOT NULL이고 기본값 0이라 기존 행도 0이다. 존재하는 위치 행의 높은 revision만 갱신. 위치 없음/일기 삭제 시 행을 실제 삭제하며 삭제 표시는 없음 (고침 #53: 부모 트랜잭션으로 동시성 보호, 고침 #44: 열 추가) |
| `created_at`, `updated_at`  | 저장·수정 시각                                                                                                                                                                                                                                                            |

산책로는 `walks`와 `walk_points` 두 테이블에 따로 저장한다. 필드와 제약은 [walk-route.md](walk-route.md#데이터-구조)에 있다.

핀 조회에 쓰는 인덱스는 `(created_by, pet_id, latitude, longitude)`로 시작하고, 데이터를 쌓아 실행 계획을 확인한 뒤 바꾼다. 이 인덱스가 최선이라는 뜻은 아니다.

정보 지도의 `places` 테이블 (#172, 계획 단계의 제안이며 [네이밍 통일 #29](https://github.com/likelion-backendschool-9th/pawmento/issues/29)에 맞춘다)

| 컬럼                           | 설명                                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `id`                           | 장소 id. 자동 증가                                                                                                         |
| `category`                     | `HOSPITAL`, `GROOMING`, `SHELTER`. 종류를 더해도 테이블을 만들지 않는다                                                    |
| `source_id`                    | 출처의 키. 인허가는 관리번호(18자리 문자열), 보호센터는 `careRegNo`. `(category, source_id)`가 유니크                      |
| `name`                         | 장소 이름                                                                                                                  |
| `address`                      | 도로명 주소. 미용 장소는 번지가 `*`로 가려진 채로 저장한다                                                                 |
| `phone`                        | 걸 수 있는 번호만 하이픈을 붙여 저장. 없으면 비어 있다                                                                     |
| `latitude`, `longitude`        | WGS84 위도·경도                                                                                                            |
| `open24h`, `open24h_basis`     | 24시간 영업 여부와 근거(`NAME`=이름 기반 추정, `HOURS`=제공된 운영 시간)                                                   |
| `opening_hours`, `closed_days` | 보호센터의 운영 시간과 휴무일. 휴무 정보가 없으면 `closed_days`는 `null`이고 연중무휴로 풀지 않는다. 병원·미용은 비어 있다 |
| `source_updated_at`            | 출처가 알려 준 기준 시각                                                                                                   |
| `created_at`, `updated_at`     | 저장·수정 시각                                                                                                             |

조회 인덱스는 `(category, latitude, longitude)`로 시작하고, 데이터를 적재해 실행 계획을 확인한 뒤 바꾼다.

## 아직 정하지 않은 것

- **검색 방식**: 1단계는 주소 검색(Geocoding)으로 시작한다. "한강공원"처럼 장소 이름으로 찾으려면 다른 검색 API가 필요할 수 있어서 확인한다.
- **네이버 지도 키를 발급할 계정**: 지도 담당(장준영)의 개인 계정으로 발급해 팀이 함께 쓰는 것을 제안한다. 팀 확인, 결제수단 등록 여부, 호출 한도(사용량이 발급 계정에 붙는다) 확인이 필요하다. 키는 git에 올리지 않고 환경변수로만 넣는다.
- **개발 서버 도메인(HTTPS)을 네이버 앱의 웹 서비스 URL로 등록하는 시기**: 개발 서버 배포(#10)와 맞춘다.
- **핀이 많을 때의 묶음 표시(클러스터)를 서버와 프론트엔드 중 어디서 할지**
- **사진 GPS 자동 연결**: [#44 설계](photo-location.md)에서 media #33·diary #32와 함께 다룬다. 업로드 전 동의 형식·대표 사진 선택·가족 지도 공유 범위는 그 문서의 제안을 검토한다. (고침 #44: 연동 범위 구체화)
- **테이블·컬럼·제약 이름**: `diary_location`의 이름은 네이밍 통일([#29](https://github.com/likelion-backendschool-9th/pawmento/issues/29))의 결과에 맞춘다.
- **처음 보여 줄 지도 위치**: 지금은 서울숲으로 고정한다. 핀이 있는 곳으로 옮기려면 서버에 "내 핀의 범위" 조회가 있어야 해서 필요한지 정한다.
- **동물약국·반려동물 동반 장소**: 1차에서 제외했고 [계획의 범위 밖](animal-places.md#범위-밖)에 이유를 적었다. 후속 이슈에서 다룬다. (#172)
