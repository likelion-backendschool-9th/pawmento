## 정한 것

- 지도는 별도의 산책 앱이 아니라 기록을 보는 방식의 하나다. 기록(일기·사진)에 장소를 붙이고 지도에서 다시 본다. (#19)
- 핀 모양은 반려동물의 모드를 따른다. ACTIVE는 발자국, GARDEN은 꽃이다. 데이터는 같고 보여 주는 방식만 다르다. 핀 이미지는 디자인에서 정한다. (#19)
- 위치는 민감한 정보라서 기본은 비공개다. 1단계에서는 기록 작성자 본인만 자기 기록의 핀을 볼 수 있다. 가족 공유가 생기면 반려동물 접근 권한으로 넓힌다. (#19)
- 지도 화면은 NAVER Cloud Platform Maps의 Dynamic Map을 쓰고, 서버는 좌표와 주소 변환을 맡는다. 서버에서 쓰는 Client Secret은 프론트엔드로 내려가지 않게 한다. 키는 저장소에 두지 않고 환경 변수로만 받는다. (#19)
- 위치는 좌표(위도·경도)가 필수이고 장소 이름·주소는 선택이다. 주소 조회가 실패해도 위치 저장은 성공한다. 외부 서비스 장애 때문에 기록을 못 남기게 하지 않기 위해서다. (#19)
- 한 기록에는 위치를 하나만 붙인다. (#19)
- #19의 수동 위치 1단계 범위는 유지한다. 사진 GPS 자동 연결은 [별도 확장 #44](photo-location.md)로 설계한다. 서버가 EXIF 제거 전에 후보를 추출하고 일기 저장 이후 지도에 연결한다. 서비스 이미지에는 GPS를 남기지 않는다. (고침 #44: 사진 장소가 있으면 지도 핀으로 연동하는 사용자 요구 반영)

## 데이터 구조 요약

`record_location` 테이블

| 컬럼 | 설명 |
| --- | --- |
| `id` | 위치 id. 자동 증가 |
| `record_id` | 기록 id. 유니크(기록 하나에 위치 하나). 다른 도메인의 엔티티를 참조하지 않고 id만 저장한다 |
| `pet_id` | 반려동물 id. 핀 조회를 위해 함께 저장한다 |
| `created_by` | 위치를 붙인 회원 id. 1단계의 접근 기준이다 |
| `latitude`, `longitude` | 위도, 경도 |
| `place_name` | 장소 이름 또는 주소. 비어 있을 수 있다 |
| `created_at`, `updated_at` | 저장·수정 시각 |

핀 조회에 쓰는 인덱스는 `(created_by, pet_id, latitude, longitude)`로 시작하고, 데이터를 쌓아 실행 계획을 확인한 뒤 바꾼다. 이 인덱스가 최선이라는 뜻은 아니다.

## 아직 정하지 않은 것

- **기록의 작성자 확인**: 위치를 붙이거나 지우려면 "이 기록이 이 회원의 것인가"를 알아야 한다. 지금 record 샘플에는 작성자가 없다. record 도메인에 작성자(회원 id)와 기록 요약(작성자 id, 반려동물 id)을 돌려주는 입력 포트가 필요하고, record 담당과 정한다. 정해지기 전에는 위치 저장·삭제 API를 develop에 두지 않는다.
- **주소 변환을 서버에서 할지, 프론트엔드(지도 SDK)에서 할지**: 서버에서 하면 저장할 때 주소를 채울 수 있고 Secret을 숨길 수 있어서 서버로 가정한다. SDK가 지원하는 범위와 호출 한도를 확인한 뒤 정한다.
- **검색 방식**: 1단계는 주소 검색(Geocoding)으로 시작한다. "한강공원"처럼 장소 이름으로 찾으려면 다른 검색 API가 필요할 수 있어서 확인한다.
- **네이버 지도 키를 발급할 계정**: 지도 담당(장준영)의 개인 계정으로 발급해 팀이 함께 쓰는 것을 제안한다. 팀 확인, 결제수단 등록 여부, 호출 한도(사용량이 발급 계정에 붙는다) 확인이 필요하다. 키는 git에 올리지 않고 환경변수로만 넣는다.
- **개발 서버 도메인(HTTPS)을 네이버 앱의 웹 서비스 URL로 등록하는 시기**: 개발 서버 배포(#10)와 맞춘다.
- **기록이 삭제될 때 위치를 함께 지우는 방법**: record 도메인에 삭제 기능이 생길 때 정한다.
- **핀이 많을 때의 묶음 표시(클러스터)를 서버와 프론트엔드 중 어디서 할지**
- **사진 GPS 자동 연결**: [#44 설계](photo-location.md)에서 media #33·diary #32와 함께 다룬다. 대표 사진 선택·자동/수동 우선순위·가족 지도 공유 범위는 그 문서의 제안을 검토한다. (고침 #44: 연동 범위 구체화)
