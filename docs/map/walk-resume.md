# 진행 중인 산책 복원

관련 이슈: [#167](https://github.com/likelion-backendschool-9th/pawmento/issues/167)
상위 문서: [산책로 기록과 날짜별 보기](walk-route.md) (#73), [프론트 구조 개편안](https://github.com/likelion-backendschool-9th/pawmento/pull/164) (#164)

## 한눈에
- 끝나면: 산책 중에 새로고침하거나 화면을 다시 열어도, 서버에 저장된 그 산책의 경로가 다시 그려지고 좌표 수집이 이어진다. 브라우저 저장소는 쓰지 않는다.
- 결정 필요: 새로 진입할 때 종료·만료 안내를 생략해도 되는지(Q1), 연습 산책(서버에 없는 반려동물)을 #164의 목업 모드로 옮기는 시점(#168 결정 뒤)
- 규모: 4단계(서버 조회 API, 화면 복원, 안내, 로컬 저장소 제거)

## 질문
- Q1: 화면을 새로 열 때(새로고침 포함) 다른 기기에서 종료했거나 새로고침 전에 만료된 산책에 대한 종료·만료 안내를 생략해도 될까요? 제안은 **생략하고 시작 화면을 여는 것**입니다. 현재 산책 조회는 진행 중인 산책만 돌려주므로 끝났는지 만료됐는지 구분할 수 없고, 이미 연 화면에서 좌표 전송이 `409`를 받을 때만 안내합니다. 안내가 꼭 필요하면 조회 응답에 최근 종료·중단된 산책(예: 24시간 안)을 담는 계약이 더 필요합니다. (답에 따라 #167-S6이 달라짐)

지금은 걷는 중인 산책의 좌표와 보낸 개수를 브라우저(`localStorage`)에 남겨 두었다가 새로고침 뒤에 복원한다([#142](https://github.com/likelion-backendschool-9th/pawmento/pull/142)). [#164](https://github.com/likelion-backendschool-9th/pawmento/pull/164)는 업무 데이터를 브라우저 저장소에 두지 않고 서버 조회로 복원하기로 했다. 이 문서는 그 대체 동작을 정한다.

## 1. 진행 중인 산책 복원 (#167-R1)
보호자가 산책 화면을 열면(새로고침 포함) 화면은 서버에 이 반려동물의 **현재 진행 중인 산책**을 직접 묻는다. 있으면 서버에 저장된 좌표로 경로·걸은 시간·거리를 다시 그리고 좌표 수집을 이어 간다. 서버는 "끝내지 않았고 마지막 활동 시각(좌표를 받은 시각, 좌표를 받기 전에는 산책을 시작한 시각)으로부터 5분 안인 산책"을 진행 중으로 보며, 산책이 며칠 전에 시작했어도 같다. 이 판정은 서버의 `Walk.status()`와 같다.

#167-S1 정상 [테스트]
- Given 반려동물 10의 진행 중인 산책 5가 있고 서버에 좌표 12개가 쌓여 있다
- When  산책 화면을 연다(새로고침 포함)
- Then  `GET /maps/walks/current?petId=10`이 200과 산책 5(`walkId`, `startedAt`, `endedAt: null`, `status: IN_PROGRESS`, 좌표 12개)를 돌려주고, 화면은 경로·걸은 시간(시작 시각부터)·거리를 그리며 "산책 중" 상태가 된다
- Then  이어서 모은 좌표는 산책 5에 쌓이고, 서버에서 읽은 12개는 다시 보내지 않는다. 같은 `recordedAt`을 다시 보내도 서버가 중복으로 쌓지 않는다(#73-S6)
- Then  브라우저 저장소(`localStorage`·`sessionStorage`)는 읽지도 쓰지도 않는다

#167-S2 정상 [테스트]
- Given 이틀 전에 시작한 산책 5가 4분마다 좌표를 받아 지금도 진행 중이고 좌표는 5,000개 미만이다(날짜별 조회에는 시작한 날에만 나온다)
- When  `GET /maps/walks/current?petId=10`을 보낸다
- Then  시작 날짜와 상관없이 산책 5를 돌려준다. 날짜를 몰라도 현재 산책을 찾을 수 있다는 것이 이 조회를 따로 두는 이유다

#167-S11 정상 [테스트]
- Given 반려동물 10의 산책 5를 시작한 지 2분이 지났고 서버에 좌표가 아직 하나도 없다(첫 좌표를 보내기 전에 새로고침)
- When  `GET /maps/walks/current?petId=10`을 보낸다
- Then  200과 산책 5(`status: IN_PROGRESS`, `points: []`)를 받는다. 마지막 활동 시각은 좌표가 없을 때 시작 시각이라 5분 안이면 진행 중이다
- Then  화면은 "산책 중"으로 복원하고 걸은 시간은 시작 시각부터 센다. 이어서 모은 좌표는 산책 5에 쌓인다
- Given 좌표 없이 시작한 지 6분이 지났다
- Then  204를 받는다(중단). 시작 화면을 연다

#167-S3 정상 [테스트]
- Given 반려동물 10에 진행 중인 산책이 없다(끝났거나, 마지막 활동 시각으로부터 5분이 넘어 중단됐거나, 한 번도 시작하지 않았다)
- When  `GET /maps/walks/current?petId=10`을 보낸다
- Then  204를 받는다. 화면은 "산책을 시작할까요?" 시작 화면을 연다. 진행 중인 산책이 있으면 시작 화면보다 복원이 먼저다

#167-S4 정상 [테스트]
- Given 좌표가 5,000개에 이른 진행 중인 산책 5(서버는 `IN_PROGRESS`로 돌려줄 수 있다)
- When  산책 화면을 연다
- Then  저장된 경로·시간·거리를 보여 주고, "기록할 수 있는 좌표 한도에 도달했어요"를 알린다. 새 좌표는 모으지 않고(`WalkRecorder`가 받지 않는다) 끝내기만 할 수 있다

## 2. 다른 계정·반려동물, 끝난 산책 (#167-R2)
서버는 본인이 시작한 산책만 돌려주므로 다른 계정의 산책은 복원되지 않는다. 조회는 현재 반려동물 id로만 한다. 끝났거나 중단된 산책은 이어 가지 않는다.

#167-S5 격리 [테스트]
- Given 회원 A가 반려동물 10의 산책 5를 진행 중이다
- When  회원 B가 `GET /maps/walks/current?petId=10`을 보낸다
- Then  204를 받는다. B의 산책만 보이므로 A의 산책과 경로는 나오지 않고, 이 조회는 반려동물의 소유 확인을 부르지 않는다(#73-S9와 같다). 로그인 없이 부르면 401이다
- When  A가 반려동물 11의 산책 화면을 연다
- Then  반려동물 10의 산책은 나오지 않는다

#167-S6 실패 [테스트]
- Given 걷는 중인 화면에서 서버가 산책을 닫았다(마지막 활동 시각으로부터 5분이 넘어 중단, 또는 다른 곳에서 끝냄)
- When  다음 좌표 전송이 409를 받는다(#73-S3)
- Then  화면은 기록을 멈추고 "끝내기를 눌러 마무리해 주세요"로 알린다(기존 동작 유지)
- Given 산책 화면을 새로 열었는데 이전 산책이 끝났거나 중단됐다
- When  현재 산책 조회가 204를 돌려준다
- Then  종료·중단 이력은 안내하지 않고 시작 화면을 연다. 조회 응답에는 끝난 산책이 없어, 다른 기기에서 끝냈는지 구분할 수 없다. 종료·중단 안내는 이 화면에서 전송이 409를 받은 경우에만 한다(새로 진입할 때 생략하는 범위는 Q1에서 합의한다)

#167-S7 실패 [테스트]
- Given 서버 조회가 네트워크 오류나 5xx로 실패한다
- When  산책 화면을 연다
- Then  "산책 상태를 불러오지 못했어요"와 다시 불러오기를 보여 주고, 읽기에 성공하기 전에는 산책을 시작할 수 없다. 읽지 못한 것을 "진행 중인 산책이 없음"으로 바꾸지 않는다

## 3. 서버에 못 보낸 좌표 안내 (#167-R3)
좌표는 15초마다 모으고 4개(약 1분)마다 서버로 보낸다. 전송이 실패하면 그 이상 쌓일 수 있다. 새로고침이나 탭 종료 때 아직 보내지 않은 좌표는 사라질 수 있다. 오프라인에서도 보존하는 영구 큐는 만들지 않고, 사라질 수 있음을 알린다.

#167-S8 정상 [테스트]
- Given 걷는 중이고 아직 보내지 않은 좌표가 있다(복원 직후 보낸 것이 없는 경우는 해당 없음)
- Then  화면에 "아직 전송하지 않은 좌표가 있어요. 새로고침하거나 탭을 닫으면 사라질 수 있어요"를 보이고, 전송을 마치면 안내를 지운다. 전송 실패가 이어져 좌표가 쌓이면 안내에 쌓인 개수를 보여 준다
- When  새로고침하거나 탭을 닫으려 한다
- Then  나가기 전 확인(`beforeunload`)을 요청한다. 브라우저는 사용자가 페이지와 상호작용한 뒤에만 이 확인창을 띄울 수 있어서 항상 보장하지 않으며, 그래서 화면 안내가 기본이고 확인창은 브라우저가 허용하는 경우에만 나온다
- Given 걷는 중이지만 보내지 않은 좌표가 없거나, 산책을 끝냈거나 시작 전이다
- Then  나가기 전 확인을 요청하지 않는다

#167-S9 정상 [테스트]
- Given 서버에 없는 반려동물(브라우저에서 만든 반려동물)의 연습 산책이 진행 중이다
- When  같은 앱 안에서 화면을 나갔다 다시 들어온다
- Then  메모리에 있는 연습 산책이 이어진다. 새로고침하면 사라진다. 어느 쪽도 브라우저 저장소를 쓰지 않는다
- Then  이 동작은 지금(#142)처럼 반려동물 id가 서버 형식(양의 정수)이 아닐 때 적용한다. #164의 목업 모드와 운영 체험 모드는 #168에서 정하므로, 이 계획은 판별 방식을 바꾸지 않는다. #168 결정 뒤 목업 모드를 켠 경우에만 연습 산책을 쓰도록 판별만 바꾼다

#167-S10 정상 [직접] (3단계 병합 조건)
- Given 개발 환경의 서버에 테스트 계정과 서버 반려동물(양의 정수 id)이 있고, 데모 계정이 아니다
- When  산책을 시작해 좌표를 보내다가 새로고침한다
- Then  `GET /maps/walks/current`가 그 산책을 돌려주고 경로·걸은 시간·거리가 다시 그려지며 이어서 걷는다
- When  이어서 좌표를 보내고 산책을 끝낸다
- Then  좌표가 같은 산책에 쌓이고 종료가 서버에 반영된다. 이 확인(확인 URL, 계정·반려동물, 단계별 결과)을 3단계 PR 본문에 적은 뒤에만 3단계를 병합한다

## 범위 밖
- 중단된 산책 이어하기: [산책로 계획](walk-route.md#범위-밖)과 같다. 중단된 산책은 이어 가지 않고 새 산책을 시작하게 한다.
- 끝났거나 중단된 산책의 이력 안내: 복원 조회는 진행 중인 산책만 돌려준다. 이력 안내가 필요해지면 따로 정한다.
- 오프라인 영구 큐와 탭을 닫는 순간의 전송: 새로고침·종료 때 못 보낸 좌표는 사라질 수 있음을 알린다. `keepalive` 요청으로 마지막 전송을 시도하는 것은 필요해지면 따로 정한다.
- 같은 산책을 두 곳(두 탭·두 기기)에서 동시에 이어 가는 경우: 서버가 `(walk_id, recorded_at)` 중복을 막으므로 좌표가 두 번 쌓이지는 않지만, 한 곳만 쓰도록 만드는 장치는 만들지 않는다.

## 작업 순서
1. 계획 문서 (이 문서)
2. 현재 산책 조회 API: `GET /maps/walks/current` 입력 포트·서비스·출력 포트·컨트롤러, 날짜별 조회와 같은 읽기 스냅샷과 `Walk.status()`의 상태 판정 (S1, S2, S3, S5, S11)
   - 변경 후보: `map` 도메인의 산책 조회 포트·서비스·저장소 어댑터·컨트롤러와 시나리오 테스트
3. 화면 복원: 읽기 포트와 어댑터(서버, 연습), 화면을 열 때의 복원, 한도·조회 실패 안내, 화면이 `localStorage`를 읽거나 쓰는 것을 중단 (S1, S3, S4, S6, S7, S9, S11)
   - 변경 후보: `walkPorts.ts`, `walkUseCases.ts`, `HttpWalkRepository.ts`·`DemoWalkRepository.ts`, `useWalkSession.ts`, `WalkScreen.tsx`, `composition.ts`
   - **병합 조건: S10을 먼저 직접 확인한다.** 병합하면 화면에서 `LocalActiveWalkStore` 호출이 끊겨 기존 복원은 그때부터 동작하지 않으므로, 병합 전에 테스트 계정과 서버 반려동물로 산책 시작, 새로고침 뒤 복원, 이후 좌표 전송과 종료까지 확인하고 결과를 PR 본문에 적는다.
   - 서버 반려동물과 테스트 계정으로 확인할 수 있는 환경이 없으면 3단계를 시작하지 않고, 그동안 기존 `LocalActiveWalkStore` 복원이 그대로 동작한다. 반려동물 서버 연동이 끝나는 것을 기다린다.
   - 이 단계에서는 `LocalActiveWalkStore` 파일과 테스트를 지우지 않는다(5단계).
4. 못 보낸 좌표 안내: 화면 안내와 나가기 전 확인 요청 (S8)
5. `LocalActiveWalkStore`와 그 테스트 제거: 3단계가 병합되고 서버 복원이 동작하는 것이 확인된 뒤에 한다. 호출부가 모두 끊긴 파일과 테스트만 지우는 정리 변경이다.

## 정한 것
- 진행 중인 산책은 전용 조회 `GET /maps/walks/current?petId=`로 읽는다. 로그인한 회원이 시작했고 끝내지 않았으며 마지막 활동 시각(좌표를 받은 시각, 좌표를 받기 전에는 시작 시각)으로부터 5분 안인 산책 하나를 좌표와 함께 돌려주고(좌표가 아직 없으면 `points: []`), 없으면 204다. 날짜별 조회(`GET /maps/walks?petId=&date=`)로는 며칠 전에 시작한 산책을 찾을 수 없다. 서버가 진행 중 여부를 시작 날짜가 아니라 마지막 활동 시각으로 판정해서, 오래 걷는 산책이 날짜 조회에서 빠지고 새 산책 시작은 409가 되는 어긋남이 생기기 때문이다. (고침 #167: 오늘·어제 날짜별 조회 두 번으로 찾는 안은 이 경우를 놓쳐 버림)
- 현재 산책 조회는 날짜별 조회와 같은 읽기 스냅샷에서 산책 행과 좌표를 읽고, 본인 확인은 `created_by`와 `pet_id`로 한다. 다른 회원의 반려동물을 조회하면 403이 아니라 204다. 계약은 [산책로 계획](walk-route.md)의 API 표에 둔다.
- 복원한 산책은 서버에 있는 좌표를 모두 보낸 것으로 보고(`sentCount = 좌표 수`), 이어서 모은 좌표만 보낸다.
- 복원 경로는 서버 조회 하나다. 브라우저 저장소로 되돌아가는 대체 경로를 두지 않는다. 서버 복원을 직접 확인(S10)한 뒤에만 화면 복원 변경(3단계)을 병합해 화면이 저장소를 읽거나 쓰는 것을 멈추고, `LocalActiveWalkStore` 파일과 테스트는 그 뒤(5단계)에 지운다. (#164의 "업무 데이터를 브라우저 저장소에 두지 않고, 대체 동작을 검증한 뒤 제거한다"와 같다) (고침 #167: 복원 변경과 같은 변경에서 지우던 것을 S10 확인 뒤로 미룸, 고침 #167: 3단계 병합 전에 S10을 확인하도록 앞당김)
- 읽기에 실패하면 "진행 중인 산책 없음"으로 보지 않는다. 그러면 새 산책을 시작해 409(진행 중인 산책 있음)가 나거나 같은 산책이 두 개처럼 보이기 때문이다.
- 서버 반려동물(양의 정수 id)은 서버에서, 그 밖의 반려동물은 메모리에 있는 연습 산책에서 찾는다(#142와 같은 구분). 목업 모드로 옮기는 시점은 #168 결정 뒤다.

## 가정
- 서버는 진행 중인 산책에 시간 한도를 두지 않는다. 마지막 활동 시각이 5분 안이면(좌표를 계속 받으면) 며칠이 지나도 진행 중이고, 좌표가 5,000개에 이르면 새 좌표만 받지 못한다(#73-S14).
- 서버 반려동물과 일반 계정의 연결은 프론트 반려동물 서버 연동 전이라 아직 없다. 개발 환경에서 테스트 계정과 서버 반려동물을 만들어 S10을 확인할 수 있으면 그 방법으로 하고, 그럴 수 없으면 3단계를 미룬다.
