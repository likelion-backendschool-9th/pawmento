# 진행 중인 산책 복원

관련 이슈: [#167](https://github.com/likelion-backendschool-9th/pawmento/issues/167)
상위 문서: [산책로 기록과 날짜별 보기](walk-route.md) (#73), [프론트 구조 개편안](https://github.com/likelion-backendschool-9th/pawmento/pull/164) (#164)

## 한눈에
- 끝나면: 산책 중에 새로고침하거나 화면을 다시 열어도, 서버에 저장된 그 산책의 경로가 다시 그려지고 좌표 수집이 이어진다. 브라우저 저장소는 쓰지 않는다.
- 결정 필요: 진행 중인 산책을 읽는 방법(아래 "정한 것" 첫째 항목), 기존 브라우저 복원 경로를 지우는 시점
- 규모: 2단계

지금은 걷는 중인 산책의 좌표와 보낸 개수를 브라우저(`localStorage`)에 남겨 두었다가 새로고침 뒤에 복원한다([#142](https://github.com/likelion-backendschool-9th/pawmento/pull/142)). [#164](https://github.com/likelion-backendschool-9th/pawmento/pull/164)는 업무 데이터를 브라우저 저장소에 두지 않고 서버 조회로 복원하기로 했다. 이 문서는 그 대체 동작을 정한다.

## 1. 진행 중인 산책 복원 (#167-R1)
보호자가 산책 화면을 열면(새로고침 포함) 화면은 서버에서 이 반려동물의 진행 중인 산책을 읽는다. 있으면 서버에 저장된 좌표로 경로·걸은 시간·거리를 다시 그리고 좌표 수집을 이어 간다.

#167-S1 정상 [테스트]
- Given 반려동물 10의 진행 중인 산책 5가 있고 서버에 좌표 12개가 쌓여 있다
- When  산책 화면을 연다(새로고침 포함)
- Then  서버에서 산책 5와 좌표 12개를 읽어 경로·걸은 시간(시작 시각부터)·거리를 그리고 "산책 중" 상태가 된다
- Then  이어서 모은 좌표는 산책 5에 쌓이고, 서버에서 읽은 12개는 다시 보내지 않는다. 같은 `recordedAt`을 다시 보내도 서버가 중복으로 쌓지 않는다(#73-S6)
- Then  브라우저 저장소(`localStorage`·`sessionStorage`)는 읽지도 쓰지도 않는다

#167-S2 정상 [테스트]
- Given 한국 시각 어제 23:50에 시작해 지금도 좌표를 보내고 있는 진행 중인 산책 5
- When  산책 화면을 연다
- Then  오늘과 어제 두 날짜의 조회에서 산책 5를 찾아 이어 간다. 산책 하나의 좌표는 최대 5,000개(15초 간격으로 약 20시간)라서 진행 중인 산책은 늦어도 어제 시작한 것이다

#167-S3 정상 [테스트]
- Given 진행 중인 산책이 없다(끝났거나 한 번도 시작하지 않았다)
- When  산책 화면을 연다
- Then  "산책을 시작할까요?" 시작 화면이 열린다

## 2. 다른 계정·반려동물, 끝난 산책 (#167-R2)
서버는 본인이 시작한 산책만 돌려주므로 다른 계정의 산책은 복원되지 않는다. 다른 반려동물 화면에서는 그 반려동물의 산책만 찾는다. 이미 끝났거나 중단된 산책은 이어 갈 수 없고, 화면은 그 상태를 알려 준다.

#167-S4 격리 [테스트]
- Given 회원 A가 반려동물 10의 산책 5를 진행 중이다
- When  같은 브라우저에서 회원 B로 로그인해 산책 화면을 연다(A는 로그아웃)
- Then  서버가 B의 산책만 돌려주므로 A의 산책과 경로는 나오지 않고 시작 화면이 열린다
- When  A가 반려동물 11의 산책 화면을 연다
- Then  반려동물 10의 산책은 나오지 않는다. 조회는 항상 현재 반려동물 id로 한다

#167-S5 실패 [테스트]
- Given 반려동물 10의 마지막 산책이 좌표를 받은 지 5분이 넘어 중단됐거나(#73-S13), 다른 기기에서 끝났다
- When  산책 화면을 연다
- Then  이어 가지 않고 "이전 산책이 중단됐어요(끝났어요)"라고 안내한다. 새 산책은 바로 시작할 수 있다
- Given 걷는 중인 화면에서 서버가 산책을 닫았다(전송이 409, #73-S3)
- When  다음 전송이 실패한다
- Then  화면은 기록을 멈추고 "끝내기를 눌러 마무리해 주세요"로 알린다(기존 동작 유지)

#167-S6 실패 [테스트]
- Given 서버 조회가 네트워크 오류나 5xx로 실패한다
- When  산책 화면을 연다
- Then  "산책 상태를 불러오지 못했어요"와 다시 불러오기를 보여 주고, 읽기에 성공하기 전에는 산책을 시작할 수 없다. 읽지 못한 것을 "진행 중인 산책이 없음"으로 바꾸지 않는다

## 3. 서버에 못 보낸 좌표 안내 (#167-R3)
좌표는 15초마다 모으고 4개(약 1분)마다 서버로 보낸다. 새로고침이나 탭 종료 때 아직 보내지 않은 좌표는 사라질 수 있다. 오프라인에서도 보존하는 영구 큐는 만들지 않고, 사라질 수 있음을 알린다.

#167-S7 정상 [테스트]
- Given 걷는 중이고 보내지 않은 좌표가 있다
- When  새로고침하거나 탭을 닫으려 한다
- Then  브라우저가 나가기 전에 확인을 묻고, 화면에 "새로고침하거나 탭을 닫으면 아직 전송하지 않은 길(최대 약 1분)이 사라질 수 있어요"를 보여 준다
- Given 걷는 중이지만 보내지 않은 좌표가 없다
- Then  나가기 전 확인을 묻지 않는다. 산책을 끝냈거나 시작 전이면 묻지 않는다

#167-S8 정상 [테스트]
- Given 서버에 없는 반려동물(브라우저에서 만든 반려동물)의 연습 산책이 진행 중이다
- When  같은 앱 안에서 화면을 나갔다 다시 들어온다
- Then  메모리에 있는 연습 산책이 이어진다. 새로고침하면 사라진다. 어느 쪽도 브라우저 저장소를 쓰지 않는다

#167-S9 정상 [직접]
- Given 데모 계정이 아니라 서버 반려동물로 산책 중이다
- When  새로고침한다
- Then  경로가 다시 그려지고 이어서 걷는다. 서버 반려동물 연동 후 확인한다

## 범위 밖
- 중단된 산책 이어하기: [산책로 계획](walk-route.md#범위-밖)과 같다. 중단된 산책은 알려 주고 새 산책을 시작하게 한다.
- 오프라인 영구 큐와 탭을 닫는 순간의 전송: 새로고침·종료 때 못 보낸 좌표는 사라질 수 있음을 알린다. `keepalive` 요청으로 마지막 전송을 시도하는 것은 필요해지면 따로 정한다.
- 같은 산책을 두 곳(두 탭·두 기기)에서 동시에 이어 가는 경우: 서버가 `(walk_id, recorded_at)` 중복을 막으므로 좌표가 두 번 쌓이지는 않지만, 한 곳만 쓰도록 만드는 장치는 만들지 않는다.
- 서버에 "진행 중인 산책" 전용 조회 API: 필요해지면 별도 이슈에서 다룬다(아래 정한 것).

## 작업 순서
1. 계획 문서 (이 문서)
2. 진행 중인 산책 복원: 읽기 포트와 어댑터(서버, 연습), 화면 열 때의 복원, 중단·종료·조회 실패 안내, `LocalActiveWalkStore`와 `localStorage` 사용 제거 (S1~S6, S8)
   - 변경 후보: `walkPorts.ts`, `walkUseCases.ts`, `HttpWalkHistoryRepository.ts`·`DemoWalkRepository.ts`, `useWalkSession.ts`, `WalkScreen.tsx`, `composition.ts`, `LocalActiveWalkStore.ts`(제거)와 그 테스트
3. 못 보낸 좌표 안내: 나가기 전 확인과 안내 문구 (S7)

## 정한 것
- 진행 중인 산책은 기존 날짜별 조회 `GET /maps/walks?petId=&date=`를 오늘과 어제 두 번 불러 찾는다. 응답의 `status`가 `IN_PROGRESS`인 산책이 복원 대상이고, 반려동물 한 마리에는 진행 중인 산책이 하나뿐이다(#73-S12). 서버는 바꾸지 않는다. 날짜는 Asia/Seoul로 나눈다. 이유: 본인 확인(`created_by`), 중단 판정(5분), 좌표가 이미 이 응답에 있어 프론트만 바꾸면 된다. 두 날짜의 좌표를 모두 받는 비용이 있어서 부담이 되면 전용 조회 API(`GET /maps/walks/current` 같은 것)를 따로 제안한다.
- 복원한 산책은 서버에 있는 좌표를 모두 보낸 것으로 보고(`sentCount = 좌표 수`), 이어서 모은 좌표만 보낸다.
- 복원 경로는 서버 조회 하나다. 브라우저 저장소로 되돌아가는 대체 경로를 두지 않는다. 같은 변경에서 `LocalActiveWalkStore`를 지우고, 대체 동작이 확인되기 전에는 지우지 않는다. (#164의 "업무 데이터를 브라우저 저장소에 두지 않는다"와 같다)
- 읽기에 실패하면 "진행 중인 산책 없음"으로 보지 않는다. 그러면 새 산책을 시작해 409(진행 중인 산책 있음)가 나거나 같은 산책이 두 개처럼 보이기 때문이다.
- 서버 반려동물(양의 정수 id)은 서버에서, 브라우저에서 만든 반려동물은 메모리에 있는 연습 산책에서 찾는다. (#142와 같은 구분)

## 가정
- 산책 하나는 좌표 5,000개(약 20시간)를 넘지 못하므로(#73-S14), 진행 중인 산책은 오늘이나 어제 시작한 것이다.
- 서버 반려동물과 일반 계정의 연결은 프론트 반려동물 서버 연동 전이라 아직 없다. 그 전의 서버 종단 확인(#167-S9)은 하지 못한다.
