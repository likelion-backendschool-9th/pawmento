# 기록에 장소 붙이기와 지도에서 보기

관련 이슈: [#19](https://github.com/likelion-backendschool-9th/pawmento/issues/19)

기록(일기·사진)에 장소를 붙이고 지도에서 핀으로 다시 본다. 위치 입력은 다이어리 body 하나로 받고 지도는 내부 반영 포트와 핀 조회를 제공한다. #34 후속 [#53](https://github.com/likelion-backendschool-9th/pawmento/issues/53)에서 별도 위치 저장·삭제 API 계획을 변경했다. 도메인 전체의 결정은 [map README](README.md)에 있다.

## 요구사항

- #19-R1 보호자는 자신이 만든 기록에 위치(위도·경도, 선택으로 장소 이름)를 붙이고, 바꾸고, 지울 수 있다.
- #19-R2 장소 이름 없이 좌표만 보내면 서버가 주소를 조회해 채운다. 외부 주소 조회 실패는 좌표 저장을 막지 않으며, 지도 DB 쓰기 실패는 일기와 함께 롤백한다. (고침 #53: 외부/내부 실패 구분)
- #19-R3 지도 화면 영역 안의 핀을 조회할 수 있다. 한 번에 최대 500개까지 돌려주고, 넘으면 잘렸다고 알려 준다.
- #19-R4 핀은 기록 작성자 본인에게만 보인다. 다른 회원의 기록에는 위치를 붙이거나 지울 수 없다.
- #19-R5 지도 화면에서 핀을 누르면 그 기록의 상세로 이동한다. 핀 모양은 반려동물의 모드(ACTIVE는 발자국, GARDEN은 꽃)를 따른다.
- #19-R6 네이버 지도 키는 환경 변수로만 받는다. 테스트는 외부 서비스를 부르지 않는다.

## 시나리오와 확인 방법

- #19-S1 [테스트] 로그인한 작성자가 diary body MANUAL/AUTO를 저장하면 같은 DB 트랜잭션에서 map 위치 하나가 갱신된다. (고침 #53: 단일 위치 쓰기와 내부 포트로 S1 확인 경로 변경) (R1)
- #19-S2 [테스트] diary body MANUAL 좌표가 비었거나 위도 -90~90·경도 -180~180을 벗어나면 400으로 저장 전체를 거부한다. (고침 #53: 단일 위치 쓰기와 내부 포트로 S2 확인 경로 변경) (R1)
- #19-S3 [테스트] 저장 트랜잭션 전에 주소를 조회해 command에 담고 apply는 외부 호출을 하지 않는다. 조회 실패/타임아웃은 주소 없이 저장한다. 외부 서비스는 가짜 서버로 대신한다. (고침 #53: 주소 조회 실행 위치 확정) (R2, R6)
- #19-S4 [테스트] diary body NONE 또는 일기 삭제가 같은 트랜잭션에서 map 행을 실제 삭제한다. 행이 없으면 무시하고 부모 버전 검사로 오래된 수정의 핀 복원을 막는다. (고침 #53: 삭제 표시 없이 위치 제거) (R1)
- #19-S5 [테스트] 지도 영역 안의 핀만 조회되고, 영역 밖 기록은 나오지 않는다. 영역의 최솟값이 최댓값보다 크면 400을 받는다. (R3)
- #19-S6 [테스트] 핀이 500개를 넘으면 500개만 돌려주고 잘렸다고 알려 준다. (R3)
- #19-S7 [테스트] 미인증 핀 조회는 401, 타 작성자 핀은 미노출이다. 타인 위치 변경은 diary 권한 검사에서 거부하며 map은 작성자를 역조회하지 않는다. (고침 #53: 단일 위치 쓰기와 내부 포트로 S7 확인 경로 변경) (R4)
- #19-S8 [직접] 기록 작성 화면에서 지도에서 위치를 고르면 주소가 보이고 저장된다. 프론트엔드 PR에서 확인한다. (R1, R2)
- #19-S9 [직접] 지도 화면에서 ACTIVE 반려동물의 기록은 발자국, GARDEN 반려동물의 기록은 꽃 핀으로 보이고, 핀을 누르면 기록 상세가 열린다. 프론트엔드 PR에서 확인한다. (R5)
- #19-S10 [테스트] 화면 확인용 예시 핀은 데모 세션이 만든 계정에만 보인다. 일반 로그인 계정은 이메일이 `@pawmento.local`로 끝나도, 브라우저에 등록한 반려동물의 지도에 예시 핀이 섞이지 않는다. 프론트엔드 PR에서 확인한다. (R5)
- #19-S11 [테스트] 네이버 지도 키가 없을 때 쓰는 예시 지도의 바탕은 같은 배치로 그려지고(나무는 공원 안에서 서로 겹치지 않음), 강과 지명은 화면 크기(데스크톱 1280×720의 추억 지도 약 1188×488, 1280×640, 휴대폰 390×700)마다 계산한 보이는 범위 안에 있다. 위치를 고르는 화면은 실제 좌표와 무관한 지명을 보여 주지 않고, 지도를 끌어도 도로·블록 배경이 비지 않는다. 프론트엔드 PR에서 확인한다. (R5)

## 작업 순서

PR은 하나의 목적만 갖도록 작게 나눈다.

1. 계획 문서 (이 문서)
2. 주소 조회: 출력 포트, 네이버 어댑터, 설정, 가짜 서버 테스트. 프론트엔드가 필요로 하면 주소 조회 API를 더한다 (S3의 일부)
3. 위치 저장소: `DiaryLocation` 도메인, `diary_location` 테이블, 핀 조회용 범위 조회와 인덱스. API는 열지 않는다. 인덱스는 데이터를 쌓아 실행 계획으로 확인한다
4. 지도 핀 조회 API (S5, S6, S7 중 조회 권한). 별도 deleted 필터는 추가하지 않는다. (고침 #53: 제거된 위치는 행 삭제)
5. [#44 위치 입력 포트](photo-location.md)와 세 가지 포트 결과·revision·실제 위치 행 삭제 구현. 다이어리가 쓰기 권한을 확인하므로 record 작성자 역조회 포트는 만들지 않는다. (고침 #53: 별도 위치 쓰기 API 제거)
6. diary body AUTO/MANUAL/NONE과 같은 DB 트랜잭션으로 연결해 S1~S4, S7의 쓰기 거부를 확인한다. (고침 #53: 조회/내부 반영은 map, 외부 쓰기는 diary)
7. 지도 화면과 다이어리 위치 선택·사전 동의 흐름을 연결한다(S8, S9).

## 정한 것

- API. 경로는 공통 접두사를 뺀 모양이다. 인증은 [member 문서](../member/README.md#도메인-담당이-쓰는-방법)의 `@LoginMember`를 쓰고, 에러 응답은 그 문서의 임시 형식을 따른다. (#19)

  | 요청 | 본문·쿼리 | 성공 응답 |
  | --- | --- | --- |
  | `GET /maps/pins` | `petId`, `minLatitude`, `minLongitude`, `maxLatitude`, `maxLongitude` | 200, `pins`(`diaryId`, `latitude`, `longitude`, `placeName`)와 `truncated` |

- **별도 위치 PUT/DELETE API는 만들지 않는다.** 위치 쓰기는 diary body 하나로 통일하고 map 내부 포트는 [#44 계약](photo-location.md)을 따른다. (고침 #53: 수동/자동 쓰기 경로 중복 제거)
- 핀 조회 경로는 `/maps/pins`이고 반려동물은 쿼리 `petId`로 받는다. 경로에 `pets`를 두면 반려동물 도메인의 경로와 책임이 섞여 보인다는 리뷰에 따랐다. (고침 #19: `GET /pets/{petId}/map-pins`에서 `GET /maps/pins?petId=`로)
- 핀 조회의 입력은 쿼리 문자열만 읽는다(`MapQueryParameters`). 같은 이름의 요청 헤더로 채우지 않고, 같은 키가 둘 이상이면 첫 값을 쓰지 않고 400이다. `petId`는 1 이상의 정수, 영역 값은 십진수(지수 표기 `1e-7` 허용, NaN·무한대·16진수·접미사는 400)이고 위도는 -90~90, 경도는 -180~180이다. 위도·경도 범위는 웹에서, "최솟값 ≤ 최댓값"은 도메인(`MapArea`)에서 입력한 십진수(`BigDecimal`) 그대로 검사하고 통과한 값만 조회용 double로 바꾼다(먼저 double로 바꾸면 90.000000000000001이 90.0이 되고 1e-400이 0과 같아져서 규칙을 통과한다). (고침 #19: 쿼리 입력을 엄격하게 해석)
- 핀 응답에는 `petId`를 포함하지 않고 요청한 `petId`가 곧 그 핀의 반려동물이다. 핀 모양은 프론트엔드가 반려동물의 모드로 정한다. (#19)
- 핀 조회의 기준은 요청한 회원이 만든 기록이다. (#19)
- 영역 안의 핀이 500개를 넘으면 위치 행 id 오름차순(먼저 위치를 저장한 순)으로 500개만 돌려주고 `truncated`를 true로 한다. 순서를 고정해야 같은 요청에 같은 응답이 나가서 정했다. 기록의 작성 순서가 아니라 위치를 저장한 순서라서, 오래된 기록에 나중에 위치를 붙이거나 지웠다가 다시 붙이면 뒤로 간다. 최근 기록을 먼저 보여 줄지는 지도 화면을 만들 때 다시 정한다. (#19)
- 외부 서비스 호출에는 짧은 타임아웃을 둔다. 값은 구현할 때 정한다. (#19)
- 패키지는 `com.pawmento.map`이고 백엔드 구조 문서(`docs/backend-architecture.md`)의 이름 규칙을 따른다. 도메인 객체는 `DiaryLocation`이다. (#19)

## 가정

- 공통 접두사 `/api/v1`은 설정(`WebConfig`, #22)으로 붙여 컨트롤러 경로에 쓰지 않는다. 위 경로의 실제 주소는 `/api/v1/...`이다(예: `GET /api/v1/maps/pins`). 개발 서버의 nginx는 `/api/`로 시작하는 경로를 백엔드로 넘긴다.
- diary가 원 작성자·아이·권한을 확인하고 map 내부 포트에 `diaryId`, `petId`, `createdBy`, `revision`, nullable 위치를 넘긴다. map은 diary 저장 트랜잭션에 참여하고 원자적 revision 조건으로 반영한다. (고침 #53: 작성자 역조회 포트 제거)
- 지도 화면과 위치 선택은 프론트엔드가 지도 SDK로 처리한다. 서버는 좌표 저장과 조회, 주소 변환만 맡는다.

## 참고

- NAVER Cloud Platform Maps는 애플리케이션을 등록하면 Client ID와 Client Secret이 나온다. 서버 호출에는 `X-NCP-APIGW-API-KEY-ID`와 `X-NCP-APIGW-API-KEY` 헤더를 쓴다. Secret은 서버에서만 쓴다.
- 웹 서비스 URL은 호스트만 등록한다. `http://localhost:8080`이면 `http://localhost`로 등록한다.
- 앱 설정에서 Geocoding에 체크하지 않으면 주소 검색 요청이 429로 실패한다.
- 요청 주소가 문서 버전에 따라 `maps.apigw.ntruss.com`과 `naveropenapi.apigw.ntruss.com`으로 나뉘어 있다. 구현할 때 최신 문서로 확인한다. 무료 한도와 결제수단 요건도 콘솔에서 확인한다.
- 환경 변수 이름은 서버 `NAVER_MAP_CLIENT_ID`·`NAVER_MAP_CLIENT_SECRET`, 프론트엔드 `NEXT_PUBLIC_NAVER_MAP_CLIENT_ID`로 시작한다. `NEXT_PUBLIC_` 변수는 빌드할 때 값이 고정된다. 개발 서버 배포(#10)의 `.env.prod.example`과 이름을 맞춘다.
- 외부 문서: [Maps 개요](https://api.ncloud-docs.com/docs/application-maps-overview), [Maps 문제 해결](https://guide.ncloud-docs.com/docs/en/application-maps-troubleshoot)
