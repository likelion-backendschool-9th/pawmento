# 다이어리 사진 위치와 지도 핀 자동 연결

관련 이슈: [#44](https://github.com/likelion-backendschool-9th/pawmento/issues/44). 선행/연계: 수동 지도 [#19](memory-location.md), [다이어리 #32](../diary/README.md), [파일 업로드 #33](../media/README.md).

사용자가 요청한 동작은 **다이어리에 등록한 사진에 위치 데이터가 있으면 지도 핀으로 출력하는 것**이다. 사진 GPS의 추출·보관과 서비스 이미지의 EXIF 제거를 구분한다. 이 문서는 설계안이며 코드·지도 배포 완료를 뜻하지 않는다. 여러 사진 처리·위치 수정 우선순위 등은 아래 제안을 검토해 확정한다.

## 요구사항

- #44-R1 서버가 검증한 다이어리 사진의 유효한 GPS를 위치 후보로 사용한다. 위치 정보 없는 사진도 정상 등록하고 현재 기기 위치나 임의 좌표를 대신 넣지 않는다.
- #44-R2 다이어리 저장 이후 기록 ID로 지도 위치를 연결하고 기존 영역별 핀 조회에서 표시한다. 핀 선택은 해당 일기 상세로 연결하며 ACTIVE/GARDEN의 핀 모양 정책을 유지한다.
- #44-R3 수동 지정 위치와 자동 위치 사용 해제 선택을 자동 연동이 덮어쓰지 않게 한다. 기존 기록당 위치 하나 제약을 유지한다.
- #44-R4 사진 교체·첨부 순서 변경·삭제와 일기 삭제를 지도에 반영한다. 중복 이벤트·역순 처리·실패 재시도에도 오래된 핀이 복원되지 않게 한다.
- #44-R5 GPS는 서비스 이미지·일반 자산 응답에 노출하지 않고 기록 위치 접근 권한을 따른다. 지도 장애나 주소 조회 실패가 일기 저장을 막지 않게 한다.

## 사진 처리와 대표 위치 제안

1. media가 원본 바이트를 검사하면서 EXIF GPS를 **서비스본의 EXIF 제거 전에** 추출한다. GPS 좌표·남북/동서 부호를 십진수 좌표로 정규화하고 유한값·범위를 검증한다. 0도는 유효하므로 0이라는 이유만으로 위치 없음으로 처리하지 않는다.
2. JPEG/PNG/WebP 중 파서가 실제로 GPS 메타데이터를 읽을 수 있는 경우에만 후보를 만든다. 확장자만 보고 GPS가 있다고 가정하지 않는다. 스크린샷·메신저 사진·메타데이터가 제거된 사진에는 후보가 없을 수 있다.
3. 여러 사진이면 **첨부 순서 중 유효 GPS가 있는 첫 이미지**를 대표 후보로 사용하는 안을 제안한다. 평균 좌표를 만들거나 사진마다 여러 핀을 생성하지 않는다. 초기 기존 map의 `record_id` 유니크 제약과 맞추기 위해서다. 이후 사진별 핀이 필요하면 별도 데이터 모델로 확장한다.
4. 위치 없는 사진만 있으면 AUTO에서도 지도 핀은 없다. 영상/음성의 위치, 촬영 시각으로 일기 날짜 추정, 브라우저 현재 GPS는 이번 자동 연동의 입력이 아니다.
5. 사용자가 직접 위치를 선택하면 MANUAL, 자동 사용을 끄면 NONE이다. 신규 생성의 기본값은 AUTO로 제안한다. 작성 화면에 자동 사용 여부·위치 후보를 표시해 저장할 위치를 확인할 수 있게 한다.

## 데이터와 API 계약

### media → diary 내부 위치 후보

- media에 비공개 `media_asset_location(asset_id PK, latitude, longitude, source=EXIF)`를 둔다. 해당 목적이 `DIARY_ATTACHMENT`인 이미지에만 추출·보관한다. 질문 답변 업로드는 위치 자동 연결 대상이 아니다.
- 일반 파일 메타데이터·서명 URL·이미지 EXIF에 GPS를 포함하지 않는다. 이미지 서비스본은 계속 EXIF를 제거한다. 필요한 좌표는 별도 비공개 DB에만 남긴다.
- 내부 `GetMediaLocationCandidateUseCase`는 요청 회원·아이·자산 목록을 받고 본인 업로드/유효한 기존 첨부·아이·용도·READY를 확인한 후보만 반환한다. 좌표를 클라이언트 파일명이나 임의 body에서 추정하지 않는다.
- 작성 미리보기 후보가 필요하면 `POST /pets/{petId}/diary-location-candidates`에 `attachmentIds`와 선택 `recordId`를 보낸다. 신규 자산은 업로더 본인만, 기존 자산은 해당 일기 작성·수정 권한과 실제 첨부 관계를 확인한다. 응답은 `{candidates: [{assetId, latitude, longitude}]}`다. 서버는 저장 때 재검사한다.

### diary 저장과 상태

일기 생성/수정에 `location`을 추가한다.

```json
{
  "content": "공원에서 함께 보낸 오후",
  "recordedDate": "2026-11-17",
  "attachmentIds": ["asset-1", "asset-2"],
  "location": {"mode": "AUTO"}
}
```

- `AUTO`: 서버가 첨부 순서로 위치를 결정한다. 좌표·자산 선택값을 클라이언트가 확정해서 보내지 않는다.
- `MANUAL`: `latitude`, `longitude`, 선택 `placeName`을 받는다. map의 좌표 유효성·기록 권한 규칙을 적용한다.
- `NONE`: 핀을 만들지 않거나 기존 핀을 제거한다. 이후 재시도·재접속으로 AUTO가 되지 않는다.
- 생성 시 `location` 생략은 AUTO, 수정 시 생략은 기존 모드 유지다. 기존 AUTO에서 사진/순서가 바뀌면 다시 대표 위치를 계산한다. MANUAL/NONE이면 사진 변경으로 모드를 바꾸지 않는다.
- 기록 위치 의도에 `mode`, `revision`, `sourceAssetId`(AUTO 후보), `latitude/longitude`(내부 선택 결과), `syncStatus`를 보관하는 안을 제안한다. 수정·재시도마다 파일 GPS를 무단 재노출하지 않는다.
- 일기 응답에 `location: {mode, syncStatus}`를 포함한다. 상태는 `PENDING`, `SYNCED`, `FAILED`다. AUTO 후보 없음·NONE의 핀 제거도 정상 동기화 대상이다. 좌표·주소 상세는 지도 권한을 확인한 경우에만 반환한다.

### diary → map 동기화

- 일기·첨부·위치 의도·outbox 이벤트를 같은 DB 트랜잭션으로 저장한다. 파일 참조 실패는 기존 설계처럼 저장 전체를 롤백한다. 지도 반영은 저장 성공 후 재시도 가능한 작업으로 분리한다.
- 이벤트는 `recordId`, `petId`, `createdBy`, `locationRevision`과 위치 의도 식별값을 가진다. map 저장은 공개 HTTP API를 다시 부르지 않고 입력 포트로 연결한다. 다른 도메인의 JPA 저장소를 직접 참조하지 않는다.
- 처리 시 최신 기록·아이·작성자·첨부·모드·revision을 확인한다. 이미 삭제됐거나 더 최신 수정이 있으면 오래된 이벤트를 무시한다. 처리 중 새 수정이 들어오는 경합까지 막도록 **map의 쓰기 시점에도 단조 증가 revision 조건**을 적용한다.
- map의 `record_location`은 `source`(MANUAL/PHOTO_EXIF), 선택 `source_asset_id`, `source_revision`을 추가하는 안으로 한다. AUTO 후보 없음/NONE/삭제로 핀이 없어진 뒤에도 마지막 적용 revision을 별도 동기화 행/삭제 표시로 유지해 늦은 이벤트가 핀을 되살리지 않게 한다.
- 수동 위치 API로 위치를 바꾸거나 지우는 경우도 같은 위치 의도·revision 경로를 사용한다. 수동 위치 삭제는 NONE으로 남겨 이전 AUTO 작업이 복원하지 않게 한다. #19의 기존 API를 유지하되 구현 담당과 이 경로를 합의한다.
- 같은 이벤트 재처리는 같은 기록 핀을 갱신하는 멱등 처리다. 기록당 위치 하나를 유지하며 새 핀을 중복 생성하지 않는다.
- 주소 조회 실패 시 좌표 핀은 유지하고 주소만 비운다. map 저장 실패는 일기를 보존하고 `FAILED`/재시도 상태를 보인다. 동기화 중에는 “지도에 반영 중”을 표시한다.
- 필요 시 `POST /pets/{petId}/diaries/{recordId}/location-sync`로 현재 버전만 재시도한다. 본인 수정 권한을 검사하며 이전 버전을 선택하거나 임의 위치를 넣는 API가 아니다.

## 수정·삭제와 권한

- 대표 사진 삭제·순서 변경 시 AUTO는 남은 첫 유효 GPS로 이동한다. 후보가 없으면 기존 자동 핀을 제거한다. 좌표 자체를 나중에 임의 수정하지 않도록 검증한 위치 후보를 사용한다.
- 일기 삭제 시 위치 삭제 의도/최신 revision을 트랜잭션에 남긴다. 지도 삭제 재시도와 파일 삭제 작업은 독립적으로 진행하고, 늦은 위치 생성 이벤트를 무시한다.
- 사진만 업로드한 상태에서는 핀이 생기지 않는다. 미연결 자산 정리와 좌표 후보 정리도 함께 처리한다.
- 초기 지도 열람·수정은 #19의 **작성자 본인** 정책을 유지한다. 가족 일기 열람이 곧 모든 가족의 지도 GPS 열람을 뜻하지 않는다. 가족 전체 지도 공유가 필요하면 별도 접근 범위 합의가 필요하다.
- 권한 없는 회원에게 위치 후보·핀·정밀 좌표를 반환하지 않는다. 가족/회원 탈퇴·아이 삭제의 후보 보관 기간과 지도 권한 회수는 공통 정책을 따른다.

## 확인 시나리오

- #44-S1 [테스트] 정상 GPS 사진을 다이어리에 저장하면 기록당 핀 하나가 영역 조회에 나오고 기록 ID가 일치한다.
- #44-S2 [테스트] GPS 없음·불완전/잘못된 좌표·현재 위치 부재에도 사진과 일기는 저장되고 핀은 만들지 않는다. 유효한 0도·남위·서경은 정상 처리한다.
- #44-S3 [테스트] 여러 GPS 사진은 첨부 순서상 첫 유효 후보 하나로 결정하고 미지원 영상/음성·질문 답변은 대상에서 제외한다.
- #44-S4 [테스트] 수동 위치 우선·NONE 유지, 오래된 AUTO 작업이 사용자 선택을 덮어쓰지 않는다.
- #44-S5 [테스트] AUTO 대표 사진 삭제/순서 변경은 위치 갱신, 후보 없음은 핀 제거, MANUAL/NONE은 사진 변경으로 바뀌지 않는다.
- #44-S6 [테스트] 일기 삭제·자동 핀 제거 후 늦은 생성 이벤트가 핀을 복원하지 않는다. 이벤트 중복/역순·처리 도중 경합에도 최신 revision만 반영한다.
- #44-S7 [테스트] 지도 저장 실패 후 일기 보존·상태 표시·재시도, 주소 조회 실패 시 좌표 핀 유지.
- #44-S8 [테스트] 비가족·타 작성자·다른 아이/자산·미완료 업로드 위치 접근 거부, 일반 서비스 이미지/자산 응답에 GPS 없음.
- #44-S9 [직접] GPS 사진 업로드 → 일기 저장 → 지도 반영 상태 확인 → 영역 핀 클릭 → 해당 일기 상세, ACTIVE/GARDEN 핀 모양 확인.
- #44-S10 [직접] 여러 사진 위치·자동 사용 해제·수동 지정·사진 교체/삭제 후 지도와 일기 상태 확인.

자동 테스트는 EXIF fixture와 가짜 지도 포트로, 실제 지도/주소 서비스 호출 없이 확인한다. 직접 시나리오는 지도 프론트 화면·권한 API가 연결된 뒤 확인한다.

## 작업 순서와 미정 사항

1. media GPS 후보 추출·서비스본 제거(#33), diary 위치 의도·outbox(#32), map 입력 포트·revision·권한(#44)을 합의한다.
2. 후보 추출 → 일기 저장/상태 → 지도 멱등 반영 → 수정/삭제/재시도 → 프론트 핀·상태를 작은 PR로 나눈다.
3. 대표 사진 첫 유효 GPS, 위치 모드 AUTO/MANUAL/NONE, 비동기 상태·재시도 API는 제안이다. 지도 담당과 API·트랜잭션 경계를 검토한다.
4. 가족 전체 지도 공유·사진별 다중 핀·촬영 시각 활용·영상 GPS·주소로 위치 추측은 이 확장 범위 밖이다.
