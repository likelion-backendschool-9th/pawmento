# 다이어리 위치와 지도 핀 연결

관련 이슈: [#44](https://github.com/likelion-backendschool-9th/pawmento/issues/44). 선행/연계: 지도 조회 [#19](memory-location.md), [다이어리 #32](../diary/README.md), [파일 업로드 #33](../media/README.md). 이 문서는 #34의 설계를 [후속 검토 #53](https://github.com/likelion-backendschool-9th/pawmento/issues/53)에서 수정한다.

사진 GPS 자동 연결과 수동 위치·위치 해제를 **다이어리 저장 한 경로**로 받는다. 같은 앱·같은 DB의 지도 입력 포트를 다이어리 저장 트랜잭션에서 호출한다. 문서 수정이며 실제 기능 구현 완료를 뜻하지 않는다.

## 요구사항

- #44-R1 업로드 전에 위치 사용에 동의한 사진의 서버 검증 GPS만 위치 후보로 사용한다. 미동의는 NONE 기본이며 위치 없는 사진도 저장한다. (고침 #53: 업로드 전 사전 동의와 기본 비사용 정책 반영)
- #44-R2 다이어리 저장과 지도 위치를 같은 DB 트랜잭션에서 반영하고 핀 선택은 해당 일기 상세로 연결한다. ACTIVE/GARDEN 핀 모양은 유지한다. (고침 #53: 비동기 지도 동기화 대신 원자적 저장)
- #44-R3 수동·자동·해제를 일기 body의 AUTO/MANUAL/NONE으로만 받는다. 별도 지도 위치 PUT/DELETE는 만들지 않는다. (고침 #53: 위치 쓰기 경로 통일)
- #44-R4 모든 위치 변경은 diary 버전 검사·동일 트랜잭션을 통과한다. 위치 제거는 지도 행을 삭제하고 남아 있는 위치 행에만 단조 증가 revision 조건을 적용한다. (고침 #53: 동기 저장에서는 삭제 표시 행 없이 부모 동시성 검사로 보호)
- #44-R5 GPS는 서비스 이미지·일반 자산 응답에 넣지 않는다. 주소 조회 실패는 주소 없는 좌표를 허용하되, 지도 DB 반영 실패는 일기와 함께 롤백한다. (고침 #53: 외부 주소 조회와 같은 DB 저장 실패를 구분)

## 업로드 전 동의와 사진 처리

1. 사진을 고른 뒤 **업로드 세션 생성·파일 전송 전에** 위치 사용 목적과 지도 노출 범위를 설명하고 명시적 선택을 받는다. 위치 사용 동의는 기본 미선택이다. 사진 GPS가 집 위치일 수 있음을 안내한다. 동의 UI의 정확한 문구·동의 유효 범위는 팀 확인이 필요하며 확정 전 자동 동의를 가정하지 않는다.
2. 동의는 `media` 자산별 업로드 세션에 묶는다. 제안 요청은 `locationConsent: {granted: true, policyVersion: "..."}`이며 생략/false는 미동의다. 서버는 회원·아이·용도·동의 문구 버전·서버 기록 시각을 보관한다. 클라이언트의 임의 동의 시각을 신뢰하지 않는다.
3. 동의한 DIARY_ATTACHMENT 이미지에만 서버가 서비스본 EXIF 제거 전에 GPS를 추출한다. 유한값·위도/경도 범위·남북/동서 부호를 검증한다. 0도도 유효하다. 불완전 GPS는 후보 없음으로 처리하고 정상 사진 저장을 막지 않는다.
4. 미동의 사진은 프론트에서 GPS 메타데이터를 제거한 사본으로만 업로드한다. 제거 여부를 보장할 수 없는 형식/오류는 업로드를 멈추고 안내한다. 서버 역시 미동의 자산의 위치 후보를 추출·보관하지 않고 서비스본의 메타데이터를 제거한다. 잘못된 클라이언트가 보낸 원본을 정상 미동의 흐름으로 인정하지 않으며 임시 파일은 검증/정리 정책에 따라 제거한다. **서버에서 업로드 후에 지우는 것만으로 사전 동의를 대신하지 않는다.**
5. 프론트가 파일 선택 전 GPS 존재를 알 필요는 없다. 사진 업로드 전에 위치 사용 선택을 공통으로 제시하면 된다. 로컬 GPS 분석은 필수 선행 작업이 아니다. 전처리 후 실제 전송 크기에 파일당 15MiB 제한을 적용한다.
6. 질문 답변 사진·음성은 위치 자동 연결 대상이 아니다. 원본·서비스본에서 GPS를 재노출하지 않는다. 일반 미리보기·자산 응답에도 좌표가 없다.
7. 동의한 이미지 여러 개에 후보가 있으면 **첨부 순서상 첫 유효 GPS 하나**를 대표 위치로 삼는 안이다. 평균 좌표나 사진별 다중 핀은 만들지 않는다. 위치 정보가 없는 경우 현재 기기 GPS·주소·촬영 시각으로 위치를 추측하지 않는다.

## media → diary 위치 후보 계약

- 비공개 `media_asset_location(asset_id PK, latitude, longitude, source=EXIF)`는 동의한 다이어리 이미지에만 만든다. 동의 여부·정책 버전·기록 시각은 media의 별도 동의 필드/행에서 관리한다.
- `GetMediaLocationCandidateUseCase`는 요청 회원·아이·자산 목록으로 업로더/기존 유효 첨부·용도·READY·GPS 동의 유효성을 검사한다. 미동의 자산에는 후보를 반환하지 않는다.
- 작성 미리보기가 필요하면 `POST /diaries/location-candidates?petId={petId}`에 `attachmentIds`와 선택 `diaryId`를 받는다. 신규는 본인 업로드, 기존은 해당 일기의 본인 수정 권한·첨부 관계를 검사한다. 후보 응답은 접근 허용된 위치만 포함한다. 지도 쓰기 API가 아니다. (고침 #32: PR #94의 diary 루트·petId 쿼리 계약과 통일)
- 사진 업로드나 후보 조회만으로 지도 핀을 만들지 않는다. 위치 저장은 다이어리 생성·수정·삭제에서만 수행한다.

## 다이어리의 단일 위치 쓰기 계약

일기 생성/수정 body에 `location`을 받는다. 다음은 기본 비사용 예시다.

```json
{
  "content": "공원에서 함께 보낸 오후",
  "recordedDate": "2026-11-17",
  "attachmentIds": ["asset-1"],
  "location": {"mode": "NONE"}
}
```

- `AUTO`: 업로드 전 유효하게 동의한 첨부에서만 서버가 대표 GPS를 고른다. 후보가 없으면 핀은 없다. 미동의 첨부만으로 AUTO를 요청하면 위치 사용을 거부하고 입력을 유지하도록 안내한다. 답변 저장 시 받은 동의로 과거 미동의 사진에서 GPS를 뒤늦게 추출하지 않는다.
- `MANUAL`: 사용자가 명시적으로 선택한 `latitude`, `longitude`, 선택 `placeName`을 받는다. 사진 GPS 동의를 대신하지 않으며 사진 후보를 읽지 않는다. 좌표·본문 형식은 다이어리가 검증하고 map 도메인도 내부 불변식을 검사한다.
- `NONE`: 위치를 저장하지 않거나 기존 핀을 제거한다. AUTO 복귀는 별도의 명시적 선택이 필요하다.
- **생성에서 생략은 NONE**이다. 동의 후에도 프론트가 명시적으로 AUTO를 선택해 전송한다. 수정에서 생략은 기존 모드 유지이며 기존 AUTO에서 사진/순서가 바뀌면 동의된 후보로 재계산한다. MANUAL/NONE은 사진 변경으로 바뀌지 않는다.
- 동의 철회/자동 사용 해제는 NONE 저장으로 핀을 제거한다. 업로드 동의 기록과 기존 자산 후보의 삭제·재사용 범위는 media 보관 정책으로 별도 결정하며 철회 뒤 재동의 없이 재사용하지 않는다.
- 지도용 `syncStatus`, PENDING/SYNCED/FAILED 응답, location-sync 재시도 API는 제공하지 않는다. 성공 응답은 지도 DB 변경도 커밋된 결과다. 좌표·주소 상세는 지도 열람 권한이 있을 때만 반환한다.

## 지도 입력 포트와 같은 DB 트랜잭션

포트 후보: `ApplyDiaryLocationUseCase`.

```text
ApplyDiaryLocationCommand(
  diaryId, petId, createdBy, revision,
  location: {latitude, longitude, placeName?, source, sourceAssetId?} | null
)
→ APPLIED | DUPLICATE | STALE
```

- `source`는 MANUAL/PHOTO_EXIF, `sourceAssetId`는 PHOTO_EXIF에만 있다. null 위치는 삭제다. `createdBy`는 일기의 원 작성자로 고정한다. 요청 회원 ID/작성자 ID를 body에서 신뢰하지 않는다.
- 다이어리가 현재 로그인 회원의 아이 접근·본인 수정 권한을 검사하고 서버가 결정한 ID/작성자를 전달한다. map은 record 작성자 확인을 역으로 요청하지 않는다. 내부 포트는 외부 HTTP로 노출하지 않는다. **지도 핀 조회의 인증·작성자 범위 검사는 그대로 유지한다.**
- 다이어리 저장 서비스의 동일 스레드·동일 DataSource/트랜잭션 매니저 안에서 map 입력 포트를 호출한다. REQUIRED로 기존 트랜잭션에 참여하고 REQUIRES_NEW·비동기 실행·커밋 후 호출을 사용하지 않는다.
- 일기·첨부·media 참조 수·위치 모드/revision·지도 행을 함께 커밋/롤백한다. 지도 DB 실패 시 일기 저장도 실패하며 입력을 보존한다. 낙관적 충돌은 409로 안내하고 새 상태를 확인한다.
- 지도 반영용 outbox·작업자·재시도 API는 제거한다. **파일 검증·물리 파일 삭제의 작업 테이블/재시도는 유지**한다. 파일 I/O는 DB 트랜잭션으로 원자화되지 않기 때문이다.
- **주소 조회는 diary의 저장 트랜잭션을 열기 전에 한다.** 비트랜잭션 조정 유스케이스가 좌표를 결정한 뒤 map의 `ResolveLocationAddressUseCase`(후보 이름)를 호출하고, 받은 `placeName`을 DB 저장 Command에 넣는다. 적용(apply) 포트는 DB 작업만 하며 외부 API를 호출하지 않는다. 현재 주소 어댑터의 연결 1초·응답 2초 제한을 유지하고 실패/타임아웃이면 주소 없이 진행한다. (고침 #53: 주소 조회 실행 위치 확정)
- 사전 조회에서 본 일기/첨부·권한은 저장 트랜잭션 안에서 다시 검사한다. 주소 조회 중 다른 수정이 커밋되면 기대 버전 검사로 거부하고 새 입력을 확인한다. 검증 실패/권한 거부는 주소 실패처럼 무시하지 않는다. 수정 요청의 기대 버전은 기존 diary API와 동일하게 받고 위치 revision만 서버가 결정한다.
- 외부 조정 메서드 전체에 `@Transactional`을 붙여 주소 조회까지 감싸지 않는다. 별도 트랜잭션 서비스/TransactionTemplate 경계를 사용하고 DB 저장이 끝난 뒤에야 성공 응답을 보낸다. 주소 조회 실패와 지도 DB 쓰기 실패는 서로 다른 정책이다.

### 결과·revision·실제 행 삭제

| 결과 | 조건 | diary 처리 |
| --- | --- | --- |
| `APPLIED` | 새 위치 삽입/높은 revision 갱신, 또는 존재하는 위치 삭제 | 같은 트랜잭션으로 커밋 |
| `DUPLICATE` | 같은 revision의 동일 명령이 이미 반영됨, 또는 지울 위치가 이미 없음 | 변경 없이 성공 처리 |
| `STALE` | 존재하는 위치의 revision보다 작은 요청 | 409 충돌로 부모 변경도 롤백 |

- diary는 **모든 생성·수정·삭제**의 존재/권한·잠금/낙관적 버전 검사를 수행하고 위치 revision을 서버에서 결정한다. 저장 트랜잭션 밖·비동기·별도 공개 API로 map을 호출하지 않는다. 같은 revision을 서로 다른 내용에 재사용하지 않으며 동일 revision의 상이한 명령은 계약 위반으로 거부한다. (고침 #53: 중복 성공과 오래된 요청 거부를 구분)
- `diary_location`에는 `source`, `source_asset_id`, `source_revision`만 추가한다. `deleted` 열이나 삭제 표시 행은 만들지 않는다. **기존 latitude/longitude의 NOT NULL은 유지**한다. 위치 없는 최초 일기도 map 행을 만들지 않으므로 NULL 좌표 저장이나 NOT NULL 해제 DDL이 필요 없다. 새 출처 열의 기존 데이터 백필·스키마 반영은 구현 PR에서 정한다. (고침 #53: 삭제 표시와 기존 DB NOT NULL 충돌 제거)
- 위치가 있으면 새 revision이 더 클 때만 원자적으로 갱신하고 같으면 DUPLICATE, 낮으면 STALE이다. 최초 동시 insert는 `diary_id` 유니크/조건부 upsert로 보호한다. 같은 기록 ID의 아이·원 작성자를 바꾸려는 호출은 거부한다.
- NONE·AUTO 후보 없음·일기 삭제는 null 위치로 apply를 호출해 실제 map 행을 지운다. 존재하는 행에 대한 삭제도 높은 revision 조건을 확인한다. 삭제할 행이 없으면 DUPLICATE로 아무 작업도 하지 않는다. 성공한 삭제 뒤 revision 이력을 map에 따로 남기지 않는다.
- **삭제 후 오래된 호출 거부의 책임은 diary**에 있다. 삭제된 일기에 대한 수정은 부모 조회에서 거부하고, 삭제와 동시에 진행된 수정은 부모의 잠금/버전 검사 실패로 지도 쓰기까지 롤백한다. map 행이 없을 때 map 포트 단독으로 과거 revision을 판별할 수 있다고 가정하지 않는다. 이 전제 밖으로 호출 경로를 늘릴 때는 별도 설계가 필요하다. (고침 #53: 같은 트랜잭션의 부모 동시성 검사로 핀 복원 방지)
- 핀 조회에는 기존 영역/작성자 조건만 사용하며 `deleted=false` 필터를 추가하지 않는다.

## 수정·삭제와 권한

- AUTO 대표 사진 삭제/순서 변경은 동의된 남은 후보로 이동하고 없으면 지도 위치 행을 삭제한다. 수동 위치와 NONE은 유지한다.
- 일기 삭제와 지도 위치 행 삭제는 같은 DB 트랜잭션이다. 파일 참조 해제·물리 삭제 작업 등록도 함께 저장하되 실제 파일 삭제는 나중에 재시도한다.
- 초기 지도 열람은 #19의 **작성자 본인** 정책을 유지한다. 가족 일기 열람이 가족 전체의 GPS 열람 권한을 뜻하지 않는다. 가족 지도 공유 확대는 별도 합의한다.
- GPS 후보·동의 기록 보관 기간과 가족/회원 탈퇴·아이 삭제 후 정책은 담당자와 합의한다.

## 확인 시나리오

- #44-S1 [테스트] 사전 동의된 GPS 사진 일기 저장과 지도 핀이 같은 트랜잭션으로 반영되고 기록 ID가 일치한다. (고침 #53: 동의·동기 저장 추가)
- #44-S2 [테스트] GPS 없음/불완전·현재 위치 부재에는 일기만 저장하고, 유효 0도·남위·서경은 정상 처리한다.
- #44-S3 [테스트] 여러 동의 사진은 첫 유효 후보 하나를 사용하고 음성·질문 답변은 대상에서 제외한다. (고침 #53: 동의된 후보로 한정)
- #44-S4 [테스트] 수동/자동/해제를 다이어리 body 하나로 받고 MANUAL/NONE을 임의 자동 값으로 바꾸지 않는다. (고침 #53: 별도 지도 쓰기 API 제거)
- #44-S5 [테스트] AUTO 사진 변경·후보 없음은 위치 갱신/삭제, MANUAL/NONE은 유지한다.
- #44-S6 [테스트] 높은 revision은 APPLIED, 같은 명령은 DUPLICATE, 낮으면 STALE로 부모 롤백한다. NONE/일기 삭제는 행 삭제, 오래된 수정·삭제 경합은 diary 버전 검사로 지도 쓰기까지 롤백한다. (고침 #53: 세 결과·실제 삭제·부모 동시성 검사로 전환)
- #44-S7 [테스트] 주소 조회 시 저장 트랜잭션이 없고 apply는 외부 호출을 하지 않는다. 주소 실패는 주소 없이 저장하며 지도 DB 실패는 일기·첨부·참조 모두 롤백한다. (고침 #53: 주소 조회 경계 확정)
- #44-S8 [테스트] 비가족·다른 작성자·아이/자산 불일치·미완료·미동의 후보 접근 거부, 일반 응답/서비스본 GPS 미노출. (고침 #53: 동의 검증 추가)
- #44-S9 [직접] 업로드 전 위치 동의 → GPS 사진 업로드 → 일기 저장 → 영역 핀 클릭 → 일기 상세, 모드별 핀 모양 확인. (고침 #53: 비동기 반영 상태 제거)
- #44-S10 [직접] NONE 기본·동의 거부·AUTO 선택·수동 지정·사진 변경/삭제 후 지도와 일기 상태 확인. (고침 #53: 사전 동의·단일 쓰기 경로 반영)
- #44-S11 [테스트] 생성 생략은 NONE, 미동의 AUTO 거부, 수정 생략은 기존 모드 유지이며 업로드 동의 기록을 검사한다.
- #44-S12 [직접] 미동의 사진은 업로드 전에 GPS 제거본으로 전송하고, 제거 실패 시 업로드 중단·안내를 확인한다.

테스트는 EXIF fixture·PostgreSQL·가짜 주소 조회 포트로 수행하고 외부 지도 API는 자동 테스트에서 부르지 않는다. 실제 지도/사진 전처리/동의 UX는 프론트 연결 후 직접 확인한다.

## 작업 순서와 미정 사항

1. media 사전 동의·GPS 제거본 전송·동의된 후보(#33), diary 단일 위치 쓰기·revision(#32), map 입력 포트·실제 위치 행 삭제(#44)를 합의한다.
2. 후보 처리 → 일기·map 같은 트랜잭션 → 변경/삭제·권한·revision 검사 → 프론트 동의/핀 연결로 나눈다.
3. 동의 문구·체크박스/모달 형태·범위(자산/묶음)·유효 버전·철회/재동의·사진 전처리 도구은 미정이다. 확정 전 기본 NONE을 유지한다.
4. 가족 전체 지도 공유·사진별 다중 핀·영상 GPS·브라우저 위치 추측은 범위 밖이다.
