# 산책로 기록과 날짜별 보기

관련 이슈: [#73](https://github.com/likelion-backendschool-9th/pawmento/issues/73)

## 한눈에
- 끝나면: 보호자가 산책을 시작해 끝내면, 지도에서 그 날짜를 골랐을 때 그날의 산책 경로가 선으로 보인다.
- 결정 필요: 진행 중인 산책을 끝내지 않고 앱을 닫았을 때의 처리(Q1), 한 산책에 쌓을 수 있는 좌표 수(Q3). 둘 다 제안을 적어 두었고 확인이 필요하다
- 규모: 5단계

## 질문
- Q1: 산책을 끝내지 않고 앱을 닫거나 기기가 꺼지면 그 산책은 어떻게 하나? 반려동물 한 마리에 진행 중인 산책을 동시에 둘 이상 둘 수 있나? (답에 따라 #73-S2, #73-S3이 달라짐)
  - 제안: 진행 중인 산책의 개수를 제한하지 않는다. 끝내지 않은 산책은 `endedAt`이 비어 있는 채로 남고, 날짜별 조회에서 마지막 좌표까지의 경로를 그린다. 새 산책은 언제든 시작할 수 있고 좌표는 지정한 `walkId`에만 쌓인다. 이렇게 하면 앱을 닫고 다시 열어도 새 산책을 시작할 수 없는 상태가 생기지 않는다. 같은 반려동물을 가족이 함께 산책시키는 경우는 가족 공유 도입 때 다시 정한다.
- Q3: 한 산책에 쌓을 수 있는 좌표의 최대 개수와 한 번에 보내는 개수는? (답에 따라 #73-S4가 달라짐)
  - 제안: 한 산책 5,000개, 한 요청 100개. 15초 간격이면 5,000개는 약 20시간 분량이라 산책 한 번에는 충분하고, 요청 100개는 25분 분량이다. 한 산책의 상한을 넘기는 요청은 409로 거절한다.

## 1. 산책 시작과 끝 (#73-R1)
보호자는 반려동물을 골라 산책을 시작하고, 산책을 끝낼 수 있다.

#73-S1 정상 [테스트]
- Given 로그인한 회원 A, A의 반려동물 10
- When  `POST /maps/walks`에 `petId=10`을 보낸다
- Then  201과 `walkId`, `startedAt`을 받고, 그 산책은 진행 중이다

#73-S2 정상 [테스트]
- Given 진행 중인 산책 5
- When  `POST /maps/walks/5/end`를 보낸다
- Then  200과 `endedAt`을 받고, 산책 5는 끝난 산책이 된다. 같은 요청을 다시 보내면 같은 결과를 받고 `endedAt`은 바뀌지 않는다

#73-S3 실패 [테스트]
- Given 끝난 산책 5
- When  `POST /maps/walks/5/points`로 좌표를 보낸다
- Then  409를 받고 좌표는 쌓이지 않는다

#73-S11 실패 [테스트]
- Given 로그인한 회원 A, 다른 회원 B의 반려동물 20, 존재하지 않는 반려동물 999
- When  `POST /maps/walks`에 `petId=20`을 보낸다
- Then  403을 받고 산책이 만들어지지 않는다
- When  `POST /maps/walks`에 `petId=999`를 보낸다
- Then  404를 받고 산책이 만들어지지 않는다

## 2. 경로 좌표 쌓기 (#73-R2)
진행 중인 산책에 좌표를 묶음으로 보내면 시간순으로 쌓인다.

#73-S4 정상 [테스트]
- Given 진행 중인 산책 5
- When  `POST /maps/walks/5/points`에 `points`(`latitude`, `longitude`, `recordedAt`) 4개를 보낸다
- Then  204를 받고, 이후 그 산책을 조회하면 좌표 4개가 `recordedAt` 순서로 나온다

#73-S5 실패 [테스트]
- Given 진행 중인 산책 5
- When  `points` 중 하나의 `latitude`가 91이다
- Then  400과 이유를 받고, 같은 요청의 나머지 좌표도 쌓이지 않는다

#73-S6 정상 [테스트]
- Given 같은 `recordedAt`을 가진 좌표가 산책 5에 이미 쌓여 있다
- When  네트워크가 끊겨 같은 묶음을 다시 보낸다
- Then  204를 받고, 같은 좌표가 두 번 쌓이지 않는다

## 3. 날짜별 보기 (#73-R3)
보호자는 날짜를 골라 그날 시작한 산책의 경로를 볼 수 있다.

#73-S7 정상 [테스트]
- Given 회원 A의 반려동물 10이 11월 17일 10:00(Asia/Seoul)에 시작한 산책과 11월 17일 23:50에 시작해 11월 18일 00:20에 끝난 산책(좌표 각 40개), 11월 18일 09:00에 시작한 산책 1개
- When  `GET /maps/walks?petId=10&date=2026-11-17`을 보낸다
- Then  200과 11월 17일에 시작한 산책 2개가 `startedAt` 순서로 나오고, 각 산책에 `walkId`, `startedAt`, `endedAt`, 시간순 좌표가 들어 있다. 자정을 넘겨 끝난 산책도 17일에 나오고, 11월 18일에 시작한 산책은 나오지 않는다

#73-S8 정상 [테스트]
- Given 11월 17일에 시작한 산책이 없다
- When  `GET /maps/walks?petId=10&date=2026-11-17`을 보낸다
- Then  200과 빈 목록을 받는다

## 4. 본인의 산책만 (#73-R4)
산책로는 만든 회원 본인만 보고 쌓을 수 있다.

#73-S9 실패 (R1·R2·R3) [테스트]
- Given 회원 B와 회원 A의 산책 5
- When  로그인 없이 `GET /maps/walks?...`를 부른다
- Then  401을 받는다
- When  B가 `GET /maps/walks?petId=10&date=...`로 A의 반려동물 10을 조회한다
- Then  200과 빈 목록을 받는다. A의 산책은 나오지 않고, 이 조회는 pet의 소유 확인을 부르지 않는다
- When  B가 `POST /maps/walks/5/points`나 `POST /maps/walks/5/end`를 부른다
- Then  403을 받고 아무것도 바뀌지 않는다

## 5. 산책 종료 제안 (#73-R5) (선택, 2단계)
한 곳에 오래 머물면 앱이 "산책이 끝났나요?"라고 묻는다.

#73-S10 정상 [직접]
- Given 산책 중이고 앱 화면이 켜져 있다
- When  같은 곳에 정해진 시간 동안 머문다
- Then  "산책이 끝났나요?"가 나오고 "끝내기"를 누르면 #73-S2와 같이 산책이 끝난다. 프론트엔드 PR에서 확인한다

## 범위 밖
- 산책로 공유, 사진·기록과 자동 연결: 필요해지면 별도 이슈에서 다룬다.
- 화면이 꺼진 상태의 위치 수집(백그라운드): 브라우저(PWA)는 화면이 꺼지면 수집이 끊길 수 있어서 화면을 켜 둔 상태를 전제로 한다.
- 집 위치 판정: 집 위치는 기기에만 저장하고 서버에는 보내지 않는다. R5의 종료 제안은 프론트엔드가 기기 안에서 판단하며 서버가 하는 일은 없다.
- 경로 단순화·지도 위 시각 효과: 1단계는 쌓은 좌표를 그대로 내려준다.
- 시연용 화면 외의 지도 화면: 프론트엔드 PR에서 다룬다.

## 작업 순서
1. 산책 도메인과 저장소: `Walk`, `WalkPoint`, 테이블, 출력 포트. API는 열지 않는다 (S2, S3의 규칙 부분)
2. 산책 시작·끝 API (S1, S2, S3)
3. 좌표 쌓기 API (S4, S5, S6)
4. 날짜별 조회 API와 본인 확인 (S7, S8, S9)
5. 프론트엔드: 산책 시작·끝 버튼, 좌표 보내기, 날짜별 경로 보기, 시연용 화면 (S10)

## 데이터 구조

산책 하나를 `walks` 한 행으로, 산책 중에 쌓이는 좌표를 `walk_points` 여러 행으로 저장한다. `record_location`과는 서로 참조하지 않는다.

`walks` 테이블

| 컬럼 | 설명 |
| --- | --- |
| `id` | 산책 id. 자동 증가 |
| `pet_id` | 반려동물 id. 다른 도메인의 엔티티를 참조하지 않고 id만 저장한다 |
| `created_by` | 산책을 시작한 회원 id. 본인 확인의 기준이다 |
| `started_at` | 산책을 시작한 시각. 날짜별 조회의 기준이다(Asia/Seoul로 날짜를 나눈다) |
| `ended_at` | 산책을 끝낸 시각. 비어 있으면 진행 중이다 |
| `created_at`, `updated_at` | 저장·수정 시각 |

`walk_points` 테이블

| 컬럼 | 설명 |
| --- | --- |
| `id` | 좌표 id. 자동 증가 |
| `walk_id` | `walks.id`. 산책 하나에 좌표가 여러 개다(1:N) |
| `latitude`, `longitude` | 위도, 경도. 필수 |
| `recorded_at` | 기기에서 좌표를 얻은 시각. 필수 |

- 중복 판정 키는 `(walk_id, recorded_at)`이고 유니크 제약으로 건다. 같은 키가 다시 오면(재전송) 새로 쌓지 않고 기존 값을 그대로 둔다. 좌표가 다르더라도 먼저 쌓인 값을 유지한다. (#73-S6)
- 이 유니크 제약이 시간순 조회(`walk_id`, `recorded_at` 순)의 인덱스도 겸한다.
- 날짜별 조회용 인덱스는 `walks (created_by, pet_id, started_at)`으로 시작하고, 데이터를 쌓아 실행 계획을 확인한 뒤 바꾼다.
- 진행 중인 산책을 반려동물당 하나로 제한할지는 Q1의 답에 따른다. 제안대로 제한하지 않으면 `ended_at`에 대한 유니크 제약은 두지 않는다. 제한하기로 하면 `ended_at`이 비어 있는 행이 `pet_id`마다 하나뿐이어야 하며, 구현할 때 제약 방식(부분 유니크 인덱스 등)을 정한다.
- 한 산책의 좌표 상한(가정의 5,000개)은 좌표를 쌓는 요청에서 산책 행을 잠그고 개수를 확인해 지킨다. 구현할 때 확인한다.
- 표 이름은 구조 문서의 복수형 규칙을 따랐다. 네이밍 통일([#29](https://github.com/likelion-backendschool-9th/pawmento/issues/29))의 결과에 맞춘다.

## 정한 것
- API. 경로는 공통 접두사를 뺀 모양이고, 핀 조회와 같이 `/maps` 아래에 둔다. (#73, 고침 #19: 경로에 `pets`를 두지 않기로 한 리뷰를 따름)

  | 요청 | 본문·쿼리 | 성공 응답 |
  | --- | --- | --- |
  | `POST /maps/walks` | `petId` | 201, `walkId`, `startedAt` |
  | `POST /maps/walks/{walkId}/points` | `points`(`latitude`, `longitude`, `recordedAt`) | 204 |
  | `POST /maps/walks/{walkId}/end` | 없음 | 200, `endedAt` |
  | `GET /maps/walks` | `petId`, `date`(`YYYY-MM-DD`) | 200, `walks`(`walkId`, `startedAt`, `endedAt`, `points`) |

- 산책로는 좌표가 시간순으로 쌓이는 데이터라서 위치 하나를 담는 `record_location`과 따로 저장한다. 경로 데이터는 지도 도메인에서만 관리해 다이어리와 겹치지 않게 한다. (#73)
- 반려동물의 존재와 소유는 pet이 판단한다. 산책을 시작할 때 pet의 `GetPetUseCase.get(new GetPetQuery(memberId, petId))`를 부르고, 정상으로 돌아오면 요청한 회원의 반려동물이다. 없으면 404, 다른 회원의 것이면 403이다. 지도는 pet의 입력 포트만 부르고 pet의 도메인·저장소를 직접 쓰지 않는다. `PetResult`에는 소유자 id가 없고 지도가 소유자를 다시 비교할 필요도 없다. (#73, pet 담당 답변: #74 리뷰)
- 좌표 추가와 종료의 본인 확인은 지도가 산책의 `created_by`로 한다. 날짜별 조회는 pet 포트를 부르지 않고 `created_by`와 `pet_id` 조건으로 걸러서, 다른 회원의 반려동물을 조회하면 403이 아니라 빈 목록을 받는다. 지도 핀 조회(#19-S7)와 같은 방식이다. 가족 구성원의 접근 확대는 소유자 기준과 별도 계약으로 다룬다. (#73)
- 산책의 시작과 끝은 보호자가 직접 누른다. 앱이 산책 시작이나 끝을 자동으로 정하지 않는다. (#73)
- 날짜는 Asia/Seoul 기준으로 나눈다. 산책이 속하는 날은 `startedAt`이 속한 날이다. (#73)
- 에러는 [백엔드 예외 처리](../backend-exceptions.md)를 따른다. 규칙 위반은 `RuleViolationException`, 권한 없음은 `PermissionDeniedException`, 상태 충돌은 `StateConflictException`을 상속한 예외로 던진다. (#73)

## 가정
- 좌표는 15초 간격으로 모아 한 번에 보낸다(예: 4개씩). 한 산책에 쌓을 수 있는 좌표는 5,000개이고 한 요청은 최대 100개다. 값은 Q3의 답과 구현할 때 정한다.
- 인증은 [member 문서](../member/README.md#도메인-담당이-쓰는-방법)의 `@LoginMember`를 쓴다.
- 지도 화면과 경로 그리기는 프론트엔드가 지도 SDK로 처리한다. 서버는 좌표 저장과 조회만 맡는다.
