# 정보 지도 검색: 장소 이름·주소, 지역·지하철역

관련 이슈: [#195](https://github.com/likelion-backendschool-9th/pawmento/issues/195), 상위 [#172](https://github.com/likelion-backendschool-9th/pawmento/issues/172) ([정보 지도 계획](animal-places.md))

## 한눈에
- 끝나면: 보호자가 정보 지도 위쪽 검색창에 "서울숲", "강남"을 입력해 병원·미용·보호센터를 이름이나 주소로 찾고, 지역·지하철역을 눌러 그 동네로 지도를 옮긴다. 최근 검색어가 남아 다시 쓸 수 있다.
- 결정 필요: 지역·지하철역(R3)의 **데이터 출처**. 시작 전에 실제로 확인해 정한다([가정](#가정)). 이름·주소 검색(R1)과 검색 화면(R2)은 결정할 것이 없다.
- 규모: 4단계(PR 4개: 문서, API, 화면, 지역·지하철역)
- "내 위치 주변" 보기와 가까운 순 목록은 이 계획이 아니라 [#226](near-me.md)에서 다룬다([범위 밖](#범위-밖)). 검색 화면에는 그 진입 버튼 자리만 둔다.

시안: 정보 지도 검색·내 주변 시안(검색창, 검색 결과, 결과 없음, 지역·역 선택). 시안 속 장소 이름·거리는 예시다.

## 1. 이름·주소 검색 API (#195-R1)
검색어로 병원·미용·보호센터를 이름이나 주소에서 찾는다. 지도 영역과 상관없이 전체에서 찾는다. 반려동물(`petId`)에 의존하지 않고 로그인한 회원이면 누구나 쓴다. 결과는 최대 20개이고 넘으면 잘렸다고 알린다.

요청은 `GET /maps/places/search`이고 `q`(검색어)를 보낸다. 선택으로 `categories`(`HOSPITAL`, `GROOMING`, `SHELTER`를 쉼표로)와 지도 중심 `latitude`·`longitude`(둘을 함께)를 보낸다. 응답은 `places`(영역 조회 `/maps/places`의 장소와 같은 필드에 `distanceMeters` 추가), `truncated`, `dataAsOf`다.

#195-S1 이름으로 찾기 [테스트]
- Given 장소 3곳이 있다: `서울숲 동물병원`(병원), `보리네 펫살롱`(미용, 주소 `서울 성동구 서울숲4길 18`), `강남 24시 동물병원`(병원)
- When  `q=서울숲`으로 조회한다
- Then  200과 `서울숲 동물병원`, `보리네 펫살롱` 2곳을 받는다. 이름과 주소 중 한 곳에 들어 있으면 찾는다. `truncated=false`다
- Then  각 장소는 `GET /maps/places`와 같은 필드(`id`, `category`, `name`, `address`, `phone`, `latitude`, `longitude`, `open24h`, `open24hBasis`, `openingHours`, `closedDays`)와 `distanceMeters`를 가진다. 응답에 `dataAsOf`도 있다(#172-S21과 같은 규칙)

#195-S2 띄어쓰기·표기가 달라도 찾기 [테스트]
- Given `스테이동물병원`이 있다
- When  `q=스테이 동물병원`, `q=스테이(동물병원)`, `q=스테이동물 병원`으로 각각 조회한다
- Then  모두 `스테이동물병원`을 받는다. 띄어쓰기·괄호·구두점·대소문자는 무시하고 비교한다(#172-S15와 같은 기준)
- When  `q=스테이병원`으로 조회한다
- Then  받지 못한다. 글자가 이어서 들어 있어야 찾는다(부분 일치이고 글자 순서가 달라지면 찾지 않는다)

#195-S3 순서 [테스트]
- Given 지도 중심에서 가까운 순으로 `A`(300m), `B`(100m), `C`(1.2km)인 장소가 모두 `강남`에 맞는다
- When  `latitude`·`longitude`를 보내 조회한다
- Then  `B`, `A`, `C` 순서로 받고 각 `distanceMeters`가 있다. 거리는 서버의 `PlaceSelection.meters`(Haversine) 직선거리를 정수 미터로 반올림한 값이다. `140m`, `1.0km` 같은 글자는 화면이 #226-S5의 규칙으로 만든다. 검색과 내 주변이 같은 계산식을 써서 같은 장소의 거리가 다르게 보이지 않는다
- When  `latitude`·`longitude`를 보내지 않고 조회한다
- Then  이름이 검색어로 시작하는 곳, 이름에 검색어가 든 곳, 주소에만 든 곳 순이고 같은 묶음 안에서는 이름순이다. `distanceMeters`는 `null`이다

#195-S4 종류 거르기와 겹침 제거 [테스트]
- Given `북악동물병원`(병원)과 같은 이름의 미용 장소가 30m 안에 있고, 이름이 다른 미용 장소 1곳이 있다
- When  `q=북악`, `categories=HOSPITAL,GROOMING`으로 조회한다
- Then  병원 하나만 나온다(#172-S15). 이름이 달라 겹치지 않는 장소는 나온다
- When  `categories=GROOMING`만 보낸다
- Then  병원이 요청에 없으므로 그 미용 장소가 그대로 나온다. `categories`를 보내지 않으면 세 종류를 모두 찾는다

#195-S5 20개 넘음 [테스트]
- Given `서울`에 맞는 장소가 21개 있다
- When  `q=서울`로 조회한다
- Then  20개와 `truncated=true`를 받는다. 순서(#195-S3)의 앞쪽 20개다. 겹침 제거 **뒤** 개수가 20을 넘을 때만 `true`다

#195-S6 잘못된 요청 [테스트]
- When  `q`가 없거나 앞뒤 공백을 지우고 2자 미만이거나 30자 넘거나, `latitude`만 있고 `longitude`가 없거나(반대도), 위도가 91이거나, `categories`에 `CAFE` 같은 없는 종류가 있다
- Then  400과 이유를 받는다. 검색어가 너무 짧거나 길다는 이유도 이 응답에 담아 화면이 안내하게 한다
- When  `q=_ _`처럼 정규화하면 비는 값(공백·구두점뿐)을 보낸다
- Then  400이다. 길이는 정규화한 뒤에 센다

#195-S7 로그인 없음 [테스트]
- Given 로그인하지 않았다
- When  `GET /maps/places/search`를 부른다
- Then  401을 받는다. 정보 지도는 로그인한 회원만 쓴다(#172-S14)

#195-S8 결과 없음 [테스트]
- Given 어떤 장소도 `동물카페`에 맞지 않는다
- When  `q=동물카페`로 조회한다
- Then  200과 빈 `places`, `truncated=false`를 받는다. 오류가 아니다
- When  `q=%%`나 `q=a\b`처럼 `LIKE` 특수문자가 든 검색어를 보낸다(정규화한 뒤 2자 이상)
- Then  특수문자를 글자 그대로 찾으므로 모든 장소에 맞지 않고 빈 `places`를 받는다(escape하지 않으면 `%%`가 모든 장소에 맞는다)

#195-S19 이미 저장된 장소도 찾기 [테스트]
- Given 이름·주소를 정규화한 열(`name_key`, `address_key`)이 비어 있는 장소가 저장돼 있다(열을 더하기 전에 가져온 장소)
- When  서버가 시작한다
- Then  비어 있는 행의 열을 채운다. 이미 채워진 행은 다시 쓰지 않는다
- When  `q`로 조회한다
- Then  채워진 뒤에는 새로 가져온 장소와 같이 찾는다. 다음 가져오기에서 같은 장소를 갱신해도 열 값이 바뀌지 않으면 그대로다

## 2. 검색 화면과 최근 검색어 (#195-R2)
정보 지도의 검색창에서 입력하고, 결과를 눌러 지도와 카드로 이동한다. 최근 검색어를 이 기기에 남긴다.

#195-S9 검색창 열기 [직접]
- Given 정보 지도가 열려 있다
- When  위쪽 검색창을 누른다
- Then  검색 화면이 열리고 입력 칸에 커서가 있다. 최근 검색어가 있으면 목록으로, 없으면 안내 문구가 보인다
- Then  "내 위치 주변 보기" 줄이 자리에 있고 누르면 [#226](near-me.md)의 "내 위치" 동작(#226-S1)을 시작한다. #226의 화면이 머지되기 전에는 이 줄을 숨긴다

#195-S10 입력하면 결과가 나온다 [직접]
- When  두 글자 이상 입력한다
- Then  멈추고 250ms 뒤에 검색한다(입력 중에는 부르지 않고, 이전 요청은 버린다). 결과는 종류 아이콘·이름·종류와 주소·24시 표시·지도 중심에서의 거리로 보이고, 입력한 글자가 이름·주소에 그대로 들어 있으면 그 글자를 강조한다. 띄어쓰기가 달라 찾은 경우는 강조 없이 보인다
- When  한 글자만 입력하거나 지운다
- Then  검색하지 않고 최근 검색어(없으면 안내)로 돌아간다
- Then  20개를 넘으면 목록 아래에 "더 있어요. 더 자세히 입력해 보세요"가 보인다

#195-S11 결과를 눌러 이동한다 [직접]
- When  결과 하나를 누른다
- Then  검색 화면이 닫히고 지도가 그 장소로 옮겨 가며 마커가 선택되고 장소 카드가 열린다(#172-S17의 카드). 검색창에는 입력했던 검색어가 남고 ✕로 지운다
- Then  지도가 옮겨 간 뒤의 영역 조회에서도 그 장소가 선택된 채 유지된다
- When  ✕를 누르거나 카드를 닫는다
- Then  선택이 풀리고 검색어가 지워진다. 종류 칩과 지도는 그대로다

#195-S12 결과 없음 [직접]
- When  검색 결과가 하나도 없다
- Then  "'동물카페'와 맞는 장소가 없어요"와 이유(지금은 동물병원·동물미용·동물보호센터만 찾을 수 있다는 것), 다른 검색어 제안(종류 이름 등)이 보인다. 오류가 아니라는 것이 분명해야 한다

#195-S13 오류와 다시 시도 [직접]
- Given 서버에 연결되지 않았거나 5xx를 받았다
- When  검색한다
- Then  예시 결과로 바꾸지 않고 오류 안내와 "다시 시도"가 보이며, 누르면 같은 검색어로 다시 부른다. 검색어와 최근 검색어는 그대로다(#172-S19와 같은 원칙)

#195-S14 최근 검색어 [테스트·직접]
- Given 이 기기의 브라우저에 최근 검색어가 없다
- When  검색 결과에서 장소를 누르거나 키보드의 검색을 눌러 "서울숲"을 검색한다
- Then  "서울숲"이 최근 검색어 맨 앞에 저장된다. 같은 검색어(띄어쓰기·대소문자를 무시하고 같으면)는 중복 없이 맨 앞으로 옮긴다. 최대 10개이고 넘으면 가장 오래된 것부터 지운다
- When  최근 검색어를 누른다
- Then  그 검색어로 바로 검색한다
- When  ✕ 또는 "전체 삭제"를 누른다
- Then  그 검색어 하나 또는 전부 지워진다
- Then  최근 검색어는 이 기기 브라우저에만 저장한다. 서버에 보내거나 다른 기기와 맞추지 않는다. 계정마다 따로 저장해, 같은 기기를 다른 사람이 써도 섞이지 않는다. 저장소를 쓸 수 없으면(사생활 보호 모드 등) 오류 없이 이번 방문 동안만 기억한다
- [테스트] 저장·중복·개수 제한·손상된 값(JSON이 깨졌거나 형식이 다름)은 무시하고 빈 목록으로 시작하는 것은 순수 로직 테스트로 확인한다

## 3. 지역·지하철역 검색 (#195-R3)
검색어에 맞는 지역과 지하철역을 후보로 보여 주고, 누르면 지도를 그곳으로 옮긴다. R1·R2가 끝난 뒤에 따로 한다. 응답에 `areas` 목록을 **더한다**(R1의 `places`는 그대로). 후보 하나는 `type`(`STATION` 또는 `REGION`), `name`, `description`(역은 노선, 지역은 상위 지역), `latitude`, `longitude`를 가진다.

데이터 출처는 시작 전에 정한다([가정](#가정)). 아래 시나리오는 출처와 상관없이 성립하게 썼다.

#195-S15 지하철역 찾기 [테스트·직접]
- Given 역 `강남역`(2호선·신분당선)이 있다
- When  `q=강남`으로 조회한다
- Then  `areas`에 `강남역`(`STATION`, 설명 `2호선 · 신분당선`)이 있고, `places`에는 이름·주소에 `강남`이 든 장소가 있다. 둘은 서로 영향을 주지 않는다
- Then  화면에는 "지역·지하철역"과 "장소 이름" 두 묶음으로 나뉘어 보인다. 지역·역 후보는 최대 5개, 장소는 최대 20개다

#195-S16 지역 찾기 [테스트·직접]
- Given 지역 `서울 강남구`가 있다
- When  `q=강남`으로 조회한다
- Then  `areas`에 `서울 강남구`(`REGION`, 설명 `지역`)가 있다. 같은 이름이 여러 곳이면 모두 보이고 설명으로 구분한다

#195-S17 지역·역을 눌러 이동한다 [직접]
- When  `강남역` 후보를 누른다
- Then  검색 화면이 닫히고 지도가 그 역 위치로 옮겨 가며 초록색 역 마커와 이름표가 선다. 그 영역의 병원·미용·보호센터가 평소처럼 보인다
- Then  검색창에는 "강남역"이 남고, 이 선택으로 영역 조회가 다시 일어난다. 최근 검색어에도 저장된다(#195-S14)
- Then  그 지점 기준의 가까운 순 목록은 [#226-S9](near-me.md)에서 다룬다. 이 단계에서는 이동과 선택 지점 표시까지만 한다

#195-S18 지역 검색을 쓸 수 없을 때 [테스트·직접]
- Given 지역·지하철역을 찾는 데이터나 외부 서비스가 실패하거나 한도를 넘었다
- When  `q=강남`으로 조회한다
- Then  `places`는 정상으로 받고 `areas`는 `null`이다(빈 목록과 구분한다)
- Then  화면은 장소 이름 묶음은 그대로 보이고, 지역·지하철역 묶음 자리에 "지금은 지역·지하철역 검색을 쓸 수 없어요"를 보인다. 전체 검색을 막지 않는다

## 범위 밖
- **내 위치 주변 보기와 가까운 순 목록**: 위치 권한과 현재 위치 표시, 반경(500m·1km·3km), 권한이 꺼졌을 때의 안내가 필요해서 [#226](near-me.md)으로 나눴다. 이 계획은 지도 중심 기준 거리만 쓴다.
- 영업 중·영업 시간 검색(원본 데이터에 없음), 길찾기, 리뷰, 즐겨찾기
- 검색어 자동완성(입력 중 제안)과 검색어 통계. 입력 중 결과가 곧 제안이다.
- 서버에 최근 검색어 저장, 기기 간 동기화
- 종류가 장소가 아닌 것(카페·공원 등)을 찾는 검색. 지금은 병원·미용·보호센터만 있다([정보 지도 범위 밖](animal-places.md#범위-밖))

## 정한 것
- 검색은 **서버가 우리 DB(`places`)에서** 찾는다. 화면에 있는 영역의 장소만으로는 다른 동네의 장소를 찾을 수 없고, 장소 데이터는 이미 우리 DB에 있다. (#195)
- 응답에 지도 중심을 받아 거리를 계산하는 이유: 같은 이름이 전국에 여럿일 수 있어, 지금 보고 있는 곳과 가까운 것을 먼저 보여 준다. 중심을 보내지 않아도 쓸 수 있다. (#195)
- 이름 비교는 #172-S15와 같은 기준(띄어쓰기·괄호·구두점·대소문자 무시)이고, 이름 비교 코드를 두 곳에 두지 않는다. 그래서 `PlaceSelection.comparableName`으로 정규화한 이름·주소를 **처음부터 열(`name_key`, `address_key`)로 저장**하고, 검색은 같은 함수로 정규화한 검색어를 그 열에 `LIKE '%…%'`로 찾는다. SQL(`regexp_replace` 등)에 규칙을 다시 쓰지 않고, 메모리에서 거르지도 않는다. 열은 가져오기에서 장소를 저장할 때 함께 채운다. 이미 저장된 장소는 열이 비어 있으므로 서버가 시작할 때 비어 있는 행을 한 번 채운다(다음 가져오기까지 기다리면 그동안 검색에서 빠진다). (#195, #194)
- 검색어는 2자 이상 30자 이하이다. 한 글자는 맞는 곳이 너무 많고, 30자는 장소 이름·주소 일부로 충분하다. 길이는 `comparableName`으로 정규화한 **뒤**에 센다(공백·구두점뿐인 검색어는 빈 값이라 400). (#195)
- 정규화한 검색어는 `LIKE`에 넣기 전에 `%`·`\`를 `\`로 escape하고(`ESCAPE '\'`) 글자 그대로 찾는다. `comparableName`은 `_`는 지우지만 `%`는 남겨서, escape하지 않으면 `q=%%`가 모든 장소에 맞는다. (#195)
- 지역·지하철역은 `areas`로 **같은 응답에 더한다**. R1의 응답은 바꾸지 않아 R3이 R1·R2의 화면을 깨지 않는다. (#195)
- 최근 검색어는 기기 브라우저에 저장한다. 서버에 검색 기록을 남기지 않아 개인정보를 늘리지 않는다. (#195)
- 사용자가 입력한 검색어는 장소와 비교만 하고 애플리케이션의 로그·오류 응답에는 남기지 않는다. 장소 이름은 공개 데이터지만 검색어는 개인이 입력한 값이다. 서버 앞의 프록시 기록은 [가정](#가정)에서 따로 확인한다. (#195)
- 로그인한 회원만 쓴다. (#172-S14과 같음)

## 가정
- 장소가 약 1.5만 곳이라 정규화한 열에 `LIKE '%…%'`를 해도 충분히 빠르다. 이 방식은 인덱스를 쓰지 못하고 전체를 훑는다. 구현 전에 실제 데이터로 재고(목표: 한 번에 100ms 이하), 초과하면 `pg_trgm` 인덱스를 더한다. 측정은 맞는 장소가 적은 검색어(`스테이`)뿐 아니라 많은 검색어(`서울`처럼 주소에 걸리는 곳이 수천 곳)로도 한다. 정렬과 `distanceMeters` 계산이 늘어나는 비용도 같이 잰다.
- 검색어 `q`는 `GET` 주소(쿼리스트링)에 담겨 가므로 서버 앞의 프록시(nginx)와 Cloudflare 요청 기록에 남을 수 있다. 구현 전에 확인하고, 남으면 문구를 고칠지 요청 방식을 `POST`로 바꿀지 그때 정한다. 지도 영역 조회와 같은 확인이다([#226-S10](near-me.md)).
- 결과 20개와 최근 검색어 10개는 화면에 한 번에 보기 좋은 크기로 잡은 값이다. 써 보고 바꿀 수 있다.
- 거리는 기존 `PlaceSelection.meters`(Haversine)로 구한 지도 중심과 장소의 직선거리다. 도로 거리가 아니다. 내 주변(#226)도 같은 식을 쓴다.
- **R3의 데이터 출처는 아직 정하지 못했다.** 시작 전에 아래를 실제로 확인하고 고른다.
  - 지하철역: 전국도시철도역사정보표준데이터(공공데이터포털 15013205, 국가철도공단, 역 위·경도 포함, XLSX)를 우리 DB에 적재하는 방법. 정보 지도의 "공공데이터를 우리 DB에 적재" 결정과 같은 방식이고 호출 한도와 키가 없다. 새 역이 생기면 파일을 다시 받아야 한다.
  - 지역(시·군·구·동): 적재할 만한 파일이 있는지, 아니면 외부 검색 서비스를 쓸지.
  - 외부 서비스를 쓰면: 서버가 대신 불러 키를 숨기고, 호출 한도와 이용 조건을 확인한다. 현재 서버의 네이버 지도 연동은 좌표를 주소로 바꾸는 역지오코딩만 있다.
- 구현 전에 확인할 것: 네이버 클라우드 Geocoding에 "강남역"을 넣어 지하철역이 나오는지(공식 문서는 주소를 좌표로 바꾸는 기능으로 설명해, 역 이름이 나온다고 보장하지 못한다), 다른 후보(네이버 검색 API의 지역 검색 등)의 호출 한도와 이용 조건.
