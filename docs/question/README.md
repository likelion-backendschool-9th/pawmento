# 질문 관리와 가족 질문·답변

백엔드 개발 설계 초안이다. 초기 데이터로 준비한 모드별 질문 풀, 가족 공통 질문 진행, 가족 구성원의 개별 답변을 다룬다. 관리자 질문 관리 API·화면은 사용자 질문·답변 흐름 이후에 구현한다. 아래 ‘확정한 사용자 요구’는 사용자가 정한 동작이고, 데이터·API·권한의 세부 설계는 구현 전 검토할 제안이다.

## 확정한 사용자 요구

- ACTIVE는 함께 지내는 일상을 묻는다. 예: “요즘 우리 아이가 가장 좋아하는 놀이는 무엇인가요?”
- GARDEN은 함께했던 기억을 묻는다. 예: “우리 아이와 처음 만났던 날은 어땠나요?”
- 질문·답변은 다이어리와 별개다. 질문 답변을 다이어리 엔티티나 공통 기록의 한 종류로 저장하지 않는다.
- 날짜가 지나도 미답변 질문을 유지한다. 자정이나 재접속만으로 질문이 바뀌지 않는다.
- 답변 날짜는 질문을 받은 날이 아니라 실제 답변을 등록한 날이다. 수정 시 최초 답변 날짜를 바꾸지 않는다.
- 가족은 같은 반려동물의 공통 질문을 본다. **한 명이 답하면 가족 모두 다음 질문으로 이동한다.** 구성원별 질문 진행 상태를 두지 않는다.
- 사진·음성 녹음을 답변에 첨부한다. 업로드·검증·열람·삭제까지 공통 media 기능으로 이번 범위에서 구현한다.
- 같은 질문에도 가족 여러 명이 각각 답변할 수 있다. 답변마다 누가 작성했는지 표시한다. 아이·날짜 단위 답변 하나 제한은 없다.

## 용어와 도메인 분리

| 개념 | 이름 | 의미 |
| --- | --- | --- |
| 질문 풀의 원본 질문 | `Question` | ACTIVE/GARDEN 분류, 질문 본문·활성 여부 |
| 아이에게 제시된 질문 | `QuestionPrompt` | 특정 아이·모드에 배정된 질문 회차, 당시 질문 스냅샷 |
| 가족 구성원의 답변 | `QuestionAnswer` | 배정된 질문에 남긴 개인 답변, 작성자·등록일 |
| 가족 공통 진행 위치 | `QuestionProgress` | 아이·모드마다 하나인 현재 질문 포인터 |
| 자유 일기 | `DiaryEntry` | [다이어리](../diary/README.md)의 별도 개체. 질문 필드 없음 |

`DailyQuestion`처럼 날짜 단위 교체를 암시하는 개체 이름은 사용하지 않는다. 화면의 ‘오늘의 질문’ 문구는 유지할 수 있지만 의미는 ‘현재 답을 기다리는 질문’이다.

프론트의 `Memory.type === DIARY`는 실제로 질문 답변을 뜻하는 잘못된 이름이다. 신규 구조에서는 `QuestionAnswer`로 분리한다. 단순히 문자열을 바꾸는 데 그치지 않고 저장소·조회·검증도 분리한다. 기존 데모 이관은 아래 ‘프론트 연결’에서 다룬다.

## 질문 배정과 진행

1. 가족이 선택한 아이의 **현재 모드**에 맞는 활성 질문 중 하나를 서버가 배정한다. 배정 시 본문과 모드를 스냅샷으로 보존한다.
2. 진행 위치는 `(petId, mode)`별 하나다. 가족·기기·회원이 달라도 같은 아이와 모드에서는 동일한 현재 질문을 본다.
3. 배정과 상태 변화는 POST로 수행한다. GET은 저장하지 않는다. 첫 진입 POST는 이미 열린 질문이 있으면 그대로 반환한다.
4. 열린 질문은 일수 제한 없이 유지한다. 예: 11월 17일 받은 질문에 11월 20일 답하면 답변 날짜는 **11월 20일**이다.
5. 현재 질문의 첫 답변이 저장되면 그 질문을 완료 처리하고 공통 진행 위치를 다음 배정 대기 상태로 바꾼다. 답변 저장과 진행 갱신은 같은 DB 트랜잭션이다. 다음 질문 보장 POST로 다음 질문을 배정한다.
6. 이미 완료한 질문도 가족의 질문 이력에서 열 수 있다. 다른 가족은 그 질문에 자기 답변을 추가할 수 있으며, 이 추가 답변은 현재 질문을 다시 진행시키지 않는다.
7. 다른 가족의 동시 답변은 모두 성공할 수 있다. 완료 처리는 최초 한 번만, 다음 질문 배정도 한 번만 일어나야 한다.
8. 배정 후 관리자가 원본 질문을 수정·비활성화해도 현재 질문과 과거 답변의 문구는 유지한다. 비활성화는 새 배정에만 적용한다. 물리 질문 삭제 API는 제공하지 않는다.
9. 활성 풀이 비어도 기존 질문 조회·답변 저장은 가능하다. 다음 질문 배정 요청만 409 `CONFLICT`와 안내를 반환한다. 다음 질문 부재 때문에 이미 작성한 답변 저장을 취소하지 않는다.
10. 모드를 바꾸면 새 모드의 질문 진행 위치를 불러온다. 이전 모드의 열린 질문과 이력은 보존하고, 다시 돌아오면 이어 본다. 다른 모드로 넘어온 뒤 이미 열어둔 편집창에서 답변을 제출하는 경합은 409로 안내하고 입력을 보존하는 안을 제안한다. 과거 모드 질문의 답변 추가는 해당 모드로 전환한 뒤 허용한다.

같은 가족이 같은 질문에 답변을 여러 개 남길지는 사용자 요구로 확정되지 않았다. **질문 회차당 구성원 한 답변**을 기본 제안한다. 가족 A·B·C는 각각 하나씩 남기고, 자기 답변은 수정한다. 같은 회원의 중복 클릭·동시 저장은 DB 제약으로 막는다. 하루 답변 수 제한은 두지 않는다.

답변을 수정하거나 삭제해도 공통 질문 진행을 되돌리지 않는 안을 제안한다. 삭제 후 재답변은 가능하지만 이미 열린 다음 질문에는 영향을 주지 않는다.

## 데이터 구조 제안

질문 데이터는 실제 diary 저장소와 별도 테이블로 보관한다. 테이블 이름은 기존 단수 `question`, `question_prompt`, `question_progress`, `question_answer`를 유지하며 공통 이름 정리는 #29의 결정을 따른다. (고침 #31: 일부 테이블만 복수화하지 않음) 삭제된 record·memory 샘플이나 `records` 테이블을 재사용한다는 전제를 두지 않으며 질문 답변 ID는 지도 계약의 `diaryId`와 독립이다. (고침 #80: 폐기 샘플과 diary 물리 테이블 이름 전제 제거)

| 테이블 | 핵심 필드·제약 |
| --- | --- |
| `question` | `id`, `seed_key`(초기 데이터용·nullable UNIQUE), `mode`(ACTIVE/GARDEN), `content`(300), `enabled`, `created_at`, `updated_at`, `version` |
| `question_prompt` | `id`, `pet_id`, `mode`, `question_id`, `question_snapshot`(300), `sequence`, `assigned_at`, `completed_at`(nullable); UNIQUE(`pet_id`, `mode`, `sequence`) |
| `question_progress` | `pet_id`, `mode`, `current_prompt_id`(nullable), `next_sequence`, `version`; PK(`pet_id`, `mode`) |
| `question_answer` | `id`, `prompt_id`, `author_member_id`, `author_name_snapshot`, `content`(3000), `answered_at`, `answered_date`, `updated_at`, `version`; UNIQUE(`prompt_id`, `author_member_id`) |
| `question_answer_attachment` | `id`, `answer_id`, `asset_id`, `sort_order`; 다이어리 첨부 연결 행과 별개 |

- `answered_at`은 서버의 실제 최초 저장 시각(UTC)이다. `answered_date`는 그 시각을 Asia/Seoul로 변환한 날짜다. 둘은 동일 시계 값에서 한 번에 계산한다. 클라이언트가 과거 날짜를 지정하지 못한다.
- 수정 시 `updated_at`만 바뀐다. `answered_at`, `answered_date`, 작성자, 배정 질문은 변경할 수 없다.
- `assigned_at`과 `completed_at`은 질문 진행 정보이고 답변의 날짜가 아니다.
- 작성자는 `@LoginMember`에서 결정한다. 작성자 이름 스냅샷은 이후 닉네임 변경·가족 탈퇴에도 누가 남긴 답변인지 표시하기 위한 제안이다. 회원 탈퇴 시 표시·익명화 정책은 별도 확정한다.
- 질문 배정 ID·본문·모드는 서버 저장값을 사용한다. 요청 본문의 임의 질문 문구나 작성자 ID는 신뢰하지 않는다.
- 진행 행 잠금 또는 조건부 갱신, 유니크 제약으로 중복 배정을 방지한다. 최초 진행 행 생성 경합도 다룬다.
- 답변 저장과 최초 완료 처리의 원자성을 보장한다. 과거 질문의 다른 가족 답변 추가는 현재 포인터를 건드리지 않는다.
- 목록 인덱스는 질문 `(pet_id, mode, assigned_at DESC, id DESC)`, 답변 `(prompt_id, answered_at, id)`부터 검토한다. 답변 날짜별 조회는 권한 범위를 포함한 실제 쿼리로 실행 계획을 확인한다.

## API 제안

경로는 공통 `/api/v1` 접두사를 제외했다. 최신 `WebConfig`가 접두사를 적용하므로 개별 컨트롤러에 중복 작성하지 않는다. 사용자 질문·답변은 `/questions`, 관리자 원본 관리는 `/admin/questions` 아래에 둔다. (고침 #31: PR #163 관리자 API 경로 통일) 사용자 API의 petId는 필수 양의 Long 쿼리이며 관리자 질문 풀 API는 아이 범위를 받지 않는다. (고침 #31: 사용자 흐름 우선 계획과 공통 API 경로 기준 반영)

| 요청 | 입력 | 응답 |
| --- | --- | --- |
| `GET /admin/questions` | `mode`, `enabled`, `q` 선택, `page`, `size` | 200, 질문 목록 |
| `GET /admin/questions/{questionId}` | 없음 | 200, 비활성 항목 포함 질문 원본 상세 |
| `POST /admin/questions` | `mode`, `content` | 201, 생성 질문 |
| `PATCH /admin/questions/{questionId}` | `content`, `enabled`, `version` | 200, 변경 질문. 모드 변경 대신 해당 모드 질문 신규 등록 |
| `POST /questions/prompts/current?petId={petId}` | 없음. 서버가 현재 pet 모드 확인 | 새 배정 201, 기존 질문 200 |
| `GET /questions/prompts/current?petId={petId}` | 없음 | 200, 현재 질문. 미배정은 `prompt: null` |
| `GET /questions/prompts?petId={petId}` | `mode` 선택, `page`, `size` | 200, 가족 공통 질문 이력·답변 수·내 답변 ID |
| `GET /questions/prompts/{promptId}?petId={petId}` | 없음 | 200, 질문과 가족 답변 목록 |
| `POST /questions/prompts/{promptId}/answers?petId={petId}` | `content`, `attachmentIds` | 201, 내 답변·질문 완료 여부·다음 배정 필요 여부 |
| `GET /questions/answers?petId={petId}` | `mode`, `promptId`, `authorMemberId`, `from`, `to` 선택, `page`, `size` | 200, 가족 답변 이력 |
| `GET /questions/answers/{answerId}?petId={petId}` | 없음 | 200, 답변 상세 |
| `PATCH /questions/answers/{answerId}?petId={petId}` | `content`, `attachmentIds`, `version` | 200, 본인 답변 변경 |
| `DELETE /questions/answers/{answerId}?petId={petId}&version={version}` | 필수 version 쿼리 | 204, 본인 답변 삭제 |

답변은 필수 content와 선택 사진·음성 attachmentIds를 지원한다. 연결·교체·삭제·인증 파일 조회는 [첨부 계약](question-flow.md#사진음성-첨부-연결-계약)을 따른다. 상세 경계는 [텍스트 답변 계약](question-flow.md#텍스트-답변-단위의-api저장-계약)을 따른다. DELETE도 필수 version으로 충돌을 검사한다. (고침 #31: 텍스트 단위와 삭제 버전 계약 확정)

PATCH는 제공한 변경 필드만 적용하고 `version`을 필수로 받는다. `attachmentIds: []`는 첨부 전체 제거다. 답변 내용은 공백 제거 후 1~3,000자이며, 질문·모드·작성자·등록일 필드는 수정할 수 없다.

답변 응답은 `answerId`, `petId`, `promptId`, `mode`, `questionId`, `question`(스냅샷), `author: {memberId, displayName}`, `content`, `attachments`, `answeredAt`, `answeredDate`, `updatedAt`, `version`이다. `diaryId`와 `recordedDate`는 사용하지 않는다.

답변 목록은 `answeredAt DESC, answerId DESC`, 질문 이력은 `assignedAt DESC, promptId DESC`로 정렬한다. `from/to`는 **답변 등록 날짜** 기준·양 끝 포함이다. 등록일이 다른 가족 답변은 각각 자신의 날짜에 조회된다. `page`는 0부터, `size` 기본 20·최대 100이며 응답은 `items`, `page`, `size`, `totalElements`, `totalPages`다.

질문 상세의 가족 답변도 무제한 중첩하지 않는다. 첫 페이지와 답변 수를 제공하고 전체 답변은 답변 목록에 `promptId` 필터를 추가해 조회하는 안을 제안한다.

관리자 목록 검색·상세·입력·충돌·스냅샷 보존의 세부안은 [6단계 계획](question-flow.md#6단계-관리자-질문-관리-api)을 따른다. (고침 #31: 가족 API와 독립적인 관리자 백엔드 계획 구체화)

## 가족 권한과 의존성

- 가족은 공용 로그인 하나가 아니라 **회원별 로그인 + 아이에 대한 가족 멤버십**으로 식별한다. 공유 비밀번호를 쓰면 누가 작성했는지 확인할 수 없다.
- pet/가족 도메인의 입력 포트로 현재 멤버십과 읽기·쓰기 권한을 확인한다. 현재 프론트의 OWNER/EDITOR/VIEWER 역할을 기준으로 OWNER·EDITOR는 답변 가능, VIEWER는 조회만 가능하도록 제안한다.
- 가족은 해당 아이의 답변을 함께 볼 수 있다. 답변 수정·삭제는 작성자 본인만 가능하도록 제안한다. 소유자라는 이유만으로 다른 가족의 답변을 수정하지 못한다.
- 가족에서 나가거나 권한이 회수되면 이후 읽기·쓰기 요청 모두 거부한다. JWT에 로그인 정보가 남아 있어도 멤버십은 서버에서 재확인한다.
- 현재 소유자 범위는 pet의 기존 접근 계약을 재사용하여 다른 소유자의 아이는 403, 없는 아이는 404로 응답한다. 아래 비가족/없는 아이 404 통일은 가족 연결 후의 목표 계약이며 현재 소유자 단계의 응답과 구분한다. (고침 #31: 소유자 범위는 pet 계약에 따라 403)
- 미인증 401, 관리자 API·읽기 전용 역할의 쓰기·타 가족 답변 변경 403, 비가족/없는 아이·질문·답변 및 경로 불일치 404, 잘못된 입력 400, 중복 답변·버전·모드 충돌 409다. 기존 `{code, message}` 에러 형식을 따른다.
- ADMIN만 질문 풀을 관리한다. 관리자 역할이 개인 가족 답변 열람 권한을 자동 부여하지 않는다.
- 관리자 질문 API는 `/admin/questions` 아래에 두고 question 웹 어댑터의 `AdminQuestionController`로 사용자 컨트롤러와 분리한다. 보안 설정은 `/api/v1/admin`·`/api/v1/admin/**`를 공통 `hasRole("ADMIN")` 검사한 뒤 일반 인증 규칙을 적용한다. (고침 #31: PR #163 관리자 경로·컨트롤러 통일 선택 반영) 각 관리자 입력 유스케이스도 질문의 관리자 확인 출력 포트로 member 입력 포트의 현재 역할을 확인해 웹을 거치지 않은 호출·역할 회수를 검증한다. member 조회 DTO·엔티티를 question 핵심에 노출하지 않으며 미인증 401·일반 회원/역할 회수 403·조회 장애는 서버 오류로 구분한다. 전역 메서드 보안 설정을 이번 문서에서 추가하지 않는다. (고침 #31: 관리자 경로 변경에 따른 권한 경계 명시)
- `com.pawmento.question`의 domain/application/adapter 구조를 사용한다. 입력 포트 후보는 `CreateQuestionUseCase`, `EditQuestionUseCase`, `ListQuestionUseCase`, `EnsureCurrentQuestionPromptUseCase`, `GetCurrentQuestionPromptUseCase`, `ListQuestionPromptUseCase`, `GetQuestionPromptUseCase`, 답변 CRUD·목록 유스케이스다.
- 시간과 질문 선택은 주입 가능한 Clock·출력 포트로 분리한다. 애플리케이션은 Spring Security·웹 DTO·다이어리 저장소를 참조하지 않는다.
- 질문 답변 저장 트랜잭션은 question 안에서 끝난다. **record/diary 입력 포트를 호출해 기록 행을 만드는 구조는 사용하지 않는다.** media 참조 획득/해제 포트만 공유하며, 답변·첨부 연결·파일 참조 수·공통 진행 변경을 같은 DB 트랜잭션으로 저장한다.

## 답변 첨부 저장

- [공통 파일 업로드](../media/README.md)로 파일을 READY까지 준비한 뒤 `attachmentIds`를 답변 저장에 보낸다. 음성은 녹음 결과 파일을 AUDIO로 업로드한다.
- 최초 등록 요청의 모든 파일은 본인 업로드·해당 아이·`QUESTION_ANSWER_ATTACHMENT` 용도·READY여야 한다. 수정 시 기존 첨부 유지와 새 첨부 연결을 구분하고 최대 개수·합계 크기·중복·순서를 검증한다.
- 업로드·검증 중에는 답변 완료로 표시하지 않는다. 파일 업로드 날짜는 답변 등록일이 아니며, 답변 트랜잭션이 성공한 시각으로 `answeredAt/answeredDate`를 기록한다.
- 첨부 연결 실패 시 답변과 가족 공통 진행도 롤백한다. 입력과 업로드된 파일 ID를 유지해 재시도하며 만료/정리된 파일은 재업로드를 안내한다.
- `attachments`는 `assetId`, `type`, `filename`, `mimeType`, `sizeBytes`, `durationMs`, `width`, `height`, `sortOrder`를 반환한다. 실제 파일 열람은 media 문서의 인증된 부모 답변 첨부 content API를 사용한다. 파일당 15MiB 추천안·Docker volume 저장은 media 문서를 따른다.
- 가족은 읽을 수 있는 답변의 연결 파일만 열람한다. 답변 제거/첨부 교체는 연결·참조 수 변경·삭제 작업 등록까지 같은 트랜잭션으로 수행하고 실제 파일 삭제는 비동기로 재시도한다. 다른 글이 쓰는 파일은 보존한다.
- 초기 개수·형식·용량 정책은 media 문서를 단일 기준으로 삼는다. 질문은 첨부 유무와 관계없이 답변 텍스트 1~3,000자가 필수다.

## 프론트 연결·명칭 이관

아래는 현재 데모와의 차이를 해소할 구현 항목이다. 이 문서 수정만으로 프론트 동작이 바뀐 것은 아니다.

1. 기존 `Memory` 혼합 모델에서 `DiaryEntry`와 `QuestionAnswer`를 분리한다. `DIARY` 질문 타입·질문용 `recordedDate`·하루 한 답변 검증을 제거한다.
2. 초기 데이터로 ACTIVE/GARDEN 질문을 준비하고 현재 질문 API에 연결한다. 관리자 화면의 질문 관리 기능은 사용자 흐름을 연결한 뒤 구현한다.
3. 날짜 해시 선정 `PoolQuestionRepository.findForDate`를 공통 현재 질문 배정/조회 포트로 교체한다. 자정마다 새 질문을 계산하지 않는다.
4. 답변 편집기의 날짜 입력을 없애고 저장 결과의 등록일·작성자 이름을 표시한다. 이력 날짜 필터는 `answeredDate`를 사용한다.
5. 가족이 먼저 답해 현재 질문이 바뀌었어도 이미 열어둔 질문 제출은 과거 질문에 대한 내 답변으로 저장할 수 있다. 다른 가족 답변 때문에 내 입력을 버리거나 새 질문에 붙이지 않는다.
6. LocalStorage 데모를 유지할 경우 저장 버전을 올려 기존 `type=DIARY`만 질문 저장소로 옮긴다. 자유 기록은 다이어리에 남기며 ID·질문 스냅샷·내용·기존 작성자와 시각을 보존한다. 과거 데이터의 정확한 등록일·작성자를 알 수 없으면 추측으로 현재 회원·오늘 날짜를 덮어쓰지 않고 ‘이전 데모 기록’으로 식별한다. 재실행 중복·실패 복구를 확인한다.
7. 영상 첨부/촬영 메뉴를 제거하고 공통 업로더의 사진 선택/음성 녹음·미리보기·업로드 진행·실패 재시도를 연결한다. 데이터 URL 대신 서버 파일 ID를 보내고 저장된 첨부는 인증된 파일 content API로 재생한다.
8. 기존 질문 상세 URL은 질문 전용 상세로 연결하고 다이어리에는 질문 이력·첨부가 섞이지 않게 한다. 서버로 데모 데이터를 자동 업로드하지 않는다.

## 작업 순서

[현재 질문과 답변부터 구현하기 — 구현 순서와 완료 경계](question-flow.md#구현-순서와-완료-경계)를 단일 기준으로 삼는다. 관리자 기능은 사용자 질문·답변 흐름 이후이며, 소유자 범위의 구현을 가족 기능 완료로 표시하지 않는다.

## 범위 밖과 아직 정하지 않은 것

- 가족 권한 연결 시 비가족과 없는 아이를 모두 404로 통일할지, 현재 소유자 단계의 403 계약을 유지할지 가족/pet 담당과 확정한다. 아이 존재 여부 노출 정책과 접근 검사·회귀 테스트를 함께 맞춘다.

- AI 질문 생성, 푸시, 질문 통계는 후속 범위다. **모드별 질문과 가족 다중 답변은 이번 범위에 포함한다.**
- 질문 회차당 같은 회원의 답변 한 개, 삭제 후 진행 유지·재작성, 모드별 진행 보존·편집 경합은 텍스트 답변 계약으로 확정한다. 실제 가족 멤버십 검증은 연결 이후에 수행한다. (고침 #31: 텍스트 단위의 진행 계약 확정)
- 같은 질문 반복 회피 기간·질문 소진 시 재배정 정책을 정해야 한다. 초기 제안은 직전 원본 질문을 가능한 한 피하고 풀이 하나일 때만 반복을 허용한다.
- 가족 초대·가입·탈퇴 API는 가족 담당 범위다. 이 작업은 확정된 멤버십·역할 포트에 의존하며, 전 회원 허용 가짜 권한으로 대체하지 않는다.
- 실제 답변이 남은 아이 삭제는 다이어리와 같이 차단하고 모든 답변을 삭제한 뒤 허용한다. 배정 행만으로는 삭제를 막지 않는다. 구성원 탈퇴·회원 탈퇴 후 답변 보존·작성자 표시/익명화 정책은 추가 합의한다. (고침 #31: 아이 삭제의 답변 보존 정책 확정)
- 공통 파일 업로드는 이번 구현 범위다. 저장소·파일 제한·검증 도구의 제안값은 [media 문서](../media/README.md)에서 확정하고 질문 답변의 첨부 연결과 부모 접근 권한은 question이 소유한다.
