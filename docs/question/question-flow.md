# 현재 질문과 답변부터 구현하기 (#31)

[질문 상위 설계](README.md)의 사용자 흐름을 먼저 구현하는 계획이다. 관리자 페이지·관리자 질문 CRUD를 선행 조건으로 두지 않고, 초기 질문 데이터를 준비한 뒤 현재 질문 배정·미답변 유지·답변 저장을 연결한다. 이 문서는 구현 전 검토안이며 단계별 세부 계약은 코드 작성 전에 확정한다.

## 확정한 동작

- ACTIVE는 함께하는 일상, GARDEN은 함께했던 기억을 묻는다.
- 질문은 날짜가 바뀌어도 답변할 때까지 유지한다. 날짜 해시로 매일 바꾸지 않는다.
- 같은 아이·모드의 가족은 같은 현재 질문을 본다. 한 명이 처음 답하면 공통 진행이 다음 질문 배정 대기로 바뀐다.
- 다른 가족도 이전 질문에 자기 답변을 추가할 수 있다. 추가 답변은 현재 진행을 다시 바꾸지 않는다.
- 답변 날짜는 실제 등록 시각을 Asia/Seoul로 변환한 날짜다. 질문 배정일이나 사진 촬영일을 쓰지 않는다.
- 질문·답변은 question의 독립 저장소를 사용한다. 다이어리 행·달력 건수를 생성하지 않는다.
- 사진·음성 첨부는 기존 media 기능과 연결한다. 영상은 추가하지 않는다.

## 구현 순서와 완료 경계

| 순서 | 구현할 내용 | 이 단계에서 확인할 것 |
| --- | --- | --- |
| 1 | ACTIVE/GARDEN 초기 질문 데이터와 Question 도메인 | 관리자 API 없이 모드별 활성 질문을 조회할 수 있음 |
| 2 | 현재 질문 배정·조회·진행 저장소 | 최초 진입 시 한 회차로 수렴하고 재접속·자정 후에도 미답변 질문 유지 |
| 3 | 답변 생성·상세·이력·수정·삭제와 사진/음성 첨부 | 작성자·질문 스냅샷·실제 등록일 보존, 첨부 참조와 함께 저장 |
| 4 | 첫 답변과 공통 진행의 연결·경합 검증 | 가족의 동시 답변은 모두 보존하고 완료 처리는 한 번만 수행 |
| 5 | 가족 멤버십 연결·프론트 API 연결 | 아이별 공동 열람·작성자 표시·본인 변경 권한과 두 계정 흐름 확인 |
| 6 | 관리자 질문 관리 API, 화면은 후속 | 질문 등록·수정·비활성화와 스냅샷 보존. 가족 API 없이 백엔드부터 진행 |

3단계부터 답변 저장과 최초 완료·진행 갱신은 같은 DB 트랜잭션으로 구현한다. 4단계는 이를 나중에 붙인다는 뜻이 아니라 가족 동시 제출·이전 회차 추가 답변까지 검증 범위를 넓히는 단계다. 답변이 저장됐는데 현재 질문이 그대로 남는 중간 상태를 완료로 취급하지 않는다.

작은 PR 단위는 **초기 데이터**, **현재 질문 배정·유지**, **텍스트 답변과 공통 진행**, **답변 첨부**, **가족/화면 연결**, **관리자 기능** 순서로 나눈다. 초기 데이터만 구현한 PR로 질문 전체 완료를 주장하지 않는다.

## 1단계: 초기 질문 데이터

### 준비할 데이터

질문은 자유 일기와 별개의 `question` 테이블에 저장한다. 기존 단수 명칭을 유지하며 테이블 이름 통일은 #29의 결과를 따른다. 필드는 `id`, `seed_key`(초기 데이터 식별자, 일반 질문은 nullable), `mode`, `content`, `enabled`, `created_at`, `updated_at`, `version`으로 제안한다. 초기 질문의 `seed_key`는 유일하며 사용자 답변의 식별자로 사용하지 않는다.

| seed_key 예시 | 모드 | 질문 예시 |
| --- | --- | --- |
| active-play-001 | ACTIVE | 요즘 우리 아이가 가장 좋아하는 놀이는 무엇인가요? |
| active-happy-001 | ACTIVE | 오늘 우리 아이가 가장 신났던 순간은 언제인가요? |
| garden-first-001 | GARDEN | 우리 아이와 처음 만났던 날은 어땠나요? |
| garden-habit-001 | GARDEN | 지금도 떠오르는 우리 아이만의 귀여운 습관은 무엇인가요? |

문구는 초기 콘텐츠 제안이다. 질문 본문은 strip 후 1~300자, 모드는 ACTIVE/GARDEN, 활성 기본값은 true, 최초 version은 0이다. 도메인이 이를 검증한다. 한 모드의 질문이 다른 모드 풀에 섞이지 않아야 한다.

### 배포·재실행 정책

- 초기 질문은 기존 시작 시 SQL 방식에 맞춰 `adapter/out/persistence`의 초기화 어댑터가 실행한다. 다이어리의 `DiarySchemaConfiguration`과 같은 `InitializingBean` 방식으로 실행한다. `EntityManagerFactory` 의존성으로 Hibernate의 스키마 준비 이후 순서를 보장하고, HTTP 요청을 받기 전 빈 초기화 단계에서 `TransactionTemplate`로 하나의 트랜잭션을 열어 `db/question-seed-v1.sql`을 적용하는 안으로 정한다. 새 이관 도구·이력 관리 프레임워크를 선행 도입하지 않는다. 사용자의 첫 GET에서 데이터를 생성하지 않는다. (고침 #31: ApplicationRunner 대신 요청 수신 전 빈 초기화로 질문 풀이 비는 구간 방지)
- 모든 인스턴스는 검사·삽입 전에 동일한 고정 키 `pawmento-question-seed`의 PostgreSQL advisory transaction lock을 획득한다. v1별 키로 나누지 않고 초기화 전체에 같은 키를 사용한다. 잠금·기존 행의 모드 검증·누락 질문 삽입은 같은 연결·트랜잭션에서 수행하며, 잠금은 커밋/롤백 때 해제한다.
- SQL 파일의 v1은 배포 리소스 버전이다. 실행 완료를 메모리 플래그로 기록하지 않고 매번 잠금 안에서 DB의 seed_key를 확인한다. UNIQUE(seed_key)와 누락 키만 넣는 충돌 무시 삽입으로 재실행·여러 인스턴스의 중복 생성을 막는다. 기존 모드 충돌은 삽입 전에 검사하며 충돌·SQL 실패 시 전체 롤백 후 애플리케이션 시작을 실패시킨다.
- 같은 seed_key가 이미 있으면 중복 삽입하지 않고 기존 본문·활성 여부·version을 유지한다. 재시작으로 관리자 수정·비활성화를 되돌리지 않는다.
- 같은 seed_key의 기존 모드가 다르면 임의로 이동시키지 않고 이관 실패로 드러낸다. 초기화는 한 트랜잭션으로 적용한다.
- seed_key는 일반 질문의 본문 중복을 금지하는 제약이 아니다. 이후 관리자 등록 질문의 ID도 DB가 발급한다.
- 이미 운영 중인 질문을 배포마다 전체 삭제하거나 고정 ID로 덮어쓰지 않는다. v1 파일은 배포 후 수정하지 않는다. 새 질문·명시적 데이터 변경은 별도 버전 SQL과 검증으로 추가하며 같은 초기화 잠금을 사용한다. 범용 스키마 이관 관리 방식은 별도 작업으로 남긴다.
- 예외로 #29의 테이블·컬럼 이름 통일 시에는 같은 PR에서 JPA 매핑·이관·시작 시 실행하는 기존 버전 시드 SQL의 물리 이름도 함께 맞춘다. 이는 질문 내용이나 seed_key 값 변경을 허용하는 예외가 아니다. 질문 ID·기존 수정/비활성 상태·잠금 키·재적용 계약을 보존하고 QuestionSeedScenarioTest로 시작·재적용·동시 초기화·롤백을 다시 검증한다. (고침 #31: #29 이름 변경과 배포된 시드 SQL 불변 규칙의 예외 명시)

이 단계는 질문 풀이 필요한 이유만 충족한다. ADMIN 인증·관리자 검색/페이지·관리자 CRUD·관리자 화면은 구현하지 않는다. 상위 #31-S1의 관리자 시나리오는 미완료로 남긴다.

## 2단계: 현재 질문 배정과 유지

- `QuestionPrompt`는 특정 아이·모드에 제시한 회차이며 당시 질문 본문·모드를 스냅샷으로 저장한다.
- `QuestionProgress`는 `(petId, mode)`별 하나다. 회원별 현재 질문 포인터를 만들지 않는다.
- 현재 질문을 보장하는 POST는 열린 질문이 있으면 그대로 반환한다. GET은 조회만 하며 미배정이면 null을 반환한다.
- 최초 동시 요청에도 진행 행과 열린 회차가 하나로 수렴하도록 실제 DB 잠금·유니크 제약을 설계한다.
- 질문 선택은 서버에서 한다. 가능한 경우 직전 원본 질문을 피하고 풀이 하나면 반복을 허용하는 안을 제안한다. 선택 로직은 테스트에서 제어할 수 있게 분리한다.
- 활성 풀이 비면 새 배정만 409다. 현재 질문 조회·기존 질문 답변 저장을 막지 않는다.
- 아이의 현재 모드를 서버에서 확인한다. 모드 전환 시 이전 모드 진행·이력은 보존하고 새 모드 진행을 사용한다.

### 현재 질문 API의 이번 구현 계약

- `GET /api/v1/questions/prompts/current?petId=`는 200과 `{petId, mode, prompt}`를 반환한다. 미배정은 prompt=null이며 진행 행도 만들지 않는다.
- `POST`는 같은 주소로 요청하며 새 배정은 201, 기존 열린 질문이면 200이다. 응답의 prompt는 `{promptId, questionId, question, sequence, assignedAt}`이며 question은 배정 시점 문구다.
- petId는 URL 쿼리에서만 읽는 필수 양의 Long이다. 누락·빈 값·중복·음수·범위 초과는 400이며 헤더·본문으로 대신할 수 없다. 사용자 요청의 모드나 질문 ID를 받아 배정하지 않는다.
- 가족 연결 전에는 pet의 기존 소유자 접근 계약을 사용한다. 비로그인 401, 다른 소유자 403, 없는 아이 404다. 가족 최종 권한 시나리오를 완료 처리하지 않는다.
- 모드는 접근 검사 시 pet 입력 포트가 반환한 현재 모드를 사용하고 응답에도 포함한다. 동시에 모드를 바꾼 요청에 대한 편집창 제출 충돌은 답변 구현 단계에서 다루며, 이번 단계는 모드 전환 후 조회·재진입의 독립 진행 보존을 검증한다.
- 배정 POST는 아이·모드별 고정 advisory transaction lock으로 최초 행이 없는 경우도 직렬화하고, 기존 진행 행은 잠근 뒤 refresh한다. 질문 회차 저장과 진행 포인터/다음 순번 저장은 같은 트랜잭션이다.
- 활성 풀이 비면 신규 POST만 409로 거절하고 진행 행·회차를 남기지 않는다. 이미 열린 질문은 원본 수정·비활성화·빈 풀에도 GET/POST에서 그대로 반환한다.
- 이번에는 답변·최초 완료·이력 페이지·가족 멤버십·프론트·관리자 API를 추가하지 않는다. 아이/회원 삭제 후 배정·답변 보존 정책은 상위 설계의 미정 항목이며, 배정 행만으로 pet 삭제를 새로 차단하는 기능을 추가하지 않는다.

## 3~4단계: 답변과 공통 진행

- `QuestionAnswer`와 답변 첨부 연결 행은 diary와 독립적이다. promptId·질문 스냅샷·작성자는 서버에서 결정한다.
- 텍스트는 strip 후 1~3,000자를 필수로 받는 기존 제안을 유지한다. 사진·음성은 답변을 보완하며 상세 정책은 media 문서를 따른다.
- answeredAt과 answeredDate는 서버의 동일 Clock 값으로 계산한다. 수정 시 최초 등록일·작성자·질문을 바꾸지 않는다.
- 질문 회차당 회원 한 답변을 기본안으로 두고 DB 중복 제약과 버전 충돌을 검사한다. 같은 날짜의 다른 가족 답변을 제한하지 않는다.
- 첫 답변·질문 최초 완료·공통 포인터 변경·첨부 참조는 같은 트랜잭션이다. 첨부 실패나 저장 실패 시 모두 롤백한다.
- 다음 질문은 별도 보장 POST로 배정한다. 다음 풀이 비었다는 이유로 방금 저장한 답변을 취소하지 않는다.
- 이미 완료된 회차의 추가 답변·수정·삭제는 현재 질문 포인터를 변경하지 않는다. 모드가 바뀐 편집창 제출 경합은 상위 문서의 409 제안을 따른다.

### 텍스트 답변 단위의 API·저장 계약

소유자 범위에서 답변 CRUD·목록과 최초 완료를 구현한다. 사진/음성 첨부 연결 계약은 아래 절을 따른다. 실제 가족 멤버십·프론트·관리자·질문 회차 목록/상세 API는 후속 단위다.

- 생성은 `POST /api/v1/questions/prompts/{promptId}/answers?petId=`에 `{content}`를 보내며 201과 `{answer, completedNow, nextAssignmentRequired}`를 반환한다. `completedNow`는 이번 요청이 최초 완료했는지, `nextAssignmentRequired`는 해당 모드의 현재 질문 배정이 필요한지다. 답변과 최초 완료·포인터 해제는 한 트랜잭션이며 다음 질문 배정을 직접 호출하지 않는다.
- 상세·목록·수정은 상위 설계의 `/questions/answers` 주소를 사용한다. 목록 필터는 mode/promptId/authorMemberId/from/to, 정렬은 answeredAt DESC·answerId DESC, page 기본 0·size 기본 20/최대 100이다. from/to는 한국 등록일 양 끝 포함이다. 목록과 건수, 상세의 답변·첨부·메타데이터는 각각 독립적인 읽기 전용 REPEATABLE_READ 트랜잭션으로 조회한다. 기존 트랜잭션에서 호출해도 REQUIRES_NEW로 분리해 답변 version과 첨부가 다른 커밋 시점으로 섞이지 않게 한다. (고침 #31: 상세 응답의 버전·첨부를 동일 스냅샷으로 조회)
- PATCH는 version 필수·content 선택이다. 최초 작성자·이름 스냅샷·등록 시각·한국 등록일·질문은 보존한다. 서버 결정 필드를 body에 넣으면 400이다. attachmentIds는 생략하면 기존 연결을 유지하고, 배열을 보내면 전체 교체한다. 응답 attachments는 아래 첨부 계약의 메타데이터를 제공한다. (고침 #31: 사진·음성 첨부 연결)
- content를 생략하고 attachmentIds도 생략하거나 기존과 동일하게 보낸 PATCH는 권한·모드·버전 검사 후 현재 값을 200으로 반환한다. 첨부 배열이 달라지면 본문 없이도 updatedAt·version을 갱신하되 최초 등록일·작성자·질문·진행은 유지한다. 같은 Clock 시각이어도 버전은 증가한다. content를 생략하고 첨부도 생략하거나 같은 순서이면 답변 저장·자산 잠금·연결 삭제/삽입·참조 변경도 생략한다. content를 명시하면 기존 본문과 같은 값이어도 수정 요청으로 처리해 updatedAt을 현재 Clock 값으로 설정하고 version을 증가시킨다. (고침 #31: 첨부만 수정하는 요청의 변경 판단)
- 작성자 이름은 회원 입력 포트에서 가져온 서버 데이터다. null·공백이면 사용자의 답변 입력 오류(400)로 취급하지 않고 저장 데이터 오류의 공통 500 응답으로 처리하며 답변·완료·진행은 저장하지 않는다.
- DELETE에도 `?petId=&version=`을 필수로 받아 편집 중 갱신된 답변을 오래된 화면에서 지우지 못하게 한다. 중복 답변·버전 불일치·이전 모드 편집창 제출은 409다. 완료된 회차의 답변을 모두 지워도 완료 시각과 진행은 되돌리지 않는다. 삭제 후 재작성은 가능하며 최초 완료를 다시 수행하지 않는다. (고침 #31: 삭제 버전 계약과 재작성 동작 명시)
- 생성·수정·삭제는 pet의 잠금 조회 입력 포트로 현재 소유자·모드를 확인하고 트랜잭션 끝까지 pet 행 잠금을 유지한다. 모드 변경이 먼저 완료되면 이전 모드 제출은 409이며 답변 저장이 먼저 잠금을 잡으면 저장 커밋 후 모드 변경이 수행된다. 최초 완료는 추가로 아이·모드별 진행 잠금 안에서 처리하고 완료 상태를 다시 읽는다.
- 답변 저장소의 UNIQUE(prompt_id, author_member_id)로 같은 회차·회원 중복을 막고, 회차·아이·모드 복합 FK로 다른 아이 회차가 섞이지 않게 한다. 답변이 남은 아이 삭제는 기존 다이어리처럼 409로 막으며 pet FK도 두어 검사와 저장의 경합을 보호한다. 배정 행만 있는 아이 삭제는 계속 허용한다. 가족 나가기·내보내기 후에도 답변·작성 당시 이름·첨부는 남은 가족에게 계속 표시한다. 회원 계정 탈퇴의 익명화·영구 삭제는 별도 정책을 따른다. (고침 #31: 사용자 확인에 따라 가족 관계 종료와 회원 계정 탈퇴의 표시 정책을 구분) (고침 #31: 실제 답변이 있는 아이 삭제의 최소 보존 정책)
- 권한 없는 아이는 기존 pet 계약에 따라 403, 없는 아이·해당 아이에 속하지 않은 회차/답변은 404, 다른 작성자의 수정/삭제는 403이다. 과거 모드의 이력은 조회할 수 있다. 가족 동시 답변 전체 시나리오는 실제 멤버십 연결 전까지 완료로 표시하지 않는다.

### 사진·음성 첨부 연결 계약

- 기존 media 업로드 API에서 `QUESTION_ANSWER_ATTACHMENT`로 사진/음성을 올려 READY가 된 자산 ID를 사용한다. 신규 공개 업로드 API나 영상 지원을 추가하지 않는다. 답변 본문 1~3,000자는 첨부와 별개로 필수다.
- attachmentIds는 최대 5개, 양의 Long·중복 불가, 합계 75MiB 이하다. 생략은 생성 시 빈 목록/수정 시 유지, 빈 배열은 전체 해제, 명시적 null·잘못된 숫자·중복·초과 개수는 400이다. 새 자산은 본인 업로드·같은 아이·질문 답변 용도·READY·미만료여야 한다. 기존 연결은 유지·순서 변경 시 참조 수를 다시 획득하지 않는다.
- question_answer_attachment에 답변 ID·자산 ID·순서를 저장한다. 첨부 CRUD는 QuestionAttachmentJpaEntity·복합 식별자·JpaRepository를 통해 처리하며 기존 테이블·컬럼·식별자를 유지한다. QuestionAnswerPersistenceAdapter가 답변과 첨부 출력 포트를 함께 구현하고 두 리포지토리를 받아 부모와 연결을 조율한다. (고침 #31: 함께 저장·변경되는 답변과 첨부를 같은 영속성 어댑터로 통합) 답변 FK는 CASCADE, 자산 FK는 RESTRICT이고 참조 확인용 자산 인덱스를 둔다. 자산을 오름차순으로 잠근 뒤 연결·참조 수·삭제 작업을 갱신하며 첫 답변·완료·공통 진행과 같은 트랜잭션이다. 실패하면 모두 롤백한다.
- 해제/답변 삭제는 연결 제거와 참조 감소·삭제 작업 등록까지 같은 트랜잭션이다. 실제 파일 삭제는 기존 media 작업자가 재시도한다. 다른 답변에 연결된 자산은 보존한다. 참조 수가 잘못 0이어도 실제 질문 연결이 있으면 정리하지 않는다.
- 생성·상세·목록·수정 응답에는 첨부 순서, filename(업로드 시 검증·저장한 원래 파일명), type/mimeType/sizeBytes/durationMs/width/height와 available을 제공한다. 파일 불일치는 unavailable로 표시하고 URL을 주지 않는다. 공개 경로나 볼륨 경로를 저장하지 않는다. (고침 #31: 원래 파일명을 생성·상세·목록·수정 첨부 응답에 전달)
- 원본은 `GET /api/v1/questions/answers/{answerId}/attachments/{assetId}/content?petId=`, 이미지 썸네일은 같은 주소의 `/thumbnail`이다. HEAD와 음성 Range를 지원한다. 부모의 현재 접근 권한과 실제 연결 관계를 먼저 검사하고 media가 아이·용도·READY·참조 상태를 재검사한다. 응답은 private/no-store, nosniff다. URL 생성과 스트리밍 Resource는 웹 어댑터에 둔다. 각 엔드포인트는 자신이 받는 쿼리 키만 해석한다. 파일·생성·상세·수정은 petId만, 삭제는 petId/version, 목록은 petId와 정의된 필터/페이지 키를 검사하며 그 외 키는 중복·값 형식과 관계없이 무시한다. petId 전용 경로는 기존 QuestionPetQuery를 재사용한다. (고침 #31: 엔드포인트별 쿼리 범위 제한과 petId 파서 재사용)
- media 참조·메타데이터·파일 입력 포트는 문자열 purpose를 명시적으로 받는다. 기존 생성자는 DIARY_ATTACHMENT를 기본으로 유지하고 질문 어댑터만 QUESTION_ANSWER_ATTACHMENT를 전달한다. 핵심에서 다른 도메인의 엔티티를 참조하지 않는다.
- #31-S16/S17과 S18의 소유자 범위만 구현한다. 실제 가족 열람·권한 회수·프론트 녹음/업로드 UI 검증은 후속이다.

- 선행: 현재 질문·답변·첨부의 소유자 범위 구현. 가족 API와 프론트 연결은 선행 조건이 아니다.

### 권한과 도메인 경계 (#31-R1)

- 관리자 API는 `/api/v1/admin/questions` 아래에 두고 question의 별도 `AdminQuestionController`에 둔다. (고침 #31: PR #163 관리자 API 경로·컨트롤러 통일) 전역 `/api/v1` 접두어는 WebConfig가 붙인다. 관리자 입력은 `petId`를 요구하지 않는다.
- SecurityConfig는 공통 `/api/v1/admin`·`/api/v1/admin/**`를 일반 인증 규칙보다 먼저 `hasRole("ADMIN")`으로 보호한다. 공개 경로에는 추가하지 않는다.
- 각 입력 유스케이스의 첫 단계에서 질문의 `CheckQuestionAdminAccessPort`로 현재 DB 역할을 재확인한다. 목록·상세는 새 트랜잭션으로 진입해 외부 호출자의 캐시된 ADMIN 엔티티를 재사용하지 않는다. (고침 #31: 상세 직접 호출의 역할 회수 반영) 외부 access 어댑터가 기존 member의 `GetMemberUseCase`를 호출하고 필요한 역할 판정만 반환한다. question 핵심은 member DTO·엔티티·Spring Security를 참조하지 않는다.
- 인증된 요청자의 memberId만 Command/Query로 전달한다. body의 역할·작성자 ID나 JWT의 ADMIN 값만 신뢰하지 않는다. 직접 유스케이스를 호출해도 검사가 적용된다.
- 무인증은 401, 현재 일반 회원·역할 회수·현재 회원이 없는 인증 주체는 403이다. member 조회의 알려진 not-found만 접근 거부로 바꾸고 일시 DB 장애는 서버 오류로 전파한다. 일괄 catch로 장애를 403으로 숨기지 않는다.
- ADMIN 권한은 질문 원본 관리에만 적용한다. 다른 회원의 반려동물·개인 답변·첨부를 관리자라는 이유로 열람하게 하지 않는다.
- 역할 확인은 유스케이스 진입 시점 기준이다. 이미 진행 중인 트랜잭션을 취소하는 즉시 회수 기능은 추가하지 않으며 다음 요청은 현재 역할을 다시 확인한다.

### API와 입력 계약

아래 경로는 공통 `/api/v1`을 생략했다. 등록·변경 응답과 목록 항목은 `questionId`, `mode`, `content`, `enabled`, `createdAt`, `updatedAt`, `version`이며 seed_key·개인 답변·첨부 정보는 포함하지 않는다.

| 요청 | 입력 | 응답 |
| --- | --- | --- |
| `GET /admin/questions` | 선택 `mode`, `enabled`, `q`, `page`, `size` | 200: `items`, `page`, `size`, `totalElements`, `totalPages` |
| `GET /admin/questions/{questionId}` | 양의 Long ID | 200: 비활성 항목도 포함하는 질문 원본 상세 |
| `POST /admin/questions` | `{"mode":"ACTIVE","content":"요즘 가장 좋아하는 놀이는 무엇인가요?"}` | 201: enabled=true, version=0인 질문 원본 |
| `PATCH /admin/questions/{questionId}` | `{"content":"함께할 때 가장 즐거운 놀이는 무엇인가요?","enabled":false,"version":0}` | 200: 변경한 질문 원본 |

- 원본 상세 GET은 목록 이후 수정 화면이 최신 version을 다시 읽기 위한 조회다. 관리자 프론트 구현은 포함하지 않는다.
- mode는 `ACTIVE`/`GARDEN`만 허용한다. content는 strip 후 1~300자로 기존 도메인 제한을 유지하며 PostgreSQL에 저장할 수 없는 널 문자(U+0000)는 400으로 거부한다. (고침 #31: 등록 본문의 저장 불가 문자 입력 경계) 등록 enabled는 항상 true다. 동일 본문의 등록은 허용하며 본문 중복 유니크 제약은 추가하지 않는다.
- 목록 기본값은 mode/활성 상태 전체, `page=0`, `size=20`이며 size는 1~100이다. 정렬은 `questionId DESC`로 고정하고 필터는 AND 조건으로 적용한다. 결과 없음·범위 밖 페이지는 빈 items와 실제 전체 건수/페이지 수를 반환한다. 비활성 원본도 기본 목록에 포함한다.
- q는 strip 후 1~300자 부분 문자열 검색이며, 생략·빈 값·공백만이면 검색하지 않는다. `%`, `_`, 역슬래시는 와일드카드로 해석하지 않고 문자 자체를 찾도록 이스케이프한다. 영문은 대소문자를 구분하지 않는다. strip 후 정확히 300자는 허용하고 301자 이상은 빈 결과가 아니라 400 `VALIDATION`으로 거부한다. (고침 #31: 검색어 길이 초과 응답 확정) SQL 문자열을 조립하지 않고 JPA 바인딩 파라미터를 사용한다.
- q의 널 문자(U+0000) 포함·strip 후 300자 초과, mode/enabled의 빈 값·알 수 없는 값, 음수 page, 범위 초과 size, 정수 범위 초과, 알려진 키의 중복·잘못된 인코딩은 400이다. enabled는 `true`/`false`만 받는다. 기존 쿼리 파서 방식을 재사용하되 사용자 API의 필수 petId 파서와 섞지 않는다. 정의하지 않은 쿼리 키는 기존 API 원칙대로 무시한다.
- PATCH의 version은 필수 0 이상 Long이다. content/enabled는 각각 생략하면 유지하며 명시적 null은 400이다. version만 보내거나 변경 필드를 하나도 보내지 않으면 400이다. 이미 같은 값이어도 현재 권한과 version을 검사한 뒤 200으로 반환하며 version/updatedAt은 바꾸지 않는다.
- questionId·mode·createdAt·seedKey는 생성 후 변경할 수 없다. POST에서 mode/content 외, PATCH에서 content/enabled/version 외의 body 필드는 400으로 거부한다. 모드를 바꾸려면 대상 모드에 새 질문을 등록한다.
- 물리 삭제 API는 제공하지 않는다. enabled=false로 신규 배정만 제외하며 같은 PATCH에서 true로 다시 활성화할 수 있다.
- 없는 양의 questionId는 404, 잘못된 ID·본문·쿼리는 400, 기대 version 불일치·낙관적 수정 충돌은 409다. 공통 기본 예외와 `{code, message}` 응답을 재사용하고 도메인별 핸들러·HTTP 상태를 아는 도메인 예외는 추가하지 않는다.

### 데이터·트랜잭션·스냅샷 보존

- 기존 `question` 테이블과 Question 도메인을 확장한다. 변경 규칙은 도메인 메서드에 두고 JPA 엔티티는 변환·영속화만 수행한다. 질문 관리용 별도 원본 테이블이나 일반 CRUD용 JDBC는 추가하지 않는다.
- 등록·수정·목록·상세는 각각 입력 포트와 서비스로 나눈다. 기존 `QuestionPersistenceAdapter`가 원본 관리 출력 포트도 구현하고 `QuestionJpaRepository`를 재사용한다. 배정·답변 저장 어댑터에 관리자 로직을 넣지 않는다.
- 변경은 같은 트랜잭션에서 현재 원본과 기대 version을 확인하고 JPA @Version으로 경쟁 요청을 보호한다. flush에서 확인된 낙관적 충돌은 409로 변환하며 실패 시 본문·활성 상태·시각을 모두 보존한다. 목록 데이터·건수는 `REPEATABLE_READ`·`REQUIRES_NEW`의 하나의 읽기 스냅샷으로 반환한다.
- 관리자 등록은 `REQUIRES_NEW` 트랜잭션에서 현재 DB 역할 검사와 신규 원본 저장을 함께 처리한다. 외부 호출자가 읽어 둔 ADMIN 캐시를 재사용하지 않으며 저장 실패 시 신규 원본은 남지 않는다. (고침 #31: 질문 등록의 현재 역할 검사와 원자성)
- 서버 Clock으로 시각을 기록하고 클라이언트의 createdAt/updatedAt을 받지 않는다. 생성 시 createdAt=updatedAt, 실제 변경 시 createdAt은 유지하고 updatedAt/version만 갱신한다.
- 원본을 수정·비활성화해도 기존 `question_prompt.question_snapshot`, 답변, 배정 ID·순서·현재 진행을 다시 쓰지 않는다. 비활성화 전에 배정된 미답변 질문은 계속 보이고 답변할 수 있다. 이후 새 배정만 활성 풀을 사용하며, 활성 풀이 비었을 때의 기존 처리 계약은 유지한다.
- 배정과 비활성화가 동시에 진행되면 배정 조회가 먼저 읽은 활성 원본은 기존 스냅샷으로 배정될 수 있다. 비활성화 커밋 뒤 시작한 새 배정 조회에는 포함하지 않는다. 이미 배정된 질문을 취소하거나 관리자 변경을 위해 아이별 진행 잠금을 추가하지 않는다.
- 관리자 등록 질문의 seed_key는 null이며 초기 데이터 키를 API에 받지 않는다. 기존 시드 질문 수정 시 seed_key·ID·mode를 유지한다. 초기화 SQL v1은 변경하지 않으며 재시작·시드 재적용으로 관리자 본문·비활성 상태·version이 복구되거나 신규 질문이 지워져서는 안 된다.

## 질문 회차 목록·상세 API (#31-R2·R3·R5)

### 목표와 범위

가족이 현재 질문뿐 아니라 이전에 배정된 질문을 찾아보고, 자신이 답하지 않은 회차에 답변할 수 있는 조회 경로를 제공한다. 기존 답변 목록은 답변이 있는 행만 보여 주므로 질문 회차 목록을 대신하지 않는다. 가족 가입 API는 선행 조건이 아니며 실제 가족 저장소 fixture로 접근을 검사한다. 실제 초대·가입·이전 종단 검증과 프론트 연결은 별도로 남긴다.

이 절은 상위 API 제안의 두 GET을 구체화하는 검토안이다. 계획 PR 승인 후 구현하며, 기존 현재 질문·답변 생성/변경·파일 경로와 공통 진행 규칙은 유지한다.

### API와 입력

| 요청 | 입력 | 성공 응답 |
| --- | --- | --- |
| `GET /api/v1/questions/prompts?petId=` | 필수 petId, 선택 mode·page·size | 200, 회차 목록 페이지 |
| `GET /api/v1/questions/prompts/{promptId}?petId=` | 필수 petId, 선택 page·size | 200, 회차 정보와 가족 답변 페이지 |

- petId·promptId는 양의 Long이다. mode는 생략하면 ACTIVE/GARDEN을 함께 조회하며 명시하면 해당 모드만 조회한다. 빈 값·소문자·모르는 mode는 400이다.
- page는 기본 0·0 이상 int, size는 기본 20·1~100이다. 명시한 빈 값·null 문자열·소수·범위 초과·받는 키의 중복은 400이다. offset은 `(long) page * size`로 계산해 int 곱셈 오버플로를 막는다.
- 각 경로는 자신이 정의한 쿼리만 검사한다. 목록은 petId/mode/page/size, 상세는 petId/page/size다. 그 외 키는 기존 질문 API의 무시 정책을 유지한다. 사용자·역할·작성자 ID를 쿼리에서 신뢰하지 않는다.
- 상세에도 가족 답변 페이지를 둔다. 가족 수에 제한이 없으므로 한 회차의 답변을 전부 응답하지 않는다. page/size는 **그 회차의 답변 페이지**이며 회차 자체는 항상 반환한다. (고침 #31: 상위 회차 상세 제안에 답변 페이지 경계 추가)
- 두 GET은 배정·완료·답변·진행·첨부·다이어리·지도에 쓰기를 하지 않는다. 읽을 회차가 없다는 이유로 질문을 배정하지 않는다.

### 응답 계약

공통 회차 항목은 다음 필드다. 모든 값은 같은 읽기 스냅샷에서 계산한다.

| 필드 | 의미 |
| --- | --- |
| promptId·petId·mode | 배정 회차 ID와 대상 아이·당시 모드 |
| questionId·question | 원본 질문 ID와 **배정 당시 본문 스냅샷** |
| sequence·assignedAt | 아이·모드별 회차 순번과 서버 배정 시각 |
| completedAt | 최초 답변으로 완료된 시각. 미완료는 null |
| answerCount | 현재 남아 있는 해당 회차의 가족 답변 수 |
| myAnswerId | 로그인 회원이 현재 남긴 답변 ID. 없거나 본인이 삭제했으면 null |
| canAnswer | 현재 접근이 허용되고, 회차 모드가 아이의 현재 모드이며 myAnswerId가 null일 때 true |

- 원본 질문의 수정·비활성화는 기존 회차의 question/assignedAt을 바꾸지 않는다. question 테이블의 현재 본문으로 덮어쓰지 않는다.
- completedAt은 회차의 값이다. 마지막 답변을 지워 answerCount가 0이 되어도 completedAt·공통 진행을 되돌리지 않는다.
- canAnswer는 조회 순간의 안내다. 작성 권한을 예약하지 않으며 실제 POST는 현재 권한·모드·중복을 다시 검사한다. 읽은 뒤 모드 변경/중복 제출이 생기면 기존 403/409 계약으로 처리한다.
- 현재 모드와 다른 과거 회차도 조회할 수 있지만 canAnswer는 false다. 같은 모드의 지난 완료 회차에서 본인이 아직 답하지 않았거나 자기 답변을 삭제했다면 true다. 이를 위해 가족별 진행 상태를 새로 만들지 않는다.

목록 응답은 `{items, page, size, totalElements, totalPages}`다. totalElements는 **회차 수**이고 가족 답변 수 합계가 아니다. 정렬은 `assignedAt DESC, promptId DESC`다. sequence는 모드별 값이라 두 모드를 섞은 전체 정렬 키로 쓰지 않는다. 빈 결과나 마지막 페이지 밖 요청은 items가 빈 배열이며 전체 건수는 유지한다.

상세 응답은 `{prompt, answers}`다. prompt는 위 공통 항목이고 answers는 `{items, page, size, totalElements, totalPages}`다. answers.items는 기존 답변 응답과 동일한 필드·첨부 메타데이터·비공개 URL 규칙을 쓴다. 정렬은 `answeredAt DESC, answerId DESC`이며 totalElements는 prompt.answerCount와 일치한다. 답변 페이지가 비어도 접근 가능한 회차 자체를 404로 바꾸지 않는다. myAnswerId는 현재 답변 페이지에 본인 답변이 없어도 전체 회차에서 계산한다.

이름은 답변의 저장된 작성자 스냅샷을 사용하며 member를 다시 조회하지 않는다. 첨부 불일치는 기존 unavailable/URL 미제공 정책을 따르고 볼륨 경로·GPS 후보·다른 아이의 파일을 응답하지 않는다.

가족 나가기·내보내기만으로 기존 질문 답변을 숨기거나 삭제하지 않는다. 남은 OWNER/FAMILY에게 기존 답변 API와 동일하게 본문·작성자 ID·작성 당시 이름·사진/음성을 계속 제공하고, 회차의 answerCount와 상세 답변 페이지 전체 건수에도 포함한다. 조회 대상 답변을 현재 멤버십으로 걸러내지 않으며 첨부의 기존 유효 참조를 해제하지 않는다. 나간 작성자는 본인이 쓴 답변·첨부도 새 요청으로 열람/변경할 수 없다. 계정 자체의 탈퇴·익명화·영구 삭제는 이 결정과 별도다. (고침 #31: 사용자 확인에 따라 가족 관계 종료 뒤 남은 가족의 열람·집계 범위를 확정)

### 권한·오류와 일관성

- 기존 질문 접근 출력 포트로 현재 OWNER/FAMILY 권한을 확인한다. ADMIN이라는 이유로 비가족 개인 회차를 열람하지 못한다. 직접 입력 유스케이스 호출에도 동일하게 검사한다.
- 미인증 401, 존재하는 아이의 비가족·권한 회수 403, 없는 아이/회차·다른 아이에 속한 promptId 404, 잘못된 입력 400이다. 현재 질문 리터럴 경로 `/prompts/current`는 기존 응답과 우선 매핑을 유지한다.
- 목록·상세는 각각 읽기 전용 `REQUIRES_NEW + REPEATABLE_READ`로 진입한다. 가족/모드 확인·회차 페이지·전체 건수·답변 집계·본인 답변 ID·답변 페이지·첨부를 같은 스냅샷으로 읽는다. 외부 RC 트랜잭션이나 이미 관리 중인 엔티티가 있어도 독립 읽기 경계를 유지한다.
- 조회 중 가족 답변 추가/삭제가 커밋돼도 한 응답 안에서 목록/건수/본인 답변/첨부가 서로 다른 시점으로 섞이지 않는다. 다음 호출부터 새 커밋이 보인다. 회수 커밋 이후 시작한 새 요청은 거부한다.
- 조회는 pet/진행/답변 행의 쓰기 잠금과 진행 advisory lock을 얻지 않는다. 기존 POST 배정·답변 쓰기의 pet 우선 잠금 순서는 변경하지 않는다.

### 헥사고날 구조와 조회 구현

- 입력 포트·서비스는 목록 `ListQuestionPromptsUseCase/Service`, 상세 `GetQuestionPromptUseCase/Service`로 나눈다. Query/Result는 application/port/in에 두고 웹 타입·JPA 엔티티를 노출하지 않는다.
- `QuestionController`에 두 GET을 추가한다. 관리자 컨트롤러나 별도 일반 사용자 컨트롤러를 만들지 않는다. 웹은 문자열/숫자 형식과 JSON 표현을 담당하며 핵심 업무 판단은 서비스/도메인이 맡는다.
- 회차 조회 출력 포트 `LoadQuestionPromptHistoryPort`를 두고 기존 `QuestionProgressPersistenceAdapter`·`QuestionPromptJpaRepository`를 확장한다. 같은 회차 대상의 새 영속성 어댑터나 JDBC CRUD를 추가하지 않는다.
- 출력 포트의 요약 계약은 회차 도메인 값과 answerCount·myAnswerId를 묶은 question 소유 타입이다. JPA projection을 핵심에 전달하지 않는다. 목록과 count는 같은 petId/mode 조건을 사용한다.
- 회차 목록의 페이지 ID 조회는 기존 답변 목록처럼 JPA repository의 native `LIMIT :pageSize OFFSET :offsetRows`를 사용하고 offsetRows를 long으로 바인딩한다. `Pageable`의 int offset 변환이나 `Query.setFirstResult(int)`로 구현하지 않는다. `page=2147483647&size=100`의 offset 214748364700도 유효하며, 해당 페이지가 비면 HTTP 200·빈 items와 실제 totalElements/totalPages를 반환한다. 페이지가 비었다고 count 조회를 생략하지 않는다. (고침 #31: 허용한 큰 page가 JPA int offset 한도 때문에 실패하지 않도록 조회 방식을 명시)
- 목록은 회차 페이지를 먼저 결정하고 그 페이지의 답변 수·본인 답변을 묶어서 조회한다. 회차마다 별도 count나 회원 조회를 하지 않는다. 본문/첨부는 목록에 넣지 않아 답변 수가 많아져도 회차 목록 크기가 불어나지 않게 한다.
- 상세는 petId와 promptId로 회차를 먼저 확인한다. 답변 페이지는 기존 `QuestionAnswerStorePort`에 해당 promptId를 강제한 Filter를 전달하고, 기존 `QuestionAnswerAttachments`로 그 페이지의 첨부만 묶어 읽는다. 가족 전체 답변을 메모리에 모아 페이지를 자르지 않는다.
- 배정과 완료의 기존 저장·FK·버전·유일 제약을 유지한다. `answerCount`, `myAnswerId`, `canAnswer`를 별도 저장하거나 캐시하는 새 테이블은 만들지 않는다.

## 가족 기능이 아직 없을 때

소유자 범위로 1~4단계 구현을 시작할 수 있다. 기존 pet 입력 포트로 소유자를 확인하고 서버 인증 회원을 작성자로 기록한다. question 핵심은 자체 접근 확인 출력 포트를 사용하고 외부 어댑터가 pet 입력 포트를 호출한다.

이를 가족 구현 완료로 간주하지 않는다. 가족 멤버십이 준비되면 같은 접근 포트에 읽기/쓰기 역할 검사를 연결하고 다음을 확인한다.

- 가족 공동 조회와 작성자 표시, OWNER/FAMILY 모두 작성·조회. 세부 권한·첨부·경합 검증은 [가족 연동 계획](../diary/family-integration.md)을 따른다. (고침 #133: 가족 역할 두 종류로 통일)
- 다른 작성자의 답변 변경 거부와 탈퇴·권한 회수 후 접근 차단.
- A·B 동시 답변 모두 저장, 최초 완료 한 번, B의 이전 질문 추가 답변.

진행 저장소는 처음부터 아이·모드 단위로 설계한다. 소유자를 가짜 가족 구성원으로 저장하거나 모든 회원을 허용하는 임시 권한을 만들지 않는다. 실제 가족 API 검사는 가족 담당의 포트 연결 이후에 수행한다.

## 헥사고날 경계와 API 원칙

- 사용자 질문 배정·답변·첨부 파일 HTTP 진입점은 QuestionController 하나에 두고 관리자 원본 API는 AdminQuestionController로 분리하며, 답변 서비스는 입력 유스케이스별로 분리한다. 일반 사용자 경로와 쿼리 검증 범위는 유지하고 관리자 경로는 `/admin/questions`로 통일한다. (고침 #31: PR #163 관리자 컨트롤러 예외 반영)
- 상세·목록은 `REPEATABLE_READ`·`REQUIRES_NEW`로 답변과 첨부를 같은 스냅샷에서 읽는다. 수정·삭제는 각 유스케이스의 트랜잭션 안에서 공통 보조 객체로 쓰기 권한 확인 → 답변 행 잠금 → 작성자·현재 모드·기대 버전 확인 순서를 유지한다. (고침 #31: 서비스 분리 이후에도 조회 일관성과 쓰기 잠금 순서 유지)
- 배정 생성·진행 저장·완료 변경은 같은 영속성 어댑터의 출력 포트로 처리한다. 최초 답변은 공통 진행을 먼저 잠그고 배정 행을 새로 읽은 다음 답변·첨부·완료·진행을 한 트랜잭션에서 저장한다. (고침 #31: 같은 배정 저장 대상을 통합하고 동시 최초 답변의 순서 유지)

- domain: Question·QuestionPrompt·QuestionProgress·QuestionAnswer와 값·진행 불변식.
- application: 입력 포트, 접근/질문 조회/진행/답변/미디어 연계 출력 포트, 트랜잭션 조정. 핵심에서 JPA·웹·다른 도메인의 엔티티를 참조하지 않는다.
- adapter: 웹 요청/응답, 초기 데이터 이관, JPA 저장소, pet/media 입력 포트를 호출하는 외부 연결.
- 도메인 간 전달은 상대 입력 포트의 DTO로 하고 서비스 안에서 도메인 값으로 변환한다.
- 일반 사용자 API는 공통 `/api/v1` 아래 question 도메인의 단일 루트 `/questions`를 사용한다. 컨트롤러 클래스는 `@RequestMapping("/questions")`, 질문 배정은 `/prompts`, 답변은 `/answers` 하위 경로를 사용하고 아이 범위는 필수 petId 쿼리로 받는다. (고침 #31: 도메인당 API 루트 하나로 통일) 상세 body/상태 코드 계약은 각 구현 단위에서 확정한다.
- 관리자 질문 API는 이후 `/admin/questions`로 설계하며 이번 사용자 흐름의 선행 API로 두지 않는다. 관리자 공통 경로 예외를 적용하며 권한 검사 방식은 [질문 상위 설계의 가족 권한과 의존성](README.md#가족-권한과-의존성)을 따른다. (고침 #31: 관리자 주소·권한 계약 동기화)
