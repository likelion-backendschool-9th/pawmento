# 현재 질문과 답변부터 구현하기 (#31)

[질문 상위 설계](README.md)의 사용자 흐름을 먼저 구현하는 계획이다. 관리자 페이지·관리자 질문 CRUD를 선행 조건으로 두지 않고, 초기 질문 데이터를 준비한 뒤 현재 질문 배정·미답변 유지·답변 저장을 연결한다. 이 문서는 구현 전 검토안이며 단계별 세부 계약은 코드 작성 전에 확정한다.

## 확정한 동작

- ACTIVE는 함께하는 일상, GARDEN은 함께했던 기억을 묻는다.
- 질문은 날짜가 바뀌어도 답변할 때까지 유지한다. 날짜 해시로 매일 바꾸지 않는다.
- 같은 아이·모드의 가족은 같은 현재 질문을 본다. 한 명이 처음 답하면 공통 진행이 다음 질문 배정 대기로 바뀐다.
- 다른 가족도 이전 질문에 자기 답변을 추가할 수 있다. 추가 답변은 현재 진행을 다시 바꾸지 않는다.
- 답변 날짜는 실제 등록 시각을 Asia/Seoul로 변환한 날짜다. 질문 배정일이나 사진 촬영일을 쓰지 않는다.
- 질문·답변은 question의 독립 저장소를 사용한다. 다이어리 행·달력 건수를 생성하지 않는다.
- 사진·음성 첨부는 기존 media 기능과 연결한다. 영상은 추가하지 않는다.

## 구현 순서와 완료 경계

| 순서 | 구현할 내용 | 이 단계에서 확인할 것 |
| --- | --- | --- |
| 1 | ACTIVE/GARDEN 초기 질문 데이터와 Question 도메인 | 관리자 API 없이 모드별 활성 질문을 조회할 수 있음 |
| 2 | 현재 질문 배정·조회·진행 저장소 | 최초 진입 시 한 회차로 수렴하고 재접속·자정 후에도 미답변 질문 유지 |
| 3 | 답변 생성·상세·이력·수정·삭제와 사진/음성 첨부 | 작성자·질문 스냅샷·실제 등록일 보존, 첨부 참조와 함께 저장 |
| 4 | 첫 답변과 공통 진행의 연결·경합 검증 | 가족의 동시 답변은 모두 보존하고 완료 처리는 한 번만 수행 |
| 5 | 가족 멤버십 연결·프론트 API 연결 | 아이별 공동 열람·작성자 표시·본인 변경 권한과 두 계정 흐름 확인 |
| 6 | 관리자 질문 관리 API·화면 | 질문 등록·수정·비활성화. 현재 질문·답변 스냅샷은 보존 |

3단계부터 답변 저장과 최초 완료·진행 갱신은 같은 DB 트랜잭션으로 구현한다. 4단계는 이를 나중에 붙인다는 뜻이 아니라 가족 동시 제출·이전 회차 추가 답변까지 검증 범위를 넓히는 단계다. 답변이 저장됐는데 현재 질문이 그대로 남는 중간 상태를 완료로 취급하지 않는다.

작은 PR 단위는 **초기 데이터**, **현재 질문 배정·유지**, **텍스트 답변과 공통 진행**, **답변 첨부**, **가족/화면 연결**, **관리자 기능** 순서로 나눈다. 초기 데이터만 구현한 PR로 질문 전체 완료를 주장하지 않는다.

## 1단계: 초기 질문 데이터

### 준비할 데이터

질문은 자유 일기와 별개의 `question` 테이블에 저장한다. 기존 단수 명칭을 유지하며 테이블 이름 통일은 #29의 결과를 따른다. 필드는 `id`, `seed_key`(초기 데이터 식별자, 일반 질문은 nullable), `mode`, `content`, `enabled`, `created_at`, `updated_at`, `version`으로 제안한다. 초기 질문의 `seed_key`는 유일하며 사용자 답변의 식별자로 사용하지 않는다.

| seed_key 예시 | 모드 | 질문 예시 |
| --- | --- | --- |
| active-play-001 | ACTIVE | 요즘 우리 아이가 가장 좋아하는 놀이는 무엇인가요? |
| active-happy-001 | ACTIVE | 오늘 우리 아이가 가장 신났던 순간은 언제인가요? |
| garden-first-001 | GARDEN | 우리 아이와 처음 만났던 날은 어땠나요? |
| garden-habit-001 | GARDEN | 지금도 떠오르는 우리 아이만의 귀여운 습관은 무엇인가요? |

문구는 초기 콘텐츠 제안이다. 질문 본문은 strip 후 1~300자, 모드는 ACTIVE/GARDEN, 활성 기본값은 true, 최초 version은 0이다. 도메인이 이를 검증한다. 한 모드의 질문이 다른 모드 풀에 섞이지 않아야 한다.

### 배포·재실행 정책

- 초기 질문은 기존 시작 시 SQL 방식에 맞춰 `adapter/out/persistence`의 초기화 어댑터가 실행한다. 다이어리의 `DiarySchemaConfiguration`과 같은 `InitializingBean` 방식으로 실행한다. `EntityManagerFactory` 의존성으로 Hibernate의 스키마 준비 이후 순서를 보장하고, HTTP 요청을 받기 전 빈 초기화 단계에서 `TransactionTemplate`로 하나의 트랜잭션을 열어 `db/question-seed-v1.sql`을 적용하는 안으로 정한다. 새 이관 도구·이력 관리 프레임워크를 선행 도입하지 않는다. 사용자의 첫 GET에서 데이터를 생성하지 않는다. (고침 #31: ApplicationRunner 대신 요청 수신 전 빈 초기화로 질문 풀이 비는 구간 방지)
- 모든 인스턴스는 검사·삽입 전에 동일한 고정 키 `pawmento-question-seed`의 PostgreSQL advisory transaction lock을 획득한다. v1별 키로 나누지 않고 초기화 전체에 같은 키를 사용한다. 잠금·기존 행의 모드 검증·누락 질문 삽입은 같은 연결·트랜잭션에서 수행하며, 잠금은 커밋/롤백 때 해제한다.
- SQL 파일의 v1은 배포 리소스 버전이다. 실행 완료를 메모리 플래그로 기록하지 않고 매번 잠금 안에서 DB의 seed_key를 확인한다. UNIQUE(seed_key)와 누락 키만 넣는 충돌 무시 삽입으로 재실행·여러 인스턴스의 중복 생성을 막는다. 기존 모드 충돌은 삽입 전에 검사하며 충돌·SQL 실패 시 전체 롤백 후 애플리케이션 시작을 실패시킨다.
- 같은 seed_key가 이미 있으면 중복 삽입하지 않고 기존 본문·활성 여부·version을 유지한다. 재시작으로 관리자 수정·비활성화를 되돌리지 않는다.
- 같은 seed_key의 기존 모드가 다르면 임의로 이동시키지 않고 이관 실패로 드러낸다. 초기화는 한 트랜잭션으로 적용한다.
- seed_key는 일반 질문의 본문 중복을 금지하는 제약이 아니다. 이후 관리자 등록 질문의 ID도 DB가 발급한다.
- 이미 운영 중인 질문을 배포마다 전체 삭제하거나 고정 ID로 덮어쓰지 않는다. v1 파일은 배포 후 수정하지 않는다. 새 질문·명시적 데이터 변경은 별도 버전 SQL과 검증으로 추가하며 같은 초기화 잠금을 사용한다. 범용 스키마 이관 관리 방식은 별도 작업으로 남긴다.
- 예외로 #29의 테이블·컬럼 이름 통일 시에는 같은 PR에서 JPA 매핑·이관·시작 시 실행하는 기존 버전 시드 SQL의 물리 이름도 함께 맞춘다. 이는 질문 내용이나 seed_key 값 변경을 허용하는 예외가 아니다. 질문 ID·기존 수정/비활성 상태·잠금 키·재적용 계약을 보존하고 QuestionSeedScenarioTest로 시작·재적용·동시 초기화·롤백을 다시 검증한다. (고침 #31: #29 이름 변경과 배포된 시드 SQL 불변 규칙의 예외 명시)

이 단계는 질문 풀이 필요한 이유만 충족한다. ADMIN 인증·관리자 검색/페이지·관리자 CRUD·관리자 화면은 구현하지 않는다. 상위 #31-S1의 관리자 시나리오는 미완료로 남긴다.

## 2단계: 현재 질문 배정과 유지

- `QuestionPrompt`는 특정 아이·모드에 제시한 회차이며 당시 질문 본문·모드를 스냅샷으로 저장한다.
- `QuestionProgress`는 `(petId, mode)`별 하나다. 회원별 현재 질문 포인터를 만들지 않는다.
- 현재 질문을 보장하는 POST는 열린 질문이 있으면 그대로 반환한다. GET은 조회만 하며 미배정이면 null을 반환한다.
- 최초 동시 요청에도 진행 행과 열린 회차가 하나로 수렴하도록 실제 DB 잠금·유니크 제약을 설계한다.
- 질문 선택은 서버에서 한다. 가능한 경우 직전 원본 질문을 피하고 풀이 하나면 반복을 허용하는 안을 제안한다. 선택 로직은 테스트에서 제어할 수 있게 분리한다.
- 활성 풀이 비면 새 배정만 409다. 현재 질문 조회·기존 질문 답변 저장을 막지 않는다.
- 아이의 현재 모드를 서버에서 확인한다. 모드 전환 시 이전 모드 진행·이력은 보존하고 새 모드 진행을 사용한다.

## 3~4단계: 답변과 공통 진행

- `QuestionAnswer`와 답변 첨부 연결 행은 diary와 독립적이다. promptId·질문 스냅샷·작성자는 서버에서 결정한다.
- 텍스트는 strip 후 1~3,000자를 필수로 받는 기존 제안을 유지한다. 사진·음성은 답변을 보완하며 상세 정책은 media 문서를 따른다.
- answeredAt과 answeredDate는 서버의 동일 Clock 값으로 계산한다. 수정 시 최초 등록일·작성자·질문을 바꾸지 않는다.
- 질문 회차당 회원 한 답변을 기본안으로 두고 DB 중복 제약과 버전 충돌을 검사한다. 같은 날짜의 다른 가족 답변을 제한하지 않는다.
- 첫 답변·질문 최초 완료·공통 포인터 변경·첨부 참조는 같은 트랜잭션이다. 첨부 실패나 저장 실패 시 모두 롤백한다.
- 다음 질문은 별도 보장 POST로 배정한다. 다음 풀이 비었다는 이유로 방금 저장한 답변을 취소하지 않는다.
- 이미 완료된 회차의 추가 답변·수정·삭제는 현재 질문 포인터를 변경하지 않는다. 모드가 바뀐 편집창 제출 경합은 상위 문서의 409 제안을 따른다.

## 가족 기능이 아직 없을 때

소유자 범위로 1~4단계 구현을 시작할 수 있다. 기존 pet 입력 포트로 소유자를 확인하고 서버 인증 회원을 작성자로 기록한다. question 핵심은 자체 접근 확인 출력 포트를 사용하고 외부 어댑터가 pet 입력 포트를 호출한다.

이를 가족 구현 완료로 간주하지 않는다. 가족 멤버십이 준비되면 같은 접근 포트에 읽기/쓰기 역할 검사를 연결하고 다음을 확인한다.

- 가족 공동 조회와 작성자 표시, OWNER/EDITOR 작성·VIEWER 조회.
- 다른 작성자의 답변 변경 거부와 탈퇴·권한 회수 후 접근 차단.
- A·B 동시 답변 모두 저장, 최초 완료 한 번, B의 이전 질문 추가 답변.

진행 저장소는 처음부터 아이·모드 단위로 설계한다. 소유자를 가짜 가족 구성원으로 저장하거나 모든 회원을 허용하는 임시 권한을 만들지 않는다. 실제 가족 API 검사는 가족 담당의 포트 연결 이후에 수행한다.

## 헥사고날 경계와 API 원칙

- domain: Question·QuestionPrompt·QuestionProgress·QuestionAnswer와 값·진행 불변식.
- application: 입력 포트, 접근/질문 조회/진행/답변/미디어 연계 출력 포트, 트랜잭션 조정. 핵심에서 JPA·웹·다른 도메인의 엔티티를 참조하지 않는다.
- adapter: 웹 요청/응답, 초기 데이터 이관, JPA 저장소, pet/media 입력 포트를 호출하는 외부 연결.
- 도메인 간 전달은 상대 입력 포트의 DTO로 하고 서비스 안에서 도메인 값으로 변환한다.
- 공통 `/api/v1` 아래 question 도메인의 단일 루트 `/questions`를 사용한다. 컨트롤러 클래스는 `@RequestMapping("/questions")`, 질문 배정은 `/prompts`, 답변은 `/answers` 하위 경로를 사용하고 아이 범위는 필수 petId 쿼리로 받는다. (고침 #31: 도메인당 API 루트 하나로 통일) 상세 body/상태 코드 계약은 각 구현 단위에서 확정한다.
- 관리자 질문 API는 이후 `/questions/admin`로 설계하며 이번 사용자 흐름의 선행 API로 두지 않는다. 도메인별 단일 루트를 지키기 위한 경로이며 권한 검사 방식은 [질문 상위 설계의 가족 권한과 의존성](README.md#가족-권한과-의존성)을 따른다. (고침 #31: 관리자 주소·권한 계약 동기화)
