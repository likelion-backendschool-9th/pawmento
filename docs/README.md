# 문서

계획·요구사항 문서를 어디에 두고 무엇을 쓰는지 정한 규칙이다.

## 위치
파일 이름에는 날짜를 넣지 않는다. 같은 페이지나 도메인의 문서가 이미 있으면 그 문서를 고친다.

프론트엔드와 백엔드를 나누지 않는다. 이슈 하나가 화면부터 API까지 다루므로 문서도 하나로 쓴다.

| 문서 | 위치 | 예 |
| --- | --- | --- |
| 도메인 전체 | `docs/<도메인>/README.md` | `docs/pet/README.md` |
| 이슈 하나 | `docs/<도메인>/<기능>.md` | `docs/pet/register.md` |
| 여러 도메인 공통 (여러 도메인을 모아 보여 주는 화면 포함) | `docs/<이름>.md` | `docs/home.md`, `docs/page-urls.md` |
| 여러 도메인 공통이고 한 파일로 길어 나눈 것 | `docs/<이름>/README.md`와 나눈 파일 | `docs/frontend-structure/` |

## 도메인 폴더
도메인 이름은 문서 폴더, 백엔드 패키지, 프론트엔드 경로에서 같게 쓴다: `member`, `pet`, `diary`. 도메인은 미리 정하지 않고, 그 도메인을 시작할 때 이 목록에 더한다.

- 도메인 `README.md`는 여러 이슈에 걸친 것을 모은다: 이슈와 문서 표(이슈 링크, 내용, 문서 링크), 정한 것(항목 끝에 이슈 번호), 데이터 구조 요약, 아직 정하지 않은 것.
- `<기능>.md`는 이슈 하나의 계획이다: 요구사항과 시나리오, 범위 밖, 작업 순서, 정한 것, 가정, 참고.
- 결정은 범위에 따라 둔다. 이 이슈에만 해당하면 계획의 `정한 것`에, 여러 이슈에 걸치면 도메인 `README.md`의 정한 것에 두고 계획에서는 링크로 가리킨다.
- 기능 문서는 그 이슈를 시작할 때 만든다. 그 전까지 이슈의 내용은 `README.md`에 둔다.

## 쓰는 것
문서에는 코드와 git, GitHub로 알 수 없는 것을 쓴다: 결정과 그 이유, 시나리오, 가정, 아직 정하지 않은 것, 외부 근거.

- 진행 상태는 이슈 링크로 두고 GitHub에서 본다.
- 동작이 바뀌면 바뀐 시나리오나 결정 끝에 `(고침 #이슈: 이유)`를 붙인다. 바뀐 이유는 바뀐 자리에 둔다. 다른 이슈의 시나리오를 바꿔도 번호는 그대로 두고, 새로 생긴 동작만 그 이슈의 새 번호(`#57-S1`)를 받는다.
- 참고에는 병합한 뒤에도 맞는 사실을 쓴다: 라이브러리·DB 동작, 설정만 봐서는 모르는 함정, 외부 문서. 작업하던 때의 코드 상태(무엇이 아직 없는지)는 계획을 세울 때만 쓴다.
