# 계획 문서 양식

기능(`Feat`) 이슈의 계획 문서를 쓸 때 복사해 쓰는 양식이다. 쓰고 싶은 사람만 쓴다. 문서를 어디에 두고 무엇을 쓰는지는 [문서 규칙](README.md)을 따른다.

## 쓰는 법

1. 이슈를 먼저 만든다. 번호에 이슈 번호가 들어간다(`#42-R1`, `#42-S1`).
2. 아래 [양식](#양식)을 `docs/<도메인>/<기능>.md`로 복사하고 `<...>`를 채운다.
3. `한눈에`와 `질문`을 리뷰어에게 보여 주고 승인을 받은 뒤 코드를 쓴다.

순서는 이렇게 생각하면 쉽다.

| 단계 | 할 일 | 끝났는지 보는 법 |
| --- | --- | --- |
| 요구사항 쪼개기 | 이슈·기획의 내용을 `R1, R2, …`로 나눈다. R 하나는 동작으로 확인할 수 있는 한 문장이다 | 원문의 모든 문장이 어떤 R이나 `범위 밖`에 들어갔다 |
| 빈 곳 메우기 | 입력이 비었을 때, 남의 글을 고칠 때, 같은 요청이 두 번 올 때처럼 요구사항이 정하지 않은 동작을 찾는다. 답에 따라 시나리오가 달라지면 `질문`에, 아니면 `가정`에 적는다 | 남은 빈 곳이 모두 `질문`이나 `가정`에 있다 |
| 시나리오 쓰기 | R마다 정상 시나리오 하나. 실패·경계는 틀리면 되돌리기 어렵거나 조용히 틀어지는 경우만 쓴다 | 모든 R에 시나리오가 있고, 모든 시나리오에 확인 방법이 붙었다 |
| 작업 순서 짜기 | 처음부터 끝까지 도는 가장 얇은 경로를 먼저 만들고 시나리오를 하나씩 붙인다 | 모든 S가 어떤 단계에 들어갔다 |

### 시나리오 확인 방법

시나리오 제목 끝에 하나를 붙인다.

| 표시 | 언제 | 어떻게 |
| --- | --- | --- |
| `[테스트]` | 다시 깨질 수 있는 것: 분기가 있는 로직, 권한·보안, 한 번 깨졌던 동작 | 자동 테스트. 이름을 시나리오 번호로 시작한다(`@DisplayName("#42-S1 …")`). 다른 테스트가 이미 확인하면 `[테스트: 파일 S번호]`로 가리킨다 |
| `[명령]` | 한 번 실행해 보면 확인되는 것: 설정, 설치, 출력 형식 | 테스트를 만들지 않고, 실행 결과를 PR 본문에 적는다 |
| `[직접]` | 사람이 보거나 기다려야 확인되는 것: 화면, 알림, 다음 날 로그 | PR 본문에 번호마다 확인한 조건과 결과를 적는다 |

### 쓸 때 지킬 것

- Given/When/Then에는 구체적인 값을 넣는다("글 25개", "HTTP 403"). 한 줄에 사실 하나만 쓴다.
- Then은 응답, DB, 화면, 로그처럼 밖에서 볼 수 있는 결과로 쓴다.
- When이 바로 앞 시나리오와 같으면 생략한다.
- 여러 R에 걸친 시나리오는 주된 R에 두고 제목에 적는다(`#42-S7 실패 (R1·R2)`).
- 질문이 없으면 `질문`을, 사람이 정한 것이 없으면 `정한 것`을 뺀다.
- 여러 이슈에 걸치는 결정은 도메인 `README.md`의 정한 것에 두고 여기서는 링크한다.
- 테스트 결과 같은 실행 기록은 쓰지 않는다. PR 본문의 확인 방법에 쓴다.
- 나중에 동작이 바뀌면 그 줄 끝에 `(고침 #이슈: 이유)`를 붙인다.

## 양식

````markdown
# <기능 이름>

관련 이슈: [#<번호>](https://github.com/likelion-backendschool-9th/pawmento/issues/<번호>)

## 한눈에
- 끝나면: <사람이 확인할 수 있는 결과 한 줄>
- 결정 필요: <질문의 요지, 없으면 "없음">
- 규모: <n>단계

## 질문
- Q1: <질문> (답에 따라 #<번호>-S<n>이 달라짐)

## 1. <요구사항 이름> (#<번호>-R1)
<요구사항 한 문장>

#<번호>-S1 정상 [테스트]
- Given <구체적인 상황>
- When  <요청이나 행동>
- Then  <밖에서 볼 수 있는 결과>

#<번호>-S2 실패 [테스트]
- Given <구체적인 상황>
- Then  <밖에서 볼 수 있는 결과>

## 2. <요구사항 이름> (#<번호>-R2)
<요구사항 한 문장>

#<번호>-S3 정상 [직접]
- Given …
- When  …
- Then  …

## 범위 밖
- <이번 이슈에서 하지 않는 것과 어디서 다루는지>

## 작업 순서
1. <단계> — S1, S2
   - 파일: <바꿀 파일>
   - 확인: `<명령>`
2. <단계> — S3
   - 파일: …
   - 확인: …

## 정한 것
- <사람이 답한 결정과 이유>

## 가정
- <묻지 않고 정한 기본값>

## 참고
- <조사로 확인한 사실: 라이브러리·DB 동작, 설정만 봐서는 모르는 함정, 외부 문서>
````

## 채운 예

반려동물 등록이라는 가상의 이슈 #42로 채운 예다. 실제로 쓴 예는 [기록에 장소 붙이기](map/record-location.md)를 본다. 시나리오가 많아 Given/When/Then 대신 한 줄로 줄여 쓴 형태다.

````markdown
# 반려동물 등록

관련 이슈: [#42](https://github.com/likelion-backendschool-9th/pawmento/issues/42)

## 한눈에
- 끝나면: 로그인한 회원이 이름·종·생일로 반려동물을 등록하고, 내 반려동물 목록에서 본다.
- 결정 필요: 한 회원이 등록할 수 있는 수에 제한을 둘지
- 규모: 3단계

## 질문
- Q1: 한 회원당 반려동물 수에 제한을 둘까요? 두면 초과 시 실패 시나리오가 하나 생긴다. (답에 따라 등록 실패 시나리오가 하나 더 생김)

## 1. 등록 (#42-R1)
로그인한 회원이 이름·종·생일로 반려동물을 등록한다.

#42-S1 정상 [테스트]
- Given 회원 A가 로그인했다
- When  `POST /api/v1/pets`에 `{"name":"콩이","species":"DOG","birthDate":"2015-03-02"}`를 보낸다
- Then  201과 `{"petId": 1}`을 받는다
- Then  `GET /api/v1/pets`에 콩이가 있다

#42-S2 실패 [테스트]
- Given 이름이 빈 문자열이거나 생일이 오늘보다 뒤다
- When  등록한다
- Then  400과 `code: "VALIDATION"`을 받는다
- Then  목록에 반려동물이 늘지 않는다

## 2. 내 목록 (#42-R2)
회원은 자기가 등록한 반려동물만 본다.

#42-S3 다른 회원 [테스트]
- Given 회원 A가 콩이를, 회원 B가 보리를 등록했다
- When  A가 `GET /api/v1/pets`를 부른다
- Then  콩이만 받는다

## 범위 밖
- 사진 업로드, 가족 공유. 각각 다음 이슈에서 다룬다.

## 작업 순서
1. 등록 API와 목록 API를 가장 단순하게 연결한다 — S1
   - 파일: `pet/domain/Pet.java`, `pet/adapter/in/web/PetController.java`
   - 확인: `./gradlew test --tests '*PetScenarioTest'`
2. 입력 검증을 더한다 — S2
   - 파일: `pet/adapter/in/web/RegisterPetRequest.java`
   - 확인: 같은 명령
3. 목록을 현재 회원으로 거른다 — S3
   - 파일: `pet/application/ListMyPetsService.java`
   - 확인: 같은 명령

## 가정
- 종은 `DOG`, `CAT`, `OTHER` 세 가지로 시작한다.
- 생일을 모르면 비워 둘 수 있다.

## 참고
- 인증된 회원 id를 꺼내는 방법은 [인증 기반](member/auth-base.md)을 따른다.
````
