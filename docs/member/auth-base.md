# 인증 기반

관련 이슈: [#14](https://github.com/likelion-backendschool-9th/pawmento/issues/14)

pet, diary를 비롯한 거의 모든 API가 "지금 로그인한 회원이 누구인가"를 필요로 한다. 도메인 담당이 현재 회원 id를 한 줄로 꺼내 쓰고, 프론트엔드가 가입·로그인 화면을 붙일 수 있는 상태를 만든다.

## 요구사항

- #14-R1 이메일·비밀번호·닉네임으로 가입하고, 이메일·비밀번호로 로그인한다. 비밀번호는 해시로만 저장한다.
- #14-R2 로그인하면 JWT 액세스 토큰을 HttpOnly 쿠키로 받고, 로그아웃하면 쿠키가 지워진다.
- #14-R3 가입·로그인·로그아웃·API 문서만 공개하고 나머지 경로는 로그인이 필요하다. 로그인 필요(401)와 권한 없음(403)은 JSON으로 응답하고, 기본 로그인 페이지로 넘기지 않는다.
- #14-R4 컨트롤러가 현재 회원 id를 받는 공통 방법을 하나 둔다. 애플리케이션 계층은 Spring Security를 직접 쓰지 않는다.
- #14-R5 서명 키는 환경 변수로만 받는다. 테스트에는 테스트 전용 값을 쓴다.

## 시나리오와 확인 방법

권한·보안이라 전부 자동 테스트로 확인한다. S1~S7은 [`AuthScenarioTest`](../../backend/src/test/java/com/pawmento/member/AuthScenarioTest.java), S8은 [`SecurityErrorResponderTest`](../../backend/src/test/java/com/pawmento/global/security/SecurityErrorResponderTest.java)에 있다.

- #14-S1 [테스트] 가입하고 로그인하면 쿠키(HttpOnly, SameSite=Lax)를 받고, 그 쿠키로 내 정보를 조회한다. 응답에 비밀번호와 토큰이 없다.
- #14-S2 [테스트] 로그인 없이 보호 API를 부르면 401과 JSON 에러를 받는다. 로그인 페이지로 넘어가지 않는다.
- #14-S3 [테스트] 비밀번호가 틀리거나 없는 이메일이면 같은 401 응답을 받고 쿠키를 받지 못한다.
- #14-S4 [테스트] 이미 가입된 이메일은 대소문자가 달라도 가입할 수 없다(409). 로그인은 대소문자가 달라도 된다. 두 가입이 동시에 중복 확인을 통과해도 하나만 저장된다.
- #14-S5 [테스트] 만료되거나 위조된 토큰으로 보호 API를 부르면 401을 받는다. 그 쿠키가 남아 있어도 다시 로그인할 수 있다.
- #14-S6 [테스트] 로그아웃하면 토큰 쿠키가 지워진다(Max-Age=0). 다른 사이트의 폼이 보낼 수 있는 형식(urlencoded, multipart, text/plain)이나 Content-Type이 없는 요청은 415로 거부되고 쿠키가 지워지지 않는다. (고침 #14: 외부 폼 요청에 의한 강제 로그아웃 방지)
- #14-S7 [테스트] 가입 입력(이메일 형식, 비밀번호 8~72자·72바이트, 닉네임 1~20자)이 규칙에 맞지 않으면 400과 이유를 받는다. 여러 항목이 틀리면 항상 가장 앞 항목의 이유를 받는다. 비밀번호의 바이트 제한도 비밀번호 항목의 순서를 따른다.

- #14-S8 [테스트] 권한이 없으면 403과 JSON 에러를 받는다. 기존 보안 응답 단위 검사에 더해 `QuestionAdminReadScenarioTest`의 #31-S22에서 `/api/v1/admin/questions`·원본 상세 GET의 무인증 401·USER 403·현재 ADMIN 허용과 실제 로그인 JWT 쿠키의 역할 회수 후 403을 요청 전체로 확인한다. 관리자 질문 등록·수정 API의 정상 요청 검증은 해당 구현 단계에서 추가한다. (고침 #31: 관리자 질문 조회 경로의 인증·현재 역할 검사 연결)

## 범위 밖

refresh 토큰 재발급, 소셜 로그인, 비밀번호 변경·찾기, 이메일 인증, 회원 탈퇴, 프로필 수정, 가족 공유 권한. 스프린트 1의 member에서 다룬다.

## 정한 것

인증 방식, 쿠키, 서명 키, 공개 경로처럼 다른 이슈에도 걸치는 결정은 [member README의 정한 것](README.md#정한-것)에 있다.

## 가정

- 프론트엔드와 백엔드는 같은 출처로 서비스된다(개발 서버의 nginx, 로컬의 프록시). 출처가 달라지면 쿠키 속성(SameSite)과 CORS를 다시 정해야 한다.
- GET 요청은 데이터를 바꾸지 않고, 데이터를 바꾸는 요청은 JSON 본문으로 받는다. CSRF 토큰을 쓰지 않는 전제다.

## 참고

- 백엔드 패키지 구조와 API 응답·에러 형식이 정해지기 전에 만들었다. 정해지면 맞춘다([아직 정하지 않은 것](README.md#아직-정하지-않은-것)).
