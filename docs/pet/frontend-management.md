# 반려동물 관리페이지 프론트 API 연동

관련 이슈: [#85](https://github.com/likelion-backendschool-9th/pawmento/issues/85). 백엔드 계약: [등록·관리](manage.md) #46, [공통 예외 전환](exception-migration.md) #72·#91, [일기와 pet 삭제 보호](../diary/basic-crud.md#반려동물-삭제와-첫-일기-생성의-경합) #89. 이 계획은 프론트만 다루며 서버 API를 변경하지 않는다.

## 한눈에
- 끝나면: 로그인한 보호자가 관리페이지에서 서버 반려동물 목록·상세를 보고 등록·프로필 수정·모드 변경을 한다. 브라우저 데모 저장을 서버 저장으로 오인하지 않는다.
- 결정 필요: 공용 의존성·라우팅·활성 세션 출처 계약(Q1), 데모와 서버 데이터의 선택·이동 경계(Q2), 전역 모드 반영 범위(Q3), 기존 생일을 비우는 UI 정책(Q4), 서버 미지원 영역의 디자인 표시 방안(Q5).
- 규모: 계획 승인 후 목록 → 등록 → 상세 → 프로필 수정 → 모드 변경을 각각 별도 구현 작업·커밋·PR로 진행한다. 삭제는 후속이다. 한 PR에 다섯 기능을 함께 넣지 않는다.
- 선행 조건: #91의 pet 공통 예외 전환까지 반영된 기존 API를 사용한다. 공통 응답은 `code`·`message`이며 pet 입력400·권한403·미존재404·동시성409를 구분한다. API 동작·담당 경계가 바뀌면 해당 단계만 재검토하고 pet 예외 클래스 이름을 프론트 계약으로 사용하지 않는다.
- 이번 문서는 계획만 다룬다. 단계별 담당 합의·계획 승인 전 코드를 변경하지 않는다. 7절의 `REPTILE` 추가는 등록·수정·조회 API의 분류 값만 확장한다. 현재 문서의 검토안이나 후속 PR 머지를 다른 담당 파일 수정 허가로 확대하지 않는다.
- 다른 도메인 백엔드가 추가돼도 관리페이지의 서버 데이터·라우트·세션 경계가 자동으로 연결되지는 않는다. community의 글 수정/삭제(#84)와 diary의 텍스트 CRUD(#89)는 각 담당 기능이며 이번 pet 관리 프론트에 그 화면·포트·API 연동을 추가하지 않는다.

## 질문·담당 합의
- Q1: `app/composition.ts`, `AppProvider`, 기존 `pets` 목록 포트·어댑터는 마이페이지도 사용한다. `/pets/[petId]/layout.tsx`의 `PetBoundary`는 로컬 workspace에서만 pet을 찾으며 다이어리·질문·가족 등 하위 화면도 감싼다. 서버 데이터만 연결하면 서버 pet을 로컬에서 찾지 못해 404가 날 수 있다. 관리 전용 의존성·상태·라우트 경계를 분리하는 안을 제안하며, 구체 배치와 최소 연결 변경을 마이페이지·인증 담당자 및 관련 화면 담당과 합의한다. 새 정적 경로 또는 라우트 그룹 분리 여부도 이때 정한다. **기존 boundary를 서버 조회로 일괄 교체하거나 공용 파일을 합의 없이 수정하지 않는다.** 목록/등록도 독립 경계와 **활성 세션 출처의 공개 계약**을 먼저 확보하며, 상세 이후를 포함해 필요한 합의 전 착수하지 않는다(S3·S11). 유효한 HTTP 쿠키가 있어도 활성 출처가 demo이면 관리용 서버 조회·쓰기를 시작하지 않는다. http 요청 도중 demo로 바뀐 경우의 응답 폐기·진행 중 쓰기 취급도 합의한다. `sessionSource()`는 현재 구현체 전용 메서드이며 공개 `AuthRepository`/유스케이스 계약이 아니므로 화면에서 구현체로 캐스팅하거나 private 상태·localStorage·쿠키 존재/계정ID로 출처를 추측하지 않는다. 공개된 세션 출처/전환 신호와 정확한 수정 파일은 auth 담당이 확인해야 한다. (고침 #85: 리뷰의 HTTP 쿠키·demo 공존 경계 반영)
- Q2: 기존 '이 친구와 기록하기'는 `workspace.selectPet`과 `/home` 이동으로 데모 상태를 바꾼다. 서버 petId를 데모 workspace에 자동 삽입하거나 로컬 기록과 이름으로 병합하지 않는다. 관리페이지 안에서 서버 저장·재조회는 완료할 수 있지만 홈·기록 선택까지 연결하려면 선택 상태의 책임·ID·데모 모드와 전환을 관련 담당과 합의한다. 합의 전 서버 pet에 기존 데모 선택 동작을 연결하지 않고, 해당 선택 기능의 노출·비활성 안내를 정한다(S11).
- Q3: 관리페이지의 모드 저장은 기존 API로 가능하다. 다만 저장 직후 전역 헤더/홈/정원 메뉴를 갱신하는 것은 공유 상태·다른 담당 화면에 영향이 있다. 우선 관리페이지 목록·상세의 서버 mode만 재조회하고, 성공 후 `/pets` 또는 관리 상세에 머무는 안을 제안한다. 앱 전체 반영·홈 이동이 필요하면 별도 계약/작업으로 분리한다. 로컬 데모 mode를 대신 고치지 않는다(S9·S10·S11).
- Q4: 기존 생일은 PATCH의 `null`/생략으로 삭제되지 않고 유지된다. 이번에는 기존 생일 삭제 UI를 제공하지 않고 날짜 변경만 허용하는 안을 제안한다. 생일 삭제가 필요하면 백엔드 담당과 별도 이슈에서 계약을 확정한다. 저장됐다고 표시하면서 서버에는 예전 날짜가 남는 동작은 허용하지 않는다(S7).

- Q5: 기존 목록의 사진·로컬 기록 수·가족 역할·‘이 친구와 기록하기’, 등록 폼의 사진 선택, 편집 화면의 삭제 진입은 서버 관리 API와 지원 범위가 다르다. 그대로 두어 데모 저장으로 오인시키거나 임의로 숨기지 않는다. 각 작은 작업 전에 유지/비활성 안내/진입 분리 등 기존 디자인으로 가능한 표시안을 사용자에게 제시하고 **시각 변경 승인을 먼저 받는다**. 담당 경계 합의와 디자인 승인을 구분한다(S1·S4·S7·S9·S11·S12).

### 서버 수정에 적용한 합의

- **Q4** — 서버 편집 화면에서 기존 생일을 비우면 ‘기존 생일을 유지하거나 다른 날짜를 입력해 주세요.’를 표시하고 저장 요청을 보내지 않는다. 다른 날짜는 저장할 수 있고, 건드리지 않은 생일은 변경 항목에서 생략한다. 저장 동작은 #85-S7에서 확인한다. (고침 #85: 서버 수정의 기존 생일 처리 기록)

### 서버 모드 변경에 적용한 합의

- **Q3** — 저장 성공 뒤 반려동물 관리 상세로 돌아가 서버 프로필을 다시 조회하고, 관리 목록을 다시 열면 서버의 변경 모드를 읽는다. 전역 선택·헤더·홈은 이번 변경 범위에서 제외한다. #85-S9·S11에서 확인한다. (고침 #85: 관리 화면 내 서버 모드 반영 범위 기록)
- **Q5** — 관리 상세 카드 하단의 ‘프로필 수정’ 오른쪽에 기존 보조 버튼 스타일로 ‘모드 변경’을 둔다. 기존 모드 선택 카드와 확인 패널을 재사용한다. 저장 전에는 기존 모드를 표시하고, 취소하면 요청하지 않는다. #85-S9·S10·S12에서 확인한다. (고침 #85: 모드 변경 진입과 확인 화면 표시 합의 기록)

## 디자인 준수

- [디자인 토큰 가이드](../Frontend/PawMento_Design_Tokens_Hexagonal.md)와 그 문서가 지정한 실제 CSS·컴포넌트를 디자인 기준으로 그대로 따른다. 색상·글꼴·간격·크기·모서리·그림자·아이콘·배치·반응형·모드별 표현을 임의로 바꾸거나 새 디자인을 제안 없이 적용하지 않는다.
- 토큰 변수뿐 아니라 `globals.css`의 후속 덮어쓰기와 화면별 모듈 우선순위까지 확인한다. 기존 공통 버튼·입력·카드·레이아웃·아이콘을 재사용하고, 스크린샷이 최신 코드와 다르면 문서가 지정한 기준 소스부터 대조한다.
- 서버 연동이나 상태 표시 때문에 디자인 변경이 꼭 필요하거나 문서·실제 컴포넌트가 충돌하면, **변경 이유·해당 화면/속성·영향 범위·기존 디자인으로 해결 가능한 대안을 사용자에게 먼저 설명하고 명시적 승인 후 변경한다.** 합의 전에는 CSS·공통 토큰·컴포넌트를 수정하지 않는다. 담당자 합의가 사용자 디자인 변경 승인을 대신하지 않는다.
- 사진·삭제 등 이번 범위 밖 기능의 버튼/영역을 숨기거나 비활성화하는 경우도 화면 구성이 달라지므로 구현 전에 사용자에게 표시 방안을 확인한다. 계획의 범위 제외를 임의 디자인 변경의 허가로 해석하지 않는다.

## 1. 서버 목록 (#85-R1)
보호자는 서버의 내 반려동물만 보며 로딩·빈 목록·실패를 구분한다.

#85-S1 정상·빈 목록 [테스트]
- Given 로그인한 A의 서버 목록에 콩이와 보리가 있고, 로컬 데모에는 다른 친구가 있다
- When 반려동물 관리 목록을 연다
- Then GET `/api/v1/pets` 결과의 두 친구만 표시하고 로컬 친구·로컬 기록 수를 합치지 않는다
- Given 서버가 빈 배열을 돌려준다
- Then 빈 상태와 등록 진입을 보여 주며 데모 친구를 대신 표시하지 않는다

#85-S2 실패·재시도 [테스트]
- Given 목록 요청이 진행 중이다
- Then 로딩을 빈 목록으로 표시하지 않는다
- When 요청이 네트워크/서버 오류로 실패한다
- Then 실패 안내와 명시적 재시도를 제공하며 등록·조회 성공을 가장하지 않는다
- When 이후 조회가 성공한다
- Then 오류가 사라지고 서버 결과가 보인다

#85-S3 세션·계정 전환과 혼합 출처 [테스트]
- Given 쿠키 만료로 API가 401을 반환하거나 서버 세션 사용이 확인되지 않았다
- When 관리페이지가 서버 데이터에 접근하려 한다
- Then 서버 로그인 필요 상태를 표시하고 이전 계정의 목록·쓰기 버튼을 노출하지 않는다
- Given HTTP 계정 A의 유효한 서버 쿠키가 남아 있고 `startDemo()` 또는 `signInDemoProvider()`로 활성 출처가 demo가 됐다
- When 관리 목록/상세를 열거나 등록·수정·모드 변경을 시도한다
- Then 합의된 공개 세션 계약으로 demo 상태를 확인해 **관리용 pet 서버 요청을 시작하지 않는다**. 쿠키 때문에 API가200/201을 줄 수 있어도 HTTP A의 목록·저장 성공을 demo 계정 결과로 보여 주지 않는다
- Given 활성 출처 http에서 A의 목록/상세/쓰기 요청이 진행 중일 때 demo로 전환했다
- When A의 응답이 뒤늦게 도착한다
- Then demo 화면에 HTTP A의 데이터를 넣거나 캐시를 현재 세션 결과로 갱신하지 않고, 저장 성공 알림·홈/정원 이동도 수행하지 않는다
- Then 이미 전송된 쓰기는 서버에 커밋됐을 수 있으므로 응답 폐기를 서버 취소/롤백으로 간주하지 않는다. 자동 재전송하지 않고, 해당 HTTP 계정으로 명시적으로 복귀한 뒤 서버 재조회로 확인하는 흐름을 Q1에서 확정한다
- Given A 요청 뒤 로그아웃·B 로그인 또는 대상 전환이 일어났다
- Then 늦은 A/이전 대상 응답은 B/현재 대상을 덮지 않는다
- 합의된 공개 세션 출처·전환 계약을 테스트의 가짜 포트로 제어해 두 혼합 사례의 요청 미호출/늦은 응답 폐기를 검증하고, 실제 전환·쓰기 안내는 S12에서 직접 확인한다. API를 항상401로 만드는 mock만으로 혼합 출처를 검증했다고 하지 않는다
- `sessionSource()`의 구체 구현 접근·쿠키 삭제·서버 강제 로그아웃·새 auth 흐름을 이 pet 작업에서 임의로 구현하지 않는다. 공개 계약이 준비되지 않으면 목록 단계도 착수하지 않는다 (고침 #85: 리뷰의 혼합 세션과 공개 계약 조건 반영)

## 2. 등록 (#85-R2)
이름·종·선택 품종·선택 생일을 서버에 저장하고 반환된 서버 ID와 태그를 사용한다.

#85-S4 정상 등록 [테스트]
- Given A가 이름 `콩이`와 생일 `2015-03-02`를 입력하고, 종류 입력에서 `웰시코기`를 선택했다 (고침 #85: 종류 입력을 품종명 하나로 통합)
- When 등록을 한 번 제출한다
- Then POST `/api/v1/pets`에 `species: DOG`, `breed: 웰시코기`를 보내고 201 결과로 관리 목록을 재조회한다 (고침 #85: 통합 입력의 기존 API 매핑 검증)
- Then 서버 petId·tag·mode를 표시하고 브라우저에서 ID·태그를 생성하지 않는다
- Then 저장 확인 전 로컬 pet을 만들거나 홈으로 이동하지 않는다

#85-S5 실패·중복 제출 [테스트]
- When 빈 이름·21자 이름·미래 생일로 등록하려 한다
- Then 입력 오류를 보여 주고 서버 검증 오류도 해당 입력 흐름에서 안내한다
- Given 등록 요청이 진행 중이다
- Then 반복 클릭으로 같은 요청을 추가하지 않는다
- When 서버가 400을 반환하거나 네트워크 결과가 불명확하다
- Then 성공 알림을 띄우지 않고 입력을 보존한다. 불명확한 POST는 자동 재전송하지 않고 서버 목록을 확인한 뒤 재등록 여부를 사용자가 판단한다
- 이름 중복은 허용되므로 이름으로 기존 등록을 단정하거나 성공으로 간주하지 않는다.

## 3. 상세 조회 (#85-R3)
관리 대상은 서버 상세로 확인하며 목록 캐시나 로컬 데모의 존재만으로 접근을 허용하지 않는다.

#85-S6 상세·접근 실패 [테스트]
- When 관리 상세 경로로 직접 진입하거나 새로고침한다
- Then GET `/api/v1/pets/{petId}`로 상세를 조회하고 로딩 완료 전 수정 폼을 오래된 데이터로 채우지 않는다
- When 403 또는 404를 받는다
- Then 각각 접근 불가·대상 없음으로 안내하고 수정·모드 저장을 허용하지 않는다
- Then 로컬에 같은 ID/이름이 있어도 서버 실패를 우회하지 않는다
- 다른 petId의 늦은 응답으로 현재 상세를 덮지 않는다.

## 4. 프로필 수정 (#85-R4)
서버 상세를 초기값으로 수정하며 실패 시 저장값과 편집값을 구분한다.

#85-S7 정상 수정·미지원 삭제 [테스트]
- Given 서버 이름이 `콩이`이고 생일은 `2015-03-02`다
- When 이름을 `콩콩`으로 저장한다
- Then PATCH `/api/v1/pets/{petId}` 성공과 재조회에 `콩콩`이 표시된다
- Then 편집하지 않은 값은 유지되고 성공 전 '저장 완료'가 표시되지 않는다
- 기존 생일을 비우는 동작은 Q4 합의안에 맞춰 제한한다. 종류 입력에서 지우기를 선택하면 기존 `species`를 유지하고 품종만 빈 문자열로 보내 재조회 결과를 확인한다. (고침 #85: 통합 입력에서 품종을 지우는 방법 명시)

#85-S8 수정 실패·이탈 [테스트]
- When 400·403·404·409 또는 통신 오류를 받는다
- Then 성공 알림 없이 오류를 구분하며, 권한/대상 오류에서는 저장을 중단하고 409에서는 서버 재조회 선택을 제공한다
- Then 재조회로 미저장 입력을 조용히 덮지 않고 비교·재입력할 수 있게 한다
- When 미저장 입력이 있는 상태에서 페이지를 벗어나려 한다
- Then 기존 이탈 확인을 유지하고 취소하면 편집을 계속한다
- 서버가 동일 필드를 이미 변경한 값을 다음 저장이 덮어쓰는 모든 경우를 방지한다고 주장하지 않는다. 현재 PATCH 계약에는 화면의 기대 버전 입력이 없으며 버전 계약 확장은 별도 백엔드 합의다.

## 5. 모드 변경 (#85-R5)
소유자는 반려동물 관리에서만 ACTIVE/GARDEN을 바꾸며 서버 성공 이후 결과를 반영한다.

#85-S9 정상 변경·취소 [테스트]
- Given 서버의 콩이는 ACTIVE다
- When GARDEN을 선택한다
- Then 기존 확인 단계를 표시하고 확인 전 PATCH를 보내지 않는다
- When 취소한다
- Then 서버 요청과 저장 mode 변경이 없다
- When 확인해 PATCH `/api/v1/pets/{petId}/mode`가 성공한다
- Then 관리 상세/목록 재조회에서 GARDEN이 보인다. 다른 친구나 로컬 데모 mode를 변경하지 않는다

#85-S10 실패·반복 제출 [테스트]
- Given 모드 저장 중이다
- Then 반복 확인을 차단한다
- When 403·404·409 또는 통신 오류가 발생한다
- Then 성공 알림·정원 이동을 하지 않고 오류와 재조회 선택을 제공한다
- Then 선택 후보 mode를 저장된 mode처럼 표시하지 않는다
- 확인 버튼 비활성만으로 권한을 보장하지 않으며 최종 권한은 서버가 판단한다.

## 6. 경계와 화면 검증 (#85-R6)
마이페이지·데모·다른 도메인의 동작을 바꾸지 않으며 기존 공통 디자인을 사용한다.

#85-S11 담당·데이터 경계 [테스트]
- Given 마이페이지가 기존 pet 목록 포트/어댑터를 사용한다
- When 관리페이지 전용 상세·등록·수정·모드 의존성을 추가한다
- Then 기존 `features/pet/api/petApi.ts`의 `listMine()`·`PetSummary`·마이페이지 호출 결과를 바꾸지 않는다 (고침 #182: 구조 개편으로 바뀐 경로)
- Then 서버 저장 실패가 localStorage 저장으로 대체되지 않고, 관리페이지가 `workspace.savePet`·`changeMode`·`selectPet`로 서버 작업을 흉내 내지 않는다
- Q1~Q3 합의 전 공용 composition·provider·boundary·인증·마이페이지 파일은 변경하지 않는다. 허용된 최소 연결부는 해당 구현 PR의 대상 파일로 명시하고 다른 기능 변경과 분리한다.

#85-S12 화면·접근성 [직접]
- When 데스크톱과 모바일 폭에서 로딩/빈 목록/실패/긴 이름/폼/모드 확인 화면을 연다
- Then 기존 토큰·버튼·카드·타이포·Icon·이탈 확인을 재사용하고 포커스·라벨·오류 안내·busy 상태가 구분된다
- Then 키보드 조작이 가능하고 작은 화면에서 가로 넘침이나 고정 탐색의 본문 가림이 없다
- 등록·수정·모드 각 PR에서 실제 서버 로그인으로 저장 후 새로고침하여 결과를 확인한다. API mock/유스케이스 테스트만으로 실제 브라우저 연결까지 검증했다고 표시하지 않는다.

## 7. 종류·품종 통합 입력 (#85-R7)

서버 등록·수정 폼에서는 `종류` 입력창 하나에서 반려동물의 품종·세부 종류 이름을 검색하거나 직접 입력한다. 추천은 브라우저의 목록에서 찾고 이름만 표시한다. 서버 분류는 강아지 `DOG`, 고양이 `CAT`, 파충류 `REPTILE`, 그 외 친구 `OTHER` 네 값이다. 등록·수정 폼에는 분류 선택창과 분류 라벨을 두지 않는다. 관리 목록·상세와 수정 충돌 비교에서도 입력한 이름만 보여 주고, 값이 없으면 `—`를 사용한다.

#85-S13 추천 선택과 등록 [테스트]
- Given 보호자가 `웰시`, `웰시 코기` 또는 목록에 등록된 별칭 `코기`를 입력한다
- Then `웰시코기`가 추천되고, 선택하면 후보에 연결된 `species: DOG`, `breed: 웰시코기`가 기존 등록 요청에 들어간다.
- Given 보호자가 `크레스티드 게코`를 입력한다
- Then `크레스티드게코`가 추천된다. 파충류 후보를 선택하면 이름은 `breed`, 분류는 `species: REPTILE`로 등록·수정 요청에 들어간다. (고침 #85: `레오`의 복수 추천 시나리오 추가)
- Given 보호자가 `레오`를 입력한다. Then `레오파드게코`와 `레오파드육지거북`을 모두 보여 주고, 보호자가 하나를 선택할 때 그 이름을 확정한다. 공백을 포함한 `레오파드 게`와 `레오파드 육`은 각각 해당 후보로 좁혀진다. (고침 #85: 여러 파충류 그룹에서 같은 접두어가 맞는 경우)
- 등록·수정에서 임의의 검색어에 같은 그룹 또는 다른 분류의 후보가 여러 개 일치하면 서로 다른 후보를 모두 표시한다. 같은 후보의 이름과 별칭이 동시에 일치해도 한 번만 표시한다. (고침 #85: 전체 추천 목록의 공통 규칙 검증)
- `도마뱀`, `뱀`, `거북이`로 검색하면 해당 그룹의 후보만 함께 보인다. 정확한 이름을 모르면 그룹 이름 자체를 선택할 수 있다. 이 경우에도 `species: REPTILE`을 쓰고 선택한 그룹 이름을 `breed`에 저장한다. (고침 #85: 그룹 이름 검색과 등록)
- `믹스`처럼 품종명만으로 분류를 특정할 수 없는 후보는 한 번만 표시한다. 신규 등록에서 이런 후보를 선택하거나 품종을 비워 두면 `species: OTHER`를 사용한다. 수정에서 기존 분류를 보존하는 규칙은 S15를 따른다.

#85-S14 직접 입력과 미확정 입력 [테스트]
- 추천에 없는 품종은 `직접 입력`으로 확정한다. 앞뒤 공백을 정리한 품종명을 저장하며 기존 100자 제한을 적용한다. 신규 등록은 `species: OTHER`를 보내고, 수정은 S15를 따른다.
- 문구를 바꾼 뒤 후보 선택이나 직접 입력을 확정하지 않고 제출하면 종류 입력에 안내를 표시하고 요청을 보내지 않는다. 직전에 확정한 품종이 새 입력과 함께 전송되는 일이 없어야 한다.

#85-S15 기존 프로필의 초기값과 부분 수정 [테스트]
- 저장된 품종이 있으면 목록에 없는 이름까지 그대로 보여 준다. 품종이 없는 기존 프로필의 입력은 빈칸에서 시작한다.
- 이름이나 생일만 수정하면 기존 `species`·`breed`를 PATCH에서 생략한다. 분류가 연결된 후보를 선택하면 변경된 값만 보낸다.
- Given 보호자가 기존 분류가 `DOG`인 프로필에서 품종을 `우리집 진도믹스`로 직접 입력하거나 분류가 없는 후보를 선택한다. Then PATCH에는 바뀐 `breed`만 보내고 재조회한 분류는 `DOG`다. 지우기를 선택해도 `species`는 유지하고 품종 삭제를 뜻하는 `breed: ""`만 보낸다. 이때 기존 분류가 화면에 표시되지 않더라도 다른 기능에서 쓰는 분류가 바뀌지 않는다.

#85-S16 등록·수정 화면과 실제 저장 [직접]
- 모바일·데스크톱에서 클릭·터치로 추천을 고르고, 키보드로 방향키 이동·Enter 선택·Esc 닫기를 확인한다. 한글 조합 중 Enter가 추천 선택이나 폼 제출을 실행하지 않는지 확인한다.
- 서버에서 파충류를 등록·수정한 뒤 목록·상세를 다시 열어 선택한 이름이 표시되는지 확인한다. `파충류`나 `그 외 친구` 같은 분류 라벨은 관리 화면에 표시하지 않는다. 미확정 입력에서는 저장 요청이 나가지 않는지 확인하고, 데모 폼을 열어 기존 두 필드가 그대로 동작하는지 확인한다.

#85-S17 파충류 서버 등록·수정·조회 [테스트]
- Given 보호자가 `species: REPTILE`, `breed: 레오파드게코`로 등록하거나 기존 프로필을 같은 분류로 수정한다
- Then 서버가 분류와 이름을 저장하고 등록·목록·상세·수정 응답에서 같은 값을 반환한다. 기존 `DOG`, `CAT`, `OTHER`의 등록·조회가 정상이며, 정의되지 않은 분류 문자열은 400으로 거절한다.
- 기존 `OTHER` 프로필은 다른 항목을 수정할 때 유지한다. 기존 데이터의 분류를 이름으로 일괄 변경하지 않는다.
- Given `pets`에 기존 행과 `DOG`·`CAT`·`OTHER`만 허용하는 `pets_species_check`가 있다. When 스키마 스크립트를 두 번 실행한다. Then 기존 행은 보존되고 `ck_pets_species` 하나가 네 값을 허용한다. 이후 `REPTILE` 등록·수정이 성공하고, 정의되지 않은 값은 DB 제약에서 계속 거절된다. 새 테이블에서의 등록 검사와 별도로 이 이전 경로를 검증한다.

#85-S18 분류 값을 사용하는 기능의 회귀 [테스트]
- Given 서버 pet의 `species`가 `REPTILE`이고 `breed`가 `레오파드게코`다
- Then 프론트 서버 응답 매핑에서 값이 누락되지 않고, 엽서 기능에 전달하는 pet 데이터에 분류와 이름이 보존된다. 공유 화면에서 새 값이 빠진 분류 매핑 때문에 빈 라벨이나 오류를 만들지 않는지도 확인한다.
- 프론트 분류 타입 `features/pet/types/Pet.ts`와 공용 매핑 `features/shell/utils/presentation.ts`에 `REPTILE`을 추가한다. `WorkspaceUi.tsx`는 기존 표시 방식으로 새 값도 표시할 수 있어야 한다. 관리 목록·상세·편집(`PetManagementList`, `PetManagementDetail`, `PetManagementEditor`)은 품종명만 보여 준다. `PetProfileFields.tsx`가 공용 매핑을 순회하더라도 데모 선택지는 기존 세 개를 유지하고, 데모 검증·저장 흐름도 확인한다.

### 정한 것

- 추천은 공백과 영문 대소문자 차이를 정리한 뒤 이름·별칭의 앞부분 일치로 찾는다. 모든 분류와 그룹에 같은 규칙을 적용해, 검색어에 일치하는 서로 다른 후보는 모두 보여 주고 자동으로 확정하지 않는다. 선택하면 입력창에는 표준 품종명을 표시한다. 품종을 확정하거나 지우기를 선택할 때 저장할 값을 갱신한다.
- 파충류 추천 목록은 아래 세 그룹과 세부 후보 여섯 개로 시작한다. 그룹은 추천을 검색하는 데 쓰며 서버에는 공통 분류 `REPTILE`과 선택한 이름을 저장한다.

  | 그룹 | 초기 후보 |
  | --- | --- |
  | 도마뱀 | 레오파드게코, 크레스티드게코 |
  | 뱀 | 콘스네이크, 볼파이톤 |
  | 거북이 | 러시안육지거북, 레오파드육지거북 |

- 서버는 허용된 분류 값을 검증·저장한다. 분류가 연결된 후보를 선택하면 그 값을 사용한다. 분류가 없는 입력은 신규 등록에만 `OTHER`를 사용하며, 수정에서는 기존 분류를 유지한다.
- `PetSpecies`와 `CreatePetRequest`·`EditPetRequest`의 `@Pattern`을 확장한다. `PetJpaEntity`의 문자열 enum을 Hibernate의 `ddl-auto: update`로 갱신해도 기존 CHECK는 바뀌지 않으므로, `db/pet-species-schema.sql`과 pet 스키마 초기화에 기존 제약을 교체하는 작업을 포함한다. `PetBirthYearSchemaConfiguration`의 초기화 순서와 [media CHECK 교체 예시](../../backend/src/main/resources/db/media-schema.sql)를 참고해 기존 `pets_species_check`를 명명된 `ck_pets_species`로 트랜잭션 안에서 교체하고 재실행이 가능하게 한다. 새 DB와 기존 DB 모두에서 요청을 받기 전에 적용한다. 요청·응답의 필드 이름과 경로는 유지한다.
- 엽서는 분류와 품종의 전달 경로를 검증한다. `CloudflarePostcardImageAdapter.animal()`은 새 값에도 현재 기본 문구 `pet animal`을 사용한다. 프롬프트를 `reptile`로 바꾸는 정책은 엽서 담당과 별도로 논의한다.
- 기존 폼의 라벨·입력·오류 표시 스타일을 사용한다. 공용 `PetProfileFields`는 데모도 사용하므로 서버 등록·수정에서 사용할 입력을 pet 내부에서 선택한다. 레이아웃과 기존 디자인 토큰의 적용은 위 디자인 준수 기준을 따른다.

## 백엔드 준비와 프론트 착수 조건

현재 계획의 필수 범위는 다음 기존 pet 계약으로 충족된다. 기능 구현/머지 여부와 실제 개발 서버 배포·브라우저 연동 검증은 구분한다.

| 관리 기능 | 백엔드 계약과 준비 범위 | 프론트에서 해결할 조건 |
| --- | --- | --- |
| 목록 | #46의 GET `/pets`, 내 소유 프로필 목록 | Q1의 세션 출처·공유 의존성, Q2 선택/이동, Q5 기록 수·사진·선택 표시 |

| 상세 | GET `/pets/{petId}`, 소유자200·타인403·미존재404 | Q1 관리 라우트가 로컬 PetBoundary에 막히지 않는 경계 |
| 수정 | PATCH `/pets/{petId}`, 이름/종/품종/생일의 부분 수정 | Q4 생일 비우기 정책, Q5 기존 편집·삭제 진입 표시. 기대 버전 입력이 없다는 한계 유지 |

- #46·#91의 구현과 공통 예외 전환은 머지됐으며 기존 pet 요청/충돌 회귀 검사가 있다. 따라서 **이 다섯 API를 위한 추가 백엔드 구현을 선행 조건으로 새로 만들 필요는 없다.** 실제 배포 API 접근·쿠키·응답을 브라우저로 연결한 검증은 각 구현 PR에서 수행하며 계획 검토만으로 통과했다고 표시하지 않는다.
- #89의 실제 diary 기록 조회·삭제 제한은 별도 확인된 연동이다. 사진·가족·기록 수 집계·생일 삭제·화면 기대 버전·전역 선택은 이 다섯 API가 제공하는 기능이 아니다.
- **지금 즉시 화면 구현 착수 가능이라는 뜻은 아니다.** 특히 Q1의 공개 세션 출처 계약은 목록부터 필요한 조건이다. 리뷰어의 기술 검토는 파일 변경 합의나 Q2~Q5의 사용자 경험/디자인 승인을 대신하지 않는다. 해당 단계에 필요한 합의·계획 승인 후 한 기능씩 구현한다.

## API와 데이터 계약

| 작업 | 기존 API (`/api/v1` 접두사) | 주요 계약 |
| --- | --- | --- |
| 목록 | GET `/pets` | 내 소유 목록. ID·이름·태그·종·품종·생일·mode |
| 등록 | POST `/pets` | 이름·종 필수, 품종·생일 선택. 201 상세, 초기 ACTIVE |
| 상세 | GET `/pets/{petId}` | 200 상세, 타인403/없음404 |
| 수정 | PATCH `/pets/{petId}` | 부분 수정. null/생략은 유지, 품종 빈 문자열은 비움 |
| 모드 | PATCH `/pets/{petId}/mode` | `{mode: ACTIVE 또는 GARDEN}`, 200 상세 |

- 서버 `petId`는 화면/도메인에서 문자열로 취급하며 정밀도를 잃는 Number 변환을 추가하지 않는다. JSON 숫자 ID의 안전 범위를 넘는 지원이 필요하면 서버 표현부터 합의한다. tag/mode를 브라우저에서 만들어 대체하지 않는다.
- 이름은 trim 후 1~20자, 품종 최대100자다. 기존 분류 `DOG`·`CAT`·`OTHER`에 7절에서 `REPTILE`을 추가한다. 기존 데모의 품종50자 제한을 그대로 서버 규칙으로 간주하지 않는다. 생일은 Asia/Seoul 오늘·과거만 허용하며 날짜 문자열을 UTC 시각 변환으로 하루 이동시키지 않는다.
- `createApiClient`의 같은 출처 쿠키·기존 경로 접두사를 재사용한다. Fetch/DTO/HTTP 상태 의존은 `features/pet/api`에서 처리하고 화면은 기술 독립 오류를 소비한다. 기존 `ApiError`/`ApplicationError` 계약을 먼저 확인하고, HTTP 상태를 해석하는 코드를 `types`·`utils`에 옮기지 않는다. (고침 #182: 구조 개편으로 계층 이름 대신 기능 폴더 기준) 새 공용 API 클라이언트나 인증 구현을 만들지 않는다.


### 현재 코드와의 연결에서 확인할 점

- `features/pet/types/PetSummary.ts`는 현재 id·name만, `features/pet/api/petApi.ts`의 `listMine()`은 마이페이지용 목록 계약을 제공한다. (고침 #182: 구조 개편으로 바뀐 경로) 서버 관리용 tag/species/breed/birthday/mode를 얻기 위해 이 타입을 변경하거나 모든 소비자에 추가 필드를 강제하지 않는다. 관리용 모델·포트 추가와 최종 주입 위치를 Q1에서 합의한다.
- `features/pet/components/PetScreens.tsx`(예전 `workspace/adapters/inbound`)의 목록·등록/편집은 `app.state.pets`와 `workspace.selectPet/savePet`를 사용한다. `app.refresh()`는 서버 관리 목록의 재조회 수단으로 간주하지 않는다. 서버 저장과 서버 재조회는 전용 관리 흐름으로 연결한다.
- `/pets/[petId]/layout.tsx`는 `PetBoundary`를 통하며 로컬 workspace에 없는 서버 petId는 먼저 차단된다. URL 숫자/문자열 변환만으로 해결되지 않는다. 기존 상세 진입과 모드 설정 경로에 서버 데이터를 주입하기 전에 관리 경로와 데모 기록 하위 화면의 경계를 합의한다.
- 현재 서버 요청 DTO는 이름 원문 길이1~20자·품종 최대100자를 검사한다. 도메인의 strip 규칙만 보고 서버가 거부할 원문 길이를 프론트에서 성공으로 판정하지 않는다. name/species/breed/birthday 변경 필드만 PATCH에 보낼지 전체 값을 보낼지 구현 단위에서 명시하고, 생일 빈 문자열은 유효한 날짜처럼 전송하지 않는다.
- 동시성409는 서버 요청 내부의 낙관적 잠금 보호다. PetResponse에는 version이 없고 관리 PATCH에도 기대 버전 입력이 없다. 오래 열린 편집 화면에서 보낸 값을 모두 감지하는 클라이언트 버전 충돌 방지 기능으로 확대 설명하지 않는다.
- 프론트 상태 가드와 최종 소유 권한을 구분한다. `accessRole` 같은 데모 역할을 서버 목록에 임의 합성하지 않고, 가족 기능이 없는 현 API의 소유자 계약과 서버403을 따른다.

### diary 연동 이후 유지할 경계

- #89는 `NoPetRecordsAdapter`를 `DiaryPetRecordsAdapter`로 대체해 실제 일기 존재를 조회한다. 기존 일기가 있으면 pet 삭제는 409 `CONFLICT`·`기록이 있는 반려동물은 삭제할 수 없습니다.`로 거절한다. FK `fk_diary_entries_pet`의 NOT DEFERRABLE·ON DELETE RESTRICT와 어댑터 flush는 첫 일기 생성/삭제 경합도 보호한다. diary만의 연결을 전체 기록 도메인 지원으로 표현하지 않는다. (고침 #85: #89 연동 반영)
- 목록·등록·상세·프로필 수정·모드의 pet 요청/응답 형식은 바뀌지 않는다. #89의 추가 예외 cause는 서버 내부 진단 정보이며 프론트 DTO나 오류 안내 필드에 노출하지 않는다. 기존 `code`·`message`만 소비한다.
- 일기 백엔드가 준비됐어도 현재 프론트의 `workspace` 데이터·`PetBoundary`·전역 선택이 서버용으로 전환된 것은 아니다. Q1~Q3을 완료로 처리하거나 서버 pet을 데모 기록/다이어리에 자동 연결하지 않는다. 기록 수 표시를 위해 이번 범위에 새 diary 목록/집계 요청을 추가하지 않는다.
- #89의 미지원 첨부·위치 정책 이동은 diary 입력 포트의 책임 정리다. pet 프로필 사진 업로드나 가족 기능이 지원된다는 뜻이 아니므로 이번 사진·가족 제외와 디자인 승인 Q5를 유지한다. 서버 통합 배포에 필요한 FK/DDL 적용 확인은 백엔드·배포 담당의 검증 사항이며 프론트 작업에서 DB 설정을 수정하지 않는다.

## 작은 작업별 구현 계획

아래 표의 한 행은 별도 구현 작업·PR이다. 이후 행을 미리 구현하지 않는다. 각 행에 필요한 모델·포트·어댑터·화면·검사만 함께 두고 다음 행의 기능은 사용자에게 완료로 안내하지 않는다.

## 확인 방법
- 계획 문서: `git diff --check`와 링크·번호·범위 검토. 실행 결과는 PR 본문에 적는다.
- 각 구현 PR: frontend에서 `npm run lint`, `npx tsc --noEmit`, 바뀐 동작의 `node --experimental-strip-types --test tests/<대상>.test.ts`만 실행한다. 미리 관련 없는 전체 테스트를 반복하지 않는다.
- 목록/등록/상세/수정/모드 각각 테스트 파일을 나누거나 해당 파일만 선택 실행할 수 있게 한다. 유스케이스의 가짜 포트, HTTP 어댑터의 요청·오류 변환 검사를 구분한다. S3의 경합은 응답 순서를 제어해 확인한다. 유효 HTTP 쿠키+활성demo에서 요청하지 않는 사례와 요청 도중 demo 전환 후 응답 폐기를 각각 포함하며, 이미 보낸 쓰기의 서버 커밋 가능성을 별도로 다룬다.
- 실제 HTTP 로그인→demo/데모 소셜 전환(서버 쿠키 유지)과 요청 진행 중 전환, 명시적 HTTP 복귀 뒤 재조회를 직접 확인한다. 이를 위해 auth 구현을 무단 수정하거나 실제 서버 쓰기를 승인 없이 수행하지 않는다.
- 화면 가드·저장 중 버튼·확인 취소·이탈 보호 등은 순수 유스케이스 검사만으로 검증됐다고 주장하지 않는다. 기존 프로젝트의 화면 테스트 방식으로 확인 가능한 범위를 정하고, 자동화하지 못한 UI는 S12에서 직접 확인한다. 보안상 서버 거절 계약과 화면 표시 검증을 구분한다.
- 의존성/설정을 바꾸지 않으면 로컬 build를 반복하지 않는다. CI의 전체 test/build·이미지 검사는 최종 PR에서 확인한다. 테스트 이동·축소 시 `docs/testing-coverage.md`에 대응과 남는 범위를 적는다.
- 기존 API가 준비됐다는 뜻이지 이번 문서 작성으로 실제 요청·브라우저 검증이 완료됐다는 뜻은 아니다.

## 가정
- 기존 디자인의 반려동물 관리 진입과 표현을 유지하되 서버가 제공하지 않는 사진·기록 수·가족 권한을 임의 기본값으로 실제 기능처럼 표시하지 않는다.
- 저장 성공 후 관리 목록 또는 관리 상세로 돌아오며, 홈 이동/전역 선택은 Q2~Q3에서 별도 합의한다. 생일 삭제는 Q4 확인 전 제공하지 않는다.
- 기존 마이페이지 pet 목록 계약은 그대로 보존한다. 관리용 데이터 모델을 상세 필드가 필요한 별도 포트로 정의하는 안이며 최종 주입 위치는 Q1에서 합의한다.
- 상위 이슈 #85는 부분 구현 PR에서 닫지 않는다. 후속 이슈를 만들면 이 문서의 기존 시나리오 번호를 바꾸지 않고 대응 범위를 연결한다.
